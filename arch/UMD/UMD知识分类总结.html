1. 定位与总体图景

在现代 GPU 软件栈里，用户态驱动（UMD）是把高层 API（Vulkan、OpenGL、CUDA Driver API、Level Zero、HIP/HSA 等）翻译成硬件可执行命令的那一层。它运行在非特权的用户进程里，通常以共享库被加载：Linux 上常见如 libvulkan_radeon.so（RADV）、libcuda.so、Intel compute-runtime；Windows 上则是 WDDM 中由 Direct3D runtime 加载的 UMD DLL。

Collabora 的 Tyr 系列把分工说得很干脆：KMD 把一块大得多的 UMD 接到真正的 GPU 上；UMD 实现 Vulkan / OpenGL / OpenCL 等 API，构造 VkCommandBuffer 这类指令结构；KMD 负责提交到硬件队列、在异步乱序完成时维护依赖，以及设备上电。该文强调：复杂度的大头通常在 UMD。（Almeida, Collabora, 2025-08-06）

Mesa RADV 文档给出同一图景的可操作版本：所有图形 API 都在用户态实现；RADV 经 winsys 与 amdgpu KMD 对话。KMD 负责 PCIe 与电源、显示、显存与 GTT、把已提交命令写入 GPU ring；UMD 负责以硬件二进制格式记录命令、编程寄存器、把 shader 编译到原生 ISA 并上传，再通过系统调用提交。（Mesa RADV 文档）

图 1. UMD 夹在框架与内核之间：它不是「多一个封装」，而是命令、地址和同步对象的作者。本图为解释图，不是某一官方插图的复制。

CUDA 官方指南把边界说得更 API 化：Runtime 写在更低层的 Driver API 之上；Driver API 实现于随设备驱动安装的 cuda.dll / cuda.so，入口以 cu 为前缀。多数应用不必直接碰 Driver API 也能跑满性能，但部分新接口会先出现在 Driver API，虚拟内存管理（VMM）等高级接口只在 Driver API 暴露。（CUDA Programming Guide §3.3，v13.5）

因此，框架里的 cudaMalloc、cudaLaunchKernel、cudaGraphLaunch，以及 Vulkan 计算路径上的 vkCmdDispatch / vkQueueSubmit，最终都要经过 UMD 变成命令流、地址映射和同步对象。UMD 的实现质量会直接表现为：提交延迟、命令条数、显存碎片、shader 编译卡顿，以及图（Graph）能否少走主机往返。

2. UMD / KMD 的职责边界

不同操作系统和厂商的用词不同（UMD/KMD、winsys、thunk、miniport），但反复出现的边界是稳定的。

几乎总在 UMD 一侧

实现用户可见 API 与状态跟踪；把 API 编码成硬件命令包；编译或加载 shader / kernel；决定 tiling / descriptor 布局；在传统模型里发起提交。

几乎总在 KMD 一侧

设备初始化、电源、显示、特权寄存器；物理显存与驻留；跨进程安全与命令校验、地址 patch；中断与完成通知，以及与 OS 调度器 / 内存管理器的接合。

RADV 把 Vulkan entry point 转到 radv_*；ANV 则把大量动态状态的打包策略写进驱动内部文档。（RADV；ANV） Tyr 文把调度和设备 bring-up 明确归为 KMD。（Almeida, 2025）

WDDM 操作流程是校验模型的完整标本：KMD 的 DxgkDdiRender 校验 command buffer、按硬件格式写入 DMA buffer 并生成 allocation list；随后 Dxgkrnl 做分页、patch 物理地址再提交。（WDDM Operation Flow）

正在前移的那条线：用户态提交

为了降低提交延迟，越来越多的栈允许 UMD（甚至 GPU 自己）直接往固件 ring / doorbell 写，内核只做队列创建、特权内存和生命周期管理：

  • Windows WDDM 3.2（Windows 11 24H2 语境，文档仍标注特性在发展中）引入 user-mode work submission：UMD 可从用户态经 doorbell 直接提交；传统内核提交必须同时保留。低延迟路径上「KMD 并不介入、也不感知每一次提交」；D3DKMTNotifyWorkSubmission 只用于少数必须通知 KMD 的场景。（User-mode work submission）
  • Linux amdgpu User Mode Queues：让用户进程直接管理提交，绕过用于提交的 ioctl，也允许 GPU 向自己提交。UMD 向 ring 写入 IP 特定包并更新 wptr，固件按 rptr/wptr 消费。（Kernel doc: User Mode Queues）
  • NVIDIA 闭源 UMD 在开源内核模块与近年论文中被描述为：把 PCIe BAR 映射进用户地址空间，直接写命令与 doorbell，不必为每次提交陷入内核。（Yan, Karlin, Grant, arXiv:2604.26889, 2026-04-29）
一句话：KMD 仍掌握信任与资源，UMD 越来越接近「命令的作者和门铃的按下者」。对 LLM 推理这种短 kernel、高提交频率的负载，这条路径往往比「再快一点的 kernel 计算」更先成为瓶颈。

3. 命令提交与 command buffer / queue

3.1 记录：API 调用变成硬件包

Vulkan 应用把命令记进 command buffer，再提交到队列。RADV 向称为 command stream（CS）的缓冲区发射 packet；提交时若干 CS 作为内核所称的 indirect buffer（IB） 交给内核——名称来自常用的 INDIRECT_BUFFER PM4 命令。包由该队列的 Command Processor（CP）执行。现代 AMD GPU 有多条队列，有时一次提交要同时打到多条硬件队列。（RADV：Command submission and PM4 packets）

Intel ANV 为降低 3D pipeline 状态的重复打包，非动态状态在 genX_pipeline.c 预打包，动态状态在 genX_gfx_state.c 补丁；间接绘制还可以用 generation shader 在 side batch 里生成主 command buffer 中的指令。（ANV 文档）

NVIDIA 没有同等的官方「如何写 pushbuffer」公开手册，但开源内核模块与独立研究给出了一致的机械图：高层 API（例如一次 cudaMemcpy）被译成 copy/DMA 描述符写入 pushbuffer（每条 4 字节）；经 GPFIFO 交给 PBDMA；用户态可写的 USERD 更新生产者指针 GP_PUT（RAMFC 位于特权区）；写 doorbell 后 PBDMA 从 USERD 载入并消费。（arXiv:2604.26889；open-gpu-kernel-modules 中 DoorbellKickoff 注释）

Maxime Peim 的 libmc 把同一条路径做成不链接 libcuda 的最小库。在 Hopper 及以上，甚至可以让一个 SM 线程写另一 channel 的 pushbuffer、发布 GPFIFO、推进 USERD GP_PUT 并敲 BAR1 doorbell，从而在没有 host 介入的情况下启动 copy engine。项目强调这不是 device-side cudaMemcpyAsync（后者仍交给驱动调度）。该能力依赖 HOPPER_USERMODE_A / BLACKWELL_USERMODE_A 这类可映射 usermode aperture；Ampere 的 AMPERE_USERMODE_A 没有这一概念。（libmc README）

3.2 提交：ioctl 路径 vs doorbell 路径

传统 ioctl 路径仍是兼容与校验的基线：UMD 填满 command buffer → 经 DRM uAPI / KFD ioctl / WDDM callback 提交 → KMD 校验并 patch / 分页 → 硬件完成后以中断或 fence 通知。WDDM 从 Draw 到 pfnRenderCb、DxgkDdiRender、paging、带 fence identifier 的 DxgkDdiSubmitCommand，再到中断读回 fence，是这一模型的逐步合同。（WDDM Operation Flow）

用户态队列 / doorbell 路径把「按铃」拉回用户态：

  • Linux amdgpu：与 KFD 用户态队列思想类似。（userq）
  • Mesa 25.0 为 RadeonSI 合并了 AMDGPU user queue：在受支持内核上以 AMD_USERQ=1 启用，使作业提交不必经过 command submission ioctl。Phoronix 原站此次抓取返回 403，内容已由 Internet Archive 核验。（Larabel, 2024-12-03；存档）
  • Intel compute-runtime（NEO）的 direct_submission/ 是绕过「每次提交都进内核」的 ring-buffer 路径。（ARCHITECTURE.md）
  • NVIDIA：上述 USERD + doorbell。Yan 等人指出，用户态虽能直接写 doorbell，仍须由内核建立到 doorbell 物理 I/O 地址的映射。

LPC 2026 上 Daniel Almeida（Collabora）与 Philipp Stanner（Red Hat）的幻灯片从内核角度补了一句现实：许多 GPU 已是任意数量的 firmware ring；内核「scheduler」往往只做依赖与生命周期跟踪，真正跑什么由固件决定。（《GPU Job Scheduling: Current Development》幻灯片）

对算子栈的含义：优化「提交」不再只是少几次 ioctl，而是要问——这条 launch 有没有变成更短的命令足迹、有没有避开主机往返、有没有把依赖留给固件或 GPU 自己串起来（CUDA Graphs、Device-Generated Commands、GPU 自提交属于同一方向）。

4. 内存管理：显存、VA、SVM / HMM 与虚拟内存 API

4.1 物理显存在谁手里，虚拟地址在谁手里

RADV 把 video memory 与 GTT 归给 KMD；UMD 决定需要什么样的 buffer，再通过 DRM uAPI 创建与映射。（RADV） Windows WDDM 更制度化：UMD 经 pfnAllocateCb 进入 KMD 的 DxgkDdiCreateAllocation，驻留与换入换出由 VidMm 和 paging DMA 处理。（WDDM Architecture）

Linux DRM 提供 GEM 与 TTM。TTM 面向带专用显存的加速器，管理 buffer object 的生命周期、迁移和 CPU mapping。（DRM memory management） Intel NEO 在用户态有 MemoryManager、GraphicsAllocation、地址空间划分，并经 gmm_helper/ 对接 GmmLib。（ARCHITECTURE.md）

4.2 CUDA 低级虚拟内存管理（VMM）

CUDA 10.2 起，Driver API 把「物理句柄」和「虚拟地址」拆开。Cory Perry 与 Nikolay Sakharnykh 的博客（JSON-LD datePublished 为 2020-04-15）介绍四件套：cuMemCreate、cuMemAddressReserve、cuMemMap、cuMemSetAccess。应用可以做可扩展 GPU buffer，避免 cudaMalloc + memcpy 式再分配，并把可共享句柄交给其他用户态驱动。（Introducing Low-Level GPU Virtual Memory Management；官方 VMM 章）

与此配套的是流序分配器 cudaMallocAsync（CUDA 11.4+）。Vivek Kini 等在 2021-07-27 的博客中讨论如何在流的生命周期内分配与释放。（Stream-Ordered Memory Allocator, Part 1） 这些接口是框架分配器「长在 UMD 之上」的钩子：不必改 KMD，只要调 Driver API，就能实现自己的 VA 策略。

4.3 HMM / SVM：共享虚拟地址

Linux HMM 官方文档：把非常规内存（如 GPU 板载显存）纳入常规内核路径，核心是设备内存也可以有 struct page，从而让 CPU 与设备共享 VA，并支持迁移。（HMM）

ROCm 的 thunk（libhsakmt）面向 KFD，导出包括 hsaKmtAllocMemory、hsaKmtMapMemoryToGPU、hsaKmtSVMSetAttr 以及 doorbell 初始化等接口。README 说明它是与 ROCk 内核驱动交互的用户态 API，仓库现已并入 ROCR-Runtime。（ROCT-Thunk-Interface；ROCR-Runtime）

需要避免的过度推断：HMM 是内核基础设施，HSA/SVM、CUDA Unified Memory、IOMMU ATS 等相关但不自动等同。公开邮件列表里长期有人提问它们的差别。本文只在资料直接支持的范围内使用这些词。

4.4 和 AI 框架分配器的交接

PyTorch 官方 CUDA 笔记（docs 2.15）说明：缓存分配器由 PYTORCH_ALLOC_CONF（别名 PYTORCH_CUDA_ALLOC_CONF）控制；backend 可选 native 或 cudaMallocAsync。expandable_segments（文档标注 experimental，默认 False）让分配器先创建一段、之后再扩展，以应对 batch size 轻微变化时「老段末尾留下无法回收的碎片、最终 cudaMalloc 失败」——它试图（按 stream）维护一段按需增长的大 segment。（PyTorch CUDA semantics）

同一页还警告：对能装进 GPU 显存的深度学习负载，显式放置通常优于 CUDA Unified Virtual Memory；显存饱和时 UVM 会做昂贵的双向搬运。这是框架层对「自动共享 VA」的实践判断，而不是 HMM 实现细节。

未在该选项的官方说明段落中写明的事：本文不把 expandable_segments 直接断言为「内部调用了 cuMemMap」。同页稍后出现的 cuMemMap 示例属于多 GPU 虚拟内存代码，不宜自动等同。

5. 同步：fence、semaphore 与 syncobj

GPU 是大规模异步设备，命令完成可以乱序。Tyr 文把「编码 job 依赖、并由内核保证这些依赖被遵守」列为 KMD 的关键责任。（Almeida, 2025）

在 Linux DRM 中，用户态显式同步的核心抽象是 syncobj。内核文档写明：drm_syncobj 为同步原语提供容器，供用户态显式同步 GPU 命令，可在进程之间、以及不同 DRM 驱动之间共享；其首要用例是实现 Vulkan 的 fence 与 semaphore。ioctl 支持创建/销毁、以 fd 导入导出、与 sync file 互换底层 fence、reset、signal 与等待；timeline syncobj 则建立在 dma_fence_chain 上。syncobj 本质上是对可能为空的 dma_fence * 的包装。（DRM Sync Objects）

这解释了 Vulkan UMD 的典型做法：VkFence / VkSemaphore（尤其是 timeline semaphore）在 Linux 上往往架在 syncobj 之上；跨进程、跨驱动也走同一套导入导出。

Windows 传统 WDDM 路径使用提交时写入 DMA buffer 的 fence identifier：GPU 完成后发中断，KMD 读回该编号并通知 Dxgkrnl。（WDDM Operation Flow）

用户态队列并不能随便写一个完成标志。amdgpu userq 文档描述一类由固件执行的包：向仅特权客户端可写的内存位置写入信号值，用户队列只有读权限；内核准备这块特权内存，包的提交本身在用户态完成。（User Mode Queues）

对框架的启示：cudaEventSynchronize、torch.cuda.synchronize()、Vulkan 的 queue 间依赖，以及 CUDA Graphs 内部的边，最终都会变成 UMD 写入的等待/信号包，或对 syncobj / 事件对象的等待。多余的主机侧同步会把异步流水线打成串行。

6. UMD 中的 shader / 编译器

「用户态驱动」里往往藏着完整的编译器，而不是只做 ioctl 封装。

6.1 Mesa：NIR + 后端，复杂度在「资源怎么接到 shader」

Faith Ekstrand 在 2024-01-16 的文章中指出，今日写 Mesa 驱动的一个高阶难题是如何在 Vulkan 与 Gallium 之间共享代码。（How to share code between Vulkan and Gallium）

XDC 2022 演讲 How to write a Vulkan driver in 2022（当时署名 Jason Ekstrand，后续公开资料多用 Faith Ekstrand）把工作拆成 Mesa 运行时、NIR、winsys 与硬件后端等可复用层。原 Collabora 博文（LWN 于 2022-03-24 报道）目前原 URL 会重定向到博客首页，故以 XDC 演讲页与幻灯片、YouTube 录像 为准，并以 LWN 报道 佐证博文曾于 2022 年 3 月发布。

XDC 2025 的 Descriptors are Hard 把编译器之外、却仍属 UMD 核心的问题单独拎出来：访问「住在 shader 之外的资源」。摘要写：shader 编译大体是已被理解的问题，但 shader 与 API 其余部分的接口仍困难；OpenGL、Vulkan、D3D12 的资源映射策略差异很大。（YouTube，上传 2025-11-10） ANV 文档则具体描述 bindless / descriptor set 如何变成硬件 binding table。（ANV）

6.2 ACO：放在 Mesa 里的 AMD 后端

ACO（AMD compiler）基于 NIR，把 shader 译成 GCN/RDNA 二进制。README 给出的动机有三条：优先编译速度（减少卡顿）、做好 divergence 分析、缺陷修复可以跟 Mesa 发版走。它维护逻辑 CFG 与线性 CFG（后者按 Whole-Function Vectorization 的思路表示硬件上的实际执行），指令选择以 divergence 分析为中心。本文使用的 README 来自 AOSP 镜像（gitlab.freedesktop.org 原文此次被反爬拦截）。（ACO README（AOSP 镜像））

相关讲座：XDC 2020 | A year of ACO；XDC 2021 | SSA-based Register Allocation（Connor Abbott 与 Daniel Schürmann, Valve）。

对 AI 编译器读者：ACO 关注的「编译延迟 vs 代码质量」与 JIT 出 kernel（Triton、动态 shape、shader 特化）是同一类压力；descriptor / binding 则对应算子里的 tensor 参数、workspace 指针如何变成硬件可寻址的资源表。

6.3 CUDA 与 Intel：模块加载 vs IGC

CUDA Driver API 把加载计算模块、取入口、启动暴露为 cuModuleLoad* / cuLaunchKernel 等；也包括惰性加载等策略。（Driver API 章；Module Management）

Intel compute-runtime 经 compiler_interface/ 对接 Intel Graphics Compiler（IGC），并有 builtin kernel 和用于调试的 System Routine（SIP）。（ARCHITECTURE.md）

摩尔线程公开的 MUSA Driver API 指南采取与 CUDA 类似的分层：Driver API 提供显式上下文、模块加载与更细的设备控制，并与 Runtime API 对照。（MUSA Driver API 开发者指南）

可动手的调试开关：RADV_DEBUG 的 dumpibs（转储 IB）、bo_history，以及 RadeonSI 侧与 userqueue 相关的 userqjoblog 等。（Mesa Environment Variables）

7.2 NVIDIA：闭源 UMD + 开源 KMD 的缝

CUDA Driver API 的实现库随驱动安装（libcuda）。开源的是内核模块 open-gpu-kernel-modules，它暴露通道、映射、doorbell 等「搭建」用 ABI，但真正把 cudaMemcpy / launch 变成 pushbuffer 并按铃的代码仍在闭源用户态。

Yan、Karlin、Grant（2026-04-29 提交，arXiv:2604.26889）利用开源内核模块，在映射路径上插桩，并在用户态映射的 doorbell 上设硬件 watchpoint，在提交瞬间抓住完整命令流。两个案例对算子/框架读者特别有用：数据搬运——识别 DMA 提交模式，并用绕过 CUDA 的受控下发把硬件带宽与驱动开销分开；CUDA Graphs——较新版本里 launch 开销下降，与更小的命令足迹和更高效的提交模式相关。（arXiv:2604.26889）

Maxime Peim 的研究仓库沿着同一条缝往下做。实践细节之一：libcuda 可能用原始 syscall 打开并 mmap 设备文件，从而绕过 glibc 包装，普通 hook 会漏掉关键映射。Medium 原文此次抓取返回 403，标题与部分技术点已由检索摘要及项目 README 交叉核验。（libcuda-research；Part 3 / Part 4 / Part 7）

7.3 AMD ROCm：图形 UMD 与计算 thunk 是两条线

计算栈上，ROCr 经 libhsakmt（thunk） 与内核 KFD/ROCk 通信：打开 KFD、查询拓扑、分配/映射内存、创建队列与事件、设置 SVM 属性、初始化 process doorbells。Thunk README 强调它不是独立产品，必须搭配正确的 ROCk 或兼容上游内核，并且从 1.7 起使用 DRM render 节点。（ROCT README；ROCR 文档）

图形栈上的 RADV/RadeonSI 走 amdgpu DRM uAPI，与 KFD 用户态队列在「用户态 ring + doorbell」思想上汇合，但代码路径和包格式并不自动相同。读 ROCm 时不要把 libhsakmt 误认为 Mesa 的 winsys，也不要把 RADV 误认为 HIP runtime。

7.4 Intel：ANV 与 compute-runtime / Level Zero

ANV 是 Intel 在 Mesa 里的官方 Linux Vulkan 驱动。从第 12 代 / Alder Lake-P 和 Arc Alchemist 起，3D 驱动栈需要 GuC firmware。（ANV）

计算侧 intel/compute-runtime（NEO）同时实现 Level Zero 与 OpenCL。ARCHITECTURE.md 给出进程级对象树：ExecutionEnvironment → 共享的 MemoryManager、DirectSubmissionController、按设备的 RootDeviceEnvironment（含 Linux DRM / Windows WDDM 的 OSInterface）。命令侧有 CommandContainer 与 Encode* 编码器。

Level Zero 规范把自己定位为更贴近金属的 offload 接口，覆盖设备抽象、内存、命令表、同步与内核提交。（Core Programming Guide）

7.5 Windows WDDM：把 UMD 写成操作系统合同

即便主要工作在 Linux 上，WDDM 仍值得读：UMD 由 D3D runtime 加载；Dxgkrnl 含显示端口、VidMm、VidSch；厂商必须同时提供 UMD 与 KMD。（Architecture，页标注更新 2025-11-07） 用户态提交、以及 UMD 与 KMD 共享 allocation backing store（WDDM 3.1 起）等扩展，说明 Windows 同样在把热点路径推回用户态。（Sharing the Backing Store with KMD）

7.6 国产 GPU：公开到「编程接口」，很少公开到「UMD 内部」

在已核验的公开材料里，摩尔线程官方文档把 MUSA 明确分成 Runtime API 与 Driver API，Driver API 负责显式上下文与模块加载，定位接近 CUDA Driver API。（MUSA Driver API 指南；Host/Device 编程模型）

海光 DCU、沐曦 MXMACA、壁仞 SUPA 等在公开网络上有产品与框架适配报道，但缺少与本文其它章节同等级的、可核验的 UMD 内部实现文档或开源树。本文不根据二手商业评论推断其 UMD 架构。若后续有官方源码或驱动开发者文档公开，应再单列补遗。

8. 调试、性能与 AI 推理 / 算子栈的关联

8.1 调试与可观察性

  • RADV / Mesa：RADV_DEBUG=dumpibs 转储 command stream；bo_history 记录 BO 操作。这是「看 UMD 到底提交了什么」的第一工具。（envvars）
  • UMR：AMD 开源的 Linux 工具，用于检查 AMDGPU 状态：寄存器读写、ring 解码、虚拟内存解码、寄存器活动跟踪。由 AMD all-open Linux 团队维护，只使用已公开的 IP 寄存器定义。（UMR 导言；代码仓库）
  • NVIDIA 闭源路径：研究侧用 doorbell watchpoint / 内核插桩捕获完整命令流。（arXiv:2604.26889；libcuda-research）

RenderDoc / 厂商 GPU profiler 更偏向图形帧调试与计数器，对「提交路径」的可见性通常不如 IB dump 或 doorbell 捕获来得直接。未在本文逐项核验其与 UMD 内部结构的对应关系，故不写成依据。

8.2 对 AI 推理和算子性能真正重要的几点

这些结论都锚定在上文已引用的资料，而不是经验口号：

  1. 提交开销是一等公民。用户态队列、WDDM UM submission、NVIDIA doorbell、NEO direct submission，全部在减少「每次 launch 进内核」的往返。短 kernel、动态 shape、频繁的小拷贝会放大这条路径。
  2. 命令足迹可以被测量、也可以被优化。Yan 等人显示，CUDA Graphs 的 launch 加速与更小的命令足迹、更高效的提交模式相关；这把「图优化」从框架典故落实到了 UMD 发出的字节。
  3. 分配器策略活在 UMD 的内存 API 上。CUDA VMM 与 cudaMallocAsync 是框架缓存分配器的底层；PyTorch 的 expandable_segments 明确针对动态 batch 造成的显存碎片。OOM 未必是「显存不够」，也可能是分配策略留下了无法回收的 sliver。
  4. 自动统一内存不是训练/推理的默认最优。PyTorch 官方笔记对装得下的 DL 负载不推荐 UVM。共享 VA（HMM/SVM/UVM）有真实的系统价值，但缺页和双向迁移的代价要算进端到端。
  5. 编译与描述符属于 UMD 热路径。ACO 把编译速度当作一等目标；Ekstrand 把 descriptor 映射称作现代驱动的主要挑战之一。对 Triton / 动态 kernel，「每个 shape 一份特化 kernel」会使 UMD 或用户态编译器的缓存与绑定模型变成可见延迟。
  6. Vulkan 计算正在成为「绕开专有 UMD API、仍复用成熟 UMD」的路径。FOSDEM 2025 上 Ruben Ortlam 指出：多数机器学习应用走 CUDA/ROCm；若改用游戏领域持续投入的 Vulkan 计算 shader，就可以借助更广泛的驱动支持。（FOSDEM 2025 日程） 这条路并不是「不用 UMD」，而是把依赖从闭源 CUDA UMD 转到 Mesa 等可调试的 Vulkan UMD。
  7. 设备生成命令 / GPU 自提交把「谁写 command buffer」继续往下推。Igalia 短视频介绍 Vulkan Device-Generated Commands；amdgpu userq 也写明允许 GPU 向自己提交。（Device-Generated Commands in Vulkan）

8.3 虚拟化与多租户（简记）

Rob Clark 在 XDC 2022 的 moar fps in a vm 讨论 VM 中的图形性能；WDDM 的 UM submission 文档明确提到：在 GPU 半虚拟化场景中，客户机 UMD 直接提交可避免每次向 host 发消息。（YouTube；UM work submission） 对云端推理多租户，提交路径上的 guest/host 往返同样是隐藏延迟。

9. 学习路径与可动手实践

按「读得懂、看得到、改得动」排列，均指向上文已列出的公开树或工具。

第一阶段：建立正确的分层图（约 1–2 天）

  1. 读 Tyr 文，只抓住职责边界与「复杂度在 UMD」。
  2. 读 RADV 的 Responsibilities / PM4 和 WDDM Operation Flow，对照 Linux 与 Windows 的提交序列。
  3. 看 XDC 2022: How to write a Vulkan driver（约 50 分钟）和/或 FOSDEM 2026: Mesa3D 总览。

第二阶段：跟着开源 UMD 走完一次提交（1–2 周）

  1. 在 Mesa 里选 RADV、ANV 或 NVK。先画「vkCmdDispatch → 发包 → QueueSubmit → ioctl/userq」的调用链。
  2. 用 RADV_DEBUG=dumpibs 跑一个最小 Vulkan compute 或 vkcube，对照 PM4/IB 概念。
  3. 若有 AMDGPU：装 UMR，对 ring 做一次解码，把用户态写的包和硬件正在执行的包对上。

第三阶段：计算栈与框架交接（1–2 周）

  1. 读 CUDA Driver API 与 VMM 博客，写一个「保留 VA + 映射物理句柄 + 扩展」的小例子。
  2. 读 PyTorch CUDA memory 笔记，用 PYTORCH_ALLOC_CONF 比较 native、cudaMallocAsync、expandable_segments 在动态 batch 下的显存曲线（只记录实验）。
  3. 读 CUDA Graphs 章，对照 arXiv:2604.26889 的 Graphs 案例：关注捕获后提交形态变了什么。

第四阶段：深入一条厂商缝（按兴趣）

  • NVIDIA：浏览 open-gpu-kernel-modules 的通道/doorbell 代码；进阶再看 libcuda-research / libmc（注意其 pinned 的驱动版本，私有 RM/UVM 接口不稳定）。
  • AMD 计算：从 libhsakmt 的队列创建、内存映射、doorbell、SVM 属性往上读到 ROCr。
  • Intel：读 NEO ARCHITECTURE.md，对照 Level Zero 命令表与 direct_submission。
  • 描述符与编译：看 Descriptors are Hard、ACO README，以及 XDC 2020/2021 讲座。
实践纪律：在自己的机器或明确授权的实验室环境观察；不把闭源驱动的逆向结果包装成「官方 ABI」；记录驱动与内核版本组合；性能结论必须带测量语境（是否 userq、是否 Graphs、分配器后端）。
