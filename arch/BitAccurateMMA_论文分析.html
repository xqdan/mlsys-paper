1. 一句话结论

这篇工作不是新加速器，而是把 NVIDIA Tensor Core 和 AMD Matrix Core 里不公开的浮点算术行为，做成对硬件输出逐位一致的白盒模型。作者在十代 GPU 上跑指令级接口，用闭环特征探测补全求和顺序、融合宽度、内部精度和舍入，并做成可执行模拟器 MMA-Sim。

2. 问题：同一条 MMA，不同芯片算出不一样的数

训练和推理已经主要跑在矩阵乘加单元（MMAU）上：NVIDIA 叫 Tensor Core，AMD 叫 Matrix Core。它们对外只给出指令或 API，内部的计算顺序、融合粒度、中间精度、舍入和特殊值处理并不公开，也没有统一标准。于是，即便输入逐位相同，不同厂商、甚至同一厂商的不同代际，都可能给出不同的浮点结果。这类差异会穿过软件栈，变成跨平台难以复现；有时还会直接伤到训练稳定性和精度。

论文点名了两组已经公开讨论过的事故：Hopper 上部分 FP8 MMA 因累加精度不够，训练精度和稳定性下降；CDNA2 上 FP16 矩阵乘会把次正规数刷成零，PyTorch 侧曾因此观察到训练不收敛，后来用把 FP16 升到 BF16 的办法换动态范围，代价是精度。作者的判断是：只在软件层对齐编译选项、随机种子和并行归约顺序，仍解释不完这些现象，缺的是对硬件算术行为的白盒模型。

难点在于搜索空间极大。可能影响结果的特征既没有完整清单，也不能从数据手册里直接读出来。此前的特征探测工作往往只覆盖部分架构、部分特征，而且很少把模型跑到「和硬件逐位一致」这一步。没有这一步，模型里残留的错误假设很难被发现。

3. CLFP 和 MMA-Sim 是什么

闭环特征探测（Closed-Loop Feature Probing，CLFP）要构造一个可执行模型 Φ，使得对接口允许的任意 A、B、C，都有 Φ(A,B,C) = MMA-Interface(A,B,C)。流程分五步：先确认接口确定、且各输出位置算术行为一致，再推断点积累加的求和树和运算目数，接着用一组可复用的特征探测测试（FPT）填写精度、舍入、内部顺序等细节并写出模型，然后用随机差分测试做位级校验；一旦对不上，就把失败用例收成新的 FPT，改模型后再验，直到通过。

MMA-Sim 是这些模型的软件实现：给定架构和指令描述，在软件里模拟 D = A×B+C，目标是和对应 GPU 指令的输出逐位相同。仓库提供 NVIDIA PTX mma.sync 和 AMD v_mfma 两套接口。论文把建模对象收在指令级，而不是 cuBLAS 一类 API，就是为了把硬件行为和编译器/程序员引入的变换分开。

覆盖的十代架构写得很清楚：NVIDIA Volta（sm70）、Turing（sm75）、Ampere（sm80）、Ada Lovelace（sm89）、Hopper（sm90）、Blackwell（sm100）、RTX Blackwell（sm120），以及 AMD CDNA1（gfx908）、CDNA2（gfx90a）、CDNA3（gfx942）。作者称这几乎覆盖了截至 2025 年带 Tensor Core / Matrix Core 的 GPU 架构。未来工作才提到 CPU、TPU 和 API 级接口。

4. 现有路线的三个缺口

从 API 反推硬件

API 结果里可能已经掺了软件改写。Hickmann 等人曾把软件相关的归约顺序算到硬件头上；Fasi 等人曾把硬件特有的 FP16 输出舍入算到软件头上。

特征覆盖不全

乘积是否先规格化、内部求和顺序、溢出和次正规数怎么处理，这些未刻画的点会让「看起来差不多」的模型在位级对不上。

缺少位级校验

不做逐位对照，错误假设可以长期留着。例如 Hickmann 等人认为 FP32 次正规数会被当零，后来被后续工作否定。

作者把早期「Tensor Core 的点积是完美二叉树乘加」的模型也列为已被推翻的简化。CLFP 的闭环就是冲着这三点去的：指令级接口、尽量补全特征、用差分测试把模型钉到位精确。

5. 做法：闭环探测，八类初等运算模型

5.1 五步闭环

第 1 步用随机测试确认接口确定；再用同一组 ak、bk、c 填满整个矩阵，检查所有 di,j 是否逐位相同。十代上的全部接口都通过了，于是后面只需为一条点积累加建模。

第 2 步推断求和树。方法改编自 FPRev：放一对能淹没其它加数的大数 ±U，看哪些小加数还能活下来。作者发现高精度融合求和会打破 FPRev 原先「有限精度融合会把中间项全部淹没」的假设，例如 CDNA1 的 mfma_f32_32x32x4bf16，于是扩展了算法，把有限精度和高精度融合分开识别。图 2 给出的典型树包括：二元链式求和（如 CDNA1 的 FP32 MMA、NVIDIA DMMA）、成对求和再累加（CDNA2 带 _1k 后缀的 BF16）、三项或五项融合求和。

第 3 步用可复用的 FPT 填细节。正文展开了四个最重要的测试：求和精度（对二元加用 Add(U,ε) 不断对半，对融合求和用 FusedSum(U,−U,ε)，若一直保持到 ε=0 则视为精确）、舍入模式、内部求和顺序，以及乘积是否规格化。其余测试主要检查次正规数等二元性质。FPT 4（乘积规格化）本身就是第 5 步从失败用例里长出来的：最大乘积满足 |Sig(ai)Sig(bi)| ≥ 2 时，旧模型会对不上。

第 4–5 步用约一百万组随机输入做差分测试。对不上就缩小到通常两到四个关键元素，改指数、翻转尾数或符号，观察匹配/失配的切换点，写成新的 FPT 再进入下一轮。

5.2 八类模型，不是一种「近似 FP32」

所有模型都由「初等运算」拼起来：一种确定的 n 元浮点映射，中间量可以不是输出格式。正文考察过的 GPU MMA 指令，没有一条是由标准 IEEE-754 乘法和加法组成的。

  • ΦFTZ-MulAdd：用于 CDNA2 的 BF16/FP16。输入次正规数刷成 +0.0；乘、加先按 RNE 进 FP32，再把绝对值小于 2−126 的结果按符号刷零。乘完后每 L∈{2,4} 个乘积成对相加，再与 C 顺序累加。
  • ΦFMA：NVIDIA 全部 FP64，以及 AMD 的 FP64/FP32。就是一条 FMA 链，默认 RNE；NVIDIA 还可配成 RZ / RU / RD。
  • ΦE-FDPA：CDNA1 的 BF16/FP16。按无穷精度算完 c+Σ akbk，再 RNE 到 FP32。
  • ΦT-FDPA：NVIDIA 上大多数混合精度指令。先对 L 对操作数做精确的未规格化定点乘，再把这 L 个乘积和累加器对齐到最大指数、截断到 F 位小数后精确求和，最后按 ρ 写成输出格式。
  • ΦST-FDPA：MXFP8/6/4。在 T-FDPA 上把块缩放因子（E8M0，尾数恒为 1.0）的指数加进乘积指数。
  • ΦGST-FDPA：部分 MXFP4 / NVFP4。先按组做精确点积再乘缩放；MXFP4 的块长 Kblock=32，NVFP4 为 16；表注写这类指令的组大小 G=16。
  • ΦTR-FDPA：CDNA3 的 TF32/BF16/FP16。截断融合之后，内部求和使用向下舍入（RD）。
  • ΦGTR-FDPA：CDNA3 的 FP8。偶、奇编号乘积先分组做截断融合，两组再对齐并用 RD 求和，最后与 C 做带额外截断的舍入累加。

6. 实验怎么做的

指令级接口：NVIDIA 用 CUDA 和内联 PTX，并核对其与 SASS 的映射；AMD 用 HIP 和指令 intrinsic，并核对函数到指令的映射。对照用的真机是 V100、T4、A100、RTX 4090、H100、B200、RTX PRO 6000 Blackwell，以及 MI100、MI250X、MI300X。

CLFP 目前是半自动的：第 1、2 步、第 3 步里跑测试、以及第 4 步可以由脚本完成；第 3 步的模型编写和第 5 步的修订仍靠人工。性能瓶颈原来在 MMA-Sim：单线程跑第 4 步的一百万测试大约要 10–20 小时，一条指令往往要一天甚至数天。作者给模拟器做了 GPU 加速，称加速超过 10×，把这一步降到大约 1 小时。优化后，一条指令通常 2–12 小时（Table I）：第 1–3 步里 GPU 测试和时间开销都不大，第 4 步模拟约 1 小时、GPU 数分钟；一旦进入第 5 步，大约还要 4 小时人工。

多数指令零次或一次修订就够；同一家族（例如 HMMA）一旦首条建模完成，其余往往可以单遍跑完 1–4 步。新家族的第一条通常要一到两次修订。最复杂的是 CDNA3 的 FP8 MMA，修订了十次。

Artifact 附录把复现材料拆成三块：CLFP 与 FPT 集合、实现了 §IV 模型的 MMA-Sim、以及十代架构的 CUDA/PTX 与 HIP 接口。软件-only 的 MMA-Sim 可以在没有 GPU 的 CPU 上跑；要对照硬件，需要带 Tensor Core 或 Matrix Core 的 GPU。附录举例说 Jupyter 笔记本需要 Turing，例如 T4；本地安装建议近期 Linux、匹配的驱动和 CUDA/ROCm，以及带 CUDA 或 ROCm 的 PyTorch 2.7+。复现笔记本在 github.com/peichenxie/MMA-Sim-MICRO2026-AE。

7. 结果怎么读

差异来自初等运算和参数，不只是「浮点不可结合」

按模型看，只有 FP64 和 FP32 MMA 能在厂商和代际之间保持一致：它们都是同一条顺序 FMA 链。混合精度则用了不同的初等运算和不同的 Lmax、F、ρ，差异因此是系统性的。

CDNA2 的分叉来自求和顺序：不带 _1k 的 BF16 是 (223+(−223−0.5))+(−0.25−0.125)=−0.375；FP16 以及带 _1k 的 BF16 则先把 −0.5−0.25−0.125 合成 −0.375 再与 ±223 相消，得到 0.0。CDNA3 的 FP8 更进一步：偶、奇组分别得到 −223 和 −0.625，−0.625 被向下舍入成 −1，最后变成 −1.0。

四个精度瓶颈，外加一种不对称

Table V 把误差源加成：FTZ、普通加减乘的 0.5 ulp、FMA/E-FDPA 的输出舍入，以及 T-FDPA 等变体里融合求和的 (L+1)2emax−F 再加上输出舍入（RNE 为 0.5 ulp，RZ 为 1 ulp）。多数指令的误差上界仍和标准 FP32 相当（0.5 ulpFP32 = 0.5×2e−23），真正构成「精度瓶颈」的是 Table VI 那几条：

  • CDNA2 的 FP16 输入 FTZ：输出侧 FTZ 最多引入 2−126，输入侧对 FP16 则可到 2−14。这对应了 PyTorch 在 CDNA2 上看到的训练不收敛。
  • Ada / Hopper 的 FP8：QMMA / QGMMA 只用 F=13，FP32 输出时 ρ=RZE8M13。相对同代 HMMA/HGMMA 的 F=24（Ada）或 F=25（Hopper），融合求和误差上界高 2048× 或 4096×，输出舍入上界高 1024×。这对应 Hopper 上 FP8 训练精度下降的讨论。
  • NVIDIA 全代的 FP16 输出：即便内部融合已经接近 FP32 精度，输出按 RNEFP16 写回，整体精度仍被 FP16 格式卡住，误差上界是 0.5 ulpFP16 = 0.5×2e−10。
  • CDNA3 混合精度的内部 RD：多数指令用对称的 RZ 或 RNE，CDNA3 的 v_mfma 内部求和用向下舍入。作者用 v_mfma_f32_32x32x8_f16 和把内部 RD 改成 RZ 的假想变体对比，A,B ~ 1000×N(0,1)、C ~ N(0,1) 时，RD 的偏差分布明显偏负，RZ 则对称。
一个容易漏掉的代际变化：Blackwell / RTX Blackwell 把 FP8 的 F 从 Hopper 的 13 提到 25，FP32 输出的舍入也从 RZE8M13 改成 RZFP32。同一组 Table IV 输入上，这两代的 FP8 结果从 Hopper 的 0.0 变成了 −0.75，和其他非 FP8 混合精度对齐。这是硬件侧对 Hopper FP8 精度问题的修正，不是软件 workaround。

三条软件 workaround，都是例子而不是通解

缩放输入针对 CDNA2 的 FP16 FTZ：把输入放大、避开次正规数，算完再缩回来。例子是 128×128，A ~ N(0, 0.0012)、B ~ N(0,1)，相对 FP64 的 MSE 从 7.632×10−9 降到 1.591×10−18。作者认为这比 PyTorch 把 FP16 转成 BF16 更保住计算精度。

MMA 不算 C针对 CDNA3 的偏差：Matrix Core 只做 C=0 的矩阵乘，累加交给通用计算单元用完整 FP32。128×128×128、A,B ~ N(0,102) 时，相对 FP64 的平均偏差从 −1.352×10−6 降到 +7.467×10−8。

换指令针对 NVIDIA 的瓶颈：不要用 FP16 输出的 MMA，改用 FP32 输出；在 Ada / Hopper 上如果更在乎精度而不是吞吐，FP8 矩阵乘改走 FP16 MMA。同一规模的例子里，FP16 输出改 FP32 输出后 MSE 从 0.247 降到 4.481×10−8（若再转回 FP16 则是 0.0551）；Ada/Hopper 上 FP8 输入改走 FP16 MMA，MSE 从 0.0103 降到 5.569×10−11。

对未来 MMAU，作者的建议很直接：避免 Table VI 里那些设计，让每个计算步骤都保持 FP32 量级的精度；舍入优先用对称模式，并建议采用 RZ，因为它在原码或一字补码下就是截断，实现比其它模式便宜。

9. 局限与落地可行性

和同场 Session 1A 的 Better Call SoL 不同，这篇几乎没有「下一代 GPU 要加一块什么」的硅片提案，落地路径反而更短：模型已经写成 MIT 许可的 Python 包，也能在 CPU 上做纯软件模拟。对调试跨卡数值差异、写数值稳定的 kernel、以及给下一代 MMAU 做精度预算，这是可以直接用的工具，而不是只能看的仿真加速比。

可行性上的边界也很清楚，不宜放大：

  • 对的是指令，不是整个软件栈。 框架、编译器、kernel 生成器仍会改变指令选择和累加方式。用 MMA-Sim 解释 cuBLAS 或 PyTorch 的端到端差异，还要自己把调用降到具体 MMA 指令。
  • CLFP 还不是全自动。 新家族的第一条指令仍然要人看失败用例、写模型和 FPT。作者自己也说，第 5 步的人工时间已经超过模拟器运行时间，后续想用脚本做最小失败集归约，并尝试用 AI agent 写修订代码。在那之前，把方法迁到新的 ISA 仍有成本。
  • 覆盖停在这十代。 文中明确写的是「截至 2025 年」的 Tensor Core / Matrix Core。没有 Intel GPU，没有 CDNA4，也没有把 CPU AMX 或 TPU 纳入本次实验。新芯片必须重新探测，不能默认算术行为沿用上一代——Hopper 到 Blackwell 的 FP8 参数变化就是反例。
  • 不模拟性能。 MMA-Sim 回答「这个输入会算出哪一个 bit pattern」，不回答吞吐、占用或数据通路延迟。它也不是时序精确的微结构模型。
  • workaround 要自己接进框架。 缩放输入、把 C 拆出去、改用更高精度指令，都是 kernel 级建议，而且数字来自给定分布的中等规模矩阵。接到生产训练或推理里，还要看动态范围、吞吐代价，以及框架默认会不会又选回那条有瓶颈的指令。
  • 位精确不等于训练可复现。 即使单条 MMA 对上了，归约顺序、并发、算法实现仍会制造差异。这篇工作消掉的是「硬件算术这个黑盒」，不是整个数值栈。

对做 GPU / AI 芯片的人，最有用的可能不是那六种输出本身，而是一套已经在十块真机上钉过的术语：Lmax、F、输出与内部舍入、是否 FTZ、是否非对称。设计下一代 Tensor Core 或兼容 CUDA/ROCm 数值的国产 MMAU 时，Table VI 可以直接当作反面清单；要兼容现有生态，则至少需要说清自己落在八类模型里的哪一类，并准备和 MMA-Sim 对位。
