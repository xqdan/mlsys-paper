1. 一句话结论与研究定位

Groq、Cerebras、SambaNova 用干净的数据流芯片来对齐 DNN 的图结构；GPU 仍是主流，却卡在 bulk-synchronous（一次一个 kernel、全局屏障）。垂直融合（TensorRT / Welder / AStitch）把多个算子塞进同一个 mega-kernel，按时间片在 SM 上轮转，仍吃不到三件事：异构资源同时开工、大中间结果不落 DRAM、从 reduction / 隐藏维抽并行。Kitsune 问的是：只改一点点 GPU，够不够在片上做同步数据流。答案是两条原语——软件环形队列（L2 + global atomics）和能配对 SIMT/Tensor CTA 的 grid scheduler——再加一个 Dynamo 后端。

这不是又一块 Groq 式干净数据流芯片，也不是 T10 那种把 IPU 核间全互连编成 rotate。Kitsune 站在现有 A100 类 GPU 上：CTA 仍是工作量子，中间 tile 走 L2 常驻队列而不是 HBM，不同算子在空间上同时占 SM（Tensor Core 做 GEMM，SIMT 做 elementwise / concat）。硬件改动被故意压到「grid scheduler 加一类亲和性仲裁」。评测跑在经过验证的 NVArchSim 上，因为这条调度改动硅片上还不存在。

2. BSP 为何对不上 DNN 图

现代 GPU：一组 SM、全局共享 L2、HBM；SM 内有大寄存器堆、可配成 L1 或 shared memory 的本地存储、SIMT 核和 Tensor Core；原子操作在 L2 完成。Grid scheduler 从驱动经 PCIe 收活、往 SM 派 CTA。A100 108 SM，H100 132 SM；L2 带宽大约是主存的 3 倍。

执行模型仍是 BSP：一个 kernel（通常对应一个 DL 算子）占满 GPU，全部 CTA 跑完才启动下一个。线程组成 CTA（threadblock），CTA 组成 grid；CTA 不可分割、映射到一颗 SM 上跑完。Warp 锁步。CUDA Streams / Graphs 理论上能标独立 kernel，实践中 grid scheduler 的 FIFO 与排队硬件几乎不允许两个 kernel 真正重叠——新 kernel 要等当前 kernel 的全部 CTA 派完才能开始派。

图 1. 论文 Figure 1(c) 的三种执行对照。BSP 按算子串行；垂直融合在时间上复用 SM；Kitsune 把不同算子铺到空间上，用片上队列衔接。

错配集中在两处：算子之间的中间张量足迹大，BSP 下容易落到 DRAM，片上局部性用不上；单个算子的并行度或算术强度不够时，大量 SM / Tensor Core / SIMT 闲着。DNN 的计算图是 DAG，BSP 却按「一层 kernel + 一道屏障」去跑。

3. 垂直融合留下的三块空白

垂直融合把若干算子编进一个 CUDA mega-kernel，CTA 在同一段代码里交替执行各算子的一部分，中间 tile 尽量留在 shared memory 或寄存器，省掉 fused 算子之间的 kernel 屏障。TensorRT 已产品化；学术界有 Welder、AStitch 等。它仍在 BSP 里：CTA 彼此不通信，tile 只在同一个 CTA 的时间片之间传递。

利用率画像（Figure 3）

用 NSIGHT Compute 把运行时间按 SM / DRAM 是否低于峰值 33% 分成四档。未融合 PyTorch：推理有 20–25%（DLRM 77%）时间「两者都低」，训练 37–67%（DLRM 89%）；Llama 的 context/train 几乎没有「双低」，已经很满。TensorRT 能压低「低利用率」比例（MeshGraphNets 除外），但「单边低」仍然很多。即便两边都不低（如 TensorRT 下的 NeRF 推理），去掉 DRAM 往返仍会腾出余量。

三种图模式（Figure 2）

(a) 大隐藏维 MLP

Linear → Elemwise → Linear，中间 N 很大（transformer FFN 把维投影上去再压回来）。A100 shared memory 192 KB，N≥768 时 GEMM tile 就塞不下，tile 进 DRAM，往返约 409 ns（1.4 GHz 下约 572 cycle）。时间复用还让 SIMT 与 Tensor Core 不能同时亮。给一颗 SM 塞多个同样的 CTA 会把每 CTA 的 shared memory 再切薄，容量问题更重。

(b) Reduction / Fan-in

Split-K GEMM 的部分和、反向里对 batch 维求梯度。Batch 本是并行来源，但归约本身在 BSP / 垂直融合里抽不出并行，少量 CTA 做 reduce，多数 SM 空转。

(c) Fan-out / 多播

一个 Elemwise 喂两个 GEMM——Linear+Activation 的反向最典型（对激活求导后再分出 dX 与 dW）。一个后继子图的状态可能挤掉另一个后继还要用的中间结果。异构算子仍然不能同时占 SM。既有垂直融合工作基本不做反向。

图 2. 论文 Figure 2 三种模式。上半：垂直融合的病（spill、欠并行、SMEM 互挤）；下半：Kitsune 用空间切分、归约树和多播队列对上。

Kitsune 的对策是换轴：算子映射到 CTA，中间 tile 经片上队列交给下游 CTA，不同算子同时铺在各 SM 上。多播和并行归约变成队列上的一对多 / 多对一。隐藏维可以空间切开，不再要求一份 tile 塞进单个 CTA 的 shared memory。改过的 grid scheduler 把 SIMT 型 CTA 和 Tensor 型 CTA 配到同一颗 SM。顺带少搬 DRAM，有机会在功耗墙里把频率撑得更高。

4. 原语一：驻 L2 的核间环形队列

执行模型被收成同步数据流（Lee & Messerschmitt 那种 SDF，不是动态 dataflow）：CTA 靠队列里有没有数据被触发或节流。子图入口从主存读（上一子图或仍走 BSP 的算子输出），出口写回主存。CTA 仍可额外读写全局内存。队列空则空转。

队列是软件环形缓冲，用 CUDA API pin 在 L2。每个 slot 带 cache-line 对齐的元数据（序号、写完成计数、读完成计数），全部经 atomic 保护。生产者 / 消费者用序号 acquire / release；通常同一时刻只有一个 CTA 在某个变量上自旋，争用很低。管理代码包在 threadIdx.x == 0 里，release 前 __syncthreads() 防数据竞争。对 CUDA 程序员或源到源编译器就是两句 API。

图 3. 论文 Figure 4 的队列。payload 走 L2，同步靠 global atomics；通常只有一个 CTA 在自旋，争用很低。

void stage0(Queue& q) {
  QueueWriter wr(q);
  for (int i = 0; i < 100; i++) {
    auto output = wr.acquire();
    stage0_work(output);
    wr.release();
  }
}

队列够不够快

微基准：无争用时 A100 每 CTA 约 1 亿次 atomic/s，折合单队列上限 385–1541 GB/s，远高于每 SM 约 61 GB/s 的 L2/HBM 份额。108 SM 上 54 条队列：payload 128–256 KB 时聚合带宽约 2 TB/s（每队列 37 GB/s）；超过 256 KB 会打穿 L2，掉到 HBM 屋顶约 1.5 TB/s。小 payload 同步很贵（1 KB 带宽掉到 1/12）；≥64 KB 时同步开销 <63%。作者认为 64–256 KB 的 tile 正好落在「atomic 够用、还住得进 L2」的区间。

图 4. 小 tile 被 atomic 同步吃掉带宽；过大则打穿 L2 掉到 HBM。Kitsune 把队列 payload 钉在 64–256 KB。

5. 原语二：感知 SIMT / Tensor 的 grid 调度

只靠队列还不能保证异构 CTA 真的叠在同一颗 SM 上。现有 GPU 的 grid scheduler 用占用率做贪心 round-robin，不保证重叠；新 kernel 还要等旧 kernel 派完。Kitsune 加一层很薄的 CUDA 抽象，叫 spatial pipeline：语义接近 CUDA Graph，但要求集合里的 kernel 同时驻留。调用方必须限制每 kernel 的 CTA 数，否则挤不下。每个 kernel 带一种动态资源标签：OP_SIMT 或 OP_TENSOR。 

cudaPipelineCreate(&pipe);
cudaGraphAddNode(pipe, kernel_a, {}, OP_TENSOR);
cudaGraphAddNode(pipe, kernel_b, {kernel_a}, OP_SIMT);
cudaGraphInstantiate(&instance, pipe);
cudaPipelineLaunch(instance, stream);

硬件侧：在原有 round-robin 仲裁上复制一套，SIMT 与 Tensor 各一个 arbiter。新 kernel 按类型选仲裁器，再按占用率往「当前考虑的那颗 SM」派。目标是同一 SM 上配到一对不同类型的 CTA，而不是把同一类型填满再换核。

图 5. 论文 Figure 6 的调度语义。CUDA spatial pipeline 给 kernel 打 SIMT/Tensor 标签；硬件用两套仲裁器保证配对，而不是把同一类 CTA 填满再换核。

这是全文唯一的硬件改动。队列、编译器、ILP 全是软件。因此硅片评测做不了完整 Kitsune，必须上改过 grid scheduler 的 NVArchSim；队列库本身在真机上表征过。

6. 编译器：选子图、插队列、ILP 配 CTA

后端接 PyTorch 2.0 Dynamo，吃前向图和训练的反向图，输出 spatial pipeline。不发明新 IR，也不做复杂代码生成后端——这是作者反复强调的工程选择。

  1. 子图选择（sf-node）。空间融合组必须「连续」（Tarnawski 等的定义：不能有边出子图后再绕回来）。实用规则：排除已经很 BSP 友好的节点，以及要对全体数据做 gather/index 的节点（如 embedding gather）。其余用手工正则在 Dynamo 的拓扑序上做模式匹配，覆盖 Figure 2 那类链。新模式就是往模式库加一条；穷尽所有线性化的自动机被明确划出范围。
  2. 流水线设计。在 sf-node 的边之间插队列；能 epilogue fusion 的仍做垂直融合。Reduction 拆成 fan-in 树 + 最终 reduce（队列构成归约树）。然后把已有 CUDA kernel 改成对队列读写，并限制 payload 为 tile。GEMM 本来就按 tile 写。作者承认对任意新算子做全自动改写接近别名分析的难度，于是手动改每个 kernel，约 8 人时、10–40 行。新算子需要库作者改一改，NVIDIA/AMD 可以把这套收进开发流程。
  3. 负载均衡（ILP）。给每个流水级分配 CTA 数。吞吐取各级最小，再受 DRAM 与 L2 带宽解析约束。第 i 级：实测 BSP 吞吐 ti × 资源缩放 ri(分配的 CTA 数) × 因操作数改走片上而来的加速 si。实践中 si = 1/u，u 为 SIMT 或 Tensor 管道的最大利用率。SIMT 级 CTA 数之和 = SM 数，Tensor 级之和也 = SM 数，允许一颗 SM 叠一对异构 CTA 且假设无互相拖累。ui 需要两遍编译、运行时剖析或 kernel 特性字典——在 TensorRT 这类策展环境里可接受。

Figure 8 用 MeshGraphNets 当贯穿例子：15 步 message passing 里抽出 MLP（Linear+ReLU 链 + LayerNorm），前向插队列并做部分 epilogue fusion；反向把 Linear+ReLU 拆成 multicast、两个梯度 GEMM、以及 dW/dB 的 fan-in + parallel reduce。CTA 分配可以很不均匀（文中示例 34 / 38 / 36 / 108）。

7. 评测：覆盖、加速、流量与敏感性

应用：DLRM、MeshGraphNets、NeRF、GraphCast、Llama 3 8B（训练整段；推理再拆 context/prefill 与 decode/token）。基线：未改的 PyTorch。垂直融合对照是作者把 TensorRT、AStitch、Welder 的机制合进同一套模型里的乐观估计——这些工作多数没演示训练，Kitsune 的 VF 训练数字因此偏向上限。仿真器：改过的 NVArchSim，对 Ampere 做过校准。队列在硅片上测过。

多数应用 >70% 算子能进流水，推理覆盖高于训练。垂直融合在训练上通常只盖前向，覆盖明显更低。Llama decode 几乎省不下流量：token 生成本就不是中间激活把 HBM 灌满的那种形态。流量下降本身被当成功耗叙事——O’Connor 等人认为 GPU 正在变成内存功耗受限。

推理（Figure 10–11）

  • 子图加速 1.04×–3.4×，几何平均约 1.9×。
  • Llama-CTX 子图最不赚钱：已经吃到机器峰值算力的 50% 以上，空间模式加分有限（4–8%），尽管时间覆盖 84%。
  • NeRF 约 2.3×：整条前向空间融合，中间结果几乎全走队列；concat 占 SIMT，GEMM 占 Tensor Core。隐藏维 256 已经让垂直融合融不动这些 Linear。
  • 端到端几何平均约 1.5×。子图通常占运行时间 >50%，且一张网里子图数量不多。

训练（Figure 12、14）

前向还要额外把中间激活写到主存给反向用，所以片上队列的收益被这条边削弱。反向大约是前向的 2 倍时间。反向里空间融合占比更小——DLRM 的 feature interaction 反向没融进去，Amdahl 很明显。端到端 1.1×–2.2×。作者的 takeaway：训练从「并行化 reduction」里拿到的相对好处，比已经并行度充足的 BSP 前向更大。

对照垂直融合

推理上 VF 几何平均约 1.14×，最好的 MeshGraphNets 约 1.4×；训练更差，因为 VF 基本只作用在前向。Welder 一类工作在「Tensor Core + 有意义 batch（如 32）」的生产设定里，相对未优化 PyTorch 大约 30%，相对 TensorRT 几乎没有；它们更常打 bs=1、FP32 这种 GPU 本就低效的角落。Kitsune 明确瞄准 batched + Tensor Core 的生产档。

利用率与硬件敏感性

Figure 13：推理「双低」时间从 BSP 的 26% 降到 15%；训练从 44% 降到 18%。训练时 Kitsune 更多时间落在「只低 DRAM」（50% vs 23%）——反向仍要存激活。引言/贡献里的敏感性：把便宜资源（片上算力、L2 带宽）加倍、贵的 HBM 带宽不动，Kitsune 推理/训练再加速 47% / 27%，基线只有 18–26%。含义是：一旦中间结果不再打满内存总线，加 SM 和 L2 才变得划算。

图 7. 左：Kitsune 把「双低」时间压下去，训练仍有大量「只低 DRAM」（要存反向激活）。右：敏感性实验的含义——空间流水把瓶颈从 HBM 挪回片上之后，便宜资源才有杠杆。

8. 相关工作

算子映射 / 垂直融合

TimeLoop、MAESTRO、AMOS、CoSA、TVM 面向单算子或空间加速器。ALCOP、Apollo、AStitch、Chimera、DeepCuts、GraphTurbo、Welder 做垂直融合，多用 anchor-and-propagate 解决层间 streaming。Kitsune 声称能把更多算子变成共驻 kernel，并覆盖反向。

GPU 多任务

HFuse 水平融合只配成对、无数据依赖。ISPA 软件共调度 Tensor+SIMT 一对 kernel，仍用现有线程调度器。SMK 用硬件抢占做细粒度共享。Kitsune 允许多级空间流水且队列携带依赖，并改 CTA 放置。

数据触发 / 干净数据流

D3D12 WorkGraphs 粒度是单条 record / shader，不编排 64 KB 级 tile 的片上驻留，也不支持不同类型输入的 join。Groq / Cerebras / SambaNova / Plasticine 是换芯片。Kitsune 把同步数据流嵌回 GPU CTA 模型。

9. 边界、方法学与可带走的判断

需要当面看的缝

  • 主结果在仿真器上。队列在 A100 硅片上测过带宽；完整系统依赖尚未存在的 dual-arbiter grid scheduler。NVAS 对 Ampere 做过校准，但「异构 CTA 零干扰共驻」是 ILP 的假设，真实 SM 上共享寄存器、shared memory、warp 调度器会互相抢。
  • 编译器不是全自动。子图靠手工正则；kernel 改队列是每算子 8 人时。新算子、动态 shape、控制流、MoE 路由都不在「透明降低」的字面范围内。
  • 垂直融合基线是合成的乐观模型，不是直接跑 TensorRT/Welder 的端到端 wall-clock。训练上的 VF 数字被作者自己标成乐观。
  • Llama decode 几乎没有流量收益，CTX 子图也接近算力屋顶。对今天最热的 LLM serving，Kitsune 更可能帮 prefill / 训练反向里的 reduction，而不是 decode 的主路径。
  • 同步数据流假定静态速率。动态 dataflow、变长序列、条件专家，队列深度和 ILP 分配都会抖。论文把动态数据流留给未来。
  • L2 pin 的容量政治。54 条队列 × 256 KB 已经在打 L2 天花板；多子图、多 multicast、更大 tile 会和普通 cache 流量抢同一块 L2。文中没有给出「pin 失败 / 被挤出」的鲁棒策略。
  • 预印本状态。2025-02 arXiv，ACM 引用 DOI 仍是占位符，会议归属未在文中写明。
可带走的判断。和 T10 对照最有用：T10 面对的是「核间已经全互连，编译器还在假装有全局内存」；Kitsune 面对的是「GPU 核间只能经 L2/HBM 说话，但 DNN 图想要空间流水」。两者都把中间结果从「写回全局再读」改成「按 tile 在片上交接」，交接介质分别是 IPU 的核间 shift 和 GPU 的 L2 环形队列。Kitsune 证明：在 GPU 上做这件事，通信原语可以是纯软件 atomic 队列，真正缺的硬件是能按资源类型配对共驻的调度器。若你在做 GPU 上的 kernel 融合，值得问的下一问不再是「还能不能再 fuse 一层」，而是「这一对生产者/消费者该不该变成两个共驻 CTA + 一条 64–256 KB 的 L2 队列」。对 LLM decode 别期待同样的故事；对 MLP 深、反向 reduction 重、中间维大到 shared memory 装不下的图，这篇的机会最大。
