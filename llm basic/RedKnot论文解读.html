RedKnot：把 KV Cache 从“整块行李箱”拆成“按需抽屉”

一篇关于长上下文大模型推理的系统论文。它的关键不是简单地“少算一点”， 而是让计算、存储和数据搬运都按照注意力头的真实需求来组织。

一句话结论

RedKnot 解决的是：重复出现的长文本明明已经算过，换个位置后却很难低成本复用的问题。 它发现不同注意力头对“前文变化”的敏感程度不同，于是只重算少数敏感的头， 复用大多数不敏感的头；再只让重要 token 经过昂贵的 FFN；最后用按头分页的 KV 存储和专用内核，把算法上的稀疏真正变成显存、带宽与延迟收益。

The problem

它解决了什么重要问题？

RAG、代码 Agent 和多轮工具调用会把大量文档、日志与历史对话塞进提示词。 同一段内容经常重复出现，却可能位于不同位置、前面接着不同文本。 这让传统的“前缀完全相同才命中缓存”远远不够。

1

长上下文太慢、太占显存

Prefill 要处理整段输入；上下文越长，注意力计算、KV Cache 容量和显存带宽压力越大。 论文举例称，70B 模型的 128K 上下文 KV Cache 可超过 40 GB。

2

已有复用方式粒度不对

现有位置无关缓存往往选择一批 token 重算。但不同注意力头重视的 token 不同， 取并集后可能接近整段文本；少选会损害准确率，多选又失去加速意义。

3

“逻辑稀疏”没有变成“物理节省”

即使算法说某些头只看很短窗口，传统系统仍按统一的矩形张量存储， 再用 mask 屏蔽无用位置。数据照样占显存、被搬运，还可能退出 FlashAttention 快路径。

还有一个容易忽略的瓶颈： 在论文测试的 2K–8K 较短上下文中，FFN 占 prefill TTFT 的 57%–62%。 所以只优化注意力，即使做得完美，也很难把整体延迟大幅降低。

The insight

最关键的观察：注意力头不是一视同仁的

一个 Transformer 层里有多个注意力头，可以把它们理解成一组分工不同的“信息侦察员”： 有的负责跨很远的文本找证据，有的主要关心附近几个词。RedKnot 将其概括为两类。

全局头：远程调查员

会回看很远的上下文，容易受新前缀影响。文档前面换了内容，它得到的表示也可能明显改变， 所以复用旧缓存时通常要重新计算。

↔

局部头：近场观察员

主要看最近的一小段 token 和少量“注意力汇聚”起始 token。 远处前缀变化对它影响很小，因此大部分旧 KV 可以直接复用。

论文在多种模型上的 needle-in-a-haystack 测试显示，局部头约占 83.4%–96.8%，全局头仅占 3.2%–16.6%。 更重要的是，一个特定 (层, 头) 属于全局还是局部，通常相对稳定， 因而可以离线分析一次，在线重复使用。

The solution

三部分协同：算什么、怎么算、怎么存

机制一

按头恢复 KV

先用 RoPE 的相对旋转把离线缓存的 key 从旧位置对齐到新位置。 然后全量重算对前缀敏感的全局头；局部头则复用大部分 KV， 只修补起始 sink token 与最近窗口。

通俗理解：搬家后先改门牌号；需要了解整座城市的调查员重新调查， 只看自家街区的调查员沿用旧记录，只更新门口附近。
机制二

只让重要 token 跑 FFN

在较深层，RedKnot 根据恢复后的注意力信号选择重要 token。 这些 token 正常执行昂贵的 FFN；其余 token 跳过 FFN 更新，只沿残差连接传递。 浅层仍保持更保守的密集 FFN，以避免早期误差被后续层放大。

通俗理解：不是给会议里的每个人同样长的发言时间； 先找出真正掌握证据的人，让他们详细发言，其余人保留原意见。
机制三

SegPagedAttention

把传统“一个 token 块中捆着所有头”的 KV 布局，改成 (层, KV 头, 分段) 可独立寻址的页列表。 全局头拥有完整页列表，局部头只保留 sink 与最近窗口的页； 融合的变长注意力内核一次处理不同长度的头，不构造注意力 mask。

通俗理解：传统仓库按日期装箱，一只箱子里混着所有部门的资料； 找一个部门也得搬整箱。现在按部门分抽屉，只取实际需要的抽屉。

How it runs

一次在线请求是怎么跑的？

01 · 离线准备 对可复用文档块计算 KV，并分析每层每个头是全局头还是局部头。
02 · 位置对齐 文档块出现在新位置时，利用 RoPE 相对旋转修正缓存 key 的位置信息。
03 · 弹性恢复 重算全局头，局部头只修补可见窗口；深层仅为重要 token 执行 FFN。
04 · 按头执行 SegPagedAttention 只读取各头实际需要的页，用融合变长内核完成注意力。

论文还试图把这一框架推广到不同架构：标准 GQA 模型管理显式 KV 页； Qwen3.5 一类混合模型还要管理线性注意力的循环状态；DeepSeek MLA 模型则管理压缩 latent state。 因此 RedKnot 抽象出“可复用状态对象”，用模型适配器完成 PROFILE、BUILDSTATE、SELECTVISIBLESTATE 和 EXECUTE。

Why it works

为什么三个机制必须一起做？

  1. 只做按头算法、不改存储： 虽然逻辑上少看了一些 token，但密集 KV 仍占显存并被搬运，mask 还可能让内核变慢。
  2. 只减少注意力、不管 FFN： 在 2K–8K 的 Agent 常见上下文中，FFN 才是多数 prefill 时间的来源，整体加速会很快碰到天花板。
  3. 只改存储、不解决缓存失真： 文档块换到新前缀后，旧 KV 缺少与新前文的交互；直接复用会伤害输出质量。
论文最完整的因果链： 按头恢复解决“该重算谁”；稀疏 FFN 解决“哪些 token 值得继续精加工”； SegPagedAttention 解决“如何让少算真正对应少存、少搬和快内核”。

Evidence

论文报告了什么效果？

实验覆盖 Mistral-7B、Qwen3-32B、Llama-3.3-70B、Qwen3.5-397B-A17B、 DeepSeek-V4-Flash 等模型，8K–128K 上下文和多种 QA / LongBench 工作负载， 主要硬件为单台 8× NVIDIA H800 80GB 服务器。

1.6–3.54× 摘要与结论强调的 TTFT 加速范围；部分大模型面板报告最高 5.16×
67–79.5% 相对密集注意力 / prefill 的 FLOPs 降低幅度
4.7–7.8× 采用按头物理存储后，每张 GPU 可容纳的并发会话提升
≥95% 多数设置下，相对密集重算保持的 F1 水平；论文称部分长上下文准确率反而更高

值得注意的具体结果

  • SegPagedAttention 的隔离微基准中，128K decode 相比 Dense+mask 从 506.8 ms 降到 24.1 ms，约 21×；128K prefill 报告约 23.3× 内核级加速。
  • Qwen3-32B 的 prefix KV 压缩在 32K 时减少 44% KV 传输， 固定显存预算下 decode QPS/GPU 提升约 1.90×。
  • 并发容量从 32K 下的每 GPU 4 个会话增至 31 个，从 64K 下的 3 个增至 14 个。
  • MuSiQue 请求流分析发现，62% 文档块从未复用；只缓存复用至少 5 次的块， 论文估算可用 7.8 GB 缓存换取 75% 的重计算节省。
如何理解“稀疏反而可能更准确”？ 超长上下文里，大量无关段落会稀释真正证据。RedKnot 在深层减少低价值 token 的 FFN 更新， 类似给信号做降噪。论文观察到在 64K–128K 区域，部分模型和任务上它超过密集计算； 这并不意味着稀疏永远更准，而是说明长上下文中的“多算”可能也会传播噪声。

What matters

这篇论文真正重要在哪里？

它把 KV Cache 从“模型计算后顺手留下的一整块被动张量”，提升为 “知道不同头价值、可独立寻址、可压缩、可分层放置、可按成本调度的运行时对象”。

这比单个稀疏算法更有系统意义。因为长上下文服务不只需要减少 FLOPs，还要共同解决： GPU HBM 容量、内存带宽、prefill/decode 节点间传输、缓存准入与淘汰、内核调度等问题。 RedKnot 的方向是让同一份“按头稀疏元数据”贯穿这些环节。

如果这一思路进入主流推理引擎，未来缓存命中可能不再只是“整块命中 / 整块未命中”， 而是：这个文档块的哪些头仍有效、哪些头要重算、每个头保留多长窗口、应放 GPU 还是低速层级， 以及它是否值得继续缓存。

Critical reading

阅读结果时要注意的局限

  • 在线 TTFT 不包含离线文档块 prefill。 这对高复用内容合理，但若文本只出现一次，离线成本无法摊薄。
  • 参数依赖离线校准。 全局头比例、局部窗口、浅层密集边界、token 选择阈值均按模型和任务配置； 工作负载变化时是否稳定，需要更多生产环境验证。
  • 并非所有端到端实验都启用了 SegPagedAttention。 论文明确指出部分 PD 分离与吞吐测试仍使用 Dense+mask 后端； 某些很高的 21×–23.3× 数字来自隔离的注意力内核微基准，不能直接等同于端到端吞吐。
  • 大模型上缺少完整的同类基线。 CacheBlend、ProphetKV 在 Qwen3.5-397B 与 DeepSeek-V4-Flash 等规模上未可靠运行， 因而这些场景主要与 full recompute 比较。
  • “局部头”并不保证所有任务都安全。 论文也提醒，检索密集型任务的答案可能落在被裁剪的前缀中段； 实际部署需要 retrieval-head 白名单或任务感知压缩。
  • 论文中的最高 TTFT 数字口径不同。 摘要 / 结论强调最高约 3.54×，而部分 Qwen3.5 / DeepSeek-V4 图中报告 3.51×–5.16×。 应按具体模型、上下文、对照实现和是否为单模块测试分别解读。

Glossary

术语速查

KV Cache
模型保存历史 token 的 key/value 表示，避免生成每个新 token 时重复计算全部历史。
Prefill
生成首个 token 前，模型处理完整输入提示词的阶段；长输入时常是 TTFT 的主要来源。
TTFT
Time To First Token，从请求到首个输出 token 的时间，直接影响交互等待感。
PIC
Position-Independent KV Cache：文本块换了位置或前缀后，仍尝试复用其预计算 KV。
RoPE
旋转位置编码。RedKnot 利用其相对旋转性质，把缓存 key 从旧位置对齐到新位置。
FFN
Transformer 的前馈网络。对每个 token 做昂贵的非线性变换，在较短上下文 prefill 中占比很高。
Attention sink
少量起始 token 会吸收较高注意力，即便它们语义上未必重要；局部窗口通常仍需保留它们。
PD 分离
Prefill 与 Decode 使用不同工作节点；KV Cache 需要从 prefill 节点传给 decode 节点。
