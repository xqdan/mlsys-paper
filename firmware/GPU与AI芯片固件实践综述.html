1. 先分清几层固件

人们说的「GPU 固件」往往不是同一块东西。一块数据中心加速卡上，至少有驱动启动时加载的运行时微码、板上闪存里的板级固件，以及整机 BMC / BIOS / CPLD / 交换机那一层。混在一起谈「升一下固件」，最常见的结果是升错层、升完不复位，或者只改了驱动、板级镜像还停在旧版本。

不要先记产品名字。先按「谁加载、存在哪里、升完要不要掉电」把栈拆开。三层的职责是叠在一起的：运行时微码再新，下面的 VBIOS 或 IFWI 不对，保密计算、分区、RAS 记录仍可能对不上；板级固件再对，BMC 和 GPU 托盘不同步，整机升级照样会失败。

图 1 · 固件不在同一层。中间两块都叫「GPU 固件」，但加载路径和升级工具完全不同；最下面一层通常走 Redfish / nvfwupd / OEM 工具，而不是 apt upgrade linux-firmware。

运行时微码

由内核驱动在初始化时加载。NVIDIA 的 GSP 镜像随驱动放在 /lib/firmware/nvidia/<驱动版本>/；AMD 的 blobs 在 /lib/firmware/amdgpu，通常来自发行版的 linux-firmware。

板级固件

驻留在卡上的闪存。NVIDIA 的 VBIOS 和 InfoROM、AMD Instinct 的 IFWI / VBIOS、Gaudi 的 SPI / eROM、昇腾的 NPU 固件和 MCU，都属于这一层。升级失败的后果通常比只换微码更重。

整机固件

BMC、主机 BIOS、CPLD、PCIe 交换/重定时器、NVSwitch、网卡和电源。数据中心 GPU 的很多「固件包」其实是整托盘一起发的，不能只抽一张卡来刷。

几个容易混的词

VBIOS 是板上的 GPU BIOS。NVIDIA 的 nvidia-smi 把它单独列成 “VBIOS Version”，并写明这是 GPU 板的 BIOS。InfoROM 是另一块小的持久存储，用来放配置和状态，例如 ECC 记录、电源管理对象；镜像版本和 VBIOS 一样，唯一标识这块板上烧录的 InfoROM，对象版本只表示能力。GSP 是 GPU 上的系统处理器，用来卸载原来由 CPU 侧驱动完成的初始化和管理；它跑的是驱动附带的固件文件，不是 VBIOS 本身。

AMD 一侧，内核文档把 PSP 称为 Platform Security Processor，SMU / SMC 是电源与系统管理，SDMA 是系统 DMA，MES 是 MicroEngine Scheduler，IMU 是 Integrated Management Unit。这些是运行时微码的角色名。板级则另有 VBIOS 和 IFWI（integrated firmware image）。Instinct 文档把「固件」明确拆成这两类：/lib/firmware/amdgpu 里的公开微码，以及经 OEM 发布的 VBIOS / PLDM 包。

再往外，是 BMC 和主机固件。它们不在 GPU 驱动里，但决定你能不能带外升级、升级后要不要 AC 下电，以及 RAS 事件能不能出带外通道。NVIDIA 的 Fabric Manager 也不是固件，而是跑在主机上、用来把 NVSwitch 系统组织成可用织物的服务；它和 NVSwitch 固件、GPU 驱动必须在同一套支持组合里。

一条可用的习惯：先用厂商的查询命令把「驱动版本、运行时微码版本、VBIOS / IFWI、整机 BMC / BIOS」四行都读出来，再决定升哪一层。只看 nvidia-smi 的 Driver Version，或只看 amd-smi version 里的 ROCm 号，都会漏掉真正决定能否启动的那一层。

2. NVIDIA：GSP、开源模块与查询

从 Turing 开始，NVIDIA 把大量原来在 CPU 侧 Resource Manager 里做的初始化和管理，搬到 GPU 上的 GSP。开源内核模块直接依赖这条路径：没有 GSP，就没有开源模块。

GSP 是什么，怎么确认它在跑

NVIDIA 驱动 README（以 580.95.05 为例）的原话是：部分 GPU 含有 GPU System Processor，可用来卸载 GPU 初始化和管理任务；这份处理器由驱动分发的固件驱动，在支持它的 GPU 上默认启用。把传统上由 CPU 侧驱动做的工作卸到 GSP，是因为 GSP 访问 GPU 内部的时延更低。固件文件名为 gsp_*.bin，安装在 /lib/firmware/nvidia/580.95.05/ 这类按驱动版本分目录的路径下，文件名按架构命名，例如 gsp_tu10x.bin 对应 Turing，一份文件可以覆盖一个或多个架构。

查询方式是官方写死的。运行 nvidia-smi -q，若 GSP 启用会看到一个有效的 “GSP Firmware Version”（通常与驱动版本相同，例如 580.95.05）；若禁用则显示 N/A。同一项也出现在 /proc/driver/nvidia/gpus/PCI-BUS-ID/information。还可以在 nvidia-smi -q -d 里单独指定 GSP_FIRMWARE_VERSION。

专有模块仍可用模块参数 NVreg_EnableGpuFirmware=0 关掉 GSP。开源模块做不到这一点：vGPU 文档把「装了开源内核模块后，即使把该参数设为 0 并重启，nvidia-smi -q 仍显示 GSP 版本而不是 N/A」记为已知限制，状态是 “Not a bug”。绕过办法是改用专有内核模块再关 GSP。这不是推荐配置，只说明两条内核模块路线对 GSP 的依赖不同。

开源内核模块和封闭固件

2022 年 5 月，R515 首次以 GPL/MIT 双许可发布开源 Linux GPU 内核模块。2024 年 7 月 17 日的 NVIDIA 技术博客宣布，从即将发布的 R560 起，默认安装改为开源模块。这篇博客和随后的驱动安装指南、580.95.05 的 Open Linux Kernel Modules 一章，合在一起可以把边界说清楚：

  • 开源模块只支持 Turing 及之后的 GPU，因为它依赖 Turing 才引入的 GSP。
  • Maxwell、Pascal、Volta 必须继续用专有模块。
  • Blackwell 及之后只支持开源模块，专有模块不再覆盖这些平台。更早的博客还点过 Grace Hopper：这些新平台必须用开源模块。
  • 保密计算、GPUDirect Storage、HMM、GPU fault handler 的 CPU affinity、CUDA 分配的 DMABUF，官方写明只在开源模块上工作。
  • 两种模块互斥，不能同时装进内核，也不该同时留在文件系统上。用户态组件则是同一套。
  • 自己编译开源模块时，必须搭配同一版本的用户态驱动和 GSP 固件。GitHub 仓库 NVIDIA/open-gpu-kernel-modules 的 README 写得很硬：编出来的模块要和对应驱动版本的 GSP 固件及用户态组件一起用，可用 .run --no-kernel-modules 只装用户态。

开源模块相对「关掉 GSP 的专有模块」，官方也列了已知差异：GPU 初始化更慢，可用 nvidia-persistenced 提前初始化来缓解；S3 / S4 / RTD3 进出更长，因为要恢复额外的 GSP 状态；部分场景功耗会有轻微影响；RTD3 只在 Ampere 及之后支持。判断当前装的是哪一种：modinfo nvidia | grep license 为 Dual MIT/GPL，或 /proc/driver/nvidia/version 里出现 “Open Kernel Module”，就是开源模块。

实践上：Turing 及更新的训练和推理节点，按官方建议走开源模块，并接受 GSP 不可关闭。旧卡或新老混插，继续用专有模块。不要把开源模块和专有模块的安装包叠在同一台机器上，也不要拿 A 版本的内核模块去配 B 版本的 GSP 固件。

持久化：不要只靠遗留的 Persistence Mode

GPU 没有客户端打开设备文件时，驱动会卸掉 GPU 状态，下一次作业就要重新初始化。对已经把大量初始化放进 GSP 的卡，这个代价更明显。NVIDIA 以前提供内核里的 Persistence Mode（nvidia-smi -pm），后来改为主推用户态的 nvidia-persistenced：守护进程打开设备文件并休眠，相当于一直有一个客户端握着 GPU，但并不真正用卡做计算。官方文档写明，近一段时间两种方案都会支持，但未来的开发和修复集中在守护进程上，并鼓励尽早迁过去。

安装注意：驱动安装器会把二进制放到 /usr/bin/nvidia-persistenced，但不会可靠地把它登记进所有发行版的 init 系统。发行版包装或管理员需要自己启用服务。保密计算的部署指南也把「确认 nvidia-persistenced 在跑」写成验证步骤之一。开源模块 README 把这个守护进程当作缓解初始化变慢的手段，不是可选项点缀。

3. NVIDIA：整机固件、NVSwitch 与保密计算

VBIOS、InfoROM 和行重映射

nvidia-smi -q 除了 GSP，还会给出 VBIOS 和 InfoROM。InfoROM 里有镜像版本，以及 OEM、ECC、电源管理等对象版本；也提供校验和状态（--query-gpu inforom.checksum_validation，值为 valid / invalid / N/A）。驱动把 InfoROM 损坏列为退出码 14。某些功能明确依赖 InfoROM 对象达到指定版本，例如 ECC 模式开关需要 ECC 对象 1.0 或更高。

从 Ampere 开始，帧缓冲内存的可靠性机制从「页退役」换成硬件 row remapping（行重映射）。官方说明：每个 DRAM bank 有备用行，重映射在硬件层替换坏单元，不会在软件地址空间里留下空洞；要生效必须做 GPU reset，并且在 GPU 生命周期内保持。相对旧方案，帧缓冲最多 512 次重映射（旧方案最多 64 次页退役）。正确纠正错误占用的备用行，在备用行耗尽时可以被不可纠正错误的重映射替换。

和 InfoROM 直接相关的 Xid 是官方写过的：Xid 63 表示成功把一条行重映射记录写入 InfoROM，Xid 64 表示写入失败；Xid 48 / 94 / 95 分别对应不可纠正 ECC、contained 和 uncontained 错误。统计既可以通过 nvidia-smi / NVML 看（已记录的重映射条数、pending、failure，以及分桶计数），也可以走带外 SMBPBI。注意：界面上的「已重映射行数」是 InfoROM 里记录的条目，不一定等于硬件此刻已经换上的行。Blackwell 上，同一 bank 第三次因不可纠正错误尝试重映射时，若有备用通道，会进入 HBM channel repair。

看到 “Row remapping pending” 不要继续当成健康卡用满。官方要求一次 GPU reset 才会生效。若 failure 标志被置位，应走现场诊断和 RMA 策略，而不是反复复位撞运气。RMA 门槛写在 GPU Memory Error Management 里，例如同一 bank 已有八行不可纠正重映射后再尝试、对已经重映射的行再次因不可纠正错误重映射、或不可纠正重映射累计达到 512 次。

DGX / HGX 的固件栈和 nvfwupd

单卡查询解决不了 HGX / DGX 这类系统。以 DGX B300 为例，官方把可升级部件拆到两只托盘：主板托盘上有 CPU、PCH、BMC 等；GPU 托盘上有 GPU、NVSwitch、HMC 等。升级可以带外走 Redfish，也可以在主机上用 nvfwupd。激活方式按部件不同：BMC 用 ipmitool mc reset cold；PCIe Switch / Retimer、BIOS、HGX（GPU 托盘）要用 ipmitool chassis power cycle；ERoT 和 CPLD 则要拔掉所有电源再上电（AC power cycle），不能用普通 reboot 代替。

图 2 · DGX / HGX 固件是按托盘打包的。工具是 nvfwupd 或 Redfish，不是 nvidia-smi 里的某个刷写开关。

DGX B200 的升级步骤把几条运维约束写得很具体，值得当成通用纪律，而不是只适用于这一个机型：

  • 开始前停掉不必要的系统活动。停掉所有 GPU 活动，包括不要运行 nvidia-smi，否则可能挡住 VBIOS 更新。
  • 升级过程中不要再加用户作业、诊断或监控。负载过高会打断升级，留下不能用的部件。
  • 部分 VBIOS 版本之间的数据结构不兼容。B200 文档举例：低于 97.00.5E.00.xx 的版本，不能直接跳到高于 97.00.7C.00.xx 的版本，必须先打过渡包。已经在 97.00.5E 及以上，才可以直接升到最新。
  • GPU 托盘更新是并行打在托盘内各部件上的（VBIOS、NVSwitch、EROT、FPGA 等）。有的步骤要确认 BackgroundCopyStatus 为 Completed，再继续。

nvfwupd 本身是跨平台的固件更新工具，不仅用于 DGX。NVIDIA 的多节点 NVLink 固件更新指南覆盖 Grace Hopper、Grace Blackwell、Vera Rubin、HGX / MGX，以及 NVLink 交换机（NVOS）和电源架。它通过 BMC 的 Redfish 接口工作，输入是 NVIDIA 签名的 PLDM 包。命令里需要指定 servertype，支持的取值包括 DGX、HGX、HGXB100、HGXB300、GB200、GB300、各类 Switch 等。集群规模上，SuperPOD / BasePOD 更新指南建议按发行说明操作，并用 BCM 做多节点分发；工具仍是同一套 nvfwupd。

Fabric Manager 和 NVSwitch

NVSwitch 系统上，GPU 之间的全互连要靠 Fabric Manager 把交换机构成可用织物。这份服务随驱动或独立包安装，日志里的 NVSwitch 错误以 SXid 为前缀，GPU 错误以 Xid 为前缀。致命 SXid 若发生在连接 GPU 的端口，会传到 GPU，可能伴随 Xid 74 和 Xid 45，正在跑的 CUDA 作业会被中止，需要按手册做恢复后再提交新作业。连接两块 GPU 基板的端口上出现致命 SXid 时，FM 会中止所有正在运行的 CUDA 作业并阻止新作业。

有两点版本事实需要单独记住。第一，从 Fabric Manager 用户指南 2.6 版（2026-09-21）起，第四代 NVSwitch 上的 Fabric Manager 开始独立版本号，起点是 GPU 驱动发行 620——也就是说，不能再默认「FM 版本等于驱动版本」。第二，DGX B200/B300 和 HGX B200/B300 不再用原来的 NVSwitch SXid 报告方式，改由 DCGM 通过 NVSDM（NVIDIA Switch Device Manager）取交换错误。

保密计算对固件的要求

NVIDIA Confidential Computing 不是只开一个驱动开关。官方 Secure AI Compatibility Matrix 列出的是 GPU、VBIOS、CUDA 驱动和保密计算模式的组合。两点写在矩阵说明里：HGX Hopper 固件 1.6.0 在 Protected PCIe 模式下有已知问题，可能导致启动时 GPU 掉总线，应使用 1.7.0；一旦使用 HGX Hopper 固件 1.8.0 或更新，就不能再回退到 1.7.1 或更早。威胁模型文档也写明，GPU 侧的保护取决于架构、安全模式、固件和驱动版本，要用这份矩阵核对已验证配置。

部署指南要求在跑工作负载之前先做 attestation：GPU 收集并签名测量值，校验器与已知良好的参考测量比较。认证成功不会自动把 GPU 设为可接受任务，还要在客户虚拟机里执行 nvidia-smi conf-compute -srs 1。事前还要确认 nvidia-persistenced 在运行，并用 nvidia-smi conf-compute -f 确认 CC 状态为 ON。

4. AMD：linux-firmware、IFWI 与版本矩阵

AMD Instinct 文档把「固件」分成两种，升级路径也不一样。一种是驱动启动时从 /lib/firmware/amdgpu 加载的、签名过的运行时微码；一种是板级 VBIOS、平台 PLDM 包等，经服务器 OEM 发布。

运行时微码：发行版包是正路

AMDGPU 内核驱动在启动过程中加载 SMU、PSP、SDMA、MES、IMU、RLC 等角色的固件。这些名字的权威释义在内核 AMDGPU Glossary：PSP 是平台安全处理器，SMU/SMC 是系统管理单元/控制器，MES 是微引擎调度器，IMU 为电源管理提供支持。它们不是「再装一个闭源驱动」那么简单，而是开源 amdgpu 正常工作的前提。

Instinct 客户验收指南写明：更新这些微码的标准、受支持做法，是更新发行版的 linux-firmware（RHEL 系 dnf update linux-firmware，Debian/Ubuntu 系 apt-get install --only-upgrade linux-firmware），或随 AMD 官方仓库里的驱动栈一起更新，然后重启使其生效。上游参考仓库是 kernel.org 的 linux-firmware.git，以及 GitLab 镜像 kernel-firmware/linux-firmware。不要从来路不明的目录随手拷一份 .bin 覆盖进去。

板级 IFWI / VBIOS：跟 OEM 和 ROCm 矩阵走

板级固件（VBIOS，或打进 PLDM bundle 的部件）由戴尔、HPE、联想、超微等 OEM 的工具发布和验证。Instinct 指南的原话是：只用 OEM 为你的确切服务器型号和 GPU 选件料号发布的包；如果平台没有对应的 GPU 固件，不要自行刷写，联系 OEM 或 AMD 支持。ROCm 发行说明里有硬件 / 驱动 / 固件依赖矩阵，规划升级时要查最新矩阵，而不是沿用上次装集群时的旧表。例如 ROCm 文档的 compatibility matrix 会按 MI350 / MI300 / MI325 等列出受支持的 PLDM bundle 版本，和驱动版本写在同一张表里。

内核文档 dGPU firmware flashing 描述了另一条、面向 Navi3x 及更新消费级/工作站 dGPU 的路径：由 PSP 编排 IFWI 更新，通过 sysfs 的 psp_vbflash 暂存镜像、再读该文件启动烧录，并用 psp_vbflash_status 轮询完成。这是内核提供的机制说明，不是 Instinct 集群的推荐流程。Instinct 服务器上，AMD 另有 FW Flash 工具（amdfwflash）用户指南，用来更新 IFWI 和远程管理固件。这份 PDF 在 AMD 的 drivers.amd.com/relnotes/ 上可以公开取到。指南里有几条运维约束写得很硬，应当当作官方规范而不是论坛经验：

  • 同一 hive（经 XGMI / Infinity Fabric 连在一起的一组 GPU）不能运行不同的固件版本，官方回答是 “No. This configuration is not supported and may cause undefined behavior.”
  • 从工具 2.00 起，烧录时可以保持 amdgpu 已加载。
  • 用 rocm-smi --showhw（或现在的 amd-smi）核对 VBIOS 列；若列不全，先检查当前启动的内核是否安装了对应的 amdgpu（dkms status 与 uname -a 是否同一内核），不要把 “WARNING: No AMD GPUs specified” 直接理解成烧录失败。

分区等高级功能也会钉死固件版本。例如 MI300X 分区文档会给出一版经验证的 VBIOS（文档中的例子是 022.040.003.043.000001），并用 amd-smi static --vbios 查询名称、编译日期、料号和版本。版本对不上，不要先怀疑分区命令，先回到矩阵。

升级后最少要验证什么

Instinct 指南给的最小验证集是：sudo dmesg | grep amdgpu 看固件是否加载成功；amd-smi version 看 ROCm / 驱动；amd-smi list 或 amd-smi monitor 看健康；必要时用 dmidecode 核对系统型号和 BIOS，以便对照发行说明矩阵。集群层面，它明确建议保持 BIOS / BMC / GPU 运行时固件和配置在节点间一致，用滚动方式减少停机，并先单节点验证再做集群检查。

发行版更新 linux-firmware 之后，amdgpu 加载失败是真实出现过的社区故障，不是理论上的边角。Ubuntu 的 Launchpad 缺陷 #2173166（社区报告，不是 AMD 官方公告）描述：某次 apt upgrade 后，RX 9070 XT 的显示微控制器固件（DMUB，DCN 4.0.1）被 PSP 拒绝，内核随后报 DMCUB 错误。处理这类问题，应先看 dmesg 里被拒绝的固件名和版本，再决定是回退 linux-firmware、换内核，还是等发行版修正，而不是直接刷 IFWI。

5. 其他 AI 加速器

这一节只写能找到可靠公开说明的厂商。公开资料少的，直接说少，不补故事。

Intel Gaudi：hl-fw-loader 和安全固件

Gaudi 的公开文档在这方面相当完整。固件升级既可以用安装指南里的流程，也可以直接用 hl-fw-loader。系统级通常只需更新 SPI（preboot）固件，版本要以 Support Matrix 为准。标准步骤是：先卸驱动（1.21.0 之后的卸载顺序与更早版本不同，文档写了两种顺序），查询当前 SPI 版本，运行 sudo hl-fw-loader，再装回驱动，用 hl-smi -L | grep SPI 核对。升级过程中官方明确要求避免网络问题或掉电。

另外还有 eROM，主要用于恢复，不影响日常使用；空的 eROM 需要按最新版本写入，Gaudi 3 在需要时可以升级。查询用 hl-smi --fw-version（或文档中的 --fw-versions）。hl-fw-loader 还提供恢复模式（-r）在标准方法失败时直接烧闪存或 EEPROM，但安全设备（secured OAM）上不可用。固件更新锁可以把带内的 hl-fw-loader 接口锁掉，不影响从 BMC 走的带外更新；掉电会解除这把锁，需要的话要重新加上。

安全固件流也是公开的：可以查询 Security / Keys / Minimal SVN / Flash 写保护等状态；启用后用 FIT 文件提升 SVN，官方写明一旦更新 SVN，就不能再降到更早的固件版本。这对「先升后回滚」的运维计划是硬约束，要在升级前提前看清楚。

华为昇腾：驱动和固件有固定顺序

华为企业支持网站上有多份 Atlas 系列「NPU 驱动和固件升级指导书」，以及 npu-smi 命令参考。公开页面里写过两条非常具体的顺序：首次安装按「驱动 → 固件」；覆盖安装或升级按「固件 → 驱动」。版本查询可用 npu-smi info -t board -i <NPU ID>；升级可用 npu-smi upgrade -t item -i id -f file_path。推理卡上还有 MCU，作为带外管理模块，负责单板监测和故障上报，需要按对应机型的安装指南单独维护。

这些文档是一手来源，但部分网络访问华为企业支持站点会遇到 403 或 Cookie 墙，撰写时从本环境不能稳定抓取全文。引用时请以你能打开的官方页面为准，并先核对该机型和软件版本的配套表，不要把某个 3010 机型的步骤套到 A2 训练硬件上。

AWS Neuron：公开的是 SDK 和实例，不是刷写手册

AWS Inferentia / Trainium 的公开文档中心是 AWS Neuron Documentation。能稳定找到的，是驱动（aws-neuronx-dkms）、运行时和框架的发行说明，以及如何在 DLAMI / EKS 上安装 Neuron SDK。关于「如何在实例上刷芯片固件」或「固件与驱动的兼容矩阵」，公开材料很少。一个相关的官方公告是：从 Neuron 2.19 之后，neuron-monitor 将不再提供 neuron-device-version 字段，改用 instance_info 里的 instance_type 和 neuroncore_version。这更像是把「器件版本」收进实例和内核版本模型，而不是给用户一条自助刷写路径。对运维来说，实际可控的通常是 AMI / 驱动 / SDK 组合，而不是独立的固件包。

Google TPU：用户选的是运行时，不是固件包

Cloud TPU 文档讲的是创建 TPU 时选择的 software / runtime version（Ubuntu、Docker 和运行框架所需的预装环境），例如 Trillium（v6e）用 v2-alpha-tpuv6e，并按 TensorFlow / JAX / PyTorch 对齐 libtpu 版本。公开文档里没有给用户的 TPU 固件刷写流程。固件由 Google 在设施侧管理，用户侧要对齐的是运行时版本和框架，而不是自己维护一组 .bin。

Tenstorrent：少见的公开固件仓库和刷写工具

Tenstorrent 是少数把板级固件和刷写工具放在公开 GitHub 上的加速器厂商。官方入门文档的安装顺序是：先装内核驱动 TT-KMD，再用 tt-flash 把 tt-system-firmware 的 bundle 烧到设备上，然后重启；Blackhole 设备要求固件 18.3.0 或更新。若工具提示固件过旧，文档允许加 --force 再刷，然后重启。之后用 tt-smi 查看设备信息、遥测和固件。仓库包括 tt-flash、tt-system-firmware 和 tt-kmd。文档提醒：各 SDK 有自己的兼容矩阵，不要只追「最新」而忽略配套。

其他厂商

Cerebras、Graphcore、SambaNova、寒武纪等在公开网上很难找到与上述级别相当的、面向用户的固件升级说明。不是「没有固件」，而是公开资料不足以写成可核对的操作指南。遇到这些平台，应以厂商支持渠道和随机文档为准，不要用 NVIDIA / AMD 的步骤去类推。

6. 集群里怎么升、怎么锁版本

集群固件运维的核心不是「尽快升到最新」，而是让同一故障域里的驱动、运行时微码、板级固件和整机固件停在一套经过验证的组合上，并且能回退。

先锁组合，再谈滚动

各家都在用矩阵说话：NVIDIA 有数据中心驱动与 CUDA 的配套说明，以及保密计算的 VBIOS–驱动矩阵；AMD 有 ROCm 的硬件 / 驱动 / PLDM 矩阵；Gaudi 有 Support Matrix；昇腾有驱动固件配套表；Tenstorrent 各 SDK 也有兼容矩阵。把矩阵里的一组版本写进集群的变更单，比在每台机器上执行「升级到当前最新」要可靠。

滚动时注意故障域的粒度。AMD 官方禁止同一 XGMI hive 内混用不同板级固件。NVIDIA 的 GPU 托盘通常是一套包打进去，也不适合托盘内各卡各升各的。Gaudi 文档允许用 -d 指定单卡，但集群目标仍应是一套对齐的 SPI 版本。昇腾的升级顺序（先固件后驱动）是覆盖安装的硬规则，滚动脚本里不能反了。

GPU Operator 管的是驱动，不是板级固件

NVIDIA GPU Operator 的官方升级文档只覆盖容器化驱动的生命周期。它会在升级时禁用 GPU 客户端、卸载内核模块、拉起新的驱动 Pod、再恢复客户端，并可用 Upgrade Controller 做并行度、不可用节点比例、等待特定 Pod 完成、驱逐 GPU Pod 等控制。预装在宿主机上的驱动，Operator 不管。整机 BMC、VBIOS、NVSwitch 固件也不在这份流程里。它们仍要走 nvfwupd、Redfish 或 OEM 工具，而且往往要在驱动升级之外另开维护窗口。一个常见误区是：改了 ClusterPolicy 里的 driver.version，就以为节点的 VBIOS 和 BMC 也会一起动。

驱动升级本身已经够「重」：必须排空或驱逐使用 GPU 的工作负载。NVIDIA 另有 NVSentinel 等组件的升级 runbook，提醒在驱动升级期间避免健康检查系统干扰。这些都是主机软件层的事，不要和固件包的激活（冷复位、power cycle、AC 下电）排在同一分钟里盲目并行。

回滚不是总是做得到

保密计算矩阵写明某些 HGX Hopper 固件不能回退。Gaudi 在提升 SVN 之后不能降到旧固件。DGX 上部分 VBIOS 不能跨数据结构直接跳版本，回滚同样可能需要过渡包。规划维护窗口时，要把「不能回滚」当成可能的结果，而不是默认总有一条退路。能回滚的层（例如发行版的 linux-firmware 包、未锁 SVN 的 Gaudi SPI、仍允许降级的 DGX 包）应在升级前保留确切的包文件和版本记录，而不是只记一个「升过了」。

Xid、SXid、dmesg 和 AER

Xid 是 NVIDIA 驱动打到内核日志里的错误报告，典型形态是 NVRM: Xid (PCI:0000:5a:00): 79, GPU has fallen off the bus. 官方现在为 Ampere 及更新的 GPU 提供一份可下载的 Xid Catalog 表格，并要求按「保留完整上下文 → 对表 → 看组合解析规则 → 执行 Tenant 动作」来处理，而不是只记住几个代号的俗称。动作关键字例如 RESET_GPU、RESTART_APP、CONTACT_SUPPORT，定义在表格的 Guidance Classes 里。复位前要看平台和虚拟机限制。

目录和旧版说明里仍然有一组被反复引用的代号，含义应以当前 Catalog 为准，下面只作定向，不代替查表：

  • Xid 48 / 94 / 95：ECC 及相关的 contained / uncontained。
  • Xid 63 / 64：行重映射写入 InfoROM 成功或失败。
  • Xid 74：NVLink 错误；在 NVSwitch 系统上常与 SXid 一起看。
  • Xid 79：GPU has fallen off the bus。这是后果描述，原因可能在电源、PCIe、固件、托盘接触或多个层同时出问题。不要一看到 79 就只重装驱动。
  • Xid 93：InfoROM 磨损限额的非致命违例。
  • Xid 45：OS 抢占式拆除通道，常见于作业被中止或恢复流程中。

NVSwitch 的 SXid 要和 Fabric Manager 日志一起看。B200/B300 则改走 NVSDM / DCGM。PCIe 的 AER 日志（dmesg 里的 AER、PCIe Bus Error）往往和 Xid 79、掉卡同时出现，应用来判断问题是在链路还是在 GPU 内部。Google Cloud 也有一份面向 GPU 虚拟机的 Xid 排障说明，内容指向同一套 NVIDIA 概念，适合云上租户对照。

升级失败和「竟然是固件」的真实情况

  1. 升级时还在跑 nvidia-smi 或监控。 DGX B200 指南把这写成会阻止 VBIOS 更新的条件。维护窗口里应显式停掉 DCGM、节点导出器和所有查询脚本，而不是只停用户作业。
  2. 跳过过渡包。 VBIOS 数据结构不兼容时，直接打最新包会失败。Redfish 路径上会出现文档所举的那类错误。先 show_version，对一下当前版本落在哪个区间。
  3. 用错激活方式。 BMC 冷复位、chassis power cycle、AC 下电不是一回事。CPLD / ERoT 只 reboot 不会生效。
  4. 开源模块配错 GSP，或混装两种内核模块。 版本必须一致；两种模块互斥。初始化异常时先看 dmesg 是否找到对应目录下的 gsp_*.bin。
  5. 行重映射 pending 却没有 reset。 卡会继续带着未生效的修复跑，后续 ECC 事件会被误判成新故障。
  6. AMD 只升了驱动，没升 linux-firmware，或发行版微码被 PSP 拒绝。 表现是 dmesg 里 firmware load failed，或显示/计算 IP 块初始化失败。先对微码，再怀疑板级 IFWI。
  7. 同一 hive 混固件。 AMD 官方直接说不支持、行为未定义。
  8. Gaudi 升级中掉电，或升完没对 Support Matrix。 文档把掉电和网络中断单独写成风险；升完必须再读 SPI 版本。
  9. 昇腾把首次安装和覆盖安装的顺序写反。 这是官方安装指引里的硬顺序，不是习惯问题。
  10. 把 GPU Operator 的驱动滚动当成固件滚动。 板级和整机固件不会跟着 driver.version 走。
  11. 保密计算组合不在矩阵里，或试图回退不允许回退的 Hopper 固件。 官方点过 1.6.0 在 Protected PCIe 下可能掉总线；1.8.0 起不能退回 1.7.1 以前。

8. 安全：签名、认证与研究

现代加速器固件普遍是签名镜像。AMD Instinct 把 /lib/firmware/amdgpu 下的文件直接称为 signed firmware，IFWI 更新由 PSP 编排。Gaudi 提供完整的安全固件流：密钥、SVN、闪存写保护、eFuse 永久启用，以及带内更新锁。NVIDIA 的 GSP 固件随官方驱动分发，开源内核模块也只能加载配套的官方镜像；保密计算还要在运行前对 GPU 做 attestation，把测量值比对照官方发布的参考值（RIM）。Tenstorrent 的刷写工具和固件包是公开仓库，但仍应以厂商发布的签名 bundle 为准。

把大量驱动逻辑搬进 GSP，等于把一块不小的可信计算基挪到 GPU 里面。LWN 对 2023 年 Linux Plumbers Conference 上 Dave Airlie 报告的记述写过几个工程后果：GSP 固件没有稳定 ABI，很多调用缺少文档，单份固件体积达到数十 MB 量级，且一台设备往往需要两份，会显著膨胀 /boot 和 initramfs——这是 Nouveau / 发行版要严格挑选固件版本的原因。这些并不是漏洞公告，但说明 GSP 已是主机和 GPU 之间一条又宽又深的接口。

公开安全研究方面，应读原论文，不要把二手标题当成结论。例如 2024 年的 Whispering Pixels（arXiv:2401.08881）讨论现代 GPU 上未初始化寄存器带来的泄露，针对的是 GPU 编程接口一侧的残留状态，不是一份 GSP 刷写指南。2026 年 6 月发布在 Zenodo 上的 A Canary in the Crypto Mine: Defeating Stack Protection in a GPU Secure Coprocessor 则把对象放在数据中心加速器的安全协处理器上（文中以与 A100 同晶圆的 CMP 170HX 为例）。这类论文说明 GPU 固件和安全协处理器已经成为被认真分析的攻击面。具体利用细节不应在运维综述里复述；补丁和缓解应以 NVIDIA Product Security 以及 AMD、Intel、OEM 的公告为准。

运维上能做的，仍然是平凡但有效的几件事：只安装厂商或 OEM 签名的包；把驱动、VBIOS 和保密计算模式限制在官方矩阵内；升完做 attestation 再放开工作负载；关注安全公告，而不是在生产集群里试验未签名或来路不明的 GSP / IFWI 镜像。

词先理解成

InfoROM板上另一块小的持久存储，记录 ECC、配置和部分 RAS 状态
GSPGPU 上的系统处理器，跑驱动附带的固件，卸载 CPU 侧管理任务
IFWIAMD 的集成固件镜像，由 PSP 或厂商工具写入板级闪存
PSP / SMU / MES / SDMA / IMUAMD GPU 上安全、电源、调度、DMA 和电源辅助等运行时微码角色
linux-firmwareLinux 发行版分发的、驱动启动时加载的固件包

nvfwupdNVIDIA 用 Redfish 打签名 PLDM 包的固件更新工具
Fabric Manager主机上组织 NVSwitch 织物的服务，不是板上固件
