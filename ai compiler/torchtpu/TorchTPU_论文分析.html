1. 一句话结论与动机

TPU 过去主要围绕 JAX 调优，大量外部用户的代码却是 PyTorch。TorchTPU 是 Google 的工程团队（与 Meta 合作）新写的一套栈，目标只有一句话：换一行 device="tpu"，训练脚本其余代码不用动。它不是在 PyTorch/XLA 外面再包一层，而是深入 PyTorch 的 PrivateUse1 后端接口，让 TPU 上跑的是普通 torch.Tensor，没有子类、没有包装器。

核心架构决策：全图编译走 Torch Dynamo 捕获 FX graph → XLA 作后端编译器 → StableHLO 作 IR，而不是走 Torch Inductor。理由是 XLA 已经在 TPU 拓扑上打磨多年，天然懂得怎么把稠密计算和 ICI 上的集合通信重叠。

2. TPU 硬件：ICI 网络、TensorCore、SparseCore

理解 TorchTPU 的设计，要先理解它面对的硬件不是"一块芯片"，而是一整张网络。一个 host 挂多颗芯片，每颗芯片既连 host，也通过 Inter-Chip Interconnect（ICI）直接连其他芯片，组成高效的 2D 或 3D Torus 拓扑——这是 TPU 能不靠传统网络瓶颈做超大规模 scale-up 的关键。芯片内部执行又分两路：TensorCore 是单线程的稠密矩阵运算单元；SparseCore 专门处理 embedding、gather/scatter 这类不规则访存，以及卸载集合通信。

图 1 · 左：多芯片经 ICI 组成 Torus，避免传统网络瓶颈。右：单芯片内 TensorCore 管稠密矩阵、SparseCore 管不规则访存与通信卸载。

PyTorch 已经是跨设备类型事实上统一的接口，这正是 TorchTPU 要接入的地方：把这套硬件能力包进 PyTorch 熟悉的使用方式里，而不是逼开发者去学一套新框架。

3. Eager First：三种 eager 模式

TorchTPU 没有先把开发者推向静态图编译，而是立下"Eager First"原则：用 PyTorch 的 PrivateUse1 接口深度集成，让 TPU 上就是普通的 torch.Tensor。由此派生出三种 eager 执行模式，覆盖从调试到追求极限性能的不同阶段。

模式调度方式同步点用途
Debug Eager单算子逐个派发每次执行后与 CPU 同步定位 shape 不匹配、NaN、OOM；慢但信息最全
Strict Eager单算子派发，但异步执行用户脚本触发同步点才等待贴近默认 PyTorch 体验，CPU/TPU 可并行
Fused Eager对算子流做自动反射，动态融合成大计算块按融合块粒度最大化 TensorCore 利用率、降低显存带宽开销；提速 50%–100%+，零配置
三种模式共享同一份编译缓存（Compilation Cache），可以只在单 host 内生效，也能配置成跨多 host 持久化——跑得越久，重复编译开销越少。

图 2 · Debug → Strict → Fused 是开发流程上逐步拧紧性能的三档，不是互斥的三条路线。

4. 静态编译：Dynamo → XLA → StableHLO

想要峰值性能的用户走 torch.compile。TorchTPU 先用 Torch Dynamo 捕获 FX graph，但接下来不走 Torch Inductor，而是把 XLA 当主编译后端——这是刻意的架构选择：XLA 在 TPU 拓扑上久经考验，天生懂得如何把稠密计算和 ICI 上的集合通信重叠调度。PyTorch 算子被直接映射进 StableHLO（XLA 的核心张量 IR），打通一条从 PyTorch 直达 XLA lowering 路径的通道，同时复用 eager 模式已经建立的执行路径。

图 3 · 全图编译路径跳过 Inductor，直通 XLA/StableHLO，复用 eager 模式已验证的执行路径。

对需要写自定义算子的开发者，TorchTPU 原生支持用 Pallas 和 JAX 写底层 kernel：用 @torch_tpu.pallas.custom_jax_kernel 装饰一个 JAX 函数，就能直接对接 lowering 路径写硬件级指令。对 Helion kernel 的支持仍在推进中。

5. 分布式训练与 MPMD 难题

TorchTPU 原生支持 DDP、FSDPv2、DTensor，并验证了许多基于 PyTorch 分布式 API 构建的第三方库可以不改代码直接用。真正的难点是它点名修复的前代 PyTorch/XLA 的一个限制：只支持纯 SPMD 代码。

现实中的 PyTorch 代码经常在不同 rank 上有轻微分叉——比如 rank 0 多做一点日志或统计工作。XLA 本身在拥有系统全局视图时能把计算和通信重叠得最好，但这种"不纯"的分叉行为和它格格不入；过去的workaround 是让开发者手动把这类分叉代码摘干净，这本身就是额外负担。

TorchTPU 的解法：架构上直接支持分叉执行（MPMD），在必要处隔离通信原语以保证正确性，代价控制到最小。这样开发者体验尽量贴近原生 PyTorch，同时在能做到全局视图的地方，XLA 仍然保留算通重叠能力。

图 4 · 右侧 rank 间允许轻微分叉（如 rank 0 多做日志），TorchTPU 在分叉处局部隔离通信，而非要求全图纯净 SPMD。

6. TPU 硬件感知：形状不是免费的

可移植性不能消除硬件现实。一个具体例子：很多模型把 attention head 维度硬编码为 64，但当前这一代 TPU 在 128 或 256 维度上才能打到矩阵乘法的峰值效率。把维度调到 128/256 能更好利用 TPU 上大而稠密的 tensor core。

TorchTPU 据此提出一个分层工作流：先保证正确执行，再用后续的深度优化指南去定位、重构效率欠佳的结构，或者注入自定义 kernel，以榨出硬件的最优利用率。换句话说，可移植性解决了"能不能跑"，但"跑得多快"仍需要对 TPU 的专门认知。

7. 2026 路线图

当前的编译团队重点在降低因动态序列长度 / batch size触发的重编译——这对 next-token 迭代式生成这类工作负载尤其重要，计划在 XLA 内实现"有界动态性（bounded dynamism）"来吸收形状变化而不产生编译开销。同时在建一套标准算子的预编译 TPU kernel 库，压低首次执行迭代的延迟。

  • 公开 GitHub 仓库，配完整文档和可复现的架构教程。
  • 与 PyTorch 的 Helion DSL 集成，扩展自定义 kernel 能力。
  • 通过 torch.compile 一等支持动态 shape。
  • 原生多队列支持，便于迁移内存流和计算流解耦的重度异步代码。
  • 与 vLLM、TorchTitan 深度集成，并验证到整 Pod 规模的线性扩展。

8. 放在编译栈坐标里怎么看

TorchTPU 解决的不是单点算子优化问题,而是一整条"框架 ↔ 芯片"适配链路：接口层用 PrivateUse1 把 TPU 伪装成一等 PyTorch 设备；执行层用三档 eager 模式在开发体感和性能之间给出连续选择，而不是非此即彼；编译层把 Dynamo 的图捕获能力接到已经为 TPU 打磨多年的 XLA/StableHLO，而不是重新发明一套后端；分布式层正面解决 SPMD 假设在真实代码里站不住脚的问题。

和本仓库里 MPK、Mirage 等 GPU 侵略性编译/融合研究相比，TorchTPU 的取舍更偏"生态兼容优先"：它不追求把整段计算打成一个 kernel，而是确保 NVIDIA CUDA 生态已经驯化的 PyTorch 开发者，换一块芯片后不需要重新学习心智模型。这是 Google 在和 CUDA 护城河的竞争里，选择从"摩擦"而不是"峰值 FLOPs"切入的信号。
