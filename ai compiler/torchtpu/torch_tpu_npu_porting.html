1. 结论先行

TorchTPU 对 TPU 的绑定比表面看起来浅得多。核心接缝只有约 7 处非测试代码，其余 39 处 "tpu" 字面量大部分是测试和注释。 真正的硬件耦合集中在三处，其中一处（PJRT plugin）本来就是官方设计的替换点。

最关键的一句证据

csrc/common/device_type.h:22 的注释：

PyTorch always sees TorchTPU as the PrivateUse1 device, but TorchTPU can be used for any XLA device type with a PjRt plugin. However, some kernel implementations may only work on some specific physical XLA device types.

这个抽象是为多设备准备的，只是还没被填满。

3. 决定性分叉：你的编译器接受什么输入

这是整个接入工作的分水岭。TorchTPU 的 lowering 目标只有一个：

PyTorch 算子 → StableHLO (MLIR) → [你的编译器] → 可执行体

唯一的编译入口是 csrc/common/compilation.cc 里的 CompileAndLoadMlirModule(client, mlir_module, options)， 它把 MLIR 模块交给 PjRtClient。也就是说：

硬事实

你的 PJRT plugin 的 PJRT_Client_Compile 收到的就是 StableHLO MLIR 字节码。没有中间层，没有别的方言。

三条路线

路线前提工作量评价
A. plugin 内转译 你的编译器前端能直接吃 StableHLO / MHLO / 标准 MLIR 最小：TorchTPU 侧零算子改动 推荐
B. 自建前端 你的编译器只接受自家 IR 最大：要写 StableHLO → 你的 IR 的完整前端 取决于 IR 差异
C. 注册成 XLA backend 你的编译器能作为 XLA 的一个 backend 中，但耦合 XLA 内部 API 不推荐

路线 B 的真实难点

TorchTPU 会为 853 个 OpName 生成各种 StableHLO 组合。你的前端需要覆盖的不只是 stablehlo.add / dot_general 这类基础算子，还包括：

  • 复合模式：softmax、layer_norm、RMSNorm 会被拆成 reduce + subtract + exp + divide 的序列，而不是单个算子
  • 动态形状：stablehlo.set_dimension_size、 dynamic_update_slice、bounded tensor types
  • collective：all_reduce / all_gather / reduce_scatter / all_to_all （带 replica_groups）
  • 控制流：while、case （来自 scan / associative_scan HOP）

为什么推荐 A

PJRT C-API 是 XLA 官方为第三方硬件设计的稳定边界，也是 xla_tpu 自己走的路 —— TorchTPU 用的是 xla::GetCApiClient（C-API client），而不是进程内 client。 这意味着你的 plugin 和 TPU 的 plugin 在架构上是平级的。 

// csrc/pjrt/pjrt_client.cc
absl::StatusOr<absl_nonnull std::unique_ptr<xla::PjRtClient>> GetPjRtClient(
    const std::string& device_type, int64_t tpu_premapped_buffer_size) {
  if (device_type == "tpu") {
    return AdaptXlaError(
        xla::GetCApiClient(
            "tpu", {{"premapped_buffer_size", tpu_premapped_buffer_size}}),
        /*context=*/"failed to retrieve the PjRt client");
  }
  return TT_ERROR(error::kInvalidArgument)
         << "unable to get PJRT client for unsupported device type: "
         << device_type;
}

GetCApiClient 走的是 xla::LoadPjrtPlugin 那套动态加载机制 —— 你的 libnpu_pjrt_plugin.so 只要导出 GetPjrtApi()，就能被同样地加载。

4. PJRT plugin 要实现什么

下面是 TorchTPU 实际调用到的 PJRT 能力清单（从代码里 grep 出来的，不是猜的）。

能力用途代码位置必需性
PJRT_Client_Create 创建 client pjrt_state.cc:275 必需
PJRT_Client_Compile 吃 StableHLO compilation.cc 必需
PJRT_LoadedExecutable_Execute 执行 pjrt_execute.cc 必需
PJRT_Buffer_* 缓冲区生命周期 全局 必需
PJRT_Client_BufferFromHostBuffer H2D 传输 pjrt_transfer.cc 必需
PJRT_Buffer_ToHostBuffer / ToLiteral D2H 传输 pjrt_transfer.cc 必需
PJRT_Event_OnReady 异步完成回调 全局 必需
PJRT_Device_*（attributes / memory space） 设备属性 全局 必需
PJRT_LoadedExecutable_Serialize / Deserialize 编译缓存落盘 compilation_cache_utils.cc:203 强烈建议
PJRT_Client_GetTopologyDescription 设备拓扑（分布式） tpu_subslice_utils.cc 分布式时必需
PJRT_RawBuffer_Extension 按字节偏移的零拷贝 DMA pjrt_transfer.cc:305 性能相关
PJRT_Profiler_Extension profiler 接入 pjrt_state.cc 可选

两个必须注意的点

1. Serialize / Deserialize 不是可选的

编译缓存 tier 2 / tier 3 完全依赖它：

// csrc/common/compilation_cache_utils.cc:203
executable->GetExecutable()->SerializeExecutable()

不支持的话，tier 2/3 全部失效，每个新进程都要重编译全部图。 对 torch.compile 的大模型来说，这是分钟级 vs 秒级的差别。

2. RawBuffer 可以退化，但有代价

TpuAsyncDmaCopyDtoH / HtoD 用 PjRt RawBuffer C-API 做 按字节偏移的拷贝。如果你们的 runtime 没有对应的 raw buffer 抽象， 可以退化到 ToLiteral —— 功能正确，但异步 DMA 路径会变慢。

plugin 版本号必须正确

编译缓存的二进制指纹包含 GetPjRtVersion()：

// csrc/common/compilation_cache_utils.cc
FingerprintCat(kTorchTpuBinaryVersion /* = 6 */, GetPjRtVersion())

你的 plugin 必须返回有意义的版本号，否则缓存会跨版本误命中 —— 编译器升级后旧的可执行体被加载，行为不可预测。

另外，缓存目录名 /dev/shm/torch_tpu_cache/<cache_name>/ 应当带上设备类型，避免 TPU 和 NPU 在同一台机器上互相污染。

5.6 参数上限与元组化

这段存在的理由

6. 真正会卡住的地方

6.1 TPU 专有的硬件语义（最麻烦）

统计 TPU 物理概念在 C++ 里的分布：

概念涉及文件数说明
mosaic53TPU 专有的低层 IR
SparseCore32TPU 专有的稀疏计算单元
Mosaic19同上
VMEM15TensorCore 的片上内存
SMEM10SparseCore 的片上内存
TensorCore4矩阵计算单元

这些不是「配置一下就能换」的，它们在语义上依赖 TPU 的物理结构：

  • CorePinningMode { kUnpinned, kTensorCore, kSparseCore } —— 算子可以被钉到特定核心执行
  • MemorySpace { kVmem, kSmem, kHbm } —— Kiln DSL 直接暴露三层内存
  • Pallas / Kiln kernel —— 手写 Mosaic，绑定 tpu_custom_call
这不是「降级」，是「不存在」

如果你的 NPU 没有对应的异构核心概念，这部分能力直接为空。 但这不影响主线功能 —— 它们是可选加速路径，不是必需路径。

6.2 特定算子的 custom call

这些算子不是纯 StableHLO，依赖 runtime 提供对应实现：

Custom call算子能否先跳过
tpu_custom_call Pallas / Kiln kernel、precompiled kernels 能（不用 Pallas 即可）
LuDecomposition torch.linalg.lu 能（回退到分解实现）
Qr / ProductOfElementaryHouseholderReflectors torch.linalg.qr 能
PadRealToStatic 动态形状 pad 不能（bounded dynamism 依赖它）
SparseMapRow / SparseIota / SparseGather TorchRec 类稀疏算子 能
ragged_all_to_all 不等分 all-to-all 能（用普通 all_to_all 替代）
annotate_device_placement ao.offload 能（Pinned host memory）
PadRealToStatic 是硬依赖

只要你想用 bounded dynamism（LLM 解码场景），就必须实现它， 或者在 _can_use_pad_real_to_static 里全返回 False， 走 _set_dimension_logical_size 回退路径。

后者能在处理 64/128 位元素类型时保持正确，但性能会差一些。

6.3 分布式

csrc/distributed/ 6,293 行，其中相当一部分是 TPU 专有的：

  • slicebuilder/discovery.cc —— 从 TORCH_TPU_SLICEBUILDER_ADDRESSES + TORCH_TPU_TOPOLOGY 构建 ICI mesh
  • O(节点数) 而非 O(rank数) 的 store 多路复用 （8K 芯片场景下这个差异是致命的）
  • WindowTpu —— 单边 RMA，走 PjRt raw DMA 分条带
好消息

collective 本身是降低成 stablehlo.all_reduce / all_gather / reduce_scatter / all_to_all， 这些是标准 StableHLO collective。如果你的 runtime 实现了 collective 语义， 主体逻辑是设备无关的。

你需要替换的是初始化路径：GetDistributedWorkerConfiguration() 怎么发现拓扑。如果你有正常的 hostname / rank 机制，这部分可以大幅简化。

6.4 性能语义的隐性假设

几处硬编码了 TPU 的物理参数：

假设出处你的 NPU 需要什么
tile 宽度 = 128 动态形状分桶 bucket_size 改成你的向量宽度
参数上限 ~16K kTupleArgumentsThreshold = 2000 通常更大，可关掉
O1/O2 的 paging 地板 ≈ 2 ms materialization_heuristics.h 完全不同的启发式
卷积的 O1/O2 交叉点 同上（35x-106x 加速区间） 必须重新测

csrc/eager/materialization_heuristics.h 的原文：

// - O1 wins on: small batches (batch <= 1), vector-aligned widths (W % 128 == 0),
//   channels_last (NHWC) layouts, and low compute volume (< 100M MACs). In
//   these cases, compact binaries fit in on-chip IMEM without overlay paging,
//   avoiding O2's fixed ~2.0 ms execution latency floor.
// - O2 wins on: heavy unaligned NCHW convolutions (batch > 1, W % 128 != 0,
//   MACs >= 100M). ... achieving 35x-106x speedups that easily amortize
//   the ~2.0 ms overlay paging cost.
这段数字是 TPU 实测出来的

~2.0 ms 的 overlay paging 地板、35x-106x 的加速区间， 在你的硬件上完全不适用。必须重新做这组实验， 否则会做出错误的编译决策 —— 而且这种错误不会报错，只会变慢。

6.5 一处真的重复实现

view decomposition 在 C++ 和 Python 里各实现一遍：

  • csrc/ops/view_decomposition/（10,824 行）—— 静态路径
  • _internal/compile/dynamic/view_decomposition.py（731 行， 用 SymPy 做符号代数）—— 动态路径

7. 高层算子与 composite 语义

「composite op」在 TorchTPU 里有三个完全不同的含义，处理方式完全不同。 混淆这三层，是移植时最容易走错的地方。

层面含义例子TorchTPU 的策略
ATen CompositeImplicitAutograd，由 PyTorch 用基本算子组合实现 aten::linear
aten::native_layer_norm		 拦截，自己注册，阻止分解
StableHLO 规范里的高层算子 stablehlo.convolution
stablehlo.reduce_window		 保留，原样传给编译器
Mosaic / 自定义 完全自定义的 kernel tpu_custom_call 包成 custom call

7.1 ATen composite op：TorchTPU 反过来阻止分解

这是最反直觉的一点。csrc/common/op_name_stack.cc 里有一个 known_composite_ops 列表（150 项），但它的语义是 「允许被分解的白名单」，而不是「要保持的清单」： 

// csrc/common/op_name_stack.cc:45
// DO NOT ADD NEW ENTRIES TO THIS LIST! Our goal is to shrink the list
// and eventually remove it.

检查逻辑（op_name_stack.cc:219）：

if (!stack_.empty()) {
  // This op is delegated from the op at the top of the stack.
  const OpName composite = stack_.top();
  if (!known_composite_ops->contains(composite)) {
    const std::string msg = absl::StrCat(
        "CompositeOpCheck: Op ", ToString(composite), " is decomposed into ",
        ToString(op_name),
        ". This is unusually not allowed - please implement the ",
        ToString(composite),
        " op by lowering it to SHLO instead. This is a TorchTPU bug.");
    ABSL_LOG(FATAL) << msg;  // CRASH_OK
  }
}
stack_.push(op_name);

机制

TT_KERNEL 会压栈。如果 aten::linear 的 kernel 内部又调了 aten::mm，栈顶是 kLinear → 压入 kMmOut。 如果 kLinear 不在白名单，直接 abort。

而且有硬性断言防止白名单变大：

ABSL_CHECK_EQ(  // CRASH_OK
    known_composite_ops->size(), 150 /* DO NOT increase this! */)
    << "The size of known_composite_ops MUST NOT go up. "
       "If you are removing entries from known_composite_ops, please LOWER "
       "the expected size in the comparison to match the new size and "
       "prevent regression. If you are adding entries, please REVERT the "
       "addition and implement the ops by lowering them to SHLO directly, "
       "without delegating to other ops. DO NOT fix this crash by "
       "increasing the expected size!";
设计意图

每个算子都必须直接生成 StableHLO，不能靠调用其他算子组合。 理由是缓存键的粒度 —— 如果 linear 展开成 mm + add， kLinear 的 param_keys 就失去意义，而且编译图会变碎。

所以对 aten::linear、native_layer_norm、rms_norm 这类「复合算子」，TorchTPU 是主动接管的： 

// csrc/eager/tpu_aten_kernels.cc
ImplStable<OpName::kLinear>(m, AtenLinear);
ImplStable<OpName::kNativeLayerNorm>(m, AtenNativeLayerNorm);
ImplStable<OpName::kRmsNorm>(m, AtenRmsNorm);

它们在 PrivateUse1 上直接注册，CompositeImplicitAutograd 的默认分解 根本不会发生。

7.2 StableHLO 层：高层算子确实被保留

这才是移植时真正关心的部分。TorchTPU 生成的 StableHLO 里，有一批高层算子没有被打散成基础算子：

StableHLO 算子出处保留理由

XLA's TPU ScanEmitter requires:
1. No external non-scanned inputs (total_inputs == num_scan_inputs), because ChloPreserveHighLevelOpsPass outlines chlo.scan into a composite function taking only (inputs, inits).
2. Statically shaped non-complex tensors of identical shape across all scanned inputs (ScanEmitter vectorizes across a uniform tile shape and does not support complex element types).

7.3 stablehlo.composite 完全没被使用

扫全仓结论

全仓零处使用 stablehlo.composite。这是个遗憾， 因为它正是 StableHLO 规范里为「保留复合语义给后端」设计的机制。 

%0 = stablehlo.composite "my.attention"(%q, %k, %v) {
  decomposition = @attention_impl
} : (tensor<...>, tensor<...>, tensor<...>) -> tensor<...>

它带一个 decomposition region，后端不认识时可以展开，认识时可以直接吃掉。

7.4 把语义保留给自研编译器的三条路

路线 1：用已有的高层 StableHLO 算子（零成本）

如果你的编译器已经能识别 stablehlo.convolution、reduce_window、 chlo.scan 等，这些已经在传给你的路上了，不需要任何改动。

先做的验证是把 TpuCompileDebug.stablehlo_forward_text 导出来， 看这些高层算子有没有被 TorchTPU 自己的 pass 打散。

注意 AddShloPasses 里的 createStablehloTargetIndependentOptimizationPass() —— 这是 StableHLO 官方的通用优化 pass，会下沉一部分高层算子。 如果它把你想要的东西打散了，可以在 csrc/mlir/pipeline.cc 里注释掉这一行。

路线 2：引入 stablehlo.composite（中等工作量，推荐）

这是最符合需求的方案。改动点：

  1. 在 csrc/ops/ 里，把关心的算子（比如 scaled_dot_product_attention）改成生成 stablehlo.composite
  2. 加一个 TORCH_TPU_INTERNAL_... 环境变量控制「保留还是展开」，便于 A/B
  3. 在 pipeline.cc 的 AddShloPasses 里加一个 pass： 根据开关决定是否 decompose composite
优点代价
语义边界清晰；stablehlo.composite 有标准定义； 你的编译器可以按名字识别 需要改 TorchTPU 代码；要处理 composite 的 decomposition region 在 split_module / 缓存键上的影响

路线 3：包成 tpu_custom_call（最灵活，但最重）

已有的机制在 csrc/ops/custom_kernels.h：

// Registers a custom kernel. This can be any kernel that has been
// serialized into an MLIR module string. ...
//  - name: The name of the custom kernel (user-provided).
//  - kwargs: a string representation of the keyword arguments ...
//  - mlir_module_string: The serialized representation of the MLIR
//    for an mlir::ModuleOp. This must be a single MLIR module, with a @main
//    function, which may have dynamic shapes (e.g. tensor<?xf32>).
bool RegisterCustomKernel(std::string_view name, std::string_view kwargs,
                          std::string_view mlir_module_string);

以及 Python 侧的 torch.tpu.pallas.jax_op / torch.library.custom_op。

代价

把整个子图变成一个不透明的 custom call，里面的 MLIR 由你完全控制。 但 TorchTPU 会失去对内部的可见性 —— 不能做 fusion、不能跨算子优化、 缓存键只按 (name, kwargs, shapes) 走。 而且 PadRealToStatic 这类动态形状算子不能塞进去。

7.5 建议路径

第一步：先测现状 1 天

debugs = []
torch.compile(model, backend="tpu", options={"debug_callback": debugs.append})
# 跑一步 forward + backward
d = debugs[-1]
print(d.stablehlo_forward_text)

数一数里面有多少高层算子。具体看：

  • stablehlo.convolution 还在吗？还是变成了 dot_general + pad？
  • stablehlo.reduce_window 还在吗？
  • chlo.scan 还在吗？还是退化成 stablehlo.while？
  • stablehlo.batch_norm_training 还在吗？

如果这些都已经在，你就不需要做任何事 —— 直接让编译器吃这些高层算子，比吃打散后的形式效率高得多。

第二步：按需加 composite 2–4 周

只有在你确实需要「某个复合语义完整传下去」时，才用路线 2 加 stablehlo.composite。典型场景：

  • attention（SDPA / flash）
  • MoE grouped matmul
  • 归一化 + 缩放融合

倾向路线 2 而不是路线 3，原因：

  • stablehlo.composite 有标准 semantics，你的编译器可以按名字匹配， 不匹配时还能 fallback 到 decomposition
  • tpu_custom_call 是不透明黑盒，失去所有跨算子优化机会
  • 路线 2 的改动更小，更容易提 PR 回上游

7.6 一个陷阱：precision_config

如果打算让编译器吃 stablehlo.convolution，注意 Attribute 里的精度配置：

// csrc/ops/op_builder_utils.cc
stablehlo::PrecisionConfigAttr::get(&ctx, {precision, precision})

TorchTPU 的三档精度（DEFAULT / HIGH / HIGHEST） 是映射到 bfloat16 的 1 / 3 / 6 次 pass。

静默偏离

这个语义在你的硬件上未必对应得上。如果你的编译器忽略 precision_config，数值行为会静默偏离 —— 不会报错， 只是结果和 TPU 上不一样。

阶段 1：跑通单算子 1–2 个月

目标：torch.ones(4,4,device="npu") + torch.ones(4,4,device="npu") 能出结果。

阶段 2：算子覆盖 3–6 个月

这是工作量最大的阶段，且高度取决于你的编译器前端成熟度。

  1. 逐个跑 tests/ops_test.py，统计哪些 StableHLO 组合你的编译器不支持 （这个测试有 50 个 shard，覆盖面很广）
  2. 补编译器的 StableHLO 覆盖 —— 这是最耗时的部分

  4. 实现 Serialize / Deserialize，打开 tier 2/3 编译缓存

  2. 重新做 materialization_heuristics 的实验 （O1/O2 交叉点、paging 成本）

9. 三个务实建议

建议一：先做「StableHLO 兼容性审计」

在写任何 TorchTPU 代码之前

这是唯一的 go / no-go 判据，应该在投入人力之前花一周验证。

具体做法：

# 从 TorchTPU 里导出几个真实模型的 StableHLO
torch.compile(
    model,
    backend="tpu",
    options={"debug_callback": collect},   # TpuCompileDebug
)

# 取 collect[-1].stablehlo_forward_text / stablehlo_backward_text
# 直接喂给你的编译器

TpuCompileDebug（_internal/compile/debug.py）会给你完整的 pre_autograd_fx_code、post_autograd_fx_forward_code、 stablehlo_forward_text、stablehlo_backward_text。

建议至少导出三个模型的 MLIR：

  1. 一个 transformer 层（Llama / Qwen 的单层）—— 覆盖 SDPA、RMSNorm、RoPE、GEMM
  2. 一个 CNN（ResNet-50）—— 覆盖 conv、batch_norm、pooling
  3. 一个 MoE 或稀疏模型 —— 覆盖 gather/scatter/ragged

如果这些 MLIR 你的编译器吃不下，整个项目就不成立。

建议二：不要长期维护 fork

device_type.h 的注释和 GetPrivateUse1DeviceDebugName() 的存在说明上游本来就想支持多设备。这些改动（加 kNpu 枚举、 把 "tpu" 参数化）几乎都是无侵入的，适合提 PR 回上游。

长期维护 fork 的代价在这个项目上特别高：

  • 上游提交量在加速（2026 年 2 月 219 次/月 → 10 月 896 次/月）
  • 大规模重构频繁 —— _backend.py 里那些 "slated for deprecation" 的注释说明接口还在快速演进
  • csrc/ops 63% 的代码是设备无关的，你会持续收到上游的算子改进

建议三（额外）：注意 CPU fallback 的隐性成本

// csrc/eager/tpu_aten_kernels.cc
ABSL_LOG(WARNING) << "operator '" << op_name
                  << "' is not implemented for TPU. Falling back to CPU";
at::native::cpu_fallback(op, stack);

这个 fallback 是静默的，只打 WARNING。在你的 NPU 上， 如果大量算子走 CPU fallback，性能会灾难性下降但程序正常结束。

建议：在移植初期把这条日志升级成可配置的 error， 或者加一个统计计数器，每次训练结束打印「有多少 op 走了 fallback」。

10. 架构判断

TorchTPU 之所以叫 TorchTPU，主要是因为它选择以 XLA/StableHLO 为目标、 以 PJRT 为运行时边界。这两条都是通用标准，不是 TPU 私有的。

真正的硬件耦合只有三处

耦合点性质你的处境
PJRT plugin 官方设计的替换点 你本来就要写
Pallas / Kiln + Mosaic TPU 专有 可以整体不用
分布式拓扑发现 TPU slicebuilder 专有 需要替换

这个项目对你的价值

如果你的 NPU 编译器接受 StableHLO、runtime 能包一层 PJRT， 那这个项目对你的价值就是 「一个已经写好的、覆盖 450 个 ATen 算子的 StableHLO 生成器 + PyTorch 集成层」 —— 这大概是 20 万行你不需要重写的东西。

但要清醒地看到不匹配的地方

  • 性能语义不是免费的：materialization_heuristics 里的所有数字都是 TPU 实测的，迁移后必须重做
  • Pallas 生态用不了：torch.tpu.pallas.jax_op 生成的 是 Mosaic custom call，你的硬件没有对应物
  • 动态形状可能成为瓶颈：如果 PadRealToStatic 实现不了， LLM 解码场景会退化到静态形状 + 每步重编译，正好是 bounded dynamism 想解决的那个问题

一句话总结

这是一个可以做，但比想象中轻的移植工程。核心工作量不在 TorchTPU 侧 （7 处硬编码 + 几个分支），而在于你的编译器对 StableHLO 的覆盖度 和你的 runtime 对 PJRT 语义的完整性。

最明智的第一步不是写代码，而是拿 TorchTPU 导出的 StableHLO 去喂你的编译器， 用一周时间确认这条路通不通。
