1. 概览

这个项目的本质是一个语义翻译层，不是一个 kernel 库。它的核心工作是把 PyTorch 的「命令式 + 可变 + 指针」语义，忠实地映射到 XLA 的「声明式 + 不可变 + SSA」 世界，同时不修改 PyTorch 源码。

2. 它解决什么问题

TPU 的编程模型和 CUDA 从根本上不同：

CUDATPU + XLA
执行单元数千线程单线程 TensorCore（脉动阵列 MXU）+ VPU + SparseCore
内存模型一维字节数组，任意偏移读写二维 tile 对齐，寄存器对齐
编程范式命令式，void 内核声明式，函数式，SSA
可变性原地写入天然支持值不可变，只能产生新值
形状运行时任意编译期已知（或 bounded）

而 PyTorch 的语义深度绑定 CUDA 模型：

  • as_strided 手动 stride，视图共享同一块 storage
  • x[i] += 1 原地修改，对其他共享 storage 的视图可见
  • torch.UntypedStorage.data_ptr() 就是一个裸地址

TorchTPU 要做的是在这两套模型之间做双向翻译，且不修改 PyTorch 源码。 官方定位很明确：PyTorch/XLA 已废弃，这是继任者，且零 JAX 运行时依赖 （Pallas 只在 trace 时用一次）。

4. 存储层间接（地基）

这是整个项目最重要的一个决策，在 docs/torchtpu_memory_model.md 和 csrc/eager/device_buffer.h 里讲得最清楚。

问题

PyTorch 的指针链是：

at::Tensor → c10::TensorImpl → c10::Storage → c10::StorageImpl
  → c10::DataPtr → c10::UniqueVoidPtr { data_, ctx_ }

data_ptr() 返回一个地址。在 CUDA 上这就是显存地址。但在 TPU 上， XLA 的缓冲区是有类型的、有确定多维形状的 —— 一个裸地址加字节数 根本不够描述。

解法

在 TPU 上，data_ptr() 不指向 HBM，而是指向一块 CPU 内存， 里面装着 DeviceBufferRef。 

// csrc/eager/device_buffer.h:144
// The c10::DataPtr at the root of the torch/aten/c10 data hierarchy holds a
// unique pointer (as a c10::UniqueVoidPointer) to a DeviceBufferRef.

DeviceBufferRef 只是 (shared_ptr<DeviceBufferList>, index) 两个字段 —— 16 字节。DeviceBufferList 才持有真正的数据形态：

  • 若已物化：一个或多个 PjRtBuffer
  • 若延迟：DeferredOp，里面有 MlirOpBuilder（惰性构造 StableHLO 的闭包）、输入 DeviceBufferRef 列表、输出 Shape 列表、缓存键

为什么必须是三层递归结构

关键约束

device_buffer.h:56 的注释：

one aten operation can produce multiple outputs; this is common for normalization functions (e.g. layer norm, batch norm, group norm). This means that deferred operations are not one-to-one with individual tensors.

native_layer_norm 返回 (out, mean, rstd) 三个张量， 但只对应一次编译。所以必须拆成三层：

DeviceBufferRef ← 单个张量的"句柄"（索引） ↓ DeviceBufferList ← 一次 aten 调用的全部产出 ↓ DeferredOp ← 一次 aten 调用本身

如果按张量一对一建模，layer_norm 会被编译三次，或者要额外写去重逻辑。

原地写怎么实现

XLA 是 SSA，值不可变。但 PyTorch 要求 x[i] += 1 对其他共享同一 storage 的视图可见。

device_buffer.h:168：

the aten/c10 hierarchy may overwrite the void* data_ in a c10::DataPtr … changing which DeviceBufferRef backs the at::Tensor … while respecting immutability at the XLA level, and preserving the void* data_ pointer's heap address.

data_ 的堆地址不变，但里面的 DeviceBufferRef 换了。 从 aten 的角度看，指向同一 storage 的所有 Tensor 都「看到」了新值； 从 XLA 的角度看，只是产生了一个新 buffer。

这同时满足了 PyTorch 的指针语义和 XLA 的不可变性，而且不需要修改 PyTorch。

由此衍生的四个能力

能力实现
视图 view decomposition（下一节）
原地写 / out= view inversion + stablehlo.dynamic_update_slice
buffer donation 最后一个引用消失时标注 donate，让 XLA 消费输入

官方文档的原话：

这和 CUDA 上的最佳实践（合并分配）正好相反。

5. View decomposition —— 项目里最硬核的算法

csrc/ops/view_decomposition/ 10,824 行，是整个仓库最大的单一模块， 比 LSTM 和 GRU 加起来还多。

为什么需要它

CUDA 用 (sizes, strides, storage_offset, dtype) 描述索引到字节的映射。 StableHLO 没有手写 stride 的能力。所以任意 stride 模式必须分解成 一串 StableHLO 原语。

原语集

观察

每个热路径结构体都有尺寸断言。这不是洁癖，是防止某次字段调整悄悄破坏 cache line 行为。

算法：头尾夹逼

DecomposeIntoViewSequence()（decomposition.cc:1250 附近） 不是正向贪心，而是：

  1. 尾：BuildTail() 求出末端的 1–2 个算子。有 broadcast 走 broadcast_in_dim；维度乱序走 reshape+transpose
  2. 头：把连续 base 摊成 1D，pad 到需要容量， 再 slice 出窗口
  3. 身：BuildBodyStep() 循环，每次补一维，直到头尾秩相等
  4. 收尾：BuildFinalDimension()、RemoveExtraDim()

两个 fast path 直接短路：纯 unsqueeze/transpose/expand， 以及「至多一个非平凡维度」。LLM 里这两个情况都很常见。

view inversion：反向跑 + mask 合成

inversion.h:37 把动机写得很直白：

x = torch.zeros(3)
y = x[1]
y += 1

求解需要把分解逐条求逆：

Reshape   的逆 → Reshape
Transpose 的逆 → Transpose
Slice     的逆 → Pad
Pad       的逆 → Slice

然后生成两个张量：一是把更新值散回 base 坐标的数据张量（空位补零）； 二是 mask 张量，标出哪些位置被更新。最后用 stablehlo.select （等价 torch.where）合并。

关键优化

如果没有 slice，就没有 pad，mask 全 true，select 可以整个省掉。 这覆盖了 x[i] = v 这类全切片更新。

两个踩过坑才写得出的细节

inversion.h:60 的注释：

If the dtypes are different sizes, we need to cast both tensors to the smaller bitwidth … to avoid truncation, and ensure that partial updates to larger base elements preserve unmodified bits.

If the contiguous base tensor is boolean type, then it needs to be converted to a uint8 tensor to preserve all assigned bytes (and not collapse them to only 0x00 or 0x01 values).

torch.bool 在存储里占 1 字节但只允许 0/1。如果直接 bitcast 到 bool 再写回， 未修改的字节会被「规范化」成 0/1，破坏其他视图的数据。这是典型的「只有正确性测试覆盖到 才会发现」的 bug。

contiguous_to_view：反函数

contiguous_to_view.h:30 是 torch.Tensor.contiguous() 的逆。 注释诚实地列了两个副作用：

  • contiguous() 对 broadcast/重叠视图会复制数据， 逆操作于是会去重，若数据不一致则 "last write wins"
  • contiguous() 会丢弃视图外的数据，所以逆操作必须填垃圾数据， 遵循 torch.utils.deterministic.fill_uninitialized_memory 的策略。 用户之后 as_strided 越界能把「僵尸数据」读出来

还有一个递归优化 GetContiguousBaseShape()：对 torch.ones(30).view(2,15)[:, :14].view(2,2,7) 这种链式视图， 它先按最小元素数做一次分解，再看首算子是不是 reshape —— 如果是，就用那个更优的 base shape 重来。用分解算法反推该不该换 base 形状。

测试覆盖

inversion_test.cc 1,619 行 + decomposition_test.cc 753 行， 合计 96 个 TEST。这符合判断：view inversion 一旦错了，所有原地写都会静默出错。

Traversal：从输出倒推输入

csrc/eager/traversal.h:70：

In eager mode, the outputs are known at traversal time, but the arguments need to be identified. In this case, we traverse the graph from the outputs to the arguments.

Eager 模式下，物化触发时你知道要哪些输出，但不知道谁是最上游的输入。 所以从输出反向 DFS，遇到非 kDeferred 状态的节点就当作 argument。

编译模式下反过来：参数和输出都已知，但图关系未知。这时需要 ValidateAndReorderArguments 显式重排，保证 Python 层的参数顺序和 PjRt 可执行体的参数顺序对齐 —— DAG 拓扑序不唯一，这是个隐蔽的正确性陷阱。

物化：两个后台线程，职责严格分离

class MaterializationWorker {
  std::thread materialize_thread_;  // 图分析 + 准备执行任务
  std::thread execute_thread_;      // 真正调 PjRt，阻塞等待
};

using ReadyWork = std::variant<EagerExecution, CompiledExecution, SnapshotRequest>;

两个线程都做同样两件事：

DisallowThisThreadToAccessContextState();
RouteWarningsOnThisThreadToDispatchThread();

后台线程不能读线程局部的编译上下文状态，但警告要能传回 Python 的发起线程。

这个分层很重要

StableHLO 构造是纯函数，可以单测；aten 校验要复刻 CUDA 的精确报错顺序 —— 注释明确写了「CUDA 先校验 dtype 和 shape，才报 unimplemented」。 目的是让用户从 CUDA 迁移过来时，报错行为一致。

没有 "mm" 绑定

ImplStable<OpName::kMmDtypeOut>  → "mm.dtype_out"

它一次性处理：

  1. 日志 —— ScopedOpName
  2. Python 上下文捕获 —— ScopedPythonContextCapturer
  3. 参数缓存键计算 —— 遍历所有非 Tensor 参数
  4. 错误归属 —— 把错误归到正确的根 op

其中有个细节很聪明：

PromotedScalar 是惰性的 —— aten::add 的标量参数在需要时才 提升为张量（因为 XLA 需要同构输入）。如果 kernel 忘了调 GetTensor()， 就会静默用原始 Scalar 算。debug 模式下用 absl::Cleanup 检查这个。

注册机制：阶段化 API + 编译期零开销警告

ImplExperimental 的实现有个精妙之处（tpu_aten_kernels.cc:322）：

It is critical that op_name is a compile-time template parameter rather than a runtime parameter. TT_WARN_ONCE dedupes warnings by its macro expansion site using a local static flag.

If op_name were a runtime parameter, the macro would be expanded in a single shared helper function. This would result in "once-per-program" behavior …

By making op_name a template parameter, ImplExperimental<OpName::kFoo> and ImplExperimental<OpName::kBar> become distinct function template instantiations. This forces the compiler to instantiate a unique lambda and a unique TT_WARN_ONCE static flag for each operator, achieving the desired "once-per-operator" warning semantics with zero runtime overhead (no mutexes or registries required).

8. 两级编译缓存

常见误解

文档说的「三级缓存」是指 TorchTPU 自己的 executable 缓存有 3 个 tier。 但在这之上还有一层 PyTorch 的 AOTAutogradCache。两层不能混为一谈。

(a) TorchTPU 的 executable 缓存

Tier范围位置 / 开关
1 进程内内存 CompilationCache 单例，flat_hash_map，总是开启
2 同机跨进程 /dev/shm/torch_tpu_cache/<cache_name>/<hex16>/<key>.bin
3 远程 / 持久 <root>/<hex16>/<key>.bin，TORCH_TPU_TIER3_COMPILATION_CACHE_ROOT

Tier 2 的并发控制

mmap 用 MAP_SHARED | MAP_POPULATE（文件在 tmpfs 上）， 访问由 <key>.lock 上的 flock 串行化 —— 并发进程只编译一次。

默认策略：world_size == 1 时关闭，> 1 或启用 tier 3 时开启。Tier 3 需要 tier 2 开启。

本地备份任务

UsesLocalBackupTaskForTier3Read()  // 默认 true
// TORCH_TPU_INTERNAL_TIER3_COMPILATION_CACHE_LOCAL_BACKUP_TASK

读 tier 3 的同时并行发起一次正常编译，谁先完成用谁。 这是个务实的赌注：远程读可能比本地编译还慢。

(b) 缓存键的构成

CompilationCacheKey = GraphKey + CompileOptionsKey + id_key

GraphKey       = ShapelessKey(FingerprintType) + DimensionsKey(FingerprintType)
CompilationKey = "<shapeless:016x>_<dims:016x>_<compileopts:016x>" (+ "_<id_key>")

  • DimensionsKey —— FingerprintCat(input_dimensions)
  • CompileOptionsKey —— FingerprintCat(Fingerprint(XLA_FLAGS), Fingerprint(LIBTPU_INIT_ARGS), Fingerprint(options))。 只有非默认字段参与指纹（「to keep existing keys stable」）

缓存键的计算是分散的：每个 op kernel 通过 param_keys 贡献自己的键。比如 div 的 floor vs trunc 必须区分； 精度也是键的一部分。

(c) Python 侧的 AOTAutogradCache 补丁

这一层有四个 TorchTPU 特有的补丁：

1. 保留 storage_offset

补丁打在 extract_tensor_metadata_for_cache_key（ _aot_autograd 和 torch._inductor.codecache 两处）。 上游会把 storage_offset 归零 —— 对其他后端无所谓， 但对 TPU 静态编译是错的，因为 slice 的偏移被编译进去了。

2. 把 inputs_meta 纳入 key

hash = sha256(f"torch={ver}_torchtpu={ver}:{cache_key_tag}:{graph_str}:{inputs_meta}")

注释明说：少了 inputs_meta，只在 storage_offset 上不同的图会撞 key。

3. process group 的 key tag

_process_group_cache_key_tag(gm) = "name:devices;..."

原因：图里引用的 process group 是按创建顺序编号的，不是按成员。 两个不同的 group 可能拿到同一个序号。

4. stub 掉 generate_guards_expression

它需要 ShapeEnv/TracingContext，这里无法安全提供。

9. torch.compile 管线与动态形状

它是一个 AOTAutograd 后端，不是 Inductor 后端

result = aot_autograd(
    fw_compiler=fw_compiler, bw_compiler=bw_compiler,
    partition_fn=min_cut_rematerialization_partition,
    decompositions=_TPU_DECOMPOSITIONS,
    keep_inference_input_mutations=False,
)(graph_module, example_inputs)

走的是和 Inductor 完全相同的 AOTAutograd 路径（包括 min_cut_rematerialization_partition 这个 activation checkpoint 分区算法）， 只是把 fw/bw compiler 换成 TorchTPU 自己的。

Inductor 只用了四处：

  • torch._inductor.utils.InputType
  • torch._inductor.output_code.OutputCode（继承它，让 AOTAutogradCache 认）
  • torch._inductor.codecache.extract_tensor_metadata_for_cache_key
  • torch._inductor.fx_passes.post_grad.decompose_auto_functionalized

_TPU_DECOMPOSITIONS 只有两个：

get_decompositions([aten.masked_fill.Tensor, aten.masked_fill_.Tensor])

为了让 masked_fill 的语义和 GPU 的 modular-truncation 行为一致。

这才是关键

TorchTPU 复用了 PyTorch 编译栈的前半段（Dynamo → AOTAutograd → 分区 → 反式分解），只在「生成设备代码」这一步换成 XLA。这才是它能做到 torch.compile(backend="tpu") 一行切换的真正原因。

FakeTensorMode 的架构性不兼容

# AOT autograd will trace the model with FakeTensorMode enabled. This
# converts all tensors to FakeTensors which do not have valid storage to
# avoid computation.
#
# TorchTPU tracing requires all tensors to have valid storage, so is not
# compatible with FakeTensorMode.
with unset_fake_temporarily():

TorchTPU 的 trace 需要真实 storage（因为它要调 aten kernel 生成 StableHLO）， 而 FakeTensor 故意没有 storage。所以必须临时退出 FakeTensorMode， 用自己造的 "storage-aware placeholder" 代替。

动态形状：bounded dynamism

XLA 传统上要求编译期形状完全已知。LLM 自回归解码时 KV cache 每步 +1， 如果按静态形状编译，每一步都触发完整重编译 —— 毫秒级的步骤变成秒级。

解法不是动态形状（不支持），而是分桶：

start_val          = max(L, hint)
first_bucket_upper = ceil((start_val + c) / step) * step - c      # _align_up
B_i                = first_bucket_upper + i * step                 # 受 aligned_upper 封顶
为什么是 128k - c 而不是简单的 128k

不是美观选择：XLA:TPU derives a bounded output's layout from its bound， 所以桶的边界落在不同的对齐类上，输出 layout 会变，触发重编译。 -c（输出形状的常量偏移，如 S+1 里的 1）就是为了让输出形状 在所有桶里保持在同一对齐类。

分桶的完整规则

  1. 128 对齐 —— TPU 的 tile 是 128 lane，bucket_size 默认 128
  2. 单次 guard 覆盖全部桶 —— 注册整个桶跨度的 range guard 给 Dynamo， 只有超出总上界才重编译
  3. 最多 8 个桶（num_dynamic_buckets <= 8）
  4. 每个候选桶都用 find_violated_guard(shape_env, upper_bounds) 验证； 任一桶违反活跃 guard → 回退到 2 × lower_bound 单桶

Padding 的语义要求

XLA pads the dynamic input tensor up to the bucket's static upper bound U and resets values in the padded region beyond the active runtime size to algebraic identity values, ensuring that padded elements do not affect the output result.

For dynamic output tensors, padding remains at the end of the buffer, allowing TorchTPU to return the buffer to PyTorch with a lightweight shape metadata update rather than physically slicing the tensor.

pad 成 0 对 sum 是单位元，对 prod 就不是；对 max 也不对。所以 pad 值必须按算子语义选择代数单位元。

10. 分布式：SPMD 与 MPMD 的矛盾

核心矛盾：

replica_groups 的坐标系转换

device_assignment_.local  = 本组设备,按 PG rank 排

replica_groups_ = positions into device_assignment_

注释强调：replica_groups_ 是 "positions into device_assignment_"，不是 world ranks。 StableHLO 的 replica_groups 期望的是 device assignment 里的下标， 不是全局 rank。搞混了就是死锁。 

%0 = "stablehlo.all_reduce"(%arg0) <{
  replica_groups = dense<[[4, 0, 1, 3], [5, 2, 6, 7]]> : tensor<2x4xi64>

PyTorch 的 dist.all_reduce 只拿到调用者所在的 subgroup。 但 stablehlo.all_reduce 需要全班的 replica_groups —— 即使当前 rank 只在 [5,2,6,7] 里， 也必须知道 [4,0,1,3] 的存在。

子组发现的三种路径

  1. world PG → 直接全收集
  2. size-1 → 无需通信
  3. GatherSubgroupsViaNodeLocalStore → 节点本地 store 多路复用

第 3 条的设计目的：让 world-store 的流量是 O(节点数) 而不是 O(rank 数)。 8K 芯片的场景下这个差异是致命的。

通信实现：没有独立通信库

allreduce.cc / allgather.cc / alltoall.cc / reduce_scatter.cc 不实现通信本身，而是把 collective 降低成 stablehlo.all_reduce / all_gather / all_to_all， 让 XLA 编进 TPU 可执行体。

取舍

好处是 XLA 能做计算-通信 overlap；代价是 collective 必须参与图的编译决策 （所以才有 OpSplitMode::kSplitBoth）。

12. 构建系统：多 ABI wheel

这是本项目工程复杂度里最容易被低估的部分。

问题

PyTorch 的 C++ ABI 不稳定。一个 wheel 要同时服务 2.11 / 2.12 / 2.13 / 2.14 / nightly，怎么办？

解法：薄 glue + 运行时选择

DEFAULT_TORCH_VERSION       = "2.11.0"
EXTRA_PYTORCH_VERSIONS      = ["2.12.0", "2.13.0", "2.14.0"]
WHEEL_TORCH_VERSIONS        = [DEFAULT] + EXTRA
NIGHTLY_TORCH_VERSION       = "2.16.0"
GLUE_TORCH_VERSIONS         = WHEEL + [NIGHTLY]
INTERMEDIATE_PATCH_VERSIONS = ["2.12.1"]
A version is added here only when that PyTorch release breaks ABI compatibility with the previous glue; the runtime dispatch then serves each install from the newest glue at or below its version, so every release between two entries — and everything after the last one — loads the preceding glue.

所以 glue 的粒度是 ABI 断点，不是 PyTorch 版本号。 2.11.0 的 glue 服务 2.11.0 到 2.11.x 所有补丁版。 INTERMEDIATE_PATCH_VERSIONS 存在是为了证明这个声明是真的 —— 有一个 nox session 专门验证 2.12.1 真的能在 2.12.0 glue 上跑。

A PathEntryFinder installed on sys.path_hooks at import time rewrites imports and pkgutil module discovery inside torch_tpu to the glue that matches the installed PyTorch, and an ExtensionProxyLoader bridges the artifact's version-suffixed filename to the unversioned PyInit_<module> symbol the C++ code actually exports.

错误处理：统一前缀 + 根 op 归属

TT_RET_CHECK(cond, error_code)      // 返回 Status
TT_CHECK_THROW(cond, error_code)    // 抛异常
TT_ASSIGN_OR_RETURN(lhs, rexpr)     // 解包 StatusOr
TT_RETURN_IF_ERROR(status)

TT_ASSIGN_OR_RETURN 会注入 TT_NORMALIZED_FILE、 __LINE__、__func__ —— 保留源头位置。 TT_CHECK_THROW 还会调 SetRootOpNamePayload， 把错误归属到正确的根 op。

这个「根 op 归属」机制在多层 op 组合时很关键：用户写 torch.nn.functional.layer_norm，内部可能调十几个 aten op， 报错要指向 layer_norm 不是某个内部 _native_layer_norm。

粘性错误闩锁

HasStickyError()  // 每次 dispatch 都读，std::memory_order_relaxed，单调 false→true

注释详细论证了内存序：只需要单调性，不需要同步。异步断言失败后置位， 后续所有 dispatch 立即短路。这是处理「设备侧错误不能在出错的 op 处抛出」的标准手法。

_tcmalloc_check.py 的注释解释了为什么这个模块不能 import torch：

It is part of the torch-free preamble of torch_tpu/__init__.py … importing torch makes PyTorch load the torch_tpu._loader backend entry point, which loads TorchTPU's C++ extensions. Doing that from here would run that setup in the middle of torch_tpu/__init__.py, and from module scope even before the version-dispatch import hook of _versioned_so_loader that selects those extensions is installed.

这是个循环依赖的精确拆解：import torch → autoload → torch_tpu._loader → C++ 扩展 → 但版本 dispatch hook 还没装。

15. 设计取向与风险

值得学的七个设计

  1. 在存储层做适配，而不是在 API 层 —— data_ptr() 指向元数据而不是设备内存，一个决策解决了 stride、视图、 原地写、copy-on-write 四个问题
  2. 不自己写图优化器 —— 4 个 MLIR pass 不到 3 千行，其余全交给 XLA
  3. 把性能实验结论编码进编译器 —— IsFastRuntimeConvolutionCandidate 里的数字是决策而不是文档
  4. 缓存键分散计算 —— 每个 op 自己贡献 param_keys， 新增 op 不会忘记更新缓存键
  5. API 阶段化 + 编译期零开销的警告 —— 模板实例化生成独立 static 标志，没有运行时哈希表
  6. 错误覆盖测试 —— ERROR_COV_INFEASIBLE 标注 + 自动化工具
  7. 诚实文档 —— 动态形状 8 条限制、contiguous_to_view 的僵尸数据、FakeTensorMode 不兼容

主要风险

风险具体表现
语义等价但性能不等价 视图在 CUDA 上是免费的，在 TPU 上可能触发完整 relayout；部分写可能复制整个 storage。代码不改就能跑，但性能特征完全不同，而且不报错
CPU fallback 是静默的 不支持的 op 只 ABSL_LOG(WARNING)。大量 op 悄悄在 CPU 上跑时， 性能灾难性下降但程序正常结束
动态形状边界很硬 最多 8 桶、不支持无界、和 Pallas kernel 不兼容、和 dynamic=True 不兼容、不进 AOTAutogradCache（每进程重编译）、计算量按桶上界算

两处手工同步无守卫 bazel/pytorch_versions.bzl → MODULE.bazel 的复制只有注释， 没有像 Python 版本那样的 sync_module_bazel_versions.py

16. 专题：与 PyTorch/XLA 的区别

先说结论

TorchTPU 没有复用任何一行 PyTorch/XLA（torch_xla）的代码。 全仓库对 torch_xla 的引用只有 8 个文件、共 6 处，其中 3 处是注释里的 bug 溯源链接，3 处是独立的基准对比代码，没有一处是 import、链接或代码拷贝。

两者共享的只是下层的 OpenXLA 组件（XLA 编译器、StableHLO、PjRt、libtpu）， 这些是 Google 的公共基础设施，不是 torch_xla 的代码。

16.3 架构上的根本差异

维度PyTorch/XLA 的做法TorchTPU 的做法
设备接入 自定义 XLATensor 类型 + 私有 dispatch key 标准 PrivateUse1 dispatch key，导入时 rename_privateuse1_backend("tpu") 改名
存储抽象 XLATensor 自己持有惰性 IR 复用 at::Tensor，data_ptr() 指向 CPU 元数据（DeviceBufferRef）
视图 / 原地写 受限，很多情况需要 contiguous() 或改写模型 完整支持 as_strided、原地写、buffer donation， 靠 view decomposition + inversion（10,824 行）
torch.compile 后期才接入，路径不统一 原生注册为 Dynamo backend "tpu"，走 AOTAutograd
执行模式 惰性图 + mark_step 显式边界 5 种模式（DeferNever / DeferAndFuse / LaunchBlocking / …）， 物化点自动决定
动态形状 重编译或改写模型 bounded dynamism，128k - c 分桶
算子覆盖 XLATensor 上的方法 853 个 OpName 直接注册进 TORCH_LIBRARY_IMPL(aten, PrivateUse1)
最关键的一条

TorchTPU 是真正的树外后端（out-of-tree backend）。 它不需要自定义张量类型，不需要 mark_step，不需要 PyTorch 的 fork。 用户代码里 .to("cuda") → .to("tpu") 就完事了， 其余 API 全部是标准 PyTorch。这正是它必须重新实现而不是继承 torch_xla 的原因 —— torch_xla 的架构（自定义张量类型）无法满足这个目标。

16.5 JAX 依赖的真相

「零 JAX 运行时依赖」这个说法需要精确理解：

是否依赖 JAX细节
纯 PyTorch 程序 否 eager 和 torch.compile 路径完全不碰 JAX
Pallas 自定义 kernel 仅 trace 时一次 jax_op 用抽象 shape/dtype 占位符把 kernel 导出成 MLIR 模块，之后运行时只跑 torch.Tensor + TPU buffer
Tokamax 预制 kernel 构建期 kernel 已编译成 Mosaic 字节数组嵌入 C++
pyproject.toml 声明了 jax >= 0.9.2 作为依赖存在，但不是运行时路径的必需品
Pallas 的那个 TODO 值得注意

pallas.py:47：

TODO: TorchXLA hit issues when working with both JAX and PT in the same process, hitting deadlocks when each framework tried to access the PJRT plugin. Unclear if this applies for trace-only, but we may need to better protect against this, see @requires_jax in PT/XLA repo.

这说明团队读了 torch_xla 的踩坑记录并借鉴了教训， 但这是「读文档」而非「用代码」。而且他们自己也不确定 trace-only 场景是否会中招 —— 这是一个已知的开放风险。

16.6 TorchAX 在仓库里的角色

perflab/torchax/ 是性能实验室里的对照组， 不是产品代码：

import torch_xla2 as torchax  # pylint: disable=unused-import
# perflab/torchax/BUILD

autoload = False,
这个 TODO 很有意思

TorchAX 和 TorchTPU 都会调用 torch.register_privateuse1_backend()，两者不能在同一进程共存 —— 所以跑 TorchAX 基准时必须关掉 TorchTPU 的 autoload。 这从侧面证明：TorchTPU 走的是 PrivateUse1 路线，TorchAX 走的是另一条路， 二者互斥。

perflab 的设计目标就是「同一套 benchmark 注册表，跑 TPU、GPU、CPU 和 TorchAX 四个后端」，用于横向对比。所以这里出现 torch_xla2 是测量需要，不是依赖。

16.7 迁移影响

如果用户从 PyTorch/XLA 迁到 TorchTPU，需要删掉的是：

torch_xla 里的东西TorchTPU 里怎么办
import torch_xla.core.xla_model as xm 删掉，用 torch.accelerator.*
xm.mark_step() 删掉，没有对应物。物化点由 .cpu()/.item()/synchronize() 自动触发
xm.xla_device() torch.device("tpu") 或 torch.accelerator.current_accelerator()
xm.optimizer_step(opt) opt.step()（标准 PyTorch）
xm.mesh_reduce / rendezvous 标准 torch.distributed + tpu_dist
PJRT_DEVICE=TPU 环境变量 不需要；用 TPU_VISIBLE_DEVICES、TORCH_TPU_TOPOLOGY
xm.save / xm.load 标准 torch.save / torch.load

反面，TorchTPU 提供而 torch_xla 没有的：

  • torch.compile(backend="tpu") 原生支持
  • bounded dynamism（避免 KV cache 增长导致的重编译）
  • 完整的 as_strided / 原地写 / buffer donation 语义
  • 三级编译缓存（进程内 / 同机跨进程 / 远程 GCS）
  • 多 PyTorch ABI 的单 wheel

16.8 继承的「基因」：不是代码，是设计

虽然没有任何代码复用，但 TorchTPU 明显继承了一系列工程经验：

痕迹证据
知道 CPU fallback 的历史坑 AtenCopyFromAndResize 的注释直接引用 pytorch/xla#2881
知道 JAX + PyTorch 共进程的 PJRT 死锁风险 pallas.py:47 的 TODO
知道 Pallas 是 TPU kernel 的正解 直接采用 JAX 的 Pallas 作为自定义 kernel 入口
知道 TPU 的 tile 对齐是 128 动态形状分桶 bucket_size = 128
知道 SparseCore 的存在 CorePinningMode { kUnpinned, kTensorCore, kSparseCore }

这与「复用代码」有本质区别：前者是读懂了平台的物理约束， 后者是借用了别人的实现。TorchTPU 选择的是前者。

一句话总结

TorchTPU 是 torch_xla 的替代品，不是它的分支或衍生品。 它们的关系类似「同一个 API 的两个独立实现」—— 共享 OpenXLA 这层公共底座， 但在 PyTorch 接入方式上做了完全不同（且不兼容）的选择。 torch_xla 用自定义张量类型 + 惰性图 + mark_step； TorchTPU 用标准 PrivateUse1 + 存储层元数据间接 + 自动物化。
