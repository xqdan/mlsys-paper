1. 一句话结论

Weave 做的不是又一个 MoE 通信库，也不是把整模编译成一颗大核。它假定 MoE 层已经融进一颗 persistent megakernel，然后在这颗核里按本步路由统计，给每张 GPU 当场选择通信 / 计算的 warp 比例，并在层的头、中、尾切换 warp 角色。对照点很明确：MegaMoE 已经把通信和 GEMM 的 warp 放在同一个 SM 上，但比例和角色在编译期就锁死；mKernel 能在运行时改 SM 划分，却把整颗 SM 交给通信，Tensor Core 只好闲着。Weave 要补的就是这一级：运行时、warp 级、而且还要快到不能把调度收益吃掉。

定位要写硬：MPK / Event Tensor / Fleet 回答如何把一张图编译或编排成 persistent megakernel；PDL 重构回答不做成常驻大核能逼近到哪。Weave 站在已经融好的 MoE 层里面，回答通信和计算的硬件资源该怎么按路由重切。它不是通用编译器，评测也基本停在 MoE 层（端到端只给了 8×SM90 相对 MegaMoE 的一张表）。论文 v1 正文仍写 will open-source soon；2026-11-25 已能在 ziyuhuang123/weave 看到官方 CUDA/HIP 实现（MIT）；2026-11-26 13:34（Asia/Shanghai）最新提交为 fb1c5081。评测数字仍以论文 v1 为准，不和仓库 README 里另给的台账混用。

2. 问题：EP 下负载跟着路由走，静态日程对不上

在 expert parallelism 下，一层 MoE 是：把 token 派到持有被选专家的 GPU（dispatch / pull），在本地做 GEMM0、激活、GEMM1，再把输出散回并做 top-k reduce（scatter + combine）。当代系统已经把这一层融进一颗 persistent megakernel，例如 DeepGEMM 的 MegaMoE。问题出在路由：同一个 token 若在一张目的 GPU 上选了多个专家，输入只需传一次，GEMM 却要按 token–专家对各做一遍。于是每张卡的通信量和计算量会独立地随路由变化，而且层与层、卡与卡都不一样。

作者把已有方案放在「空间粒度 × 决策时刻」的格子里（文中图 2）：

  • 不切分：SGLang 一类把算子串在多颗核上，通信和计算很难在 warp 级重叠。
  • 编译期按整颗 SM 切开：NanoFlow、DeepEP、FlashMoE。通信 SM 上的 Tensor Core 闲着。
  • 运行时仍按整颗 SM 切开：mKernel。粒度细了一档，但通信 SM 的矩阵单元照样闲着。
  • warp 级、但编译期锁死：MegaMoE 让每个 SM 同时住着通信 warp 和计算 warp，矩阵单元都在工作，可是比例和角色不能跟着路由改。

静态日程会在三个阶段留下气泡。作者用 Qwen3.5-397B 在 SM103 上拆 MegaMoE 的 warp-time（总启动 warp 数 × 层时间）：

  • 头部：GEMM warp 要等输入。S≤1K 时浪费 11.0%–12.7% 的 warp-time，S=20K 仍有 3.7%；头气泡表现为 MMA warp 空等 24.3–36.2 µs。
  • 中段：pull 结束后通信 warp 闲着，同时 epilogue warp 在做 scatter。S≤1K 浪费 15.3%–16.9%，S≥4K 也有 7.9%。把 scatter 交给空闲通信 warp 并不是免费的：S=128 时 epilogue 直写更快，S=20K 时通信 warp 代发更快，静态二选一两边都会输。
  • 尾部：MegaMoE 在 top-k reduce 前加全 GPU 屏障，快卡要等慢卡；屏障之后又只让 epilogue warp 做 reduce，其余 warp 闲着，再浪费 4.1%–6.2%。

三块加起来，S≤1K 浪费 32.8%–34.1% 的 warp-time，4K / 8K / 20K 分别是 25.1%、21.2%、15.8%。带宽侧还有一个观察：SM103 上 pull 带宽跟的是通信 warp 总数，不是它们散在多少个 SM 上——固定 128–512 个通信 warp，每 SM 放 4 到 32 个，带宽相差不到 1%；而 epilogue 写回带宽会随每 SM 的 epilogue warp 数从 4.6 升到 5.6、6.8 TB/s。所以空间问题不是「要不要专 SM」，而是「GPU 范围的通信 warp 总数、以及每 SM 留给 epilogue 的条数」要能按本卡负载微调。

3. 和 9 月前作的关系

同一组作者在 2026-09-18 先放了 arXiv:2609.21483（v3，09-25 修订），标题还是 Weave，但副标题是 Fine-Grained Dynamic SM Scheduling。那篇的核心是：路由一旦完成，本层通信量 / 计算量就已知，于是在 persistent megakernel 里用轻量代价模型，按卡、按层动态划分通信 SM 与计算 SM，并在时间上协调两组 worker。评测是 4×H100 SXM、六个主流 MoE，相对五个基线给出 MoE 层几何平均 2.89×、端到端几何平均 1.33×。作者阵容接近，当时还没有上海 TokMach 的 Qingyun Chen。

11 月这篇把粒度从「整颗 SM」推进到「SM + warp」，并显式把 MegaMoE、mKernel 写成对照：只改 SM 划分仍然会让通信 SM 的 Tensor Core 闲着；要同时对准路由、又保持矩阵单元全开，必须在 SM 内部改 warp 比例，并在阶段之间改角色。评测平台也换了：8×SM103、8×SM90（均 EP8），以及两机 16×CDNA3（EP16）。不要把 9 月文的 2.89× 和这篇相对 MegaMoE 的 1.30× 放在同一条轴上——对照集合、硬件和调度粒度都不同。仓库里若以后只收一篇 Weave 笔记，应以 11 月这篇为准，把 9 月文当作前作交待即可。

4. 做法：空间比例、阶段换角色、launch 时联合选策

系统概览在文中图 5。每张 GPU 在 kernel launch 时，由 CTA 0 读入本卡路由统计和一组校准过的硬件参数，在候选政策里选出一对 (r, s)：r 是空间 warp 比例，s 是中段 scatter 走 epilogue 还是走通信 warp。随后整颗 megakernel 按这个计划执行。

空间调度：比例在 warp，矩阵单元保持全开

Weave 不把整颗 SM 划给通信。每个 SM / CU 上，负责 Tensor Core 或 Matrix Core 的控制 warp 始终在；只把其余 warp 在通信（comm）和计算 / epilogue（epi）之间挪。不同架构能选的离散比例不同（文中表 I）：

平台每 SM / CU精度候选 (comm, comp/epi)多给通信时主要牺牲什么
SM10316 warpsFP8 / FP4(4, 8)、(8, 4)Epilogue 写回带宽（TMEM 把 MMA 和写回解开了）
SM9020 warpsFP8 / BF16(2, 16)、(10, 8)数学 warp（累加器寄存器和通信共享）
CDNA38 wavesFP8 / BF16(0, 8)、(4, 4)数学 wave（同样是共享寄存器）

同一张 GPU 上的不同 SM 可以走不同比例：每个常驻 CTA 用硬件 SM ID 和一个代价模型给出的阈值，在两个 intra-SM 比例里挑一个，从而精细控制整卡通信 warp 数 Nc，又不必为每种全局比例编译一个 kernel 变体。卡与卡之间用点对点队列解耦发送 / 接收 warp 数，每张卡只看自己的路由统计选 r。这是对图 3c 那种「每卡 comm / compute 分布不一样」的直接回应。

时间调度：头、中、尾换角色

任务仍按 MegaMoE / MPK / Event Tensor 那一派，用全局队列加 atomicAdd 领取。三个阶段各自处理一种气泡：

  • 头部 all-warp pull。一开始所有 warp 都去拉远端输入。SM103 上 setmaxnreg 给 TMA/MMA、comm、epi 分别是 72 / 168 / 208 个寄存器，作者按预算各编译一套 pull，寄存器多的 warp 可以把更多 load 留在飞行中、少 spill。拉到预设 token 数之后，TMA、MMA、epi 切回 GEMM，通信 warp 继续把剩余 pull 做完。
  • 中段两条 scatter 路径。Epilogue scatter：epi warp 直接把输出写出去，没有交接开销。Comm scatter：已经空出来的通信 warp 从全局队列领取写好的输出，经 shared memory 发出，同时 GEMM 还在跑。选哪条由代价模型决定，不再编译期锁死。
  • 尾部按 token 就绪做 reduce。不再等全 GPU 屏障。每张卡本地统计每个 token 已到达的专家输出个数，满 k 路就开始 reduce。epi、TMA/MMA、comm 三组 warp 空出来就加入；每个 token 再沿隐藏维 N 切成片，避免只有少量 warp 有活干。

联合代价模型：必须一起选，而且要够便宜

CTA 0 在 launch 时读取本地各专家 token 数 me、合计 M、以及 pull / scatter 计数，给每个候选 (r, s) 打分。链路带宽随通信 warp 数线性涨到峰值 Blink 为止，于是 pull / scatter 时间写成容量除以 min(Blink, N·单 warp 带宽)。计算侧把每个专家的 token 按 tile 高 BM(r) 垫成 Ke(r) 个 tile：权重要按 tile 各载一次，激活按 token–专家对计。主循环时间取 HBM 与 Tensor / Matrix Core 的较大者。

架构差异写进了公式。SM103 有 TMEM，MMA 和 epilogue 写回可以重叠，计算时间取 max(Tmma, Tepi)；SM90 和 CDNA3 共享寄存器，两者串行相加，而且更大的 Nc 会逼小 BM(r)，tile 数上升、峰值算力下降。两条时间政策是：

  • Epi scatter：T = max(Tpull(Nc), Tcomp(r) + Tscat(Ne))，pull 和计算重叠，scatter 走 epi warp。
  • Comm scatter：T = max(Tpull(Nc) + Tscat(Nc), Tcomp(r) + Thoff)，通信 warp 先 pull 再 scatter，并付一次交接开销 Thoff。

CTA 0 在设备上取 arg min。因为只扫本地专家和少数候选，开销几乎与 S 无关：SM103 中位 3.65 µs（3.58–4.29），SM90 中位 1.86 µs（1.86–1.92），CDNA3 中位 3.00 µs（3.00–3.36）。相对端到端，SM103 上测到 −0.08 µs（成对 ±1.3%），SM90 上中位多 0.6 µs（约 0.1%）。

实现要点

NVIDIA 侧是 CUDA C++，AMD 侧是 HIP C++。SM103 上 4 个 warp 固定做 TMA、MMA 和调度，其余在 (4, 8) 与 (8, 4) 之间按 SM 混搭；SM90 是一个 producer warpgroup（2 TMA + 2 comm）配 4 个 math/comm warpgroup，两边都用 setmaxnreg。CDNA3 的 reduce 用 FP32，CU 走 (4, 4) 或 (0, 8)，两机 EP16 上节点间走 GDA RDMA、节点内走 xGMI。另外三项是文中称为标准的优化：通信 warp 经寄存器把远端 token 拉进 HBM、不走 shared memory，以便给 GEMM 多级缓冲留空间；工作列表优先本地 token，给远端 pull 藏启动延迟；每个专家可在 {32, 64, 128, 256} 里自选块高，尽量大、同时少 padding。

5. 评测：层数字很大，端到端要单独看

设置与口径

平台是 8×SM103（148 SM，2032 MHz，CUDA 13.2，EP8，NVLink）、8×SM90（78 SM，1830 MHz，CUDA 13.3，EP8），以及两机 16×CDNA3（每卡 80 CU，节点内 8 卡 xGMI，EP16，ROCm 7.2.0）。负载是表 III 六个 MoE 层：Qwen3.8-2.4T、MiniMax-M3、Qwen3.5-397B / 122B / 35B、DeepSeek-V4-Flash。路由来自真实 ShareGPT，权重和激活是 randn（SM103 用 FP8/NVFP4，SM90 与 CDNA3 用 FP8）。S = batch × sequence length，从 decode 扫到 prefill。数字是 warmup 之后最慢那张卡的中位时延。

基线要按平台分开读。SM103：DeepGEMM-MegaMoE（SM100，commit bdea79976f，deep_gemm 2.6.1）、FlashInfer、SGLang（DeepEP+DeepGEMM）、把五颗 DeepEP/DeepGEMM 核放进一张 CUDA Graph 并开 PDL 的 Graph+PDL，以及作者在 SM103 上重做的 mKernel、FlashMoE（tcgen05/TMA）、NanoFlow（双流 NCCL/DeepGEMM nanobatch）。SM90：FP8 MegaMoE（nv_dev b64107f2）和 FlashInfer v0.6.8。CDNA3：两条官方 RCCL+AITER fused_moe 路径——一阶段 ASM（AITER-1stage，五模型验证过，MiniMax-M3 未过 FP64 检查）和两阶段 CK（即 vLLM 路径）。文中写 SGLang+MORI 超过了这套集群 64 MiB 的 RDMA NIC MR 上限，所以没有列入。

层性能：三块平台，走势并不一样

图 7 每块平台 6 个模型 × 5 个 token 数，共 30 个负载。SM103 上 Weave 相对 MegaMoE 每个负载都更快，范围 1.05–1.97×，几何平均 1.30×；相对 FlashInfer 几何平均 1.40×；相对「该负载最快基线」几何平均 1.22×。加速随 S 变大：小 S 更偏 HBM / 延迟，静态 epilogue scatter 往往够用；S≥8K 的 12 个负载上，MegaMoE 卡在 epilogue scatter，Weave 用通信 warp 在 GEMM 底下把 scatter 流出去，几何平均 1.55×（1.18–1.97×）。相对其他基线的几何平均是：SGLang 4.28×、mKernel 3.26×、FlashMoE 3.62×、NanoFlow 5.00×、Graph+PDL 2.30×（1.82–3.00×）。关掉 PDL 平均只改 −0.5%：CUDA Graph 和 PDL 主要藏 launch 和 prologue，跨 stream 重叠也只能按 SM 切，通信 SM 上的计算仍然浪费。

SM90 的曲线倒过来。相对 MegaMoE 几何平均 1.24×（1.01–1.72×）：S≤128 为 1.37×，S=1K 为 1.38×，S≥8K 只剩 1.06×。作者给的解释是算力 / NVLink 比：SM90 是 0.92 TFLOPS per GB/s，SM103 是 12.6。大 batch 上 SM103 吃的是 NVLink，所以 warp 级重叠还有 1.55×；SM90 已经算力受限，MegaMoE 的 Tensor Core 利用率可到 85.0%，再切比例空间不大。小 S 上 Tensor Core 没吃满，去掉头尾气泡才拿到 1.37–1.38×。相对 FlashInfer 几何平均 1.95×，相对最快基线 1.21×。

CDNA3（EP16）上对照的是官方多核路径，不是 MegaMoE。相对每负载最快官方基线几何平均 1.44×（最高 2.87×）：S≤128 为 1.91×，1K 为 1.20×，S≥8K 仍有 1.19×（最高 1.50×）。相对 AITER-1stage（25 个通过验证的格子）几何平均 1.43×，相对两阶段 vLLM 是 1.67×。这里的增益有很大一块来自「把 dispatch、fused_moe、combine 融进一颗核，并让节点间 GDA RDMA 和节点内 xGMI 与 8-wave GEMM、协同尾 reduce 重叠」——和 NVIDIA 上「已经是 megakernel 的 MegaMoE 再改日程」不是同一件事。

端到端：只有 8×SM90 一张表

表 IV 是 8×SM90 上相对 MegaMoE 的端到端时延（ms）。Decode（S=128，4K 上下文）五个模型从 1.40/0.86/0.65/0.91/0.90 ms 降到 1.28/0.81/0.60/0.81/0.87 ms，加速 1.09 / 1.07 / 1.08 / 1.12 / 1.04×，几何平均 1.08×。Prefill（S=16K）是 19.84→19.76、5.60→5.49、4.05→3.99、9.31→9.36、10.11→10.10，加速 1.00 / 1.02 / 1.02 / 1.00 / 1.00×，几何平均 1.01×。MiniMax-M3 的 prefill 从 9.31 ms 落到 9.36 ms，文中仍标 1.00×，实际上略慢。Decode 增益更大，是因为 MoE 占 decode 时延的 59%–75%；prefill 里 attention 占 40%–67%，而且 SM90 Tensor Core 已经饱和。文中没有给出 8×SM103 或 16×CDNA3 的端到端表，层上的 1.30× / 1.44× 不能外推成服务吞吐。

6. 消融、代价模型与 EPLB

表 V 每块平台 48 个负载（12 个 S≤128，18 个 1K–4K，18 个 S≥8K），和前面图 7 的 30 个负载不是同一集合，几何平均也会略有差别。逐步关掉空间比例（−S）、再关掉时间重叠和尾 reduce（−S−T）、再关掉代价模型（−S−T−C）后，全集合几何平均单调下降：SM103 从 1.301× 到 1.192×、1.010×、0.996×；SM90 从 1.162× 到 1.137×、1.053×、0.947×；CDNA3 从 1.309× 到 1.166×、1.033×、0.848×。读含义时按平台分开：

  • SM103：时间切换在 S≤128 把 0.915× 拉回 1.076×（去头尾气泡），在 S≥8K 把 1.185× 拉到 1.416×（通信 warp 做 scatter）；空间微调在 S≥8K 再加 15.7%。
  • SM90：小 / 中 S 的增益主要来自时间调度；S≥8K 若再去掉代价模型，会掉到 0.836×，静态默认值跑不过 MegaMoE。
  • CDNA3：空间、时间、选策三块在所有 S 上都有贡献；S≥8K 从静态默认的 0.638× 拉到完整 Weave 的 1.176×。

代价模型准不准，作者用穷举 oracle 衡量。SM103 上离线选定的固定配置相对 MegaMoE 是 1.301×，oracle 是 1.332×，平均选策误差 2.6%（几何平均 2.4%），48 个里 38 个完全命中。SM90 上固定选择达到 oracle 的 99.5%（1.164× vs 1.170×），32/48 完全命中，41/48 误差在 1% 以内；核内在线选择是 99.3%（1.162×）。也就是说，这套线性加 max 的模型在作者的离散候选里够用，并不是在预测任意连续配置的绝对时延。

和第 5 节的专家均衡是正交的。EPLB 用冗余专家把 token 在 GPU 之间摊平，Weave 在单卡内部按 comm / compute 需求切 warp。24 个负载（6 模型 × S∈{128, 1K, 4K, 16K}）上，32 个冗余专家把 max/mean 不均衡从 1.37 降到 1.27，但给 Weave 平均加了 12.9% 时延。相对「原始路由的 MegaMoE」：只用 Weave 是 1.274×（24/24 都更快），Weave+EPLB 是 1.128×（17/24 更快）。小 / 中 S 上复制专家会把每专家 token 数 me 削薄，tile padding 和重复载权变重，MegaMoE+EPLB 甚至掉到 0.986×；到 S=16K padding 被摊掉，Weave+EPLB 相对 MegaMoE 是 1.52×，仍低于不加 EPLB 的 1.65×。结论不是「不要 EPLB」，而是：均衡跨卡负载和调度卡内 warp 解决的是两件不同的事，叠在一起不会自动变快。

7. 和已有笔记的分工

  • MPK / Event Tensor / Mirage / Fleet：编译器或任务抽象，目标是把一般张量程序（含通信）降成一颗或一层 megakernel。Weave 假定 MoE 层已经是一颗手写 / 特化的 persistent 核，贡献在核内的硬件资源日程，不提供新的 IR，也不做整模自动 mega-kernelize。
  • PDL 重构 Megakernel：把一颗手写大核拆回普通核，再用 PDL 追吞吐。Weave 在 SM103 上相对 Graph+PDL 仍有 2.30× 几何平均，作者的解释是 PDL / CUDA Graph 只藏 launch，跨核重叠到不了 warp 级。两篇可以对照着读：PDL 说明「常驻」本身不是全部收益；Weave 说明在已经常驻、而且要把通信和 GEMM 叠在同一 SM 时，还缺运行时 warp 日程。
  • One Megakernel is Not Enough：讨论融合边界该切在哪。Weave 不讨论要不要把 attention 和 MoE 融进同一颗核，它的对象就是单独的 MoE 层。
  • Mixture-of-Kittens（尚未成篇）：训练侧、面向 NVL72 的 MoE megakernel，关键设计是按算子选 push / pull、重组算通重叠、去掉 CPU–GPU 同步。Weave 是推理侧、按路由做 warp 级资源划分。两篇都会写到 dispatch / combine，但机制不同；以后写 MoK 时不要把 Weave 的日程公式再抄一遍，也不要把 MoK 的生产训练数字安到这篇上。
相关工作里还点了 Comet、Triton-distributed、FlashMoE、UniEP、DeepEP：它们在融合核里做细粒度算通重叠，但线程块或 SM 划分仍是编译期静态的。mKernel 能改 SM 数，却仍把整颗 SM 交给通信。Warp 特化本身不是新事物（CUTLASS、FlashAttention-3、ThunderKittens，以及若干编译器自动 warp specialization）；MegaMoE 已经把通信和 GEMM warp 放在同一 SM。Weave 自称的差别是：在分布式 MoE 里，用设备上的代价模型，在运行时同时做空间比例和时间角色切换。

8. 落地与局限

先说能落地的部分。设计是完整的：CUDA / HIP 实现路径、三种架构的离散设计空间、launch 时微秒级代价模型、以及和 EPLB 的关系都写清楚了。对照实现也落到了具体 commit（DeepGEMM bdea79976f、MegaMoE nv_dev b64107f2），层评测覆盖了 NVIDIA 两代和 AMD CDNA3 两机 EP16，这比只在单代 GPU 上讲「我们融得更快」要有用。对已经在用 MegaMoE 或准备在 AMD 上把 RCCL+AITER 换成融合层的团队，这篇的可迁移判断是：运行时 warp 比例、头尾角色切换、以及「scatter 交给谁」应当跟路由走，而不是再锁进编译期常量。

官方实现已经公开，仓库在 github.com/ziyuhuang123/weave（MIT）。一作账号于 2026-11-19 20:48（Asia/Shanghai）建库，README 引用的就是 arXiv:2611.27765。2026-11-26 13:34（Asia/Shanghai）看到的最新提交是 fb1c5081。安装入口仍是 pip install -e .，推理侧从 deep_gemm.mega 引入 weave_mega_moe；新硬件可先跑一遍 python -m deep_gemm.mega.autotune，再在运行时自动选参，文档在 docs/AUTOTUNE_AND_TUNING_GUIDE.md。公开参数面仍是 14 个正交旋钮：空间 5、时间 3、实现 6。硬件范围和论文一致，只是写得更具体：NVIDIA SM100/SM103、H20（SM90）和 AMD MI308X（CDNA3 gfx942），分别走 CUDA C++ 与 HIP C++。相对 2026-11-25 核到的 94053c83，之后最实质的代码更新是 2026-11-26 12:09（Asia/Shanghai）的 bfd03df4：在 MI308X 上接入 CDNA3 AGPR/MFMA 的单机 EP8 路径（仓库现同时写明单机 EP8 与两机 EP16），并校正了 MI308X 的 cycle-domain 时间线；同日稍后几次提交主要是 README 三硬件对照表和示意图整理。仓库另有 90 格台账、WeaveProfiler 时间线和消融说明，那些数字是仓库自己的实测记录，本笔记的倍数仍只引用论文 v1，二者不要混用。

即便代码在手，也不能假装容易搬。实现高度绑定架构：SM103 依赖 TMEM 和 setmaxnreg 的三档寄存器预算，SM90 / CDNA3 的公式完全不同，CDNA3 还绑了 GDA RDMA 与 xGMI。换一家 GPU，离散比例、带宽模型和交接开销都得重标定。代价模型只在「每卡两三个候选」里做 arg min，不是通用调度编译器。

评测边界同样要写进结论。层实验用真实路由，但权重和激活是随机数，不涉及数值正确性之外的模型质量；端到端只在 8×SM90 相对 MegaMoE 给了五个模型，decode 几何平均 1.08×、prefill 基本持平，其中 MiniMax-M3 prefill 还略慢。没有 vLLM / SGLang 的端到端对照，也没有 SM103、CDNA3 的端到端表。CDNA3 上很大一块加速来自「多核路径 → 融合核」，和 NVIDIA 上「融合核 → 更好的 warp 日程」要分开引用。作者自己写的局限只有一句：还没在非 GPU 加速器上评，那些器件的计算核和 DMA 层级与 GPU warp / wavefront 不同。此外，Weave 只管 MoE 层，不管 attention、KV cache 或整模常驻；S 很大且平台已经算力受限时，相对 MegaMoE 的空间本来就小。

若只保留一句：MoE megakernel 里真正难的往往不是「再融一次」，而是路由把每张卡的通信 / 计算比拉歪之后，还能不能在 warp 级把日程改过来，并且改得足够便宜。Weave 把这件事做成了 launch 时的一次 2–4 µs 选择；官方代码现在可以读、可以按文档去标定，但仍然绑在 SM103 / SM90 / CDNA3 的公式和互连上，不是一份通吃的可插拔层。
