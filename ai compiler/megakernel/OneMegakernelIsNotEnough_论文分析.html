1. 一句话结论

这篇补的是现有 megakernel 笔记都没写成主题的那一问：融合边界该切在哪里，一颗整模大核何时反而更慢。它不是新的 persistent-kernel 编译器，而是一套边界规划器：用常规图 profile、独立算子基准和实现合约，给候选打一个确定性的「首包」分数，不必把每个组合端到端跑一遍。在作者实现并过合格验的验证池里，13 个模型–batch 组合全部选中了实测最快的设计；最好的答案从来不是一颗整模 megakernel，而是两到四颗专用核，或完全退回常规图。

2. 问题：融到什么程度、边界留在哪

流式推理里，只要实时因子 RTFx 大于 1，用户能感觉到的等待主要由首包决定：TTS 是 Time to First Audio（TTFA），LLM 是 Time to First Token（TTFT）。作者关心的是：在尽量大的 batch 上，把 TTFA / TTFT 压到可接受范围。

Megakernel 在文中的定义很明确：把多个算子融进一颗 persistent kernel，thread block 常驻 GPU，算子之间交接而不回到 host。现有设计通常只把 LLM 的 decode 做成 megakernel，prefill 留给常规执行，或干脆不讨论。MPK 在小 batch 解码上相对 vLLM / SGLang 报过最多 1.7× 的 per-token 时延下降。问题是，流式 TTS 不是「prefill 一次 + decode 循环」这么两段。

以文中的 NH-TTS（即将发布的自回归 TTS，backbone 是 Nemotron-H）为例，一次请求要跑：

  • Prefill，每请求一次；
  • 自回归 producer：每步一次 Nemotron-H backbone，再对每个 codebook 跑一遍 local transformer，产出一帧声学码；
  • Consumer：codec 按 chunk 把帧解成 PCM。

这些阶段的速率、张量形状、thread-block 几何都不同。每一刀决定三件事：哪些阶段共用一次 launch 配置、thread block 被占用多久、阶段之间怎么分享 GPU。切错的代价不是抽象的：对 NH-TTS 和 Qwen3-TTS，次优布局比最优慢 3% 到 29%。NH-TTS 的搜索空间有 81 个候选，穷举实现再计时不便宜。

作者反对的「惯例」有两种：小 batch 上用一颗整模 monolith megakernel；或者只把模型的某一段做成 megakernel，其余仍走常规图。他们的结论是：最好的配置是多颗 megakernel、且不和常规图混叠，或者完全走常规图。在评测过的 13 个组合里，最优从来不是一颗整模单核。图 1 里「常规图 prefill + 一颗大核」的 hybrid 布局直接标了 Not reported，没有实测数字可引。

3. 做法：用 profile 选切分，不必端到端穷举

规划器的输入是「模型 + 已有运行时实现」，不是一张空白的算子图再从头生成 CUDA。它用三类证据：常规图 profile、独立算子或一步基准，以及源码声明的实现合约（几何、存储、编译入口成员、同步）。输出是：把模型划成哪些连续区域、每个区域用常规图还是 megakernel、区域之间如何分享 GPU。候选的分数是确定性的首包分数，只用来排序，不是在预测时延分布或 p95 本身。

图示重画规划器的三层图。计时证据只来自常规图和独立基准，不对候选组合做端到端测量。

切分规则：cover 与三种分享策略

先把模型收成区域图 rGraph。节点是三类 group：Admission（每请求一次，如 prefill）、Producer（每生成步一次）、Consumer（每输出 chunk 一次）。边是数据、状态和发布依赖。一个 region 是一段连续 group，由一个后端执行：要么常规图（一算子一 kernel），要么一颗 persistent megakernel。一个 cover 是对固定顺序 group 的划分，并给每个 region 指定后端。过滤实现支持之前，n 个 group 有 2 · 3n−1 种 cover。

再配执行策略，决定区域怎么分享 GPU：

  • Serial：区域轮流占用整卡。
  • Fixed split：producer 与 consumer 全程共驻，CTA 预算为 X 和 Y。
  • Dynamic split：在 consumer 输入就绪前，producer 占用整卡；就绪后 producer 用 X 个 CTA，consumer 用 Y 个。

策略必须是实现支持的 launch 配置，只挂到适用的 cover 上。文中的 overlap 要求 producer 各 group 合成一颗 megakernel，consumer 也必须是 megakernel；dynamic split 还要求它们是两次分开的 launch。没有匹配服务成本证据的候选直接排除；模拟死锁的视为不可行。并列最低分全部保留，不用验证集实测来打破平局。

NH-TTS 露出四个有序 group：P（prefill）、B（Nemotron-H backbone）、L（local transformer）、C（codec）。四个 group 给出 54 个 serial cover；fixed split 适用于 6 个 cover，dynamic split 只适用于其中 producer / consumer 分开 launch 的 3 个。三种 CTA 预算对再加 27 个候选，合计 81。流式日程用三个参数刻画：延迟 d 步（产出暂不发出）、首个 chunk 的 c1 步、以及判断流是否继续的 lookahead l 步。首个 consumer chunk 在第 r = d + c1 步后才具备资格；producer 要跑到 h = d + c1 + l。在所评估的策略里，第一次发布要同时等解码完的首个 chunk，以及再多一步 generation。

用 profile 做选择：tGraph 填服务表

每个 group 建一张 tile 图 tGraph（文中引用 Welder，不是把 MPK 的编译 IR 原样搬过来）。支持的输出 tile 成为 task，带着计算、权重与激活负载、写回和 staging 存储；边记录 tile 之间的张量依赖，原来的 kernel 屏障另存为一组边。没有 tile 分解的算子按不透明 task 处理，缩预算时用 CTA-wave 近似：网格有 g 个 CTA、预算为 W 时，计算时间按 ⌈g/W⌉ / ⌈g/132⌉ 缩放——132 是 H100 NVL 的 SM 数，并假设各 wave 成本相同。

tile 调度是事件驱动的 list scheduler，工作者池大小等于 CTA 预算 W。两种 megakernel 机制作用在这张表上：去掉屏障边，让下一 kernel 已就绪的 tile 填空闲 worker；以及 weight prefetch，让正在计算的 worker 预取即将到来的 tile 权重。结果是一张服务表：每个 group 在每种后端、每种 CTA 预算下的一次执行时间，记为 S[g, β, W; κ]。上下文 κ 包括线程数、block 几何、调用与存储策略、编译入口成员和同步要求。同一 group、同一后端、同一 CTA 预算，包进不同实现时成本可以不同。计时记录只在键完全匹配时复用；规划器不从常规图时间去「猜」任意融合入口的编译行为。

运行时如何执行：evGraph 模拟到首包

每个候选降到一张事件图 evGraph，延伸到第一次可发布。常规区域保留其算子 launch；megakernel launch 在其全部 task 结束前一直占着 CTA 配额，包括这些 task 在等依赖的时间。Dynamic split 在第 r 步结束「整卡 producer」那次 launch，随后改成预算 X、Y 的两次 launch。节点时长来自服务表。发布条件写成

Tpub = max(Fchunk1, Fproducer h)

其中 F 是模拟完成时间。共驻 launch 只通过 Algorithm 1 的联合模拟交互：争 CTA，并按共享带宽以 min(1, Bmem / Qtot) 降速。规划器不用实测的共跑时间。

文中用一个示意数字说明切分为何能赢。假设 chunk 在 20 ms 就绪；剩余 producer / codec 串行要 4 / 6 ms，在 88/44 分裂下要 6 / 8 ms；串行与 overlap 的切换成本分别是 0.1 / 0.2 ms，且先不计带宽争用。分数是 20+4+6+0.1 = 30.1 ms，对上 20+max(6, 8)+0.2 = 28.2 ms。各自变慢了，overlap 仍然更早发布。

在 NH-TTS、batch 32 上，规划器选出的是 P / (B+L) / C：prefill、融合后的 backbone+local transformer、codec 各一颗 megakernel，producer / consumer 做动态分裂，CTA 为 88/44。这就是图 3 标成 Optimal performance 的那张布局；整模 monolith 被标成 Not optimal。

按论文图 3 重画的 NH-TTS batch 32 选出布局。CTA 分裂随 batch 会变，不能把 88/44 当成该模型的固定答案。

4. 和 PDL、MPK、Event Tensor、Fleet 的差别

这篇几乎不发明新的 kernel 写法。它假设区域内的常规图或 megakernel 实现已经存在，只在「支持的组合」里做选择。和同目录几篇笔记的差别，要按机制说，不要说成同一条流水线的下一步。

对照对方在做什么这篇怎么不同
CUDA PDL Programmatic Dependent Launch 让后一个 kernel 在前一个尚未完全结束时就开始，用 launch 重叠逼近「常驻」效果。PDL 笔记的主题是：不必融成一颗 persistent megakernel。 文中的 megakernel 仍是 persistent kernel：block 常驻，不回到 host。它讨论的「切」是两次 launch 之间的真边界，用来换几何、释放被占用的 CTA、支付 dispatch 成本。正文引用了 CUDA graphs 降 host launch，把 kernel 边界写成屏障，但没有评估 PDL。若边界本身可被 PDL 重叠，规划器给「一切」标的成本会变；这是这篇没做的实验。
MPK 的 tGraph MPK 把张量程序编成一张 task 图，再放进一颗 persistent mega-kernel，由去中心事件运行时调度。 这里的 tGraph 引用的是 Welder：用来给一个 group 在给定后端和 CTA 预算下估服务时间，填服务表，并不把整模型编译进一颗核。evGraph 在服务表之上模拟「多颗核 + 流式发布依赖」。MPK 是「如何 mega-kernelize 给定区域」；这篇是「区域该怎么切」。作者把 MPK 和 Event Tensor 放在相关工作里，用的就是这句分工。
Event Tensor 把 event 做成带符号 shape 的张量 IR，一张图覆盖动态 batch 和数据依赖控制流（如 MoE 路由）。 这里的 evGraph 是候选布局的模拟图，不是可编译的 IR。动态性的处理是按离散 batch 分别规划（评测里每个模型只看几个固定 batch），没有符号 shape，也没有一张图走完动态路由。
Fleet 在 MPK 运行时上加 Chiplet-task，把调度对齐到多 die 的私有 L2。 这篇完全是单卡 H100 NVL（132 SM，94 GB HBM3）。正文和引用都没有讨论 chiplet 或多 die。Fleet 不在参考文献里；对照是笔记之间的分工，不是论文自己做的比较。

相关工作还点了手写 Llama-1B / Llama-70B megakernel、Ada-MK、TileRT、FlashMoE：都是「给定区域之后把核写快」。Rammer、VersaPipe 也做边界或流水段选择，但作者强调自己的目标是对首包敏感的组合，证据停在常规图和算子级测量。

5. 模型给出的四条规则

第 V 节用 tile / event 图解释，为什么「更快的核」或「少一切」并不自动等于更快的管线。

1. 更快的核可以让整条管线更慢

Launch 合约从准入到收尾一直占着 CTA。共驻者只通过模拟交互。NH-TTS 上，producer megakernel 用 88 个 CTA 而不是 80 个，单独快 2.2%；但和常规 codec 并排时，整对慢 30.3%，因为 codec 少了 8 个 CTA。换成 codec megakernel，整对反而快 2.0%。规划器不用实测共跑时间，这条要靠模拟打出来。

2. 共驻代价取决于对方的实现

Persistent launch 在结束前不放 CTA。表 II 是 NH-TTS 的 Stage 0 × Stage 1 四格时延（对照图 3）：两边都是 megakernel 为 0.991 ms，Stage 0 为 MK、Stage 1 为 TensorRT 为 1.290 ms，反过来 1.216 ms，两边都是 TensorRT 为 9.760 ms。作者据此写道：常规 codec 在 producer megakernel 旁边慢 7.57×，codec megakernel 只慢 1.23×。同一套分配，干扰可以差一个数量级。混用常规图和 megakernel，不是免费的折中。

3. 合约固定时，串行切可以是中性的

排除 dispatch、并固定实现与资源合约后，插入串行边界不改变所建模的 device 日程。NH-TTS 全部由 megakernel 构成的八种划分，都预测成 37.067 ms TTFA p95。实测上，monolith 和只在 prefill 处切开的两核设计，实现与 CTA 分裂相同，各 batch 相差不超过 0.5%。monolith 比串行三核慢，原因不是「多了一刀」，而是它全程用 512-thread block；三核设计的 Stage 0 用 256-thread block。差距来自特化，不是边界本身。

4. 固定成本决定常规图何时赢

Megakernel 的 launch、host 协议、内部同步和跨算子 cache 驻留是按步付的固定成本，不随它省下的工作一起缩小。大 batch 上，常规图把这类开销摊到更多计算里。一旦领先小于固定成本，常规图更早发布。Qwen3-TTS 的四区 megakernel 领先从 batch 16 的 15.9 ms 降到 batch 64 的 0.65 ms，而固定成本仍在 0.7–1.1 ms，所以 batch 48 和 64 常规图获胜。NH-TTS 的领先随 batch 增大，所测 batch 上常规图从未赢过。

6. 评测：分模型看，别把局部数字说成通论

设置与口径

全部结果来自单卡 NVIDIA H100 NVL：132 SM，94 GB HBM3，峰值带宽 3.9 TB/s；CUDA 13.2，驱动 595.84。每个设计独占一张 GPU、独立进程。设计之间共用权重、算子精度、输入夹具、生成上限、确定性解码和发布规则。计时前对照未融合参考做正确性检查：生成的 token 或 code 索引、发布前提必须完全一致，浮点输出的相对 L2 误差不得超过 10−2。失败的设计只报告、不进入计时。合格设计在匹配的 GPU block 内做平衡随机序测量。每进程丢掉两个 warmup cohort。

规划器用独立开发集固定打分规则和候选生成策略；评估用的 batch 与输入夹具不进入开发。服务记录、预测分数和平局规则在端到端计时前冻结。验证结果不用来改模型。作者写过「artifact 记录了 checkpoint 哈希、软件版本、文本/上下文长度和 (d, c1, l)」，但 v1 没有给出获取地址。

图 2 把同一设置的三核设计拿来和常规图、monolith 比，柱上标的更细：TTFA 为 145.892 / 45.776 / 35.985 ms，RTFx 为 225.017 / 210.533 / 269.430。由此得到摘要里的几句：相对 monolith，mean batch-p95 TTFA 低 21.4%，吞吐高 28.0%；相对 TensorRT 常规图，engine-level mean batch-p95 TTFA 为 4.05×，吞吐高 19.7%。必须一起读的细节是：整模单核的 RTFx（210.533）低于常规图（225.017）。一颗大核在这个点上用时延换掉了吞吐；三核布局把两边都拿回来。

这个排序在其他 batch 上仍然成立。作者给出的首包时间：batch 64 为 47.4 ms，对 monolith 61.0 ms、常规图 221.5 ms；batch 1 为 27.5 ms，对 32.7 ms 和 73.0 ms。图 4 还显示，同一套三核切分在 batch 64 上改选 80/52 的 CTA 分裂，次优是 2 MK，差距 28.60%——和引言「次优慢 3% 到 29%」的上沿对得上。batch 32 上次优是 4 MK dynamic，差距 6.67%；batch 1 上次优是 1 MK，差距 19.30%。规划器在三核布局内部也对了资源策略：batch 32 上 80/52 比 88/44 慢 1.0%；batch 64 上三核串行比 overlap 慢 4.2%。

Qwen3-TTS：小 batch 四核，大 batch 退回常规图

五个 batch 里，规划器与实测一致：batch 1 / 16 / 32 选四颗 megakernel，batch 48 / 64 选常规图。图 4 上相对次优的差距是 8.10%、10.20%、10.10%、4.20%、3.20%。正文补充了 95% 区间：batch 1 上两核比四核慢 8.1%（7.8–8.3%）；batch 48 和 64 上四核比常规图慢 4.2%（3.1–4.9%）和 3.2%（3.0–3.4%）。这里没有 NH-TTS 那种「切完又同时赢吞吐」的柱状图，不要把 4.05× 或 +28% 借到 Qwen 上。口径也不同：Qwen 的 TTFA 在 host 侧计量。

Llama 3.2 1B：TTFT 上始终是两核，不是一颗合体核

五个 batch（1、2、16、32、48）全部选「prefill、decode 各一颗 megakernel」，次优都是把两段打成一颗。图 4 把五次差距画成 7.8%–14.9% 的区间。即便目标只是 first-token latency，合体入口也会因为寄存器溢到 local memory，让每一层 prefill 变慢——规划器的一步基准里，batch 1 为 316 μs 对 276 μs，大约慢 15%。所以这里的「切」首先是为了保住 prefill 的实现合约，不是在 TTFT 路径上叠 decode。

文中把 Llama 写成：对 first-token latency 是 megakernel-stable，对 inter-token latency 是 megakernel-receding。图 4 与表 III 的评测指标是 TTFT，ITL 没有另给一张表。后半句是分类上的判断，不要当成已经画出的 ITL 加速数字。

规划器准的是名次，不是绝对时间

冻结后的规划器在 13/13 个留出的模型–batch 组合上唯一选中了实测最快设计。它给设计排序，并不校准绝对时延。常规设计因为分数来自一次实测 run，落在验证的 5% 以内；NH-TTS 的一核、两核设计共用同一套 persistent 实现，也在 5% 以内；三核设计共用另一套实现，被高估 6% 到 22%——被选中的 batch 32 设计预测 42.52 ms，实测 35.99 ms。Llama-1B 最多被高估 11%；Qwen3-TTS 的四核设计在 batch 48 和 64 被低估 1.1 到 1.5 ms。绝对误差在，名次仍然对。

消融把这一点说得更窄。服务成本和候选池相同：完整规划器 13/13；把事件服务与 dispatch 做加性求和，或去掉 overlap、按固定拓扑串行化，都是 11/13，最大 regret 为 4.50%（regret = 所选设计的实测时延 / 池内实测最低时延 − 1；平局预测不算唯一命中，并取其成员中最差的 regret）。两次失手都在 NH-TTS 的 batch 32 / 64，更简单的选择器挑了串行，完整规划器靠 chunk 就绪、CTA 分配和并发完成才选对 overlap。作者的定位是：事件模拟的收益集中在对 overlap 敏感的决策上；执行是串行时，实现相关的部件成本就够用。

7. 融合该走多远：四类模型

第 VII 节把「融到何处」写成一笔按步支付的固定成本 F，对上该区域相对常规 kernel 省下的 S(b)。CUDA graph 已经去掉的 launch / host dispatch 与 b 无关；不再落内存的中间流量随 b 增长；一份编译日程和逐个调过的 kernel 之间的服务差，可以随 tile 填满和 wave 数变大、变小，甚至变号。区域在 S(b) > F 时才划算。F 固定、S(b) 会动，所以最佳融合范围随 batch 走，而且不同模型方向不同。

大 batch 仍然划算大 batch 不再划算
小 batch 划算 Megakernel-stable（已观察到）：NH-TTS；Llama-1B 的 first-token latency Megakernel-receding（已观察到）：Qwen3-TTS；Llama-1B 的 inter-token latency
小 batch 不划算 Megakernel-advancing（只是预测）：常规成本被与工作量成正比的流量主导，或被可被 persistent 日程重叠的串行计算 / 内存 / 通信主导 Megakernel-averse（只是预测）：区域已经 compute-bound，例如大模型 prefill

一个模型要被算作 stable，文中给了三条：对目标路径上的时间占大头（TTFT 的路径只有 prefill，所以 Llama 在 TTFT 上 stable、在 decode 上 receding）；能形成连续区域，且在每个被看的 batch 上节省都超过固定成本——稳定的核若一个个夹在别的核中间，付不起周围那些切；以及不会把收益输给共驻的常规部分，即第 2 条规则。单独看未必值得做成 megakernel 的区域，共驻时仍可能受益，作者用 Nemotron 上的实验说明这一点。

融合可以停在两个极端之间的任何地方：常规图，或整模 monolith。作者的答复是：答案从「多颗 megakernel」到「每阶段成千上万个常规 kernel」都有可能，取决于架构、batch 和优化目标。值得保留的边界，是跨越它的成本低于它所保护的特化与发布控制。advancing / averse 两类在本文评测里没有观察到，不要当成已经证实的分类结果。

8. 落地与局限

  • 实现未公开。截至 arXiv:2610.35336v1（2026-10-26），论文、arXiv 摘要页和 HTML 版都没有代码、模型或 artifact 链接。正文只说 artifact 记录了哈希与软件版本。规划器依赖「源码声明的实现合约」和已经存在的 megakernel / 常规图实现；没有这些实现，这套方法不能从一张 PyTorch 图凭空切出可跑的核。
  • 硬件只有 H100 NVL。作者明确写了：13/13 不能外推到其他 GPU 架构。CTA-wave 近似里的 132、寄存器上限「每 SM 驻留线程分到的寄存器，最多 255」，都钉在这张卡的模型上。
  • 模型范围很窄。一个尚未公开发布的 Nemotron-H TTS、Qwen3-TTS、Llama 3.2 1B。没有更大的稠密 LLM，没有 MoE serving，没有多卡。NH-TTS 是主数字来源，也是唯一同时报 TTFA 与 RTFx 的案例。
  • 和生产 serving 的差距。测量是独占 GPU、固定夹具、确定性解码、按给定 batch 跑完，不是在线到达的连续批，也没有调度器在真实 trace 上的排队与抢占。NH-TTS 的 TTFA 在 engine 发布点计量，Qwen 在 host 侧计量，两者不能直接横比。Llama 只报了 496-token prompt 上的 TTFT。
  • 选择范围是验证池，不是设计空间全集。hybrid 布局在图 1 标 Not reported。未实现或未通过相对 L2 ≤ 10−2 检查的设计不进入计时。规划器可能在未测候选里打出更低的 Tpub，但那不是这篇能证实的「最优」。
  • 分数是排序代理。三核设计绝对时延可被高估 6% 到 22%。把它当成性能模型去报「预计 TTFA」会偏。它可靠的是：在冻结规则下，池内名次对了。
  • 两类模型分类仍是假说。megakernel-advancing 与 averse 没有实例。文末提出的两个后续问题也还没有答：stable 架构是否在同等精度下计算性能全面更好；软件调度能否避免常规图与 megakernel 共驻时的干扰。

9. 和已有笔记的分工

同目录五篇笔记加上这篇，可以压成六句，不要互相替代。

  • Mirage：为单个 task 搜索并生成 CUDA。
  • MPK：把 task 图编译进一颗 persistent mega-kernel，并给出运行时。
  • Event Tensor：把 event 升成带符号 shape 的张量 IR，一张图覆盖动态 batch 与 MoE 路由。
  • Fleet：在 MPK 运行时上加入 Chiplet-task，把调度对齐到多 die 的私有 L2。
  • PDL 重构 Megakernel：不把模型融成常驻大核，用 PDL 重叠依赖 launch，看能逼近一颗 megakernel 到什么程度。
  • 本篇：在已经有常规图和 megakernel 实现的前提下，决定切几刀、切在哪、要不要共驻。它引用 MPK 与 Event Tensor，但不依赖、也不评估 Fleet 或 PDL。
若只保留一句：前面几篇把「一颗核」写快或逼近「一颗核」；这篇说明「一颗」常常不是正确的粒度，而且这个粒度可以在不做端到端穷举的情况下，用常规图和算子基准预测出来——至少在 H100 NVL、三个模型、已实现的验证池里是这样。
