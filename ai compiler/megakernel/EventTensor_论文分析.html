1. 一句话结论与研究定位

MPK 和 HazyResearch 的手写 mega-kernel 已经证明：把算子切成 tile、用核内信号做细粒度依赖，能去掉 launch 间隙、露出核间并行。它们过不了生产 serving 的两道坎——动态 shape（连续批）和数据依赖控制流（MoE 路由）。Event Tensor 把「一簇 SM 级任务完成」升成编译器里的一等张量，形状可以是符号，下标可以是运行时算出来的。

信号量不是新东西。论文的新颖点是：把它们做成 IR 里的张量，从而直接复用编译器已有的符号 shape 设施（PyTorch 2 / Relax），并且用同一套变换生成静态或动态调度的 persistent kernel。ETC 做在 Apache TVM 上，device function 用 TVM DSL 写，抽象本身声称 DSL 无关。

2. Mega-kernel 在动态负载上卡住

Launch 仍贵：一次 5–10 μs，最快的核 2 μs 就跑完。CUDA Graph 把 launch 间隙压没，但核边界还在，细粒度重叠做不到。Mega-kernel 把算子切成 tile task、用轻量信号保序，理论上能同时解决两件事。

动态性

连续批让 batch / 序列长度成为符号。按每个 shape 重编译或重捕获，启动延迟不可接受，shape 空间太大时根本枚举不完。MoE 的 expert 路由在编译期未知，静态任务图无法表达「这个 GroupGEMM tile 处理哪些 token」。

可编程性

开发者要手写百万级细粒度依赖。静态调度（每 SM 预分配队列）和动态调度（核内 scheduler 派 ready task）各有适用场景，理想情况是同一份 IR 上选变换，而不是重写整颗核。

这两件事不是 mega-kernel 独有：CUDA Graph 在生产 serving 里最大的痛就是按 shape 反复捕获。低 batch、延迟敏感的 agent / 编程助手把问题放大——这时候核间并行才是在砍每请求延迟。

3. Event Tensor 是什么

Event：一簇在 SM 粒度上完成的任务。Mega-kernel 把算子切成大量 tile，对应的同步事件自然长成和数据张量同构的多维数组。Event Tensor 就是这张数组，每个元素有初始 wait count，支持 notify()、wait()，动态调度下还可以触发下游 task。

语言里三块构件：

  • Device function：一组按多维坐标发射的 tile，坐标标识跑在哪颗 SM 上的 task。内部可写 warp specialization、tensor core。
  • Event Tensor：多维事件。单独管每个 event 在百万级规模下会把任务图管理打爆；收成张量后，一次对象表示成千上万个事件。
  • Graph function：call_device 构成的计算图，同时包含数据张量和 Event Tensor。每个 launch 标注 in_edges / out_edges 以及坐标映射（einsum 风格，如 "ij->i"）。

默认模式是「生产 task → event → 消费 task」：out_edges 在生产 task 末尾隐式 notify，in_edges 在消费 task 开头隐式 wait。也允许 device function 把 Event Tensor 当参数，在内部显式 notify/wait——这是写融合变换时需要的一等能力。

图 2 · 论文 Figure 3 的 split-K：四列部分和完成才触发对应行的 final_sum。传统 kernel-by-kernel 会等全部部分和结束。

4. 两类动态：符号 shape 与数据依赖

Shape dynamism

Event Tensor 的维可以含符号（batch、序列长度）。这张符号图是任务图模板：runtime 填入具体 B=1 或 B=2，实例化出 1×H 或 2×H 的依赖，不重编译、不重捕获。这是相对 CUDA Graph / 静态 tGraph 的核心差别。

图 3 · 论文 Figure 4。符号维把「任务图」变成模板；concrete B 只在运行时填进去。

Data-dependent dynamism

MoE：token 按 runtime 的 topk 分到 expert，再 GroupGEMM。编译期不知道哪个 tile 处理哪些 token。Event Tensor 用两个机制：

数据依赖的 event 更新

grouping tile（每 token 一个）按 topk[i,:] 去 notify 对应 expert 的 event。每个 expert 的 wait count 初始化为分到它的 token 数——这个数本身是 runtime 算的。

数据依赖的 task 触发

exp_indptr（CSR 风格前缀和）记录每 expert 要发多少 GroupGEMM tile。Expert i 激活区间 (indptr[i], indptr[i+1]) 内的 tile。

整条链仍是前馈：Attention → TopK → Grouping → GroupGEMM。TopK 对 Attention 的依赖是普通静态边；数据依赖机制只管后面「谁 notify 谁、触发多少 tile」。结合符号 shape，全部编译发生在离线，推理时零编译开销。

图 4 · 论文 Figure 5。黄色边在 runtime 由 topk / exp_indptr 决定；编译器事先只知道「会有这种映射」，不知道具体下标。

5. 静态调度：预排队列 + notify/wait

静态调度把多个 device function 融成一颗 persistent 核：host 上为每颗 SM 生成执行队列，核内主循环不断取预计算的 (task_idx, task_type)，在 GEMM 末尾 notify、在 Reduce-Scatter 开头 wait。同步开销最低，适合可预测负载。

GEMM + Reduce-Scatter（张量并行标配）：每个 RS tile 覆盖两个 MM tile，event 初值 2。SM0 做完 MM0 后计数变 1，队列里下一个是 RS，进 spin-wait；SM1 做完对应 MM 后计数归零，SM0 退出等待开跑 RS。GPU 在等待期间仍被其他 MM 占着。

静态调度本身不擅长动态。ETC 的补丁：shape 上采样代表点，未见过的 shape 复用「下一个更大采样」的队列；数据依赖上按最坏情况改写 notify/wait。队列构造用 round-robin。这能跑，但保守。

图 5 · 论文 Figure 7。SM0 的 RS 自旋，但 SM1 继续算 MM；计数归零才结束等待。适合规则、可预测负载。

6. 动态调度：核内 push/pop

任务耗时不可预测时，静态绑定会让部分 SM 堆积长 tile、其余空转。动态调度：event 计数归零后，把全部消费者原子 push 进核内 scheduler；空闲 SM 原子 pop 一个 ready task。tile 顺序在 runtime、符号值和路由结果都已解析之后才决定，因此天然覆盖两类动态。

同一 GEMM+RS 例子：SM0 做完 MM0 计数变 1，立刻 pop 下一个 ready 的 MM1，不空等；SM1 做完后计数归零，RS 被 push，SM1 pop 到 RS 开跑。没有 host 预计算队列。

实现用全局内存里的集中队列，求简单，作者承认大规模下可能争用。附录 E 的优化：early push——生产者刚被派到 SM（不必等算完）就把消费者推进 ready 队列，依赖仍由消费者入口的 wait 保证，push 开销和生产者计算重叠。

折中是经典的。静态：调度税最低，适合规则、可预测。动态：负载均衡，适合 MoE / 通信抖动，付 push/pop 税。分布式上动态调度往远端队列 push 会很贵（Qwen3-32B TP=4 上动态相对未融合 mega-kernel 只有 0.83–0.89×）。所以端到端 decode 用静态，大 batch 算通重叠用动态。

图 6 · 论文 Figure 9。空闲 SM 立刻去队列里抢活，不再 spin-wait。通信抖动和大 batch MoE 走这条；低 batch decode 走静态。

7. 降低到「整数张量 + 原子」

调度逻辑编译进 mega-kernel，不在内存里物化任务图，也不需要通用图执行器。Event Tensor 降成整数张量，复用现有张量数据结构：notify = 原子减，wait = 自旋到 0。Runtime 状态 = 这些整数张量 + scheduler 的 task 队列。

图 7 · 论文 Figure 10。把调度变成编译变换之后，runtime 不再需要一张展开的任务图。

对比「传统 runtime 执行器」：任务图在内存里展开，只编译 tiled 算子，执行器遍历图再 launch。ETC 是 compiled-in control flow。流水线：图级优化（含内存规划）→ tile 级指令与流水 → 静态或动态调度变换 → persistent 代码生成 → 按注解生成 weight prefetch → 若静态则物化每 SM 队列。

8. 评测：算通融合、MoE、serving、warmup

8×B200 NVLink，Ubuntu 24.04，PyTorch 2.8，CUDA 13.0。基线已含 CUDA Graph、PDL、torch.compile。作者说明现有 mega-kernel 框架只针对单 batch 稠密推理，动态 shape / 数据依赖下无法公平对比（点名 MPK 与 Spector）。

融合通信 + 计算（8192 token，TP=8）

模式实现选择为何这套调度结果
GEMM + Reduce-Scatter multimem PTX + 动态调度 网络争用让完成时间不可预测 相对 cuBLAS+NCCL 最高 1.40×
All-Gather + GEMM copy engine 环形 + 静态调度 只有 GEMM tile 占 SM，到达顺序由 ring 决定，预计算队列即可重叠 同样最高 1.40×

TP-Async 切块粒度要么吃不满 SM、要么藏不住通信；Triton-Distributed 的 B200 GEMM 尚未充分特化。未融合的 cuBLAS+NCCL 有时反而接近这些「融合」基线——说明融合本身很难做对。ETC 的优势来自把整段流水画成细粒度任务图，并按负载选调度器。

MoE 层（Qwen3-30B-A3B，128 expert，topk=8）

现有系统有高效 persistent GroupGEMM，但完整 MoE 仍是一串独立 launch。ETC 把数据依赖数据流融进一颗核，动态调度。最高 1.23×（1024 token）。来源：打破全局屏障，两段 GroupGEMM 细粒度流水（减轻 wave quantization）；核内动态调度给不规则路由做负载均衡。

端到端低 batch serving

Decode 为主（prefill / 大 batch 已经吃满 GPU，mega-kernel 边际小，除了算通重叠）。静态调度覆盖完整 decode 管线（Attention、RoPE、KV、Norm、MLP、MoE），不只 GEMM。数据集：prefill 512、生成 100 token，batch 1–128。

  • Qwen3-30B-A3B TP=1：bs=1 相对 vLLM 1.48×、SGLang 1.20×。
  • Qwen3-32B TP=1：相对 vLLM 最高 1.15×（bs=1），相对 SGLang 最高 1.09×（bs=64）。
  • Qwen3-32B TP=4：相对 vLLM 0.99–1.06×；SGLang 因 CPU 调度器更省分布式开销，端到端 TPOT 有时更好。

附录给了剥离框架开销的 raw kernel 时间：MoE 模型 bs=1 相对 vLLM 1.49×、SGLang 1.27×；稠密 TP=1 平均约 7%，最高 1.13×；TP=4 相对 vLLM 最高 1.08×。偶发落后被归因于编译生成的 GEMM tile 不如 cuBLAS、以及 serving 引擎的 CPU 开销——不是抽象本身的上限。

融合带来的具体优化：Attention 里 Q 的 Norm+RoPE 与 K 的 Norm+RoPE+CacheAppend 并行；MoE / MLP 里 GroupGEMM 流水减轻 wave quantization；权重在激活到达前 prefetch。

9. 和 MPK 的关系、局限

相关工作里点名 Cheng et al. 2025（即 MPK）和 Spector et al. 2025：它们只支持单 batch 稠密、只实现一种调度。Event Tensor 补的是 shape / 数据依赖的系统化 IR，以及静态+动态两套变换。和 Cilk / Legion / Realm / OpenMP Tasks 的关系：那些是 CPU 编排的粗粒度任务；和 Graphene / Cypress 的关系：那些优化单核，Graphene 把线程当成带同步能力的张量，概念相近，但不做多算子 mega-kernel 融合。

还没做的

  • 更高层 pass：从普通计算图自动生成 Event Tensor 任务图。当前仍要在图上标注 Event Tensor 和 tile 切分（Triton / 编译器 builtin / TVM DSL）。
  • 动态调度的集中队列在规模上的争用，只承认了，没有多级队列数据。
  • TP=4 低 batch 的端到端仍受 CPU 调度和通信尾延迟限制，抽象解决不了 serving 引擎的宿主机路径。
  • 评测几乎全在 B200；IR 层声称与代数无关，但生成的 GEMM tile 质量仍绑定后端。
可带走的判断：mega-kernel 要从「手写或按 shape 特化一张静态任务图」变成「生产可用」，缺的不是又一个 scheduler，而是把同步做成和数据一样的符号对象。Event Tensor 是这个判断的 IR。MPK 的 tGraph 规范化/线性化是静态、具体 shape 下的高效编码；Event Tensor 是它的动态、可变换上界。
