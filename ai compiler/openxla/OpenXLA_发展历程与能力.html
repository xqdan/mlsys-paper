1. 写什么、不写什么

这是一份面向笔记仓库的中文技术综述，目标有两件：把 OpenXLA 组织里真正还在演进的项目按一条编译栈讲清楚；再把 torch_tpu 放到这条栈上，补上「现在能做什么、边界在哪」，而不是再写一遍已经存在的论文精读。

时间、引语和能力声明只采用官方博客、项目文档、README、release、论文或可核验的公开仓库元数据。仓库创建时间来自 GitHub created_at（UTC），文中一般记为日历日。星标、issue、最近推送等指标取自 2026-11-23 的公开 API 快照，会随时间变化。

本仓库 ai compiler/torchtpu/ 里已有三篇笔记： 论文分析 解读 2026 年 Google Developers Blog 对 TorchTPU 的设计叙事； 开源代码分析 基于 v0.2.0 / HEAD 2092cb8a（2026-10-26）做静态剖析； NPU 移植指南 讨论如何把自研加速器接到这套 PJRT / StableHLO 接缝上。 下文只引用结论，不重复算子表、view decomposition 或移植清单。

2. 这条编译栈怎么拼

OpenXLA 给自己的定位是「把前端框架和硬件后端之间碎片化的工具打通」。官方网站的原话是： an open ecosystem of performant, portable, and extensible machine learning (ML) infrastructure components that simplify ML development by defragmenting the tools between frontend frameworks and hardware backends（openxla.org）。

落到工程上，可以看成四层契约，外加两块「锦上添花」的配套：

图 1 · OpenXLA 栈的分层关系（据官方文档归纳，不是仓库里的一张官方架构图）。

一条典型路径是：框架把计算降到 StableHLO；如需多设备，就在这层或随后的 HLO 上走 Shardy（或历史上的 GSPMD）做切分；XLA 做图优化和后端代码生成；框架通过 PJRT 把可执行体和缓冲交到具体硬件。需要手写高性能算子时走 Tokamax / Pallas；上线非 LLM 长解码类推理时，可以用 XLA Serving Engine 把同一份 StableHLO 制品拿到 C++ 运行时；调优则看 XProf。

TorchTPU 不在 openxla 组织里，但它是这条栈在 PyTorch 侧的一等前端：用 PrivateUse1 把 TPU 暴露成 device="tpu"，把 ATen 语义翻译成 StableHLO，再经 PJRT 调用 XLA / libtpu。它和 PyTorch/XLA 共享的是下层 OpenXLA 组件，而不是同一份前端代码。详见第 13 节与已有笔记。

4. 发展历程时间线

OpenXLA 不是 2022 年凭空出现的编译器，而是把已经在 TensorFlow、JAX 和 Google 生产环境里用了多年的 XLA，从单一框架里拆出来，补上可版本化的 IR 和可插拔运行时，再逐步加上切分、kernel 库和 Serving。

  • 2017-02 / 03

    TensorFlow 1.0 发布前后，Google 公开 XLA（Accelerated Linear Algebra）。2017-03-06 的 Developers Blog 文章 XLA - TensorFlow, compiled 把它定位为 TensorFlow 的域特定编译器：通过编译子图提升执行速度、降低内存、减少对手工融合自定义算子的依赖，并为新硬件提供相对容易的后端接口。

  • 2017–2022

    XLA 在 TensorFlow 树内演进，并成为 JAX 的默认编译路径；PyTorch 则通过 PyTorch/XLA 使用它。HLO / 后来的 MHLO 是这一时期的编译器接口。GSPMD 等切分工作也在这条管线中成熟（论文 arXiv:2105.04663）。

  • 2022-07 / 08

    TensorFlow 社区出现 建立 SIG OpenXLA 的 RFC（2022-07-21 发帖，评论截止 07-25）。RFC 合并后 SIG 启动，首次社区会议定在 2022-08-09。GitHub 组织与 openxla/community 随之建立：community 仓创建于 2022-08-03，stablehlo 于 08-04，xla 于 08-09。

  • 2022-10-11

    Google Cloud Next 上对外宣布 OpenXLA Project。Google Cloud 博客 Open source collaborations and key partnerships 写道：社区将首先协作演进「正在从 TensorFlow 解耦的 XLA 编译器」以及「使框架更易部署到不同硬件的可移植算子集 StableHLO」。创始成员包括 AMD、Arm、Google、Intel、Meta、NVIDIA 等。

  • 2022 年底

    据 StableHLO 早期 release 说明，StableHLO「自 2022 年底起已在生产中作为 MHLO/HLO 的编译器接口替代被使用」。

  • 2023-01-23

    RFC: OpenXLA PJRT Plugin 提出把 PJRT 作为 OpenXLA 支持的设备插件机制。RFC 曾建议另建 openxla/openxla-pjrt-plugin 仓库；当前组织列表中并无此仓，PJRT 实现位于 openxla/xla。

  • 2023-03-08

    Google Open Source Blog 宣布 OpenXLA is available now：XLA、StableHLO 和 IREE 仓库开放使用与贡献。联合开发方名单扩大到 Alibaba、AWS、AMD、Anyscale、Apple、Arm、Cerebras、Google、Graphcore、Hugging Face、Intel、Meta、NVIDIA、SiFive 等。

  • 2023-04-03

    PyTorch 官方博客发表 PyTorch & OpenXLA: The Path Forward，把 OpenXLA、PyTorch 2.0 与 PyTorch/XLA 2.0 放在同一时间点讨论。

  • 2023-05-08

    PJRT: Simplifying ML Hardware and Framework Integration 正式把 PJRT 作为 OpenXLA 的一部分开源。文章称 PJRT 是 TensorFlow 与 JAX 的主要接口，对 PyTorch 有完整支持，并且是 Google 内部大多数生产负载的默认运行时路径。Intel 当时已用它为 TensorFlow / JAX 提供 GPU 后端。

  • 2024-01

5. XLA：编译器与后端

openxla/xla 是组织里体量最大、也最核心的仓库。README 的定义是：an open-source machine learning (ML) compiler for GPUs, CPUs, and ML accelerators，输入来自 PyTorch、TensorFlow 和 JAX，为不同硬件生成高性能可执行体（官方文档入口）。普通模型开发者通常不必克隆该仓，而是通过各框架预构建的 XLA 使用它。

IR 与编译流程

据 XLA architecture，编译器消费 StableHLO 程序，经过大致三步：

  1. 目标无关优化：CSE、与目标无关的融合、缓冲分析等，同时把 StableHLO 转成内部 HLO 方言。
  2. 后端相关的 HLO 优化：例如 GPU 后端按 GPU 编程模型做融合、划分 stream，或把模式匹配到优化库调用。
  3. 目标代码生成：官方文档写明，随 XLA 提供的 CPU 与 GPU 后端使用 LLVM 做低层 IR、优化和代码生成。GPU 后端经 LLVM NVPTX 支持 NVIDIA GPU；CPU 后端支持多种 CPU ISA。新硬件可通过抽象接口接入（Developing a new backend）。

官方写明的优化目标

执行速度

编译短生命期算子以去掉运行时开销，流水线融合以降低访存，对已知形状做更激进的常量传播。

内存

分析并调度内存使用，去掉大量中间缓冲。与 eager 分配器不同，调度器可以「看见未来」。

减少自定义算子依赖

让自动融合的低层算子接近手工融合自定义算子的性能。

可移植性

为新硬件写一个后端，使大量模型无需改写即可运行；而不是为新硬件逐个特化巨型算子。

并行与 GPU 管线中的关键能力

XLA:GPU Architecture Overview 把前端到设备的合同写得很清楚：框架把用户程序变成大约 100 个高层算子的 StableHLO，执行时调用 PJRT 完成「在指定设备上，用给定 StableHLO 程序填充指定缓冲」。文档中强调的优化包括：

  • SPMD Partitioner（历史上以 GSPMD 为主）：消费带切分注解的 HLO，生成可在多主机、多设备上运行的切分 HLO，并试图重叠计算与通信。
  • Layout assignment：逻辑形状与物理 layout 解耦，为算子选择更优 layout，冲突处插入 copy。
  • Fusion：文档称之为 XLA「单一最重要的优化」——把多个算子收进一个 fusion，不把中间张量物化到 HBM，一个 fusion 对应一个 GPU kernel。
  • 代码生成策略：库调用（如 NVIDIA 的 cuBLAS、cuDNN、NCCL）、直接生成 LLVM IR，以及把包含 matmul / softmax 等的高级 fusion 降到 TritonIR 再生成 PTX。XLA 维护 openxla/triton 分叉，正是这条路径的配套。

硬件后端：能核实的范围

  • CPU、NVIDIA GPU：架构文档中的一等、随仓库提供的后端。
  • AMD GPU（ROCm）：不是「只存在于厂商插件、与上游无关」的状态。2026-06-29 的 AMD 官方技术博客明确写：OpenXLA 栈已在上游跑在 ROCm 上，XLA PR 在真实 Instinct 芯片上与 CUDA 路径并列门禁，并可经 Triton + LLVM-AMDGPU 或 hipBLASLt / MIOpen 等库下降。
  • TPU 及其他 ML 加速器：产品文档与框架集成（JAX、TorchTPU、XSE）都把 TPU 作为一等目标。需要注意：公开树里 xla/backends 目前可见的目录是 cpu、gpu、interpreter、autotuner、profiler，没有同级的 tpu 目录。TPU 编译与运行时有多少在公开树、多少在闭源 libtpu，公开材料没有一份完整清单（见第 15 节）。
  • 其他硬件：通过实现 PJRT plugin（或历史上的 XLA 后端接口）接入。2023 年的宣布与合作声明提到 AWS Neuron（Trainium / Inferentia）、Graphcore IPU、Cerebras、Intel GPU 等；这些是厂商侧集成，不应理解成 openxla/xla 里都有对等的一等后端目录。

已知限制（官方口径内）

XLA 长期更擅长编译期形状已知的计算。动态形状、尤其是自回归解码里步步变化的 KV cache，会触发重编译——这正是 TorchTPU / 2026 路线图里强调「有界动态性 / 分桶」的原因。GPU 架构文档里也曾写 CUDA graph 提取「仍在进行中，仅部分节点受支持」（该文档会随代码演进，引用时以当时文本为准）。XLA 也不试图单独充当连续批处理的 LLM serving 引擎，那是 vLLM / SGLang 等系统的职责。

6. StableHLO：可移植算子层

StableHLO 的官方定义（openxla.org/stablehlo）：它是面向机器学习高层运算的算子集，essentially, it's a portability layer between different ML frameworks and ML compilers。产出 StableHLO 的框架，可以对接消费 StableHLO 的编译器。目标是在 TensorFlow、JAX、PyTorch 与 XLA、IREE 等之间建立互操作。它基于 MHLO，并补上了序列化与版本化；序列化格式是 MLIR bytecode。

当前主要能力（官方 v1.0 及文档）

  • 完整规格：v1.0 发布说明写明约 98 个算子均有规范、verifier 与类型推断；官网当前表述为「约 100 个算子」，并覆盖动态性与量化能力。
  • 兼容承诺：portable artifact 提供 5 年向后兼容、2 年向前兼容（新特性除外）。细节与「不在范围内」的事项见 compatibility.md。
  • 参考解释器，以及 C++ / Python API、nightly wheel。
  • 可扩展性：composite 与 custom-call，便于实验或表达厂商专用运算。
  • 程序变换：与硬件无关的简化、用具体输入细化动态形状、以及向 linalg / tosa 等上游 MLIR 方言的转换。
  • 测试集：官方提到含动态与量化程序及黄金结果的大规模 testdata，用于厂商集成与兼容性回归。
  • 仓库还提供把 StableHLO 程序（含权重元数据）转成 TensorFlow SavedModel 的工具。
兼容保证只覆盖按官方 API 生成的 portable artifact，不包括漂亮打印的方言文本，甚至不包括「未经兼容 API 的 SteadyHLO 方言 bytecode」。不在范围内的还有：尚未写入规格的特性、与规格矛盾的实现 bug、跨实现 / 跨版本的数值精度，以及 C/C++/Python 源码级 API 稳定性（文档称源码兼容仍是 aspirational goal）。

前端合同上，TensorFlow、JAX、PyTorch（经由 TorchTPU 或 PyTorch/XLA 等路径）都可以导出 StableHLO；消费端至少包括 XLA、IREE，以及 Google AI Edge 的端侧场景。roadmap 曾把「让 StableHLO 取代 MHLO/HLO 成为编译器接口」「把与硬件无关的优化迁到 StableHLO，使非 XLA 的 PJRT plugin 也能受益」列为明确方向。

7. PJRT：框架与硬件的接口

PJRT 没有独立的产品仓库。官网把它列为生态组件，并写明：PJRT is a hardware and framework independent interface for ML compilers and runtimes. It is currently included with the XLA distribution（openxla.org）。

2023-05-08 开源博客给出的长期愿景是：框架（JAX、TensorFlow 等）只调用 PJRT，设备相关实现对框架不透明；每家硬件专注实现 PJRT API，也可以对框架保持不透明。硬件厂商实现 API、打成含编译器与运行时钩子的 plugin 并注册；框架发现并加载一个或多个动态库；之后就可以把工作负载送到目标硬件。API 计划保持向后兼容。

接口里有什么

PJRT C++ Device API Overview（文档标注更新于 2025-10-28）描述的核心对象包括：

PjRtClient

框架与设备之间的全部通信与状态，拥有该 plugin 的 devices 与 memory spaces。

PjRtDevice / MemorySpace

单设备描述（种类、在设备网格中的位置）以及钉扎 / 未钉扎的内存空间。

PjRtBuffer

设备上的数据，可与宿主 xla::Literal 互转，支持外部引用。

Compiler / Executable

把输入模块变成可执行体；支持序列化，以及 addressable / sharded / portable 等执行入口。

Futures

异步 enqueue，先返回尚未 ready 的 buffer，真正读值时再阻塞。

可选进阶能力

自定义 layout、send/recv、host offload、sharding 等，JIT 基本路径可以没有它们。

对自研芯片来说，PJRT 是官方设计的替换点。本仓库的移植笔记已经据此论证：TorchTPU 把 PyTorch 始终看成 PrivateUse1 设备，但「可以用于任何带 PjRt plugin 的 XLA 设备类型」——只是部分 kernel 仍可能绑定特定物理设备。见 把新 NPU 接入 TorchTPU。

8. Shardy：切分与并行

Shardy 是「面向所有方言的、基于 MLIR 的张量切分系统」。官方概述（Overview）写明：它由 GSPMD 与 PartIR 两个团队合作，吸收两者之长。相对旧路径，文档强调更可预期的用户控制（把 GSPMD 的传播与 PartIR 的增量切分结合起来）、对 reshape 这类容易引入多余通信的算子给出更好的支持，以及更接近 NamedSharding 的轴切分表示，便于阅读和调试。

组件

  • Sharding representation：绑定到某个逻辑 mesh，用轴名描述每个维度如何切分；支持约束、为 reshape 等拆分轴、优先级（增量切分）等。维度可以是 open（允许传播继续切）或 closed（用户指定即为最终切分）。
  • Compiler API 与传播算法：结合用户优先级、算子优先级和代价模型 / 启发式。
  • SPMD partitioner：把传播结果降成 SPMD 程序并插入必要的数据搬运与 collective。官方概述的短期方案是复用现有 GSPMD SPMD partitioner，长期计划是新的基于 MLIR 的 partitioner。本稿无法从公开材料确认「长期 MLIR partitioner」在 2026-11 是否已经完全替换前者，故不强作结论。

与 JAX / 状态声明

JAX 用户指南说，在 Shardy 之前，JAX 把切分指示编码进 StableHLO，再由位于 XLA 管线中段、运行在 HLO 上的 GSPMD 消化；现在 Shardy 在 JAX 中始终启用。切分标注从 GSPMD 那种设备列表形式，变成更接近 PartitionSpec 的 #sdy.sharding<@mesh, [{"data"}, {}]>。

需要同时记下两份官方文本之间的张力：Shardy 首页 仍写 Shardy is a work in progress. The core dialect and C bindings are fully functional. The python bindings are under development.（该页标注 Last updated 2024-12-03）。仓库 README 还写「Currently we are not accepting contributions directly to the GitHub repository」。与「JAX 中已始终启用」并不必然矛盾——生产路径可以已经接通，而独立仓库的绑定与贡献流程仍在收紧——但读者不应把「WIP」四个字忽略掉。

9. Tokamax：自定义 kernel 库

Tokamax 是自定义加速器 kernel 库。官方页面（openxla.org/tokamax，标注更新 2026-10-06）把它分成两根支柱：面向最新开源模型训练 / 推理的优化算子组合，以及 autotuning、低开销 benchmarking、共享 API 下多实现等基础设施工具。kernel 通常建在 JAX 与 Pallas 上，并在 TPU 上提供原生 PyTorch API，以便和 TorchTPU 一起使用。安装入口是 pip install -U tokamax。

文档明确提到会针对下一代硬件做主动优化，举例包括 TPU v7 Ironwood、NVIDIA Blackwell 以及即将到来的 TPU v8 系列。Fall 2025 DevLab 介绍时，已提到 MaxText 用其 kernel 在当时新宣布的 Ironwood 上做高性能演示，以及 DeepMind 科学模型在 GPU 侧使用这些 kernel；同时仍称官方正式发布还在路上。到本稿基准日，仓库与文档都已相当具体，supported ops 页标注更新于 2026-11-21。

公开算子组合（据 2026-11-21 文档，不穷尽抄表）

Attention 变体

Splash Attention、paged / ragged paged attention、标准 FlashAttention、Kimi Delta Attention / Gated DeltaNet，以及面向 DeepSeek-V4 / GLM-5.2 等的一系列 MLA / indexer / top-k / SparseMLA 构件。部分标为 experimental（FlexAttention、MoBA、NSA、RWKV-7、Raven 等）。硬件覆盖以 TPU 为主，部分算子同时支持 GPU。

MoE 与杂项

grouped matmul（ragged_dot）、token gather / scatter、router top-k，以及若干 fused MoE（部分 experimental）。另有融合的 linear+softmax cross-entropy、mHC、GPU 上的 GLU / normalization、AlphaFold 风格的 triangle multiplication、experimental 的融合 FP8 matmul 等。

表格里单独标出了哪些算子提供 PyTorch TPU API、哪些有反向。这是它和 TorchTPU 栈最直接的连接点：常见 LLM / MoE 构件可以不手写 kernel，直接走生产就绪的 Tokamax 路径——这一点与 代码分析笔记第 11 节 的分类一致。

10. XProf：性能分析

XProf 是面向现代 ML 栈的性能分析工具，官网称其适用于 JAX、TensorFlow 和 PyTorch/XLA，帮助理解并优化 TPU 或 GPU 上的应用（文档）。安装：pip install xprof，另有 xprof-nightly。也可与 TensorBoard 一起使用。Google Cloud 推荐用 xprofiler 在云上收集与查看 profile。

Overview

宿主与全部设备的聚合视图：step time 分解、逐步耗时曲线、运行环境摘要。

Trace Viewer

时间线：每个 op 的时长、在宿主还是设备上执行、设备间通信。

Memory Profile

监视模型内存使用。

Graph Viewer

可视化模型的 HLO 图结构。

README 还提到分布式 XProf（多 worker 聚合）以及 Kubernetes 部署指南。截至本稿，GitHub 上最近的正式 release 标签包括 2026-09 的 xprof-v2.23.2。仓库未关闭 issue 数量很多（约 600），其中应同时包含功能请求与历史条目，不宜直接等同于「有 600 个严重缺陷」。

11. XLA Serving Engine

XLA Serving Engine（XSE） 是面向 OpenXLA 生态的 C++ 推理运行时和模型打包工具。官方一句话是：从 JAX（Flax、Keras 3 或普通 jax.jit）或经 torchax 的 PyTorch 导出一次，然后在 CPU、NVIDIA GPU 或 Cloud TPU 上用同一份自包含制品服务，请求路径上没有 Python。文档在 xla-serving.readthedocs.io。Python 导出包：pip install xla-saved-model。预构建服务镜像发布在 us-docker.pkg.dev/xla-serving-engine/xla-serving/，覆盖 CPU、CUDA 12/13 与 Cloud TPU。

设计要点

  • 导出走 jax.export，直接捕获 StableHLO 与 Orbax checkpoint，不经过 ONNX 或 TensorFlow 图转换；并声称完整支持自定义 XLA call、Pallas kernel 与多设备切分。
  • 独立 C++ 进程处理 gRPC、动态组批、宿主侧预/后处理，以及 PJRT / IFRT 设备执行，避免 GIL 与庞大的 Python 运行时。
  • 同一导出目录可携带 cpu / cuda / tpu 的 lowering；可在本地 CPU 上验证，再部署到 GPU 或 TPU 容器。
  • 组批、warmup、宿主特征流水线、可选 AOT 可执行体打进制品，而不是散落在一组服务器 flag 里。
官方把适用面写得很具体：推荐 / 排序、视觉与多模态编码器、encoder 风格语言模型，以及短且固定步数的解码（例如几个 token 的 beam search）——这些场景里请求延迟和单次查询成本更关键。它不是带 paged KV cache 的连续批处理 LLM 引擎。长文本开放生成应使用 vLLM（含 vllm-jax / vllm-torchtpu）或 SGLang（含 sglang-jax / sglang-torchtpu）。

2026-11-05 的开源宣布给出一组内部对比数字：短请求上，XSE 达到「所能构建的最好 Python 服务器」吞吐量的 2–5 倍，相对「直白的」Python 服务器达到 8–36 倍，每预测 CPU 时间少 30–70%，内存约为四分之一。这些数字来自官方博客，不是本稿复现的基准。仓库结构上分为导出库 xla_saved_model（含 xsm-cli）、用于进程内校验的 Python runner、宿主预处理库，以及 C++ Interpreter / batch scheduler / gRPC 服务器。

12. 次要仓库与历史分叉

openxla/triton

这是给 OpenXLA 使用的 Triton 分叉，不是对外产品。XLA:GPU 文档把 Triton 当作 matmul / softmax 等高级 fusion 的代码生成层；该分叉让 XLA 可以钉住自己需要的 Triton / LLVM 版本。跟踪 XLA:GPU 性能时需要意识到这条依赖，但不必按独立项目做周报。它与上游 triton-lang/triton 的具体分叉差异，本稿未做逐提交对比。

community 与治理

2022–2024 年的 RFC、会议纪要存放在已归档的 openxla/community。当前对外沟通渠道以 openxla-discuss、Discord 和 openxla.org 为主。XLA README 仍提到「在 TensorFlow 治理之下，SIG OpenXLA 的社区空间遵循 TensorFlow 行为准则」——这说明治理叙事还带有从 TensorFlow 拆出时的痕迹。社区文档整体迁到了哪里，公开页面没有给出单一说明。

IREE：曾经在栈内，现在在组织外

2023-03-08 的开源宣布把 IREE 与 XLA、StableHLO 并列。约一年后 IREE 迁出 OpenXLA 组织（维护者 2024-01-14 的公开声明）。StableHLO 文档至今仍把它列为消费者，这是 IR 层的互操作，不再等于「同组织项目」。写 OpenXLA 现状时，不应再把 IREE 算进 openxla 组织的主要仓库，也不应假装这条历史不存在。

13. TorchTPU：当前状态与栈内位置

TorchTPU 是 Google（与 Meta 联合推进）的 PyTorch TPU 后端，仓库在 google-pytorch/torch_tpu，用户文档在 torchtpu.readthedocs.io。它不属于 openxla 组织，但深度依赖这条编译栈。设计叙事见 论文分析；实现细节见 开源代码分析。这里只补当前公开状态、能核实的能力，以及和 OpenXLA 的接口关系。

13.2 官方 README 列明的能力

  • 为 TPU 提供 PyTorch ATen kernel 实现。
  • 针对 XLA computation 的编译缓存。
  • 分布式训练：Data Parallelism、Tensor Parallelism。
  • 示例覆盖 Llama、Qwen、ResNet、DLRM、minGPT、UNet 等。
  • 与 torch.compile() 集成，用于图模式执行。
  • 调试与基准工具。

这些是仓库自己的功能清单，没有夸大成「任意模型、任意并行策略都已生产完美」。更细的执行模型、缓存层级、动态形状规则，以代码分析笔记为准。

13.3 它在 OpenXLA 栈里处于哪一层

代码分析笔记的核心判断仍然成立，且与当前 README、移植笔记相互印证：

  • 本质是语义翻译层，不是 kernel 库。 它把 PyTorch 的命令式、可变、指针语义，映射到 XLA 的声明式、不可变、SSA 世界，并且不修改 PyTorch 源码。设备通过 PrivateUse1 dispatch key 改名为 "tpu"。
  • 降低目标是 StableHLO，运行时是 PJRT，编译器是 XLA。 团队刻意少写图优化（分析时 csrc/mlir/passes 只有少量 pass），fusion / tiling 交给 XLA。自定义高性能算子走 Tokamax 或 Pallas（jax_op），而不是在 TorchTPU 里再造一套编译器。
  • 不复用 PyTorch/XLA（torch_xla）的代码。 二者共享的是下层 OpenXLA 组件（XLA、StableHLO、PJRT、libtpu）。官方 FAQ 把三者区分为：PyTorch/XLA 拦截在 C++ ATen 的惰性图并降到 HLO；TorchAX 在 Python 层降到 JAX；TorchTPU 走 PrivateUse1，直接构造 StableHLO，核心路径不依赖 JAX 运行时（Pallas 仅在 trace 时用到）。
  • torch.compile(backend="tpu") 复用 Dynamo → AOTAutograd 的前半段，只在生成设备代码时换成 XLA，而不是做一个 Inductor 后端。

图 2 · TorchTPU 与 OpenXLA 组件的关系：翻译与设备伪装在上，编译与切分在下。

13.4 Eager、编译与动态形状（只记边界）

论文分析把产品策略概括为 Eager First：先提供与 CUDA 心智模型接近的 eager 体验，再在需要时用 torch.compile 吃到 XLA 的整图优化。三种 eager 模式、以及「形状不是免费的」（例如 head 维度与 TPU 矩阵乘法效率）的讨论，见该笔记，此处不重复。

动态形状方面，代码分析笔记依据项目文档指出：XLA 传统上要求编译期形状已知，TorchTPU 用有界分桶而不是任意动态形状来吸收 KV cache 增长；存在桶数量上限、对齐约束、与部分 Pallas kernel / 某些 compile 标志不兼容等硬边界。2026 路线图（论文分析第 7 节）把降低动态序列长度 / batch size 触发的重编译、以及标准算子的预编译 TPU kernel 库列为方向。这些是「已知限制」，不是已经消失的问题。

13.5 分布式与生态集成

README 确认支持 DP 与 TP。更深的矛盾在代码分析笔记第 10 节：XLA/TPU 通信栈假设 SPMD（各 rank 执行相同 StableHLO，collective 必须匹配），而 PyTorch 允许 MPMD 式分叉。项目用 skinny collectives（默认，在 collective 处切开）、@spmd_safe 融合，以及跨 rank 的 compilation handshake 来折中。通信本身并不另起库，而是降成 stablehlo.all_reduce 等，交给 XLA 做计算-通信重叠。

生态上，当前能从公开材料核实的连接包括：

  • Tokamax 为部分算子提供 PyTorch TPU API，面向 TorchTPU 使用场景。
  • XSE README 把长文本 LLM serving 指向 vllm-torchtpu、sglang-torchtpu；XSE 自己的 PyTorch 导出示例走的是 torchax，不是把 TorchTPU 训练图直接变成 XSE 制品。三条路径不要混为一谈。
  • 论文分析提到的 2026 路线图还包括与 Helion DSL、vLLM、TorchTitan 的集成，以及多队列支持。路线图是方向声明，是否已经全部落地，需要看当时仓库与文档，不能把博客里的「计划」写成「已支持」。

13.6 对自研芯片读者的含义

移植笔记的判断可以直接引用：TorchTPU 对某一代 TPU 的硬编码比表面看起来浅，真正的硬件耦合集中在少数接缝，其中 PJRT plugin 是官方替换点；算子层大部分是设备无关的 StableHLO 构造。但 TPU 专有硬件语义、特定 custom call、分布式拓扑假设，以及「能跑不等于同样快」，仍然是真实障碍。若目标是新的 NPU，应先做 StableHLO 兼容性审计，而不是长期维护一个巨大 fork。细节见原文，不在此展开清单。

14. 能力边界与未决问题

把前面各节里「现在就能用」和「不要误读」的部分收拢如下。

已经相当稳的部分

StableHLO 作为框架↔编译器合同（含多年兼容承诺）；XLA 对 JAX / TensorFlow / PyTorch 前端的生产级编译；PJRT 作为硬件接入面；CPU 与 NVIDIA GPU 一等后端，以及上游 ROCm 路径；JAX 中的 Shardy 切分；XProf 作为通用分析工具。

仍在快速成形的部分

Tokamax 的算子组合与多硬件覆盖（大量条目仍标 experimental）；XSE 作为 2026-11 刚对外宣布的 Serving 组件；TorchTPU 在开源后的 API 表面与版本节奏（PyPI 已到 0.3.0，正式 GitHub Release 说明却很少）。

不要期待这条栈单独解决的问题

开放域、连续批处理、paged KV 的长文本 LLM serving（官方把这交给 vLLM / SGLang）；任意动态形状而不重编译；在 CUDA 上「免费」的 view / 原地写入，换到 TPU 上仍有同样的性能语义。

文档与实现可能不同步之处

Shardy 首页的 WIP 声明 vs JAX「始终启用」；XLA README 仍提及 TensorFlow 治理；IREE 已离开组织但仍出现在 StableHLO 消费者列表。引用时应对着日期读。

15. 资料里不确定或找不到的地方

下面这些是本稿明确没有写死、或公开材料不够的点，避免把推断写成事实。

  • openxla/xla 树内 xla/backends 可见 cpu / gpu / interpreter 等目录，没有同级的 tpu 目录。TPU 代码生成与运行时有多少位于公开树、多少位于闭源 libtpu，没有找到官方的完整划分说明。
  • Shardy 的「长期 MLIR-based SPMD partitioner」是否已经完全替换短期沿用的 GSPMD partitioner，公开概述没有给出 2026-11 的明确切换声明。
  • StableHLO 在 2024-05-14 的 v1.0.0 之后，GitHub Releases 未见后续带说明的正式版本；版本以仓库内的 weekly bump 为准。本稿没有再去核对 Version.h 里的当前精确版本号。
  • torch_tpu 的 GitHub Releases 为空，仅有 tag v0.2.0；PyPI 已发布 0.3.0，但没有找到对应的正式 changelog，因此不能核实 0.3.0 相对 0.2.0 增加了哪些能力。已有静态分析笔记也尚未覆盖 2026-10-26 之后约一个月的提交。
  • 2023 年 RFC 提议创建的 openxla/openxla-pjrt-plugin 仓库，当前组织列表中不存在。PJRT 现居于 xla 仓库；该独立仓是否曾经建立后又合并，未再追提交历史。
  • openxla/community 归档后，RFC 与会议记录的「现行」存放位置，公开站点没有单一入口说明。
  • XProf 仓库 created_at 为 2020-03-10，早于 OpenXLA 组织。它应是迁入或由 TensorFlow Profiler 一线演化而来，但迁入 OpenXLA 组织的准确公告日期未核到。
  • openxla/triton 与上游 Triton 的功能差集、以及 XLA:GPU 当前构建是否仍必须对该 fork 而不是上游，本稿未做构建系统级核对。
  • XSE 宣布中的 6M QPS、2–5× / 8–36× 吞吐量等数字来自 Google 官方博客，不是第三方复现，也未给出可公开重跑的完整实验配置。
