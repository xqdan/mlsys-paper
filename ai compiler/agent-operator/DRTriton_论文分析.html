DRTriton：先合成可验证的 PyTorch 程序，再把 7B 模型训成 Triton 翻译器

和大规模调用通用智能体去搜 kernel 不同，这篇走的是“训练一个小的专用模型”。标题里的 92% 要连着测试时搜索一起读；没有搜索时，二十算子程序的通过率是 0。

1. 一句话结论

DRTriton 从 Qwen-2.5-Coder-7B-Instruct 出发，先用 2,026 对由 DeepSeek-R1 或 GPT-5.2 生成并经过校验的单算子 PyTorch–Triton 样本做 SFT，再在 100,000 个合成 PyTorch 程序上做课程强化学习，训练出一个把 PyTorch 翻成 Triton 的 7B 模型。配上把长程序切成片段、再挑最快合法组合的测试时搜索后，它在 KernelBench Level 2 上有 96% 通过验证，其中 92% 快于 PyTorch eager、56% 快于 torch.compile。

这和“再做一个能在 B200 上搜出 7,000 行 CUDA 的智能体系统”不是同一条路：它试图把能力训进一个可重复部署的小模型里。代价是算子集合目前只有 61 个，后端固定为 Triton，而且长程序的高通过率主要来自测试时搜索，不是模型一次写出整个融合 kernel。

2. 问题：真实 Triton 数据又少又难控

手工写高效 CUDA 仍然贵，Triton 降低了门槛，但写出快的 Triton 同样要试错。用 LLM 做 PyTorch 到 Triton / CUDA 的翻译，通用模型在相对简单的任务上就已经不行。先前工作（如 AutoTriton、TritonRL）从公开仓库收集成对数据，作者指出两个硬限制：规模不够（文中举例是 14k 和 11k 条）；难度和质不可控，稀疏奖励下如果过早喂难题，模型会长期拿到零奖励。

DRTriton 的对策是不依赖“找到足够多的真实 Triton”，而是先收集 61 个常用 PyTorch 算子（包含 KernelBench 用到的那些），把合法程序生成写成有向无环图上的约束满足问题，再用课程 RL 从易到难训练。

3. 做法：CSP-DAG、课程 RL、测试时搜索

3.1 CSP-DAG

程序被表示成 DAG：边是形状待定的张量，节点是算子。节点分两类：OpCompute 吃张量、出张量；OpCreate 无张量输入、只创建张量。生成时维护候选张量列表，迭代加入计算节点；输入不够就插入创建算子。形状和广播约束交给 CP-SAT 求解。作者认为这种扁平、一行一个算子的形式，接近 torch.export 降下来的函数式 IR，所以后面能把 KernelBench 里面向对象的模型先导出再翻译。

3.2 校验器

一个 Triton 翻译被算作正确，需要同时满足：语法有效（至少有一个 @triton.jit，并能编译）；忠实性（用 monkey-patch 把 kernel 换成空操作，防止模型直接复述 PyTorch 却宣称自己写了 kernel）；正确性（从对应 PyTorch 程序构造 5 组随机输入，输出必须与 PyTorch“精确匹配”——原文用的是 matched precisely）。

3.3 SFT 冷启动与课程 RL

SFT 只用 Level 1（恰好一个 OpCompute）程序，由 DeepSeek-R1 或 GPT-5.2 生成 Triton 并经过校验，最终 2,026 对、覆盖 61 个算子，10 个 epoch，学习率 2×10^{-6}，批大小 64，大约 2 小时。

随后的 RL 不用把正确性和速度揉成一个稀疏标量，而是用 DRPO：提高正确输出的对数似然，并用速度奖励给它们加权；压低不正确输出的对数似然；再加上信任域式的 KL 约束。速度奖励定义为 PyTorch 与 Triton 执行时间之比的函数，消融里对数形式好于幂函数。课程上，当前难度在留出程序上的 Pass@1 超过 50% 就升一级，实验中在 Level 5 停止升级。实际训练分三阶段：Level 1 20k、Level 2 60k、Level 5 20k，共 100k 个合成程序，学习率 1×10^{-6}，每条提示 8 个 rollout，8×H100，大约 10 天。

3.4 测试时搜索

当程序太长、难以写进单个 Triton kernel 时，把长度为 n 的算子序列切成所有长度 1 到 min(5, n) 的连续片段，共 O(n) 个。模型为每个片段生成 kernel 并校验，再用通过的片段替换原程序中对应部分，其余算子仍走 PyTorch，最后在这些混合实现里选最快的一份。这保证最终方案在已验证选项里最快，但并不试图穷尽非连续或更复杂的融合。

4. 合成基准：搜索决定覆盖，RL 决定速度

合成测试集是 400 个与训练无重叠的程序：Level 1 / 2 / 5 / 20 各 100 个。指标有三项：通过校验的 Acc；既正确又比 PyTorch 快的 Faster1；以及几何平均加速——只在成功题上算（Success），或失败记 1 倍后对全部题算（Full）。

把同一套搜索套到不同检查点上，可以分开看模型和搜索的贡献（合成基准）：基模型加搜索在 Level 20 已有 81% Acc，但全基准 Full 加速只有 1.03 倍，Level 1 / 2 的 Faster1 不超过 14%。第一次 DRPO 就把 Full 加速从 1.05 倍（仅 SFT + 搜索）拉到 1.29 倍，Level 2 Faster1 从 14% 到 62%；后两阶段再到 1.51 和 1.53 倍。作者的判断是：测试时搜索主要提高覆盖，最终速度主要由 RL 训出来的模型决定。Stage 2 在 Level 1 / 2 最好，Stage 3 的平均加速最高。

5. KernelBench：先分清带不带搜索

KernelBench 提供的是面向对象的 PyTorch。评测时先用 torch.export 降成与合成数据同构的扁平函数式 IR，再做测试时搜索，速度同时对比原始 PyTorch 和 torch.compile。表中 TE 是快于 Torch Eager 的比例，TC 是快于 torch.compile 的比例；Acc 与 Faster1 的单位都是百分比。

摘要写“DRTriton-7B 在 KernelBench Level 2 的 92% 任务上相对 PyTorch 有加速，GPT-5.2 为 23%，Claude-Sonnet-4.5 为 19%”。分母里的 92% 来自 DRTriton + 测试时搜索，而 23% 和 19% 来自两个通用模型不带搜索的 TE。更整齐的对照是同样加搜索的 Claude-Sonnet-4.5：Level 2 上 Acc 同为 96%，但 TE / TC 是 68% / 42%，低于 DRTriton 的 92% / 56%。Level 1 上 Claude + 搜索的速度比例反而更高（TE 41% / TC 30% 对 17% / 12%）；Level 3 上 Claude 与 AutoTriton 加搜索的 Acc 都是 86%，高于 DRTriton 的 76%，Claude 的 TE 也更高（64% 对 54%），DRTriton 只在相对 torch.compile 的比例上略高（34% 对 30% 和 20%）。作者强调这是 7B 开放模型取得的结果。

Level 1 加速偏弱，论文的解释是这些单算子在 PyTorch 里已经优化得比较好。在 Stage 1 的同一 SFT 检查点上，DRPO 在 Acc 和 Faster1 上稳定优于把正确性与速度加在同一个奖励里的 GRPO。

6. 落地可行性

如果目标是得到一个可反复调用、不必每次都请前沿智能体团队的 PyTorch→Triton 翻译器，这条线比 CompoundingKernel 一类的大规模搜索更像产品形态：7B 模型、8 张 H100 上大约两小时 SFT 加十天 RL，测试时搜索是模型无关的，也可以套到别的模型上。把 KernelBench 先 torch.export 再翻译，说明它默认工作在静态、可导出的图上，这和许多推理编译流程是对得上的。

落地时要先接受几个边界。

  • 算子集合只有 61 个。作者在结论里把扩展稀疏算子、自定义 CUDA 扩展、以及直接生成原生 CUDA，列为重要后续。超出这个集合，CSP-DAG 和课程数据都不会自动覆盖。
  • 长图几乎离不开测试时搜索，而且融合被限制在长度不超过 5 的连续片段。没有搜索时，二十算子合成程序的通过率是 0。部署时要把“一次生成一个大融合 kernel”的预期改成“片段翻译 + 组合选择”，并承担多次生成和多次计时的成本。论文没有把 KernelBench 上的测试时 token 数或延迟写成与训练开销并列的数字。
  • 对照摘要时容易看高。如上一节所述，92% 对 23% / 19% 不是同等测试时计算下的比较。更稳妥的读法是：在同样加搜索时，7B 模型在 Level 2 融合上快于 Claude-Sonnet-4.5，在 Level 1 速度和 Level 3 通过率上并不全面领先。
  • 正确性是 5 组随机输入上的精确匹配，加上反作弊的空操作检查，不是等价证明。数值容差、归约顺序、低精度累加这些在真实模型里常见的问题，正文没有展开成生产级校验协议。
  • 硬件与形状。训练在 8×H100 上；KernelBench 结果没有像 KernelOPT 那样写明卡型和是否固定形状以外的泛化。也没有报告把生成 kernel 接进完整服务栈后的端到端收益。
  • 工件。论文清单称讨论了数据和代码的开放获取，但正文结论没有给出仓库链接；本笔记写作时未把它当作已确认的开源发布。
和同目录已有的 CAKE / FABRICA，以及本次一起收录的 CompoundingKernel、KernelOPT 放在一起看：DRTriton 是“把翻译能力训进小模型 + 用搜索补覆盖”，CompoundingKernel 是“固定大模型 + 海量可靠评测做进化搜索”，KernelOPT 是“对着编译产物做模型级去留”。三条路互补，不要用同一张加速表直接横比。
