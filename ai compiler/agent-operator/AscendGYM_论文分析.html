AscendGYM：给定已经正确的昇腾实现，智能体还能不能在预算内再快一点

48 个来自真实训练/推理负载的 kernel、三档难度；本技术报告只系统评了 Batch 1 的 17 题。约 70% 的模型–工具组合几何平均加速不到 1.2×。STS 把最终加速和“改进来得有多晚”写进同一个分数。

1. 一句话结论

这不是又一个从 PyTorch 定义冷启动生成 Triton 或 CUDA 的榜，而是针对昇腾 NPU 的已有实现再优化基准：每个任务都给出可运行的初始源码，以及从真实训练/推理负载里取出的形状、类型和计算参数。初始套件有 48 个 kernel、分三档难度，但文中系统评估只覆盖 Batch 1 的 17 题。作者报告，约 70% 的被评模型–工具组合几何平均加速低于 1.2×；最大单题加速大约 3.29×（fused_gdn_gating），13 道题上各组合的中位加速仍低于 1.1×。

和昨日仓库里已有的 CompoundingKernel、KernelOPT、DRTriton 相比，它把问题从“会不会写核”换成了“面对已经能用的昇腾 C 实现，在真实形状和明确预算下还能不能榨出可复用的改进”，并用 Speedup–Token Score（STS）把成本和来得晚的改进一起算进去。

2. 问题：生成榜回答不了“再优化已有实现”

KernelBench 评的是按给定 PyTorch 工作负载生成高效 kernel；NPUKernelBench 和 CANN Bench 把类似的生成评测延伸到了昇腾，看编译、正确性和性能。作者要问的是另一件更接近工程现场的事：已经有一份正确实现时，某个智能体能否在可接受预算内、对目标负载再把它加快，并且保持正确。

同一 kernel 在不同输入配置下，优化重点可以完全不同。例如 attention 在 prefill 和 decoding 处理的数据规模不同，组织计算的方式也会变。FlashInfer-Bench 已经用真实推理轨迹说明了输入配置和应用场景的关系。昇腾上还要协调 host 与 device 的编译、在 NPU 上执行和计时。只报最终加速，分不清“几次就找到改进”和“搜了很久才碰上”。

3. 任务怎么从真实负载里抽出来

AscendGYM 把任务分成三批、难度递增：Batch 1 偏基本 kernel 的访存优化，Batch 2 是归一化、量化这类多步计算，Batch 3 针对复杂 attention 和融合（含稀疏 attention）。本报告评的是 Batch 1 的 17 题；Batch 2（17 个）和 Batch 3（14 个）声明留给后续更新。

任务来自在 MindSpeed-LLM、vLLM-Ascend 等框架上做的 profiling，优先抽对负载影响大的瓶颈核。每个测试用例保留部署上下文：目标模型、执行阶段、硬件与并行配置，以及由此得到的张量形状、数据类型和计算参数。被评任务的源码来自 CANN 的 ops-nn、ops-transformer 和 vLLM Ascend；任务包会写明源码版本、测试输入和数值比较规则。基线是任务包随附的初始昇腾 C 实现，在评测环境里测得的延迟作为参照，所有加速都相对这份初始实现。

文中的例子是 AddRMSNorm：取自 Qwen3-0.6B 推理前向的 residual 加法加 RMS 归一化，prefill、无量化、eager、单卡、TP 1、BF16、batch 1、序列长度 32；branch 输出和 residual 形状都是 [32, 1024]，归一化权重 [1024]。该负载下每次前向调用 56 次，占总计算时间 8.77%，进入累计耗时前五。

每个任务提供基线源码、描述输入输出形状的模板元数据、测试输入，以及由对应 CPU 实现生成的参考输出，用来做数值检查和隔离的 kernel 计时。

4. AscendForge 与评测协议

内置沙箱 AscendForge 建在 SandboxFusion 之上，加上 host 侧注册、device 侧 kernel、目标 SoC 和自定义 kernel 包之间的依赖适配，负责候选编译、Python 接口绑定、正确性检查和性能测量。它分成执行与构建、资源编排、开发反馈、部署运维四层，支持 Ascend C 和 Python NPU 后端，并适配 CANN 算子仓库、自定义 kernel 构建模板和 vLLM Ascend 一类工程。客户端打包源码和测试驱动，调度代理按设备数量、SoC 类型和工作组选 worker；测试驱动先验证正确性再采集性能。编译失败、数值失败和性能回退是分开回报的。

模型–工具组合评测用 Claude Code、Codex CLI 和 OpenCode，模型包括 Claude Opus 5、GPT-5.6 Terra、GLM-5.3、Qwen3.5-122B-A10B、Qwen3.6-35B-A3B 和 DeepSeek-V4-Flash。模型评测则固定 Default 工具（文中也称 AuraKernel），在固定工作流下评 GPT-5.6 Luna，并比较 cold、warm、no lessons、code only 四种配置。

每次模型–工具组合运行最多 80 次候选评估，提示里有“探索约 50 个实质不同方案”的软目标；失败提交计入预算，基线测量不计。搜索本身没有硬性的总 token 或墙钟上限。搜索结束后，最终实现再做 5 次额外性能测试，不消耗搜索预算，也不反馈给后续优化。正确性按各任务预定测试脚本和数值误差准则；只有通过全部检查的实现才算有效结果。计时协议是 8 轮执行、3 轮预热，对其余轮次的 device 侧 kernel 时间取算术平均，用 msprof 采集。硬件是昇腾 910C（运行时标识 Ascend910_9392），单次评估占用一张 NPU；软件栈包括 CANN 9.0.1、torch_npu 2.10.0.post2、ccec / Clang 15.0.5，设备栈记录日期为 2026-10-21。

5. STS 和其他口径

STS 在给定 token 预算 Bmax 下，同时看最终加速和每次改进发生时已经花了多少 token：

STS = 100 log2 Sn − 50 Σk (Bk / Bmax) Δgk，其中 Δgk = log2 Sk − log2 Sk−1。Sk 是第 k 次评估之后、通过正确性验证的最好加速；找不到改进时保留参照实现，所以 S0 = 1 且 Sk ≥ 1。第一项奖励最终加速，第二项惩罚来得晚的改进。没有改进时 STS = 0。文中把每任务预算分成 10M、20M、50M 三档，分别称为紧张、适中和宽松。

此外还有 Cost-to-Gain（CTG）：相对某个检查点再提高 1%、5% 或 10% 加速所需的额外 token，达不到记为 +∞；以及 KernelBench 风格的 GM Speedup 和 fastp、累计/平均 token、交互轮次、墙钟时间，还有候选通过率和任务通过率。找不到改进时性能指标会保留初始实现，所以必须和任务通过率一起读：通过率高只说明写出了正确候选，不说明真的变快了。

6. Batch 1 的主结果怎么读

约 70% 的被评模型–工具组合几何平均加速低于 1.2×。作者据此认为，在一大片已有实现上取得可观改进仍然困难。不同预算下的 STS 轨迹也不一样：例如 Opus 5 配 Claude Code 和 OpenCode 在 10M token 时 STS 相近，预算加大后 Claude Code 的性能项继续涨，OpenCode 的额外收益更有限。只看搜完全程后的最终加速，会丢掉“在更紧的预算里已经能拿到什么”。

CTG 说明“单次改进更便宜”和“覆盖的题目更多”不必同时成立。在 50M token、10% 增益目标下，Opus 5 配 OpenCode 与 Claude Code 在已达成题目上的中位成本分别是 3.8M 和 6.6M token，但前者只在题目子集上达到目标（+10% 为 13/17），后者覆盖全部 17 题。因为达成集合不同，更低的条件中位数不能直接说“同一批题上更省”。

Claude Code / Opus 5 和 Codex / GPT-5.6 都让全部 17 题加速，但分别有 7 题和 3 题超过 2×。GPT-5.6 配三种工具都能通过全部任务，几何平均加速却差很多：配 Codex 约 1.69×，配 Claude Code 约 1.05×。正确候选并不能保证可观加速。

任务级上，最好的观察加速大约 3.29×（fused_gdn_gating），moe_gating_top_k 只有 1.17×；13 道题上，各支持组合的中位加速仍低于 1.1×。选中的 kernel 可以有明显收益，但多数题–配置组合的改进仍然有限。

模型评测里，GPT-5.6 Luna 的 warm 配置在三档预算下 STS 都最高：10M 时性能项已超过 cold，成本扣减更小；预算加到 50M 后 cold 能追回一部分，但 warm 仍更高。code only 在三档预算上都优于 no lessons，两者都低于完整的 cold。Default 配置本身也会改变结果。warm 对 CANN 任务会从其他 kernel 导入 5 条策略经验，但不会继承 cold 已经改过的代码或搜索检查点。

7. 落地可行性

如果你已经在用昇腾 910C，并且关心的是“智能体改 CANN / vLLM-Ascend 里现成的昇腾 C 还能不能再快一点”，这套基准比 KernelBench 更贴现场：形状来自真实负载，沙箱按 host/device 的实际构建路径走，还把 token 成本写进分数。代码已公开。

要把它当成可以日常决策或直接指导 NVIDIA 侧搜核的通用标尺，现在还早。

  • 评测覆盖不完整。48 题里只系统报告了 Batch 1 的 17 题，归一化、量化和复杂 attention 还在“后续更新”。不能把 17 题上的 1.2× 结论外推到更难的融合核。
  • 加速口径是相对初始昇腾 C，不是相对硬件上限或官方库峰值。和 SOL-ExecBench 那种对照 t_sol 的读法不同，1.2× 可能离装置上限还很远，也可能已经接近这份初始实现所能改出的空间。文中没有给出与手写极限或官方调优库的对照。
  • 平台绑定紧。计时在 910C + CANN 9.0.1 + torch_npu 上完成。没有 910C 集群就无法复现；结果也不能直接搬到 CUDA / ROCm。
  • 预算不小。STS 分析用到每任务 10M–50M token；搜索最多 80 次候选评估，且搜索阶段没有硬性墙钟上限。复制这张表，先要有能排队编译和上卡计时的昇腾评测服务，而不只是多买 API 额度。
  • STS 是新指标。公式清楚，也确实能分开“终局加速”和“改进来得晚”，但社区还没有统一采用；横向对比时仍应同时看 GM、fastp 和通过率。
对仓库读者的建议：把它读成“昇腾侧、面向已有实现的、带成本的优化基准”，而不是又一份 KernelBench 的 NPU 移植，更不是可以 pip install 进生产编译器的新后端。和同目录里已有的 CompoundingKernel 等生成/搜索工作是互补的：那些论文在 NVIDIA 上从零搜核，这篇问的是昇腾上还能不能改得更快。
