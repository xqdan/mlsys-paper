KernelArmor：测试通过的 CUDA，仍可能在未测到的输入上不安全

用大模型写注解、用扩展后的 VerCors 做 SMT 验证。740 个实例、1,370 个生产级 CUDA kernel 上，11.4% 在给定契约下得证，78.6% 报告带反例的潜在缺陷，10% 无法判定。放进优化回路后，77 条轨迹都能交出已验证的 kernel，几何平均速度是无约束臂的 0.99 倍。

论文：Bodhisatwa Chatterjee, Mohamed Tarek Ibn Zaid, Sana Damani, Siva Kumar Sastry Hari, Christos Kozyrakis. KernelArmor: End-to-End Agentic System for Establishing Memory and Thread Safety for CUDA. arXiv:2611.18754。 提交于 2026-11-11。通信作者 Bodhisatwa Chatterjee（NVIDIA，bchatterjee@nvidia.com）。作者单位为 NVIDIA 与 Stanford。

1. 一句话结论

KernelArmor 要解决的不是“再写出更快的核”，而是让已经写出来、甚至已经通过测试的 CUDA，在显式契约下获得内存安全和线程安全的证明。它用大模型生成前置条件、后置条件、循环不变式和同步注解，再用扩展后的 VerCors（经 Viper/Silicon 落到 Z3）检查；注解被剥掉之后，源码必须与预处理基线逐字节一致。在 740 个实例（1,370 个 kernel）上，它完全建立安全性质的有 84 个（11.4%），报告潜在发现的有 582 个（78.6%），无法判定 74 个（10%）。每个潜在缺陷都带回能触发它的反例。把验证门放进优化回路后，11 道 KernelBench 题、每题 7 条独立轨迹（共 77 条）全部得到已验证 kernel，几何平均加速是无约束臂的 0.99 倍。

2. 问题：动态工具看不到的输入，形式化工具又吃不下现代 CUDA

智能体已经能大规模写和改 CUDA，但测试覆盖取决于用过的输入。Compute Sanitizer 一类动态工具可以抓住执行中见到的越界和共享内存冲突，却不能对未跑到的路径给出“没有这类错误”的结论。形式化验证可以覆盖模型允许的全部行为，可是给优化过的 CUDA 写规格、不变式和证明注解成本很高，SMT 证明也不稳定。

现有 GPU 验证器往往只支持 CUDA 的一个小子集。专家或智能体写的快路径会用到 warp shuffle、cp.async、内联 PTX、张量核指令。验证器若建模不了这些，就只能拒掉最快的核，或干脆不查。把验证器放进优化回路时，还需要能指到源码里失败的安全义务，并分清三种该采取不同动作的情况：像是缺陷、应当修；证明没完成；以及构造超出了验证器模型。

文中的动机例子包括：cache_position = [0,0]、batch = 1、seq_len = max_seq_len = 2 时，不同 block 里对应线程会撞上同一处打包 BF16 cache 项，构成全局内存竞态；以及逻辑视图越界但访问仍落在更大已初始化分配内时，只做分配级边界检查的工具发现不了。

3. 做法：注解智能体 + 完整性护栏 + 扩展 VerCors

流程是：先预处理 CUDA（报告不支持的构造，规范化语法，把支持的内联 PTX 访存降成带显式安全契约的调用）；再由注解智能体根据 VerCors 验证手册做 in-context 学习，提出契约、不变式和同步注解，并在有 host 代码时提取 launch 元数据；剥掉注解注释后与预处理基线做逐字节比对，防止模型在“写注解”时改程序；最后交给 VerCors 检查。失败则用诊断修注解，再过完整性护栏。回路最多 K 轮，结局是三种之一：verified（所需检查都通过）、potential bug（有被验证过的安全证据支持该项发现）、否则 inconclusive。

对 VerCors 的 CUDA 前端、内存模型和同步语义做了扩展，覆盖的能力包括：模板与编译期常量特化；cp.async 的未完成拷贝资源（错配 wait 或过早消费会失败）；按 __syncwarp(mask) 限制在参与 lane 内的权限转移；由 launch 字节数推导动态共享内存边界，并把被修改或取地址的参数建成线程局部副本；保留指针算术的字节偏移（BF16 走 1 步是 2 字节，uint4* 走 1 步是 16 字节）；把打包访问降成标量访问但保留对齐要求；检查 block barrier 的参与和所有权转移；以及为支持的 cuBLAS / cuBLASLt / CUTLASS / WMMA / PTX 操作提供类型化安全契约。当前版本假定外部库实现本身是正确的。作者还改了 Silicon 的权限选择与谓词匹配。

实现上，扩展后的 VerCors 从源码构建，工作流用 NeMo Agent Toolkit 编排，净增约 20.6 KLOC（不含测试），支持 CUDA 13.1。评测里的注解生成和精化全部使用 GPT-6 Astra。验证跑在一台 16 核 Xeon Gold 6444Y、247 GiB 内存的 Ubuntu 服务器上，这是 CPU 侧证明，不是在 GPU 上跑 kernel。

4. 740 个实例上的验证结果

“实例”指一道基准工作负载的一份实现，包含相应 host 代码，并可能有多个 CUDA kernel。三个套件是：SOL-ExecBench 的 64 个实例（46 道题、235 个 kernel）；一份 Optimized CUDA Suite，28 个生产级实现（70 个 kernel），覆盖 attention、归一化、卷积和矩阵运算；以及 KernelBench 的 648 个生成实例（1,065 个 kernel）。

生产级手工/优化套件上得证比例很高（25/28），潜在缺陷主要集中在智能体生成的 KernelBench 上。作者写到，这些潜在缺陷也出现在相对简单的工作负载里（82% 在 activation 类）。整数溢出（311，占 53.4%）和未对齐访问（175，占 30.1%）合起来占主要发现的 83.5%，其余是空指针、非法指针构造和内存竞态。一个典型模式是：包装器接受的输入范围，宽于优化实现对齐或 32 位索引算术所假定的范围。例如 MaxPool2D 里 b * C + c 在提升到 64 位之前按 32 位求值，作者给出能溢出的配置 b = 65536, C = 32768, c = 0。矩阵和融合 GEMM 占 KernelBench 无法判定结果的 75%，作者将其部分归到库建模的限制。KernelBench 平均轮次高于 SOL-ExecBench（每实例 5.35 对 3.92），主要被 60 个用尽 12 轮修复预算仍未证明的案例拉高。

手册消融只做了随机 6 例、每例 16 轮：有手册 3/6 得证，无手册 2/6；两边都能过的两例里，去掉手册后轮次从 6 增到 12、从 7 增到 8。样本量很小，只能说明手册有帮助，不足以单独支撑“手册是正确性的关键”这种强结论。

5. 和现有内存 / 竞态工具比什么

在 cuCatch 的内存安全基准上，KernelArmor 报告 56/56（100%）检出；文中引用的对比数字是 Compute Sanitizer 20/56（35.7%）、GMOD 8/56、GPUShield 24/56、cuCatch 40/56（71.4%），后三列部分来自已发表数字。作者还写到，Compute Sanitizer 会漏掉非相邻缓冲区溢出，cuCatch 仍会漏掉分配内越界；KernelArmor 还发现套件中一处使潜在越界变得不可达的问题。

在 cuHadron 竞态基准上，必须把范围读清楚。范围内指同一次 kernel launch 内的线程之间（含该 kernel 发出的异步拷贝）：KernelArmor 为 14/14，SuperCollider 13/14，Compute Sanitizer 9/14，iGUARD 1/14。范围外是另一 kernel、host 发起的拷贝、另一块 GPU 或 CPU：KernelArmor 对这类竞态是 0/9，但在其中 3 个测试里另外标出了有符号整数溢出；SuperCollider 是 7/9。全套 23 个有竞态测试上，KernelArmor 的覆盖是 14/23（61%，另加 3 个非竞态内存问题），四种无竞态对照上没有误报（0/4）。和动态工具比，它做的是静态分析，不靠跑起来观察竞态，但也因此吃不到跨 launch / 跨设备的交互。ProofWright 在作者扩展后的语料上对 1,370 个 kernel 的支持率为 0%，因为超出了其验证范围。

6. 放进智能体优化回路

回路设定是：Claude Opus 4.8 把 PyTorch 算子换成 CUDA 并优化 8 轮。11 道 KernelBench 题，每题每臂 7 条从零开始的独立轨迹，共 77 条，每条 6 小时预算。Kernel 跑在 NVIDIA A40（48 GB，驱动 590.48.01，CUDA 13.1），时钟锁定 1410 MHz。无约束臂保留最快的正确核；门控臂里，每个将要成为新最优的正确候选必须先通过 KernelArmor，智能体收到失败义务和源码位置、无法完成证明、或不支持构造的说明。门控提示要求核在 host 包装器接受的每个输入上都安全。用回路内计时挑选每条轨迹的最好核，再在单独的基准运行中报告相对 PyTorch 参照的加速。

77 条轨迹上门控臂的几何平均加速是无约束臂的 0.99 倍，且每个被接受的门控核都已验证。无约束臂最终核被验证通过的只有 12/77 条，集中在 ReLU、GELU 和一条 Gemm+GroupNorm+Hardtanh。事后过滤行不通：对无约束臂的产物再做验证，只有 31/77 条还留得下一个核，而且常常是偏早、偏慢的版本——cumsum 是 0.16×，LayerNorm 是 1.74×，而在回路里分别到了 8.3× 量级。文中观察到的修复（64 位或有界的上取整除法、未对齐 float4 视图的标量回退、输入输出重叠检查）没有测到可感知的速度损失。一个具体例子是：一个 6.4× 的 Gemm+GroupNorm+Hardtanh 核因 B * G 在 B = 227 时发生有符号整数溢出被拒，下一轮仍保持基于 cuBLAS 的设计并通过验证。

门控不是免费的。77 条里有 13 条曾拒绝过比最终核还快 1% 以上的候选：7 条是 inconclusive，4 条是潜在缺陷，2 条是不支持的库配置。单次 KernelArmor 运行的中位时间是若干分钟；门控轨迹中位数有 1.45 小时花在 KernelArmor 上，最多 5.3 小时。341 次验证运行中：243 次得证，63 次潜在缺陷，28 次无法判定，5 次不支持，2 次出错。平均成本按 GPT-6 Astra 标准 API 定价估算，约为每实例 29 万 token / 3.58 美元，每 kernel 18.3 万 token / 2.26 美元。

7. 落地可行性

如果你已经在用智能体搜 CUDA，并且担心“基准形状上测过、换个更大或未对齐的输入就炸”，KernelArmor 是目前公开文献里少有的、真正把门放进优化回路、还能几乎保住速度的系统。生产级 28 个实例里 25 个得证，也说明它不是只能在玩具核上工作。cuCatch 全中、范围内 cuHadron 全中，对动态工具做了有意义的补充。

要把它当成发布前的必过闸门，仍有几条硬限制，作者的口径本身也比较克制。

  • 得证是有条件的。表里的 Verified 带星号，含义是在给定的 kernel / 库前置条件下成立。库契约假定外部实现正确；安全保证随着建模假设走，不是对真实 GPU 上全部行为的无条件证明，更不包含数值等价。
  • 大量“潜在缺陷”是包装器输入空间上的溢出和对齐问题，不一定会在基准形状上触发。582 个发现带反例，但优化回路一节写得很清楚：其中一些在基准形状上根本不会触发，测试那些形状暴露不了它们。把 78.6% 读成“八成已发布的核都是现场必现的 bug”会过激；更准确的说法是：许多快路径对包装器声称接受的输入并不安全。
  • 范围外的竞态查不到。跨 kernel、host 异步拷贝、多 GPU、CPU–GPU 统一内存上的竞态是 0/9。需要这类覆盖时，仍要靠 SuperCollider 一类动态工具。
  • 无法判定会挡住更快的核。13 条轨迹里有 7 条是因为 inconclusive 拒掉了更快候选。矩阵 / 融合 GEMM 占 KernelBench 无法判定的 75%。证明失败不等于程序有错。
  • 成本和工具链不轻。中位每个门控轨迹 1.45 小时花在验证上；还依赖扩展后的 VerCors、CUDA 13.1 和 GPT-6 Astra。手册消融只有 6 例。论文给出了 VerCors 上游仓库，但未在摘要里提供一个可直接 pip install 的 KernelArmor 发行。
对仓库读者的建议：把它读成“搜核回路里的安全门 + 现代 CUDA 子集上的分离逻辑验证”，而不是功能正确性证明，也不是可以替代 Compute Sanitizer 做全集覆盖的动态检测。和同目录里 CompoundingKernel 等“把测量做可靠”的工作是同一条线上的互补：一边防奖励黑客和计时偏差，一边防测试覆盖之外的内存 / 并发洞。
