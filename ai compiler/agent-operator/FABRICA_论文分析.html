1. 概述

这篇论文处理的是把 CUDA kernel 移植到 Cerebras 晶圆级引擎（WSE）的问题。CUDA 用 grid/block/thread 和访存模式来表达任务分解、局部性和同步，程序员面对的是一台由运行时负责调度的虚拟机器。CSL（Cerebras Software Language）则要求把代码显式放到 PE 坐标上，自己管理分布式 SRAM、静态 fabric 路由、事件驱动的任务，以及主机与设备之间的符号契约。作者的判断是，这中间隔的不是 API 差异，而是执行模型和观测模型都换了一遍，所以移植是重新构造一个分布式程序，而不是做语法替换。

难点在于 CSL 几乎不在预训练语料里。公开资料基本只有官方 SDK 示例、教程和少量第三方技能笔记，没有社区代码库。作者测下来，前沿模型单次生成在 28 个 Level 1–3 任务上只过 6 个。于是他们做了两件事：一个 49 对 CUDA/CSL 配对任务的基准 Fabrica-Bench，和一个免训练的智能体框架 Fabrica。框架的组成是目标架构知识检索、沙箱执行、按失败类型分流的修复，以及只在程序已经正确之后才启动的周期优化。

2. 两台机器的执行与观测模型

WSE-3 集成约 90 万个计算核和 44 GB 分布式 SRAM，排成二维网格，每个 PE 有本地 SRAM，fabric 路由在编译期静态配置。CSL 把这台空间机器直接暴露出来：layout 程序负责把代码分配到 PE 坐标并配置路由，PE 程序持有本地缓冲、用数据结构描述符（DSD）做批量访存、把任务绑到队列或事件上，再加上主机可见符号和入口点。CUDA 里的 per-thread 实现变成常驻的 PE 分片执行，GPU 内存变成 PE 本地 SRAM 加描述符寻址的缓冲，条件与事件触发变成 color、queue、wavelet 和路由。

论文强调的一点是，两台机器不只跑法不同，能看到的东西也不同。CUDA 开发者用 Nsight 的那套指标推理：带宽占用、访存吞吐、warp 级并行。这些在 WSE 上都不存在，profiler 给的是编译诊断、fabric 模拟器周期数、时间戳计数器、wavelet 与指令轨迹、ELF 内存元数据。两套优化词汇几乎不重叠，「提高 occupancy」对 CSL 没有直接含义，「链式描述符偏移」在 CUDA 里也没有意义，所以在 GPU 上学到的性能知识不能直接搬过来。

3. 三个障碍

论文把动机拆成三条，也按这三条组织后文。第一条是可学的资料太少。CSL 的公开语料基本就是 SDK 示例、教程和几份第三方技能笔记，背后没有社区代码库，前沿模型单次生成只过 6/28。第二条是现有编码智能体是围绕 CUDA 长出来的。作者的实验里，模型能恢复局部算术和单个 CSL 调用，但没法把参数、任务、队列、颜色、集合通信、导出符号和数据传输拼成一份能跑的程序：跨 11 个模型，Claude 系列过 24–26/28，开源权重模型在同一集合上最多过 2；另一个 12 项探测集上，一个开源模型过 1 项，其余五个全零。189 次分类修复中有 130 次是局部 CSL 实现修补，而不是算法层面的改动，说明卡住的是目标语言的写法。

第三条是没有基准测这件事。KernelBench 提供工作负载语义但没有晶圆级目标，SDK 示例提供原生空间机制但没有配对的 CUDA 输入。两边各缺一半，无法判断一个智能体是不是真的学会了架构之间的映射。

4. 翻译中的保留、丢弃与新建

论文用三个动词描述翻译器的职责。跨架构仍然成立的信息要保留，比如依赖关系和 I/O 形状；源架构独有的设计选择要丢弃，比如为 GPU 挑的 block 大小；剩下的从每 PE 计算、fabric 布局到主机接口都得新建。后两件事在源程序里没有任何对应物。

任务分解需要重新推导而不是映射：CUDA 的 block 大小在固定 PE 网格上没有意义，thread 索引要变成 PE 坐标加一个本地循环，所以翻译器得先搞清楚这个 kernel 算的是什么，再挑一种源程序从未包含的分解。通信更彻底，因为没有共享全局内存也没有屏障原语，每次跨 PE 传输都要落成静态路由 color 与队列上的一次 wavelet，线程块屏障要变成一个路由模式加一次任务激活。这也是为什么只熟悉一侧架构的模型会写出看起来合理、实际跑不起来的 CSL。

5. Fabrica-Bench

基准包含 49 对可执行的 CUDA/CSL 配对，其中 31 对来自 SDK 示例和科学计算 kernel，另外 18 对补充了机器学习算子和集合通信。新增部分由模型辅助初译，之后手工接入并端到端验证，论文没有把它们当作独立的专家参考，报告时单独成组。每项任务带 CUDA 源码、经过验证的 CSL bundle，以及记录形状、划分、参考周期、hold-out 种子和构造等级的元数据。

构造等级描述的是需要多少 CSL/WSE 结构，与预期加速无关。这一点在后面的硬件结果里会再出现一次：Level 1 的 ReLU 反而拿到最大加速。

5.1 三种工作流

基准通过控制可见范围和可编辑范围，把翻译、共设计与优化分开，这样可以区分合成失败与优化失败，也能检验一个看起来像算法问题的失败是不是其实来自 layout。

工作流隐藏内容可编辑范围考察目标
W1　固定布局翻译验证过的 compute CSL只有 compute 文件给定 layout 能否写出正确的 PE 程序
W1-C　计算/布局共设计compute 与 layout两者都可改放置与路由需要一起调整的情况
W2　从正确 CSL 优化—已知正确的程序纯粹的减周期能力

基础分 fast_0 要求程序能编译、能运行、数值与参考一致；性能用核内周期而不是模拟器墙钟时间，更高的分数要求达到或超过参考。另有六项完整性检查，分别针对参考泄漏、隐藏评测输入、冻结计时与接口函数、拒绝把计时器关掉的可疑路径、核对数值输出，以及拒绝那些不检查结果就报成功的 runner。

6. 框架结构

一项任务以 CUDA 源码、规格说明和允许的主机–设备接口进入系统，参考隔离防火墙先扣住验证过的 compute CSL 和 hold-out 输入，然后六个阶段按固定顺序执行：分析师恢复每 PE 算法，第二阶段推导源程序隐含的多 PE 通信，架构师把它变成放置与 layout 设计，实现者写出 PE 与 layout 的 CSL，评审者读编译与运行输出并决定下一步由哪个阶段接手，优化器在程序已经正确之后提出减周期的改动。实现上是一个编排器发起六次角色特定的模型调用，而不是六个常驻智能体。确定性的边界负责隔离参考、路由执行失败，以及只在改动仍然有效且中位周期下降时接受优化。

图 5　对应论文 Fig. 3。生成之前还有一个确定性抽取器，只扫描可见文件，取出编译期参数、主机启动顺序、导出符号、layout 拥有的任务与 color 标识、保留队列；另一个选项把 D 解析成 mesh、分片、缓冲、集合、任务、color、队列记录，检查 mesh 是否一致、每 PE 48 KB SRAM 预算和资源冲突。

知识库是这套设计里比较特殊的一环。因为 CSL 基本不在预训练数据里，知识库需要承载语言本身：SDK 文档与发布说明、公开教程与示例、第三方 CSL 技能笔记。检索按角色过滤，架构师拿到分解模式，实现者拿到 CSL 与 API 规则，评审者拿到失败处置方案。这个做法沿用 DocPrompting 的思路，只是在这里它不是补充，而是主要手段。运行记录是 append-only 的，保存提示、候选、结果和周期数，但先前的代码只以经过筛选的聚合经验回流，避免把之前的程序直接当成隐藏基准的答案。

7. 两个例子：GEMV 与 Softmax

论文用一个 512×256 的 GEMV 走完六个阶段。分析师保留了输出行之间的独立性和沿矩阵列的规约；架构师把矩阵铺到 8×8 个 PE 上，广播向量与 bias，按行规约，从最后一列收集结果；编译器反馈先修掉一个参数名写错的问题，之后由原始 runner 验证数值。周期数把各阶段的贡献分得很清楚：第一次正确时是 58,610 周期，三次优化改动之后是 7,861 周期，专家参考是 10,309 周期。这条轨迹取自训练池，与覆盖评测里数值无效的那个固定布局 GEMV 不是同一个案例。

图 6　GEMV-Large 的分解与周期数。第一次能跑的版本代价很高，实际加速来自之后三次经过正确性检查的改动。

另一个例子是 RowParallel-Softmax，它更能说明修复过程本身携带的信息。七次尝试依次暴露出 layout 与 PE 参数不一致、异步任务与描述符错误、分布式规约在数值上不正确、作用域与类型故障。第八次尝试通过三个隐藏种子，用 17,892 周期；之后两次被接受的改动降到 13,688 周期，相对 17,714 周期的参考是 1.29 倍。编译器诊断、数值结果和周期数是接替出现的三类证据，分布式契约不是一次写对的。

也有停在持平附近的情况：GEMM-Collectives-2D 是 48,188 对 51,738 周期（1.07×），GEMV-Collectives-2D 是 4,336 对 4,003 周期（0.92×）。后者正确但更慢，论文用它说明正确性与速度是分开记账的。

8. 验收条件

每个候选都会被 staged：拷进参考 bundle 的一个新克隆，由这个 bundle 自己未经修改的脚本来构建和运行，因此智能体无法改变自己被测试的方式。主机–设备接口是不允许破坏的部分，包括主机驱动、启动顺序、导出符号和 layout 拥有的标识符。记 P 为 staged 候选，H 为其接口，IS 为任务 S 的可见与 hold-out 输入，主验收条件是：

Valid(P, S) ≡ Build(P) ∧ Run(P) ∧ Contract(P, H)
∧ Timing(P, S) ∧ ⋀u ∈ IS Correct(P, u)

五项分别要求编译成功、运行成功、接口保持、计时路径有效（周期计数器确实覆盖了被修改的代码区域），以及在可见与 hold-out 输入上数值一致。只考察正确性的任务里，Timing 仍检查成功关卡但不要求给出周期值。不满足上式的候选不会被记速度分。优化沿用同一条件：若 cj(P) 是第 j 次重复测得的设备周期数，改动 Q 取代当前最优 P 的条件是 Valid(Q, S) 成立，且 Q 的周期中位数低于 P。内层搜索可以不对每个 hold-out 输入都重跑来排序候选，但胜出的改动在被接受前必须过 hold-out 关卡，这样一条又快又错的路径就进不了优化器状态。

9. 正确率与消融

实验协议把任务集、重复次数和尝试上限都写死，不同行的结果不合并统计。主要的对照、覆盖和优化研究用 Claude Opus 4.8 与 SDK 1.4.0 模拟，都在新的 bundle 上跑原始数值检查，训练与测试划分不相交。11 个模型的研究只改生成模型，覆盖三个商业前沿模型和八个开源权重模型，每个模型–任务对只跑一次工作流。GEMM 与 GEMV 留在训练池，因为检索到的 WaferLLM 模式与这两个家族重叠。硬件回放把保留下来的 bundle 在 SDK 2.10 下重新编译，在 appliance 模拟器和 WSE-3 上各测一次。

9.1 完整工作流

在冻结的 28 项核心集上，单次生成通过 6 个（21%），只有一个结果快过参考。完整工作流通过 26 个（93%），其中 22 个达到或超过参考，16 个严格更快。这个差值是检索、多候选、分阶段修复和优化共同作用的结果，后面的受控行才把单个机制分开看。

9.2 目标知识与设计记录

知识消融固定 Sonnet 4.6、评审者和 20 次尝试预算，在 15 项 Level 1–3 面板上跑 45 次翻译。完整知识通过 7 项；去掉检索到的 Cerebras 材料只剩 1 项；再去掉 CSL 入门材料仍是 1 项。多出来的六个成功全部需要集合操作、halo 交换或 DSD 与队列配置，而无知识条件唯一通过的是一个单 PE 的矩阵向量 kernel。也就是说在固定修复预算下，更长的重试环补不回缺失的目标 idiom。

另一侧的结果没有那么符合直觉。把 G/D 设计记录加进提示，无引导条件下保留通过数从 21/40 变成 20/40，有引导条件下翻译阶段成功数从 33/40 变成 32/40。记录让每个映射方案可以被检查，但测到的正确率基本没动。这与第 4 节的说明一致：它们是提示引导，不是编译器保证。

9.3 覆盖评测

49 项全部跑一遍，38 项至少产出一个正确程序（78%）。按来源拆开是：原始 hold-out 14/23，原始训练 6/8，后加入的 18/18，也就是原始集合 20/31、全部 hold-out 任务 32/41。后加入的参考经过手工整合，单独作为一组报告。最后三项做了三种子的补充实验：GEMM-1PE 三次全过，几何均值 7.64 倍；Laplacian2D-Reduce 三次全过，1.78 倍；LorenzoPredictor-Tile 三次过两次，2.36 倍。合起来 8/9，每次通过都快过参考。32 个通过的 hold-out 任务里，28 个周期数低于参考，2 个持平，2 个更高。

49 项中有 47 项选用了通用的单 PE 起步模板，因此论文把覆盖结果解释为「一个稳定的初始结构加上执行引导的修复」，而不是专用模板起了作用。反馈消融那边，起步模板模式在诊断面板上保留 30/40 次最终通过，包含三个最简单 Level 1 算子的全部 15 次重复。

10. 优化与硬件回放

10.1 从已正确的程序出发

W2 以正确 CSL 为输入时，优化器改进了全部 14 个被测参考，几何均值 1.44 倍，其中七个改进至少 25%。这一行把优化空间与翻译成败分开。可优化余量主要在 PE 本地算术上：批量 DSD 操作、融合算术、循环化简和编译期常量能消掉不少工作；库委托和通信主导的计时路径更常停在持平附近。整个反馈引导模式与覆盖扫描里，601 个提议改动中有 110 个（18%）同时过了正确性与周期两道关卡。

图 10　论文 §V-E 的数据。批量 FMAC 被提议的次数最多但通过率最低，说明提议频率与实际收益并不一致。

10.2 模拟器与 WSE-3

冻结的硬件回放集合里有 35 个通过的 bundle 及其参考，都走同一条 SDK 2.10 主机路径。27 对在两个目标上都以可比较的设备内计时通过，其中 23 个生成程序在硬件上更快，26 个达到或超过参考。几何均值从模拟器上的 3.75 倍变为 WSE-3 上的 3.47 倍。这个位移是两个实现之间的相对效应，对目标 t 记 St = ctref / ctgen，则

Shw / Ssim = ( chwref / csimref ) ÷ ( chwgen / csimgen )

生成程序与参考的硬件对模拟器几何均值分别是 1.030 和 0.953，合起来是 7.5% 的整体下降。单个 kernel 的移动可以大得多。DFT 从 10.21 倍升到 10.92 倍，因为它的生成程序在硬件上相对更快（比值 0.934），参考几乎没变（0.998）。Prefix-Sum 从 2.11 倍掉到 1.54 倍，生成程序变慢到 1.111 而参考降到 0.810。ReLU 是最极端的：生成路径从 142 周期涨到 222 周期，参考从 12,299 降到 10,252，加速比因此从 86.6 倍降到 46.2 倍。

图 11　对应论文 Fig. 5 与 Fig. 6 右侧。Level 1 的跨度最大，从 0.97 倍到 ReLU 的 46.2 倍；Level 4 的 RowParallel-Softmax 贴近专家参考。构造等级与实际加速衡量的是程序的不同性质。

10.3 架构映射暴露的边界

Laplacian2D 在执行引导修复下五次全过，无引导条件下五次全败，说明分阶段反馈能把 halo 契约拼出来。Cholesky 更能看出边界在哪。允许编辑 layout 之后，至少五次早期的接口卡死消失了；再加入一个从训练池派生的 collectives_2d 示例，才得到一份能跑的 383 行共设计，九次尝试里五次到达数值检查阶段，对角块通过。这个过程把不可变路由、跨文件连线和操作数投递分成三层，也把最后一层——把分布式操作数送到内部 PE——留成了后续工作。

图 12　对应论文 Fig. 7。扩大可编辑范围先解除接口层面的阻塞，分布式程序还需要一个目标侧的集合通信范例才能拼出来。

11. 运行日志与后训练

每次运行都留下完整日志：提示、每次尝试产出的 CSL、编译与运行反馈、最终结果。导出器把每个产出代码的回合与保存的尝试对齐，然后按一条确定性规则打标签：该回合本身通过记 1；该回合未通过但同一次运行的后续回合通过记 0；其余记 −1。整次运行都失败的日志不进数据集。论文强调这不是学出来的奖励模型。

削减过程是逐步的：1,741 个运行目录中 1,673 个能对齐，最终通过的运行给出 7,619 个监督候选，去掉 306 个重复和 1,247 条超出每 kernel 500 条上限的记录后剩 6,066 条，其中 2,440 条是验证通过的，3,626 条是中间修复。偏好数据要求相同的提示前缀和相邻的「失败到通过」转移，取通过的为正例，去重后得到 2,249 对，并过滤掉过短的回答、疑似参考泄漏和架构重置回合。

图 13　数据管线与 SFT 试点。14B 的 loss 从 0.823 降到 0.639，服务日志加载的是 checkpoint-153 而非基座模型。8B 的结果方向不一致：usable 从 0.38 降到 0.29，vocabulary 从 0.52 降到 0.46，contract 与 chrF 略有上升。

论文对这一节的定位很谨慎：这些是无需 SDK 的结构性代理指标，不是可执行的正确性，生成的程序仍然需要编译、数值检查和设备计时。8B 上出现的退化也提示，容量不足时把修复轨迹和通过样本混在一起微调，可能先学到 CSL 的表面形态而不是契约。

12. 局限与讨论

论文自己给出的工作流建议是：先检索目标知识，PE 本地任务走短路径直接生成，观察到编译、接口或数值失败之后再调用分类修复，只对已验证的程序做周期优化，并且始终在同一目标上用设备内计时来比较。它还明确指出下一步应该是把类型化映射 lowering 成 CSL，而不是继续往提示里堆事实，方向上对齐 MLIR 的晶圆级 CSL 编译工作。

图 14　论文结论中点出的四个中心因素，以及各自对应的实验证据。

12.1 局限

  • 49 项覆盖按「任一调度的工作流通过即算该任务成功」计数，三项用三种子、其余一项一次，得到 38/49 和 8/9 两个数字，分母与核心集的 26/28 不同，不能直接比较。
  • SFT 试点报告的是无 SDK 的结构性指标，不是可执行正确性。
  • G 与 D 可检查但不是 IR，没有 lowering pass 生成 CSL，解析是尽力而为的。
  • 剖面反馈有界且带启发式，包括事件混合、dispatch-span 代理、wavelet 与反压信号、SRAM 估计；交互式调试器、可视化和逐周期轨迹仍是给人用的，没有接成自动信号。
  • 后加入的 18 对参考由模型辅助初译再手工整合，不作为独立的专家基线。
  • 模型研究每个模型–任务对只跑一次，作者自己称之为 preliminary，只支持能力差距的结论。

12.2 与相邻工作的关系

工作起点目标与 Fabrica 的差别
KernelBench 与各类 CUDA 智能体规格或 CUDA仍是 GPU在熟悉的执行模型内优化，观测词汇可以直接复用
KernelCraft规格新兴加速器场景接近，但不从已有 CUDA 出发，也不针对晶圆级网格
UniPar、MLIR lowering中间表示特定领域构造保证更强，代价是每种表示与领域都要扩展编译器
晶圆级 stencil MLIR、WaferLLM领域 IR 或手工实现WSE领域专用；Fabrica 跨工作负载翻译已有 CUDA，靠目标工具链筛掉错的和更慢的候选
CAKECAKE IR仍是 NVIDIA GPU改的是智能体书写的表示与编译器返回的证据；Fabrica 改的是跨机器的程序构造流程

12.3 可以带走的部分

如果要把类似做法用到别的空间架构上，比如近存网格或其它没有共享全局内存的 PE 阵列，这篇论文里比较有参考价值的有三点。一是知识检索的优先级高于延长自我调试：在预训练空白的目标语言上，文档和成功范例补的是模型没见过的通信形状，而重试环只能修局部实现。二是正确性必须先于周期，空间架构上很容易写出路由看起来对但数值已经漂掉的版本，或者把计数器挪到未被修改的区域，两道关卡保护的其实是测量本身。三是同目标测量不能省，整体上模拟器到硬件只掉了 7.5%，但 ReLU 和 Prefix-Sum 单个 kernel 可以差近一倍。

另一方面，工作流能把 Opus 从 6 项提到 26 项，却没能把 gpt-oss-120b 从 2 项提上来。这说明目前跨架构 kernel 生成仍受限于基座模型是否具备写分布式空间程序的能力，脚手架不能替代这一点。
