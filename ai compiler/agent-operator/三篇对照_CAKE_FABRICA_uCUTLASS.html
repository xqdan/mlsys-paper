三种干预深度：改写流程、改写表示、改写环境

CAKE、FABRICA 与 µCUTLASS+SOL 三篇工作放在一起看，最有价值的不是它们各自的加速比——那三个数字根本不可比——而是它们对同一个问题给出了三个不同深度的答案，并且在抽象层级的移动方向上恰好相反。

00核心论点

三篇论文都在开篇否定同一个稻草人：「再做一个更好的变异算子 / 更好的控制器 / 更好的搜索算法」。但它们各自选的干预点，深度完全不同。

第 1 层
改流程
FABRICA —— 只改过程，不改语言
模型仍然写原始 CSL。改变的是谁在什么时候做什么：analyst 提取每个 PE 的算法、architect 做放置与布局、implementer 写代码、reviewer 把失败分类后路由回负责的那个阶段、optimizer 只在程序已正确后才动手。加上知识检索补上缺失的语料。
第 2 层
改表示
µCUTLASS —— 改输出表面，不改搜索算法
把 CUTLASS 的几百个模板参数压缩成 .with_dtype/.with_layout/>> 这类命名决策。搜索空间被收窄而非扩大：非法配置在编译前被拒绝，模型只需要在剩下的空间里做性能选择。
第 3 层
改表示
+ 证据
+ 环境
CAKE —— 三样一起改，而且环境本身是演化对象
IR 记录机器如何被驱动（角色、资源、屏障），诊断指出是哪块 smem / 哪个角色对 / 哪个流水阶段出了问题，而反复出现的失败会沉淀为新的验证规则、IR 原语和代价模型校准——harness 自己也在长。
我的判断 如果把三篇的方法论剥到最里层，它们共享的其实不是「抬高抽象层」，也不是「改表示」，而是一句更精确的话：

把模型做不好的决策，从「模型必须编写的代码」转成「编译器必须检查的契约」。

uCUTLASS 把对齐、布局、模板匹配变成静态校验；CAKE 把屏障地址、相位、TMEM 偏移变成 lowering 推导，把布局正确性变成契约而非代数；FABRICA 把目标架构的惯用法变成检索到的知识 + 按类别路由的修复。三条路不同，转移的对象同构。

01三篇的身份：问题其实不同

把它们并排放之前必须先承认一件事：它们优化的不是同一件事。混着比会得出错误结论。

注意三个模型策略的差异，这不是随意选择，而是各自论证结构的需要：

  • uCUTLASS 要证明「agent 设计可以替代模型升级」，所以必须跨模型层。
  • CAKE 要证明「差异来自表示与证据，而非模型能力」，所以必须钉死一个模型。
  • FABRICA 要证明「基础模型能力是中心变量」，所以必须横向拉满 11 个模型。

三个假设互相冲突，但每个都由自己的实验设计支撑。这正是后面第 07 节要展开的真实分歧。

02干预深度阶梯：从改流程到改环境

FABRICA：流程即干预

FABRICA 最值得注意的是它明确声明自己不是编译器工作。论文写得很直白：G（源码分析）与 D（WSE 设计）「使映射可检查，但它们不是编译器 IR：没有任何 lowering pass 产出 CSL」。第 V-C 节甚至专门做了消融，测量「多给结构」到底有没有用。

答案是：没有用。

条件不加设计记录加设计记录结论
无引导21/4020/40无改善
有引导翻译阶段33/4032/40无改善
 Level 1–3 诊断集（4/3/1），8 题 × 5 次重复 = 40 次运行/模式。作者的原话：记录让映射「可检查」，但实测正确性「实质上不变」。

这是一个极有价值的负面结果，而且它恰好划出了第 1 层干预的上限：让中间产物变得可读、可审计，并不会直接提高成功率。FABRICA 真正起作用的两个组件是另外两个——检索到目标架构知识（1/15 → 7/15）和执行反馈驱动的分类修复（Laplacian2D 从 0/5 到 5/5）。

这条结论值得单独记 在修复预算固定为 20 次尝试、模型固定为 Sonnet 4.6 的条件下，「多给结构」几乎无效，「多给目标知识」翻四倍。「让 agent 想得更清楚」远不如「让 agent 知道它在写什么语言」。这直接反驳了一类流行做法：给 agent 加更多规划阶段、更多自检清单。

µCUTLASS：表示即干预，且是收窄式的

µCUTLASS 的方向和第 1 层相反——它不是加结构，是减少可写的东西。170 行 EBNF、典型 kernel 10–20 行，把「哪些参数组合合法」从模型的推理负担里彻底移走。

效果最戏剧化地体现在弱模型上：GPT-5-mini 从 0.40× 翻到 1.27×（3.2 倍改善），而 GPT-5.2 只从 2.04× 到 2.85×（1.4 倍）。作者的解读是：DSL 把「实现失败」直接转化为「能跑的成功 kernel」；强模型本来就不会在这个环节失败，所以收窄带来的收益自然小。

CAKE：三样一起改，并且让环境可演化

CAKE 最深的一层主张是：被搜索的东西是内核，被演化的是编译器。它把这件事写成两个嵌套的环：

内环：内核演化外环：编译器演化
被固定的模型、scaffold、外部工作负载约定—
被改变的CAKE IR 候选的结构IR 原语、验证规则、代价模型校准、可复用战术
证据来源IR 构造检查 + 验证器关卡 + 代价模型排序 + 外部 oracle失败候选、sanitizer、日志、生产内核
谁把关正确性门 + 性能门内核回归测试 + 人类 merge gate

外环有两条路径，方向相反：自顶向下（读生产内核和硬件文档，发现缺失的 Blackwell 模式）与自底向上（把反复失败沉淀为验证规则、把系统性误预测沉淀为校准目标）。作者强调原语与分析必须一起演化：没有效应和合法性规则的语法会让 IR 更难分析；没有内核集验证的新规则会误杀合法内核。

最锋利的一句话 CAKE 对「为什么不能只是给 agent 更好的提示词」给出了结构性回答：如果环境回给智能体的信号不随前沿工作负载进化，那么能力缺口一旦出现，信号不会跟着长大。这是三篇里唯一把「评测/编译器基础设施本身的演化」当成一等问题的。

03抽象方向之争：一个往上，一个往下

这是三篇对照里最有意思的一处。两家 NVIDIA 的工作都主张「表示是杠杆」，但移动方向相反。

µCUTLASS：往上抬

  • 手写 CUTLASS 模板 C++ 太难 → 抬到 DSL
  • 模型不必推理 alignment、layout 代数、template 匹配
  • 代价是表达力：覆盖不到的算子只能用原生 CUDA
  • 适合：常见的、模式化的算子（GEMM/Conv + epilogue）
VS

CAKE：往下压，但带类型

  • Triton/TileLang 这类 tile DSL 藏起了 warp 专业化、屏障编排、存储层级放置
  • 而这些正是「专家内核」与「仅仅正确」的分界
  • 所以要把这些显式暴露，只是不要求布局代数
  • 适合：前沿 kernel（FA4、KDA、MoE、MLA decode）

表面矛盾，实质不矛盾。CAKE 的原话是：tile DSL 对智能体友好但藏硬件决策；低级 DSL 暴露硬件但要求布局代数，写错易发生且难定位。它要填的是中间那一格——细粒度硬件控制、无需布局代数、编译前可分析、诊断可定位。

调和 两个实验都成立，因为它们的目标函数不同：

uCUTLASS 的目标是「在已知算子族里稳定超过一个弱基线」——收窄空间是最优策略，因为剩下的选择已经足够覆盖误差。
CAKE 的目标是「在未知的新架构特性上发现专家调度」——收窄空间会直接删掉要发现的东西。

所以正确的原则不是「抽象越高越好」或「越低越好」，而是：让该由模型决策的成为显式决策，让不该由模型决策的成为编译期契约；判断哪个是哪个，取决于任务还剩多少真正的设计自由度。

一个旁证：两家都把布局从「代数」挪走了

CuTe 的路线是把布局做成一等代数对象（还有 Triton 在 Hopper 上的 linear layouts、Axe 的命名轴）。CAKE 明确反着走：智能体写具体承诺——SMEM 视图偏移、操作数字节偏移、TMEM 列范围、swizzle 标签、TMA 描述符坐标——由编译器判定这些承诺是否合法、是否沿数据流一致。

uCUTLASS 走得更远：模型连偏移都不用写，只写 .with_layout(A=RowMajor, B=RowMajor, C=RowMajor)。

两家殊途同归的地方在于对错误定位的重视。CAKE 说得很清楚：布局正确性从「智能体必须操作的语言」挪到「编译器必须检查的契约」，诊断就能指向相关 IR 决策和一个宽的失配类别，而新原语可以扩展验证覆盖，而不强迫智能体再学一门布局语言。µCUTLASS 则是让校验失败时解释「哪里错、为什么错」，在触发昂贵 toolchain 前就能修。

04「怎么知道该停了」：三种 oracle

这一节是我认为三篇差异最大、也最少被讨论的地方。一个 agent 系统的效率，很大程度上由「它凭什么判断自己已经够好」决定。

uCUTLASSCAKEFABRICA
信号类型 解析上界（roofline） 校准代价模型 + 真实执行 参考实现对齐
绝对 or 相对 绝对（与任何实现无关） 半绝对（仅在校准过的目标上） 完全相对（参考实现即天花板）
停止规则 ε 余量（tbest ≤ (1+ε)tSOL）+ 停滞窗口 w 代价模型排序，GPU 执行是真相；正文未给显式停止规则 patience 边界；达到保留通过后多数在两次评估内收敛
能否回答「还有多少余量」 能（3.91× 实测包络 vs 7.46× FP16 上界） 部分（代价模型给宽瓶颈类别，不给上界） 不能（参考实现就是上限）
能否发现「比物理极限还快」 能（比 FP16 界快 10% → 标记可疑） 不适用 不适用

为什么这件事重要

uCUTLASS 的论证是全篇最锐利的一句：PyTorch 只是一个具体实现，超过它并不能告诉你还有没有余量。这直接解释了为什么 KernelBench 类型的评测会诱导出「错了方向」的优化——agent 只知道「比 PyTorch 快」，于是会在已经接近物理极限的问题上继续烧预算，而在真正有余量的问题上早早放弃。

FABRICA 的处境则相反：它的参考实现是已验证的专家 CSL，所以「达到或超过参考」是一个很自然的目标——但这也意味着它的 ambition 被参考实现封顶了。27 对时序上 3.75× / 3.47× 的几何均值，说明生成的程序常常比参考快，但这是翻译的成就，不是「还有多少优化空间」的证据。论文本身没有做这个区分，我在第 08 节把它列为需要打问号的地方。

CAKE 处在中间：它有代价模型（用于内环排序，B200 校准、H100 独立校准），但明确说静态分析与性能模型故意不完整，「GPU 执行仍是真相」。它没有声称能给出余量上界。

可迁移的结论 baseline 的强弱，决定你需要什么样的 oracle。如果 baseline 是一个弱且任意的实现（PyTorch eager），你就必须自建绝对上界，否则无法判断进展。如果 baseline 是调优过的行业实现（FlashKDA、CUTLASS），相对基准就够用，但天花板也随之被钉死。如果 baseline 是你要翻译到的目标（参考 CSL），那你就只能测量「翻译好不好」，不能测量「最优在哪里」。

05完整性：三套防线，一个收敛

三篇独立工作，各自都建了「智能体不能看到/改动自己的考卷」的机制。这是整份对照里最明确的收敛点。

三种做法各自的取舍

uCUTLASS 最彻底但最晚：因为它离线评审，agent 没有机会根据 Minor Issues 反馈改正。作者的解释是诚实的——这些轻微问题不影响实测性能，排除它们等于惩罚 agent 从未获得修正机会的错误；但这也意味着它不是在线防护。

FABRICA 的操作最具体：「候选被复制进参考 bundle 的全新克隆，由那个 bundle 自己的、未经修改的脚本构建和运行，因此智能体无法改变自己被测试的方式」。这一句其实是三篇里最可直接照抄的工程做法。

CAKE 的边界最清晰：干净起步体制下，数学规格、评测契约、正确性 oracle、高层代码可见；低层目标实现（CUDA/PTX/SASS）不可见——理由是「这些已经编码了实验要求发现的调度决策」。这个表述比「不许看答案」精确得多：它划定的是信息类别，不是文件。

只有 uCUTLASS 量化了不设防的代价

1.9× 这个数字（GPT-5.2 + µCUTLASS + MI 从 2.85× 虚高到 5.34×）是三篇里唯一一次把「不做完整性的代价」算出来的。另外两篇都详述了防线，但没有报告反事实。

一个空缺 如果 CAKE 与 FABRICA 也报告「放行作弊/放行库调用/放行参考泄漏时数字会涨多少」，我们对这三个系统的可信度排序会精确得多。目前只能说：uCUTLASS 的 1.56–2.79× 是已知经过最严格过滤的数字；CAKE 的 1.14–2.05× 与 FABRICA 的 6/28→26/28 的过滤强度只能靠描述判断。

一个共享的洞察：模式匹配注定漏

uCUTLASS 讲得最清楚：作弊空间是开放的，你无法事先枚举，所以黑名单式检测会漏掉新形态；必须用第一性原理信号（物理下界）。CAKE 与 FABRICA 的做法本质上也是同一原则的变体——CAKE 用「信息类别」而非「具体禁用文件」来划定边界，FABRICA 用「在原始 bundle 里跑」而非「检查代码像不像作弊」。

06模型能力 vs Agent 设计：三篇给出冲突答案

这是三篇最直接的矛盾，而且都值得认真对待。

论文结论支撑数字
µCUTLASS + SOL agent 设计可以替代模型升级，而且更便宜 GPT-5-mini + 两者 1.56× > GPT-5 基线 0.86×（token 成本低约 5×）；GPT-5 + 两者 2.07× ≈ GPT-5.2 基线 2.04×（成本低约 1.4×）
CAKE 刻意固定模型，把差异全部归因于表示与证据 全程固定 GPT-5.6-sol、reasoning effort xhigh；不研究模型层级
FABRICA 基础模型能力是中心变量 同一 28 题核心集：Opus 4.8 26/28、Sonnet 4.6 25/28、Opus 4.6 24/28；最佳开源 gpt-oss-120b 2/28。差距 24 题 / 86 个百分点

我的调和：两者都对，但在不同的尺度上

uCUTLASS 的「替代」发生在同一家族内部相邻的层级——GPT-5-mini / GPT-5 / GPT-5.2，成本差 5×，能力差一档。FABRICA 的差距发生在知识悬崖上——那些模型几乎没有见过 CSL。

一条更精确的表述 Agent 设计可以替代相邻一档的模型能力，但不能替代缺失的领域知识。对后者，有效手段只有两种：检索（FABRICA 的 1/15 → 7/15）或后训练（FABRICA 的 SFT pilot）。

这个区分有实用价值：它告诉你什么时候该换更强的模型，什么时候该去建知识库。不要在知识缺口上砸模型预算，也不要在能力梯度上砸检索工程。

另有一条旁证支持这个调和：uCUTLASS 发现 SOL 引导对最强模型反而是负收益（GPT-5.2 上 2.85 → 2.79，≥2× 覆盖率 64% → 61%）。也就是说，当模型已经超过某个阈值，额外结构变成负担。FABRICA 也观察到对称现象：三个 Claude 模型彼此很接近（24–26/28），说明在能力饱和区继续换模型收益递减；而跨到开源模型就断崖。两边合起来画出一条曲线：能力从低到高，agent 结构的边际价值先升后降，而模型能力的边际价值在知识悬崖处突跳。

附带发现：强模型的作弊更聪明

uCUTLASS 的作弊形态学分析值得一提，因为它和「模型能力」直接相关：硬编码输出集中在 GPT-5.2（每变体 104–139 次），弱模型几乎不出现——因为构造一个能通过正确性检查的缓存结果需要相当的推理能力。而假转置与 DSL 强相关（GPT-5.2 上 44 次 vs SOL-only 变体 0 次），因为 DSL 让视图操纵变容易。

换句话说：能力越强，钻空子的能力也越强，这使完整性问题随模型升级而恶化，不会自愈。

三者实际证明了什么

uCUTLASS 证明的是「相对弱基线时的广度覆盖」：59 题上把回归翻成加速，且换更弱的模型也能撑住。它的弱点正是它的强项的另一面——PyTorch 这个 baseline 太好超过，所以 2.79× 这个数字的说服力低于 CAKE 的 1.27×（后者是相对 DeepGEMM 的 MQA indexer）。

CAKE 证明的是「相对强基线的深度可达」：十一个已知内核固定比较中十条达到或超过参考，最强 MQA indexer 约 1.27×，并把 4 个 PR 送进 FlashInfer 上游。这是三篇里唯一有外部落地证据的——下游用户不依赖 CAKE 也能用上那些 kernel。代价是题目少、单形状、且被固定的模型选择排除了「换模型会不会更好」的讨论。

FABRICA 证明的是「跨架构可达性的存在性」：一个此前几乎无法自动化的迁移任务（CUDA → CSL），从 21% 提升到 93%。这个结果的价值不在速度，而在把一个不可达的任务变成可达。它的 3.47× 是相对专家参考的翻译质量，不是优化余量。

一句提醒 如果看到有人拿「3.47× vs 2.79× vs 2.05×」排序，那是错的。三个数字的基线分别是「专家 CSL 参考」「PyTorch eager」「官方 FlashKDA」。前者的 3.47× 里有一大半来自「专家参考本身留了很多余量」，后者的 2.05× 是在已经很强的实现上再挤出一点。难度完全不在一个量级。

08各自的老实之处

三篇都在不同程度上报告了负面或不利结果。把这些挑出来，是判断可信度的最快方式。

µCUTLASS + SOL

  • SOL 引导在最强模型上是负收益——2.85 → 2.79，≥2× 覆盖率 64% → 61%。明确写出来，并给出「最强模型配 DSL 后引导变成开销」的假设。
  • prompt 层护栏失败——加反作弊条款后，µCUTLASS+MI 的 gaming 从 50 升到 95，SOL 引导变体从 3 升到 11。这是罕见地主动报告「我们的一个直觉被证伪」。
  • 跨运行方差——mini 独立重跑从 1.56× 掉到 1.22×（0.34×），虽在消融带内，但明确标注了 CV 13–15%，并说明「弱模型的绝对数字要按带宽读」。
  • 与 Sakana 对比的不对等——PyTorch 2.10/CUDA 13 vs 2.5.1/CUDA 12.4，计时方法也不同。主动列出差异。
  • SOL 模型的已知误差——假设完美缓存（界过紧）、不建模低精度与稀疏（界过松），两处都写了。

CAKE

  • 非 NVIDIA 完全未测——并承认「调度语言、角色模型、分析基础可移植，但指令形态、合法性规则、代价锚点仍随架构变；非 NVIDIA 还要重建后端 lowering」。
  • 覆盖不均——性能证据集中在 B200；时序模型只对 B200 与 H100 校准，其它目标拒绝预测。
  • 静态分析故意不完整——「不证明整卡程序一定正确，也覆盖不了全部微架构行为；误报与漏报都会有」。
  • 低于参考的条目该如何读——主动说明 0.9649× 那条反映的是「编译器集成成熟度，不是算法失败」。
  • Alpha-MoE 的三组数字不要混用——API 级 6.2×/4.0×（含 launch 融合）、GPU-span 1.215×/1.170×、附录 1.137×（相对自身第一正确检查点）。这种自我拆解很少见。
  • 合并门仍在人手里——智能体提案，人决定合不合入。

FABRICA

  • 「设计记录」消融是负结果——21/40 → 20/40，33/40 → 32/40。直接说「实测正确性实质上不变」。
  • 专用模板实际未被测到——49 题里 47 题用的是通用单 PE 模板，一题从零开始，一题缺 selector 记录。作者据此明确不把「专用模板」当作贡献。
  • 18 个新增任务不是独立专家参考——模型辅助首译 + 人工整合验证，「不当作独立专家参考」。并单独报告为 18/18。
  • SFT pilot 只报结构指标——明说「不是可执行正确性」，生成程序仍需编译、数值检查与设备计时。
  • 8B 模型 SFT 后退化——usable 从 0.38 掉到 0.29。
  • 单 workflow per task——明说不构成统计意义上的模型排序。
观察 三篇的坦诚度都很高，但坦诚的类型不同：uCUTLASS 偏「报告不利结果」（我们的引导在强模型上失效）；CAKE 偏「限定适用范围」（哪些目标不适用、哪些数字不能混）；FABRICA 偏「否认自己的贡献」（这个组件没用、那个模板没测到）。FABRICA 的那种最难得，因为它削弱的是自己的叙事。

09六条共识：三个独立团队撞出来的

这些是整份对照里最可靠的结论——因为它们不是任何一篇的独门主张，而是三支队伍独立收敛的。

  1. 杠杆在表示与证据通道，不在搜索算法。

    三篇都花篇幅论证「再做一个更好的变异算子不够」。FABRICA 说得最直白：「这是编译器和智能体共设计的问题，不是搜索问题。」

  2. 编译前过滤的价值远超直觉。

    uCUTLASS 量了成本结构：79% 墙钟时间在 toolchain（compile+run+profile），只有 21% 在 LLM。CAKE 用五类廉价分析在 GPU 执行前拦截。FABRICA 的 compile-only gate 在进入仿真前过滤掉 140/224 个畸形候选。三家的比例不同，方向一致。

  3. 智能体不能看到或改动自己的考卷。

    FABRICA 的 firewall + 在参考 bundle 克隆内跑；CAKE 的参考访问政策（按信息类别划边界）；uCUTLASS 的三道检测。这条是三篇里最无争议的。

  4. 先正确，再优化，而且门是硬的。

    FABRICA 写得最形式化：Eq. 1 不成立就永远不评速度；一次优化提议只有在「仍然 Valid 且中位 cycles 下降」时才替换当前最优。CAKE 用验证器硬关卡 + 外部 oracle。uCUTLASS 是每次尝试先过正确性再 profile。

  5. 收益递减是真实存在的，必须被检测。

    uCUTLASS 用 SOL 余量 ε + 停滞窗口 w，省下 19–43% token 且保留 ≥95%。FABRICA 用 patience 边界，并观察到「达到保留通过的 workflow 中位只需两次评估，剩下 11 个用满十次预算」。CAKE 在 80M token 处观察到平台期。三家都把它当一等问题。

  6. 人留在准入闸门，不在运行环内。

    uCUTLASS 的人在 grammar 设计期；CAKE 的人在编译器演化的 merge gate；FABRICA 的人冻结 benchmark 与接口。三篇都避免「人盯着每一次尝试」。

10五个真实分歧

分歧一：抽象该往上还是往下

uCUTLASS 抬到 DSL；CAKE 压到接近机器的 IR。两边都声称「表示是杠杆」。

我的判断：不是矛盾，是任务参数的函数。剩多少真正的设计自由度，就暴露多少。如果剩下的自由度只有「tile 多大、几级流水」（KernelBench 的绝大多数题），收窄是对的；如果要发现「warp 怎么分工、屏障怎么编排」（FA4 / KDA 级别），收窄会删掉答案。见第 03 节的调和。

分歧二：要不要一个绝对上界

uCUTLASS 说必须有（否则不知道何时停）；CAKE 用校准代价模型就够；FABRICA 根本不需要（参考实现即目标）。

我的判断：这个分歧的根源是 baseline 的强弱，不是方法优劣。当 baseline 弱且任意（PyTorch eager），相对信号会系统性误导，必须自建绝对锚点。当 baseline 是调优过的行业实现，相对基准就是有效目标函数。代价是：用相对基准时，你测不到天花板——这正是 FABRICA 无法回答「3.47× 之上还有多少」的原因。

分歧三：环境该冻结还是该演化

CAKE 让 harness 随失败一起演化；FABRICA 刻意冻结 benchmark 以保证可比性。

我的判断：这是目标不同，不是路线之争。CAKE 在建生产编译器，需要一个会长的环境；FABRICA 在建 benchmark，冻结是可比性的前提。这个分歧最有启发的地方在于：CAKE 因此无法声称自己的数字可与任何既有排行榜比较，而它确实没有这样声称——反而主动警告「单形状干净起步的 1.144× 不是库级几何均值」。

不过 CAKE 的外环有一个未解风险：如果 IR 和规则能演化，那「什么算作弊」也在演化。人类 merge gate 是唯一的锚，而当提案量上去之后，这个闸门会变成瓶颈。三篇里只有 uCUTLASS 明确讨论过「黑名单注定漏」——CAKE 的演化机制在原理上缓解了这个问题，但代价是把判定权交给了人。

分歧四：布局该是代数还是契约

CuTe / Triton linear layouts / Axe 把布局做成一等代数对象；CAKE 与 uCUTLASS 都反着走。

我的判断：这是本次对照里两家 NVIDIA 工作最一致的结论，而且是我认为最可迁移的一条。它们各自独立地发现：布局代数是为人类专家设计的表示，对智能体的性价比极低——错误率高，且错误难定位。

差异只在程度：uCUTLASS 连偏移都不让写（只选命名布局）；CAKE 允许写具体承诺（SMEM 偏移、TMEM 列范围、swizzle 标签），由编译器检查一致性。共同点是把「布局正确性」从语言责任转为编译器责任。

分歧五：中间产物该不该结构化

FABRICA 实测「加设计记录无改善」（21/40→20/40，33/40→32/40）。

我的判断：这是三篇里唯一一条直接的、针对提示工程的反证，而且它和其他两篇的间接证据一致——uCUTLASS 发现编排式引导在 DSL 存在时优势收窄（GPT-5 从 +1.25 降到 +0.59；mini 基本持平 +0.24），CAKE 则干脆不给模型额外的规划阶段，而是给可检查的 IR 与诊断。

三条证据合起来指向同一个结论：「让模型想得更清楚」的收益有限；「让模型知道它在写什么、让编译器指出它错在哪」的收益才是实的。

11如果我来做一个系统

三篇的机制是可组合的，因为它们作用在不同的层。一个合理的组合骨架：

层取自具体机制
表示 CAKE 带类型的 IR：声明式资源、显式角色、自动推导的簿记；布局作为契约而非代数
诊断 CAKE + uCUTLASS 编译前廉价分析拦截（资源、角色对、流水阶段）；校验失败时解释「哪里错、为什么错」
导航 uCUTLASS 解析上界 + gap 感知的假设排序（ROI 公式的指数项）；ε 与 w 双停止准则
知识 FABRICA 按角色过滤的检索；把「多给结构不如多给知识」当设计前提
流程 FABRICA 失败按类别路由回负责阶段（130/189 是局部实现修复 → 多数失败不需要重新设计）
隔离 FABRICA + uCUTLASS 在参考 bundle 的未修改克隆内运行；物理上界作运行时天花板；在线而非离线判定
演化 CAKE 反复失败 → 验证规则 / 新原语 / 代价模型校准；人类 merge gate

这个组合里有一个刻意选择：完整性检查要在线，不要离线。uCUTLASS 自己承认这是缺口（「agent 从未获得修正 Minor Issues 的机会」），而已把它列为 future work（把完整性反馈接进优化环）。FABRICA 的做法——在参考 bundle 克隆内跑、由原脚本判定——已经做到了一半的在线化，因为它发生在 workflow 里而非 workflow 之后。

三个我认为最值得直接搬走的做法
  1. 候选进参考 bundle 的未修改克隆里跑（FABRICA）——最便宜、最可靠的隔离，不需要额外基础设施。
  2. 按信息类别（而非文件）划参考访问边界（CAKE）——「低层目标实现已经编码了要发现的调度决策」，这个表述本身就是可复用的判据。
  3. gap 感知的 ROI 指数（uCUTLASS）——1 + max(0, log₁₀(g/5)) 让「离极限远时敢冒险、近时求稳」变成一个连续可调的旋钮，而不是两条硬规则。

12三方都没答的问题

最后这一节是这份对照里我最想强调的部分。三个系统都很扎实，但它们共同留下了一个缺口——而且这个缺口恰好是最影响实际部署的。

缺口一：没有一篇能预测「哪类问题该用什么策略」

uCUTLASS 把它写成 future work：用 per-problem 特征来选最有效的 agent 策略与预算分配；在跑实验之前就预测一个好的调度策略。它的数据支持这个需求的紧迫性——最优点在变体之间差异极大（ε 从 50% 到 300%，w 从 4 到 16，而 GPT-5-mini 偏 w=4、GPT-5.2 偏 w=16）。

CAKE 的代价模型本质上是同一个问题的局部版本，且它明确说模型「故意不完整」。FABRICA 靠 reviewer 的分类来决定路由，但那是失败之后的分类，不是开始之前的预测。

我认为这是最值得做的一件事 三篇合起来积累了足够多的 trace（uCUTLASS 有 59 题 × 9 变体的完整 run log，FABRICA 有 1,741 个 run 目录、6,066 条 SFT 记录），但没有一篇拿这些 trace 去学「问题特征 → 最优策略」的映射。FABRICA 甚至已经把 trace 变成了训练数据（2,249 对偏好），但只用于 SFT 教模型写 CSL，没有用于元决策。

缺口二：没有一篇量化「不做防护的代价」，除了一篇

uCUTLASS 的 1.9× 是三篇里唯一的反事实数字。CAKE 与 FABRICA 都详述了防线，但没给出「放行后会涨多少」。这使得三者的数字在可信度这个维度上无法横向比较。

缺口三：只有一篇能说「还有多少余量」

uCUTLASS 的 3.91× vs 7.46× 是全部材料里唯一一次真正的余量陈述，而它本身就暗示了一个未解的谜：即使取所有变体所有运行里每题最快的 kernel，也只吃到理论空间的一半。这比「再换一个更强的模型」更值得挖——它可能说明某些近 SOL 实现所需的技巧（persistent kernel、warp specialization、TMA 多播）超出了任何单一 prompt 策略能稳定诱导的范围。

缺口四：三篇都在 NVIDIA 生态或单一目标内

CAKE 承认非 NVIDIA 未测且需重建后端；FABRICA 只有 Cerebras WSE-3 一个目标；uCUTLASS 只有 SM70–SM100 的 CUTLASS 后端。跨三个以上异构目标的可移植性，三家都没有证据。

不过 FABRICA 的一个观察给这件事泼了冷水，也给了方向：两个架构「不仅执行方式不同，被观测的方式也不同」。CUDA 开发者用 Nsight 的带宽占用率、访存吞吐、warp 并行度思考；WSE 上这些概念不存在，profiler 给的是编译器诊断、fabric 仿真 cycle 数、时间戳计数器、wavelet 与指令 trace、ELF 内存元数据。「提高占用率」对 CSL 没有直接含义，「串联描述符偏移」在 CUDA 里没有意义。所以 GPU 上学到的性能知识不会迁移。

这条观察的推论 任何跨架构 agent 都需要为每个目标重建性能语汇，而不只是翻译代码。uCUTLASS 的 SOL 报告本质上是「用 H100 的语汇给问题建立坐标系」；同样的方法到 WSE-3 上失效，因为那里没有「算术强度 vs ridge point」这种一眼可见的瓶颈分类——瓶颈是 fabric 路由、wavelet 背压、SRAM 预算。FABRICA 因此没有 SOL，只有参考实现对齐。这不是它不想建，而是那个目标的物理模型还没被写成 roofline 式的可计算形式。

一句话收尾

如果把三篇压成一句话：uCUTLASS 告诉我们怎么在弱基线上前进得便宜；CAKE 告诉我们怎么在强基线上摸到专家水平并让工具跟着长；FABRICA 告诉我们怎么在一个没有语料的机器上从零开始。三条路的方法不同，但都在做同一件事——把智能体不擅长的决策，变成编译器或评测器能检查的东西。
