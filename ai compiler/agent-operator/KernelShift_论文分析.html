arXiv cs.CL · 2026-11-22 arXiv:2611.29590v1 算子生成 · 智能体评测 CMU / Arm 只评 Arm CPU；SME2 证据主要来自 20 个 KleidiAI 核

KernelShift：成熟向量扩展上智能体能超通用库，但 SME2 这种编程模型换代还过不去

从 ncnn、llama.cpp、Arm SIMD Loops 和 KleidiAI 做出 99 个真实 kernel、约 1.6K 组工作负载，在 Graviton3 / Graviton4 / Apple M4 上闭环评测。对已站稳的 Neon / SVE，智能体相对自动向量化起点的各列几何平均加速是 2.4–19.8×，相对 ncnn Neon 参考最高 2.74×；相对 KleidiAI 手工核最好只有 0.70×。两台 LLM 的端到端 prefill 相对 llama.cpp 的 i8mm 快路径是 1.30–1.57×，decode 只有 1.04–1.10×，而且换进去的是按形状特化的核。

论文：Shuaiwei Huang, Weihua Du, Allen Wu, Ivan Fox, Manupa Karunaratne, Yiming Yang, Sean Welleck. KernelShift: Benchmarking Kernel Optimization Across Evolving Hardware. arXiv:2611.29590。 提交于 2026-11-22。Huang、Du、Wu 为共同第一作者。单位为 Carnegie Mellon University 与 Arm Ltd.。 项目页 cmu-l3.github.io/kernel-shift；代码 cmu-l3/kernel-shift；数据 l3lab/KernelShift。

1. 一句话结论

KernelShift 要回答的不是“智能体能不能再写一个更快的 GEMM”，而是：当 CPU 的指令扩展从固定宽度向量走到可伸缩向量、再到矩阵 tile 时，写核的智能体能不能换一套优化策略。它用智能体辅助、人工验收的流水线，把正在维护的开源仓库做成可扩展基准，并在目标机器上提供编译、评测、反汇编三种工具。当前套件 99 个 kernel、约 1.6K 组工作负载。在 Graviton3 的 SVE 上，最强系统相对 ncnn / llama.cpp / SIMD Loops 专家参考的几何平均 Speedup@40 分别是 2.74× / 1.95× / 1.56×，但相对 6 个 KleidiAI SVE 核最好只有 0.70×。从 SVE 换到 SVE2 几乎不掉；换到 SME2 时，五个模型里有三个相对专家参考的成绩掉到原来的 0.41–0.46。用 Claude Code + Fable 5.1 为 Qwen3.5-4B 和 Llama-3.1-8B-Instruct（均为 Q4_K_M）写出按形状特化的量化矩阵核并替换进 llama.cpp 后，Graviton4 上 prefill 相对官方 i8mm 快路径加速 1.30–1.57×，decode 1.04–1.10×，困惑度不变。

2. 问题：硬件在变，写核的策略也得变

前沿实验室已经在用智能体改生产级 GPU kernel。CPU 这边，硬件演进常常表现为新的架构扩展：同一功能的高效写法，可能要从 Neon 的固定宽度向量，换成 SVE / SVE2 的可伸缩向量，再换成 SME2 的二维矩阵 tile 和外积累加。智能体如果还按旧接口写，程序可以正确，却用不上新硬件。

已有 KernelBench、TritonBench、MobileKernelBench、SimdBench 以及跨设备的评测，多半是在一个或一组固定目标上看生成质量。KernelShift 把硬件看成一条扩展序列，在覆盖允许时用同一组 kernel 跨代比较，专门看智能体能不能适应新指令和新的编程抽象。

分数 s 是隐藏工作负载上、相对该目标上专家参考的运行时间几何平均；任一正确性检查失败则 s = 0。主指标 Speedup@40 是 40 次工具调用内最好的正确实现，再对 kernel 做几何平均。编译、评测、反汇编都计入预算。

3. 做法：仓库出题，真机给反馈

构造流水线由编码智能体按固定规程执行，背后是确定性的生成和校验脚本。人只做少量决定：选哪些 kernel、在追不到模型执行轨迹时批准工作负载、审查抽出来的专家参考。每个任务包含一份可移植的标量 C++ 起点、暴露给智能体的上下文、隐藏工作负载，以及仓库里若有同功能优化实现则抽出的专家参考。入选前要在目标硬件上把起点编译并跑通。

能从模型执行里收集形状时就收集形状，不保留原始激活值——作者假定性能主要由张量尺寸和算子配置决定。ncnn 的形状来自视觉模型，llama.cpp 的形状来自 ShareGPT 上的推理。去重并子采样后作为隐藏评测集。没有明确源模型的核，则分别构造正确性边角和工作负载规模两组合成例子。

评测是硬件在环的。统一控制面把相同的三种工具（compile、evaluate、disassemble）交给所有 harness，请求被路由到跑在目标机器上的 evaluator。正确性先于计时；两边用同一台机器、同一套计时协议。因为不是所有目标都有可靠的周期计数器，性能用墙钟时间。单核重复测量，每次评测在隔离进程里，并拒绝违反约束的实现（例如使用多线程）。

SVE2 · Graviton4

AWS c8g，Neoverse V2。增量扩展对照，以及端到端替换实验。

4. 成熟向量扩展上能超通用库

在 Graviton3 的 SVE 上，强系统确实能吃到生产库里的优化空间。Table 2 里各列最好的 Speedup@40（括号里是超过专家参考的核占比）是：

来源最好系统Speedup@40超过参考
ncnn（23）nanobot + GLM-5.32.743×91%
llama.cpp（26）nanobot + GLM-5.31.954×85%
SIMD Loops（24）Claude Code + Opus 4.81.555×96%
KleidiAI（6）Claude Code + Opus 4.80.701×33%（2/6）

编译器自动优化离专家参考很远：即便 -O3 且打开 SVE，相对专家参考最多也只有 0.468×（SIMD Loops），ncnn / llama.cpp / KleidiAI 分别是 0.229× / 0.126× / 0.035×。这份 -O3 + SVE 的标量起点，也是每个智能体的出发实现。附录 D 把 Table 2 的同一批运行改成相对起点报告：每一列的几何平均都高于起点，范围是 2.4–19.8×（最低一格是 Codex + GPT-5.6-luna 在 SIMD Loops 上的 2.41×，最高是 Claude Code + Opus 4.8 在 KleidiAI 上的 19.77×）。这是“各系统在各来源上的几何平均”，不是“每个 kernel 都超过起点”——SIMD Loops 上超过起点的核占比是 79%–92%。专家参考本身相对同一起点是 4.37× / 7.97× / 2.14× / 28.20×。

单次生成、不用工具的 Claude Opus 4.8 要弱得多（ncnn 0.577×，llama.cpp 0.324×），说明成绩主要来自带真机反馈的迭代，而不是一次写对。

不要把“超过 ncnn 2.74×”读成“已经接近硬件上限”。附录 D 用 tfloor = max(W/P, Q/B) 估理论下限：ncnn 和 llama.cpp 的专家参考大约只到上限的 7–8%，前沿智能体是这个数字的两到三倍；KleidiAI 专家参考到 43%，仍然领先所有智能体。Speedup@40 大于 1，首先说明参考路径还有空间。

5. 换代：SVE2 还行，SME2 跨不过去

真正吃力的是 SME2：它引入的是流式模式和 ZA 矩阵 tile，而不只是再加一批向量指令。在同一组 6 个 KleidiAI 核上，把 Speedup@40 从 SVE 换到 SME2（nanobot，3 个种子的均值 ± 标准差）时：

模型SVE（Before）SME2（After）After / Before
Claude Opus 4.80.436 ± 0.020.562 ± 0.201.29
Claude Sonnet 4.60.258 ± 0.020.266 ± 0.021.03
GLM-5.30.464 ± 0.050.213 ± 0.190.46
DeepSeek-V4-Pro0.213 ± 0.030.091 ± 0.010.42
GPT-5.6-luna0.178 ± 0.040.073 ± 0.010.41

GLM-5.3 在 SVE 上是这五者里最强的之一，换到 SME2 掉到一半以下。SVE 上表现好，并不能保证会用新的编程风格。附录 F 统计最终解是否真的用了目标扩展：SVE 上几乎都会用 SVE intrinsic；在这 6 个核、3 个种子共 18 个最终 SME2 解里，用了 ZA tile 的分别是 Opus 15 个、Sonnet 5 个、GLM-5.3 5 个、DeepSeek-V4-Pro 1 个。个案 gemm_bf16_n512_k512 上，Opus 切到流式模式并用 MOPA / ZA 累加，达到专家实现的 0.94×（附录轨迹里最好一次是第 29 次调用的 0.935×）；Sonnet 和 DeepSeek 仍停在旧的向量写法，只有 0.06× 和 0.05×。

固定在 Apple M4、用 nanobot + GPT-5.6-luna、在 20 个 KleidiAI SME2 核上做指令阶梯（3 个种子）：只给 Neon 是 0.141×，加上流式 SVE（不含 ZA）掉到 0.059×，再打开完整 SME2 只回到 0.085×。每个种子都是 Neon > SME2 > 流式 SVE。恢复并不是因为用上了 ZA 外积：智能体只是比“只给流式 SVE”时更常保住 Neon 核。该设置下，最终 SME2 档没有一个核使用 ZA 外积；全部运行里只写过两次 ZA 代码，都没通过。第一种子里，编译失败率从 Neon 档的 13% 升到流式 SVE 的 20%、完整 SME2 的 24%。

相比之下，SVE 到 SVE2 是增量扩展。在 8 个专家 SVE2 实现必须用到 SVE2 专有指令的 SIMD Loops 核上，各模型的 SVE2 / SVE 比值在 0.94–1.05。Graviton4 上固定机器的指令阶梯里，只给 Neon 和加上 SVE2 分别是 1.105× 和 1.101×。作者把 SVE 档的落后拆成两半：大约一半是 SVE 代码过不了正确性检查、退回标量；另一半是 SVE 代码正确但更慢、没用对指令。这是 SME2 失败的较弱形态：新接口用不好时，结果可能还不如老的 Neon。

6. 加速从哪来，怎样才能更好

在 79 个 SVE 核上，专家参考相对未向量化标量代码越强，智能体的中位 Speedup@40 越低（Spearman ρ = −0.69；llama.cpp 内部是 −0.75）。大的 Speedup@40 常常反映参考路径偏弱，而不是智能体特别强。llama.cpp 的 RMSNorm 参考只比标量快 1.3×，智能体中位超过它 6.0×；q4_K_M 的 GEMM 和 MoE 专家实现已经比标量快 25–29×，智能体只到专家的 0.57–0.69×。

测试时扩展方面，大部分提升发生在前 40 次调用内，但 40 次之后仍有回报：Claude Sonnet 4.6 在 100 次时比 40 次高 23–25%，主要来自大约 40–60 次之间少数核的结构性改写，60 次之后曲线基本收敛。

消融（nanobot + GPT-5.6-luna；SVE 用 32 核子集，SME2 用 20 个 KleidiAI 核）里，更值得记下的是失败，而不是又加了一种工具：

  • SVE 上提供 Arm 文档，Speedup@40 从 1.074 降到 0.997；跨 kernel 记事本是 0.974；去掉反汇编是 0.999。轨迹里智能体很少用反汇编，而人类专家设计高级核时常用。
  • 禁止 SIMD intrinsic、只准靠编译器自动向量化，成绩从 1.074 掉到 0.300。智能体的主要收益来自把提供的 intrinsic 用对。
  • SME2 上加 Arm 文档把 0.083 提到 0.130，但并不是写出了更好的 SME2 代码：有文档时没有一份最佳版本使用流式 SVE（没有文档时有 6 份），20 个里 14 个改用 Neon（没有文档时是 7 个），编译错误从 102 降到 54。
  • 把常见 SME2 陷阱和失败例子写进提示，20 个核上的 Speedup@40 从 0.083 加倍到 0.167，但其中 5 个核反而变差。
官方文档帮不上忙去学会一种新的编程模型；把具体失败模式写进提示更有效，也不稳定。要让智能体用上 SME2，更像是缺“会用 ZA 的示范和约束”，而不是缺一份 ISA 手册。

7. 塞进 llama.cpp 之后

主实验是一次优化一个核。为了看应用层有没有增益，作者用 Claude Code + Fable 5.1，为 Qwen3.5-4B 优化 11 个量化矩阵核、为 Llama-3.1-8B-Instruct 优化 7 个（均为 Q4_K_M），在 Graviton4 上替换进 llama.cpp，对照原来的 repacked i8mm 快路径。Table 6：

线程数Qwen prefillQwen decodeLlama prefillLlama decode
11.395×1.045×1.568×1.099×
41.348×1.059×1.454×1.069×
161.298×1.048×1.391×1.102×

正文把两模型、1–16 线程汇总为 prefill 1.30–1.57×、decode 1.04–1.10×。Qwen 的困惑度 9.504 对 9.506，Llama 两边都是 7.879，作者称为不变。18 个核都用了 Graviton4 的 i8mm，并加上按形状的分块、布局和预取。单独测量时，这些核比 llama.cpp 自己的 repacked 核平均快 1.45×（Qwen）和 1.62×（Llama）；正文约写成 1.5×。prefill 的优势随提示变长而下降，因为没被替换的算子（主要是 attention）占比上升；batch size 为 1 时行为接近 decode。

每个生成核只服务一个固定形状，而通用库必须覆盖更宽的形状分布。作者明确写了：这不是“智能体已经在端到端上全面超过专家库”，只说明部署时按硬件和形状特化有潜力。

8. 落地可行性

如果你关心的是 CPU 侧、尤其是 Arm 服务器或端侧上，用智能体去挤通用库（ncnn、llama.cpp）里还没手写到极致的核，KernelShift 给出的证据是扎实的：题来自正在维护的仓库和真实模型形状，评测在目标机器上闭环，而且端到端替换后 prefill 有 1.3–1.6× 量级、质量指标没有变差。代码和数据集都已公开。同目录里 KernelOPT、CompoundingKernel、AscendGYM 主要看 GPU / NPU；这篇把镜头转到“指令扩展换代时策略会不会跟着换”，是补了一块之前几乎没被对准的评测。

若要把结论外推到“智能体可以替代厂商微核、或自动跟上每一次 ISA 换代”，限制同样清楚。

  • 只评了 Arm CPU，而且核级实验是单核、禁止多线程。x86 和 GPU 会不会是同一趋势，文中明确列为未知。多核部署里的缓存、亲和性和并行开销也不在核级分数里。端到端虽然跑了 1–16 线程，替换的仍只是部分矩阵核。
  • 大加速经常来自参考路径偏弱。ρ = −0.69 这一条必须和 2.74×、1.95× 一起读。对手已经 25–29× 于标量的 q4_K_M GEMM / MoE，智能体只有专家的 0.57–0.69×；对 KleidiAI 这种专门手写的微核，最好也只到 0.70×，并且 43% 峰值利用率仍领先所有智能体。
  • SME2 的证据面窄，而且多数模型并没有真正用上矩阵 tile。作者自己写了：新硬件缺少专家参考，限制了跨代可比较的核数；SME2 证据主要建立在 20 个有专家参考的 KleidiAI 核上。跨代表里更只有 6 个核。不少看起来的“恢复”其实是退回 Neon。
  • 端到端核是按形状特化的。换模型、换序列长度分布，这些核不能当通用库用。decode 收益很小，长上下文时 prefill 优势也会被 attention 吃掉。
  • 基准扩展仍要人盯着。一次给端到端 GEMM 任务扩容的记录里，人工发了 37 条消息，其中 17 条改变了走向（14 个决定、3 个纠正）；智能体还写错过两个形状。命令本身大约 23 分钟，Graviton 实例连同下载和重跑占了约 4.5 小时。流水线能减轻重复劳动，但不能无人值守地“自动跟上所有新仓库和新芯片”。
  • 公开仓库有污染风险，但作者做了针对性检查。智能体在多数 ncnn / llama.cpp / SIMD Loops 核上超过了专家实现，并用了库里没有的 intrinsic 和不同算法结构；起点是带基准接口的可移植标量代码，不是库的原文件。KleidiAI 的 SME2 专家核同样公开，智能体反而差得远。在 Table 3 完整 SME2 臂的 20 个核里，GPT-5.6-luna 知识截止日期（2026-02-16）之后才进入 KleidiAI 的 6 个核，成绩与更早的 14 个接近（0.088 对 0.082）。正确性和计时用的工作负载也对智能体隐藏。
对仓库读者的建议：把它读成“CPU 核优化智能体的换代评测床”，而不是又一份 KernelBench 的 GPU 成绩表。能用的结论是：在熟悉的向量 ISA 上，带真机反馈的智能体已经可以超过通用库里偏弱的路径，并在部署时按形状特化出可测量的 prefill 收益；不能用的结论是：它们已经学会了 SME2 这类新编程模型，或可以整体替换 KleidiAI 这一级的手写微核。
