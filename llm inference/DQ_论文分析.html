1. 一句话结论

Prefill 吃的是算力，Decode 吃的是权重带宽，却长期共用同一套量化。DQ 把计算格式、权重、甚至存放位置按阶段拆开，再用同一套回答目标把两条路径训到一起。格式拆分几乎零成本地抬高 Decode 侧精度；完全拆分再给 Prefill 单独一份计算原生权重，低比特 Decode 的精度和长 prompt 的首字时延可以同时变好。

2. 问题：Prefill 和 Decode 要的不是同一种量化

线性层要做两件事：把权重和激活从显存搬进来，再做 GEMM。权重是 H×H，激活是 T×H，搬运大约是 O(H²+TH)，计算是 O(TH²)。Token 数 T 越大，权重搬运越容易被摊掉。于是出现两种完全不同的负载：batch=1 的 Decode（T=1）几乎是在为搬权重付钱；足够长的 Prefill（T≫1）则是算力瓶颈。

现有量化大体顺着这两头各走一条路。一条把权重量得很紧，用复杂的 weight-only 编码减 Decode 的访存，激活不必进硬件计算格式；另一条把权重和激活都量化到 INT4、NVFP4 这类计算原生格式，换 Prefill 的 GEMM 吞吐。把后一种格式硬套到 Decode 上，就要给激活也量化，还常常要把紧凑编码再转一遍，精度先掉一截。

服务侧其实早就把两个阶段拆到不同实例了：各自留一份权重，中间只交 KV cache。论文认为，量化也可以按阶段特化，同时仍然对着同一个回答目标来训练。架构还是预训练好的 decoder-only 注意力，改的是线性层用什么计算、存哪一份权重、这份权重要不要常驻设备。

作者先做了一个对照：只量化其中一个阶段。Decode 重的推理任务上，只量化 Decode 带来的精度损失，多数模型是只量化 Prefill 的 2–4 倍，Gemma3-1B 上到 7 倍；Prefill 重的长上下文任务上，八个模型里有七个反过来，只量化 Prefill 的损失是只量化 Decode 的 1.1–4.1 倍。后面跟踪两类任务，就是为了把两边的改进拆开看。

3. 三种拆法

DQ 是一把伞，下面有三级，对应三种成本轴。越往下，Prefill 侧能力越强，代价是多存一份 checkpoint，或把这份 checkpoint 放到 SSD 上。

格式拆分

权重还是一份。Prefill 走计算原生格式（如 NVFP4），Decode 走 weight-only（如 NVFP4A16 或 LUT2/3）。显存和 Prefill 成本不变，Decode 还少做一次激活量化。

完全拆分

Prefill 另训一份计算原生权重，Decode 继续用紧凑的 weight-only。KV 的层、头维度不变，注意力不用改。多存一份 Prefill checkpoint。

ODP 卸载

完全拆分的 Prefill 权从 SSD 按块流进设备，用完即释放。设备上的权重占用回到 Decode 那一份，长 prompt 还能把加载藏进计算。

图 1　三种方案。格式拆分仍受 Decode 侧紧凑编码约束，因为 Prefill 看到的是同一份权的再量化视图；这是完全拆分要单独训 Prefill 权的原因。ODP 用块缓冲代替把第二份权常驻设备。

4. QADD：一次前向把两条路径训到同一个回答

Quantization-aware distillation with disaggregation（QADD）建在普通的量化感知蒸馏上。关键一步，是把 SFT 里本来只用来遮损失的 assistant mask，同时拿来选线性层走哪条计算路径：用户轮（prompt）走 Prefill，助手轮（response）走 Decode。

蒸馏损失只监督回答 token，但梯度会顺着 Decode 要用的 prompt 侧 K、V，回到 Prefill 权重。于是两条路径在同一次前向–反向里，对着同一个回答目标更新。共享主权重、各备一份主权重、只训 Prefill 而冻住已有解码器，三种配置都走这套构造。

核心实验对未量化教师做 KL(pteacher ‖ pstudent)，数据是 Tülu 3 SFT 语料里的 1 亿 token。统一量化和拆分量共用同一语料、同一 token 预算和同一优化日程，避免把“多训了一会儿”算进拆分的增益。

5. DQ 的四个机制

核心想法：不要逼一套格式同时当好算力格式和访存格式。先按阶段选计算，不够再给 Prefill 单独的权，最后用 SSD 把多出来的那份从设备上请走。

5.1 格式拆分：Decode 不再量化激活

NVFP4 对权重和激活都量化，Prefill 快；它的 weight-only 变体 NVFP4A16 不量化激活，精度更高，但 Prefill 也跟着失去加速。格式拆分的 NVFP4 只在 Decode 关掉激活量化：存储和 Prefill 成本与普通 NVFP4 相同，Decode 因为少做激活量化，还会略快一点（Table 1 与附录 C.2：Qwen3-8B 从 2.86× 到 2.93×，Gemma3-12B 从 3.18× 到 3.27×，都相对 BF16）。

同一思路可以接到任意紧凑编码上。论文还看了 2-bit / 3-bit 标量查找表编码，称作 LUT2A16、LUT3A16；若要在这上面跑低精度 GEMM，就要把权和激活临时再量化到 NVFP4，对应 LUT2、LUT3。不拆分时，Prefill 和 Decode 都做这次 autocast；格式拆分只让 Prefill 做 autocast，Decode 保持 weight-only。Prefill 仍然受那份低比特权的表示约束，也不会因为这份编码本身而把 NVFP4 GEMM 变得更快——所以下一步要给 Prefill 自己的权。

5.2 完全拆分：Prefill 另有一份计算原生权

两份权都从同一个未量化模型出发，在各自的格式下由 QADD 一起优化，得到一份原生 NVFP4 的 Prefill checkpoint 和一份 weight-only 的 Decode checkpoint。每一种 Decode 格式都搭配自己训出来的 Prefill，而不是一份 Prefill 通吃所有比特数。

推理时，Prefill 在每一层写出 prompt 的 K、V，Decode 再来做注意力。cache 仍用原模型的层数和头维度，拆权重不必改注意力。速度上，它同时拿走 NVFP4 Prefill 和低比特 Decode 的好处。代价是多存一份 Prefill checkpoint。数据中心的 PD 分离本来每边就要留一份模型；单卡本地部署时，两份都常驻往往会挤不下。

5.3 ODP：按块从 SSD 流进 Prefill 权

一个 Prefill 块算出输出之后，它的权重在本轮助手回答里就用不到了，只有 cache 还要留着。ODP 因此按 transformer 块从 SSD 加载 Prefill 权，设备上的缓冲循环使用。Prefill 计算随上下文变长，加载一份 checkpoint 的成本大致固定，所以 prompt 越长，加载占比越低。论文在 DGX Spark 上看到：Qwen 3 各尺寸大约从 8K 上下文起，计算开始超过加载。

两个设备块缓冲就够把计算和加载重叠：一块在算当前层，下一块已经往另一个缓冲里装。缓冲空间从此时用不到的 Decode 权里切一块出来，生成开始前再填回去。这样 ODP 不增加设备上的权重占用，但会多一次读写，并且短 prompt 可能在加载上卡住。

图 2　ODP 的双缓冲。第一块有冷启动；之后加载与计算重叠。论文强调：省的是权重占用，不是 KV cache 或其他运行时分配；多出来的 Prefill checkpoint 仍然要占 SSD。

论文把 ODP 主要写成稠密模型的本地部署工具。MoE 里活跃参数比例低，加载相对计算会贵很多，要到极长上下文才摊得平，所以不把 ODP 推荐给 MoE。

5.4 Prefiller：给已经量化好的解码器补一门 Prefill

很多解码器已经用复杂算法或闭源数据量化好了，不能或不需要再跟 QADD 一起训。这时只训 Prefiller：解码器反量化后冻住，梯度穿过它的计算回到 Prefill 路径，让 NVFP4 Prefill 去适应这份现成解码器要用的表示。解码量化流水线可以当黑盒，只要最终 checkpoint。推理时 Decode 路径和压缩权都不变，Prefill 换成硬件原生的 NVFP4，ODP 负责不增加设备权重占用。

6. 实验怎么做的

核心 QADD 做在经过后训练的指令模型上，因为 DQ 需要逻辑上的输入 / 输出分界：Qwen 3 的 0.6B / 1.7B / 4B / 8B，以及 Gemma 3 的 1B / 4B / 12B。Qwen 3 的推理块可选，打开会加长 Decode。

Decode 重任务用 GSM8K、MATH-500、MMLU-Pro 的生成式设定，Qwen 3 开、关推理各跑一遍。Prefill 重任务用 RULER 的 13 个任务，在 4K / 8K / 16K / 32K 上下文上评估，Qwen 3 关掉推理。精度摘要来自真实的分离式服务：vLLM 加 NIXL。家族数字是各尺寸的未加权平均；每个尺寸再对一次 QADD 跑的最后五个 checkpoint 取平均，误差条是这一次训练里的时间波动，不是多次独立实验。

时延都在 DGX Spark（NVIDIA GB10，sm_121，PyTorch 2.13 / CUDA 13.2）上测。Decode 是 vLLM 里 batch=1 的端到端每输出 token 时延，用 n=8 和 n=128 两次生成的时间差去掉 Prefill，前缀缓存关闭，CUDA Graph 打开。Prefill 是用 vLLM 内核搭的自定义栈，计时范围是第一层输入到最后一层输出，不含 embedding、最终归一化和输出头。LUT2 / LUT3 的 Decode 用作者自己的 weight-only 内核，在 Spark 上用软件查表，不要求硬件原生 LUT。

27B 的 Prefiller 实验换到 Qwen3.8-27B，使用 Unsloth 发布的八个 GGUF（IQ1_S 到 Q3_K_XL）。Prefill 用文本-only 的代码和数学推理轨迹训 9500 万 token，最终取 step 980。评测是 MMLU-Pro 和带视觉的 MMMU-Pro，两边都开推理。TTFT 另在 llama.cpp 里测：把同一套卸载式 NVFP4 Prefill 接到 llama.cpp 的 prompt 路径，没有再做额外内核优化；基线是 Unsloth IQ1_S 的原生 llama.cpp。预热一次后重复三次，关闭 prompt cache。

更大规模的验证不再训练，只做 NVFP4 PTQ，最保守的干预就是 Decode 关掉激活量化。模型包括 Qwen3.8-27B、Gemma 4、Muse Glimmer、Nemotron 3，以及 Kimi-K3-2.8T，评 MMLU-Pro / MMMU-Pro，用配对逐条检验，每项重复四次。

7. 结果怎么读

格式拆分：几乎是免费的 Decode 精度

相对不拆分的同格式方案，格式拆分在 Decode 重任务上，七个模型都有提升：NVFP4 在 Qwen 3 / Gemma 3 家族均值上分别 +1.9 和 +3.1 点，LUT3 是 +4.5 和 +3.7，LUT2 是 +2.5 和 +1.8。Prefill 重任务上，所有家族和格式的变动都不到 1.3 点——它主要修的是 Decode 阶段的误差。

速度上，Prefill 与不拆分的 NVFP4 相同，相对 BF16 最高 1.49×（Qwen3-8B）和 1.67×（Gemma3-12B）；Decode 因跳过激活量化再快 2–3%。存储不变。论文把它写成单用户、显存紧、又想保住原模型交互性时的即插即用替换。

完全拆分和 ODP：低比特两边一起抬

完全拆分在两类任务上都超过不拆分格式。相对不拆分，LUT3 的 Decode 重 / Prefill 重增益是 6.3 与 5.2、4.1 与 4.3 点（Qwen 3、Gemma 3）；LUT2 按 Table 1 是 10.7 与 7.4、15.3 与 10.5 点。第 3.2 节正文把 Qwen 3、LUT2、Prefill 重写成 5.3 点，与表格 76.6−61.3=15.3 不符，这里以表格为准。相对已经训练过的 LUT2A16 weight-only，2-bit 完全拆分仍然高出 4.5–12.5 点，同时还带上更快的 Prefill。Table 1 里写得更具体：Qwen 3 家族均值是 Decode 重 45.5 对 38.4（+7.1）、Prefill 重 76.6 对 64.1（+12.5）；Gemma 3 是 38.2 对 33.7（+4.5）、61.3 对 52.4（+8.9）。

设备权重要多存一份 Prefill。Qwen3-8B 上，LUT2 从 4.66 GB 升到 8.57 GB，LUT3 从 5.53 GB 升到 9.44 GB。ODP 把设备占用打回 Decode 那一档，代价是 SSD 带宽和很短序列上的 TTFT。16K 以上，卸载给常驻 NVFP4 Prefill 时延加的幅度，Qwen 3 不到 5%，Gemma 3 不到 8%，主要来自第一块冷启动和同步；此时流式栈相对 BF16 仍是 1.47×（Qwen3-8B）和 1.58×（Gemma3-12B）。Decode 加速与格式拆分相同。

现成 1-bit GGUF：精度可以翻倍，3-bit 就不要硬加

给冻住的 Qwen3.8-27B GGUF 训 NVFP4 Prefiller，IQ1_S 的 MMLU-Pro 从 29.04 到 61.54（+32.50），MMMU-Pro 从 24.39 到 59.65（+35.26），解码 checkpoint 不变，大约是“翻倍有余”。2-bit 量级的 IQ2_XXS 大约 +7.4 和 +6.3 点；再往上增益变小。到 3-bit（IQ3_S、Q3_K_XL），出现小幅下降，例如 IQ3_S 在两个基准上是 −0.63 和 −2.77 点。训练语料没有多模态样本，低比特的增益仍然迁到了 MMMU-Pro。

同精度的 RTN Prefill 远不如训过的 Prefiller：IQ1_S 上，匹配训练的 Prefiller 比 RTN 高出 13.1（MMLU-Pro）和 29.4（MMMU-Pro）点。换一个 Prefiller 去配另一份解码器，有的组合甚至略高于“原配”，但论文的结论是：训练本身比“随便挂一个 NVFP4 Prefill”重要，配对也不是可以完全忽视。

TTFT：8K 上下文从 12.27 秒降到 6.90 秒，即 1.78×。在测过的 4K–32K 上，加速介于 1.38× 和 1.78×；更短的 prompt，SSD 加载会让 ODP 更慢。附录 B.5 还指出，解码器不变不等于生成成本不变：IQ1_S 在 MMMU-Pro 上平均回复从 14,579 降到 6,582 token，截断率从 24.57% 降到 4.16%，精度提升不是靠把回答写得更长买来的；但在 MMLU-Pro 上，多数格式的平均长度反而增加。生成代价要单独看，不能默认更短。

大模型 PTQ：只关 Decode 激活量化也站得住

不做再训练的格式拆分，在 13 个模型–基准组合里有 11 个点估计上升，6 个在 α=0.05 下显著，没有显著下降。这是 DQ 最保守的实例，用在最大到 2.8T 的开源模型上。

8. 落地可行性

这套东西不是只停留在仿真里。官方仓库提供 QADD 训练、分离式 vLLM 服务和评测脚本，Hugging Face 上已经放了 Qwen3.8-27B 的 NVFP4 Prefiller；ODP 在论文里是 llama.cpp 的分支实现。想动手，有三条远近不同的路。

只做格式拆分

共享权重，Prefill 走 NVFP4，Decode 走 NVFP4A16 或 LUT weight-only。不增加存储，适合已经在用分离式服务、又不想多一份 checkpoint 的集群。大模型上甚至可以先 PTQ、不重训，作为最低成本验证。

本地单卡加 ODP

给现成 GGUF 挂上发布的 Prefiller，长上下文的 TTFT 有实测。前提是稠密模型、SSD 带宽够、prompt 不要太短。仓库说明训练启动脚本面向 SLURM / 容器，不是笔记本上开箱即跑。

集群 PD 分离

Prefill 实例和 Decode 实例本来就要各留一份模型，完全拆分的额外存储在这里最说得通，而且 Decode 仍是内存瓶颈时收益最大。论文的核心精度就是在 vLLM + NIXL 的分离服务里测的。

和仓库里已有笔记的关系也清楚：BitDecoding 解决的是低比特 KV 能不能跑上 Tensor Core，Shannon 界那篇做的是权重无损压缩；DQ 做的是 Prefill / Decode 要不要用不同的量化格式和不同的权。它不替代前两篇，但可以直接接到已经量化好的 Decode 权上。

相对好落地的原因有三：不改注意力形状；格式拆分可以先当开关来试；Prefiller 不必重训已有 GGUF。相对难落地的也有三：完全拆分要训（或下载）第二份权；ODP 依赖 SSD 且对 MoE 不友好；核心速度数字来自 batch=1 和 DGX Spark，高并发、多轮、H100 / B200 上的表现还没有同等口径的表。

9. 局限：这些倍数依赖什么假设

  • 没有高 batch、没有多轮、没有 agent。 评测是 Decode 重的推理题，加上单轮、长 prompt 短答案的 RULER。多轮里，缓存里的助手 token 带着 Decode 写出的 KV；如果后来用 Prefill 重建同一段历史，表示可能不同。这种缓存策略敏感性，论文明确写了未测。
  • 速度口径很窄。 核心 Prefill / Decode 时延在 DGX Spark、batch=1。LUT2 相对 BF16 少搬 6.4 倍权重比特，端到端却只有 3.82× / 4.15×，因为输出头保持 BF16，注意力、归一化、残差也不会跟着加速。把这些倍数搬到别的卡或高并发上，需要自己重测。
  • 27B 的精度和 TTFT 不是同一条流水线。 精度是 GGUF 反量化到 BF16 后，在分离式 vLLM 里测的；TTFT 是 llama.cpp。不要把 61.54 的 MMLU-Pro 理解成“原生 1-bit 内核跑出来的准确率”。
  • 3-bit 以上不要默认加 Prefiller。 1-bit / 2-bit 增益大，3-bit 出现小幅下降。Prefiller 也不是对所有解码器即插即用，换配要重新看表。
  • ODP 不是通用卸载。 主要针对稠密模型的本地部署；短序列 TTFT 可能变差；MoE 的加载 / 计算比不合适。它也不减少 KV cache 占用。
  • 训练预算和硬件绑定。 核心 QADD 是 1 亿 token；27B Prefiller 是约 9500 万 token 的文本推理轨迹。官方脚本按多机多卡来写。投稿状态是 ICLR 2027 submission，这里按 2026-09-22 的 v1 阅读，不把它写成已录用。
