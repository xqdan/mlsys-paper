1. 一句话结论与研究定位

ExpertPlex 的核心主张是：不要在 Prefill / Decode 两阶段各复制一份完整 MoE 模型，也不要在每张 GPU 上用 Green Context 把两阶段“切死”；而应共享占参数 95% 以上的 Expert，只把轻量 Attention 按阶段分离。再配合 tile 级可抢占的自适应持久化内核、Attention 发起的单边通信，以及 tile-to-cluster 联合优化，把 goodput 相对实例级 PD 分离最高提升 2.01×，相对 Green Context 共置最高提升 1.66×。

这不是又一篇“把 Prefill 和 Decode 拆开”的工作。它针对的是 MoE 权重膨胀之后，实例级 PDD 部署粒度变得过粗 这一新瓶颈：DeepSeek-V3 一类部署单元可达 32P+320D=352 GPU，小集群配不出目标 P:D 比，大集群又弹性差、故障爆炸半径大。

2. 问题背景：MoE 服务为何难

2.1 MoE 把“容量”和“算力”解耦，却把“内存”和“动态性”绑死

Transformer 层由 Attention + FFN 组成。前沿模型用稀疏 Mixture-of-Experts 替换稠密 FFN：router 为每个 token 选 top-k 个 routed experts，再加少量 shared experts。这样可以大幅增加参数量，而不按比例增加每 token 计算。

论文给出的权重占比非常极端：

模型MoE 权重占比含义
DeepSeek-V4-Pro95%几乎整模都是 Expert
GLM-5.1-FP896%Attention 只占约 4%
MiniMax-M2.798%跨阶段复制 Expert 代价极大

因此，服务系统必须同时面对两件事：专家权重大到必须用 Expert Parallelism（EP）切开；以及 路由随 token / layer / rank 变化，计算与通信都高度动态。

图 2　左：稀疏路由只激活少数 expert，但 all-to-all 仍随 token 变。右：权重质量比决定“该共享什么、该分离什么”。

2.2 Prefill 与 Decode 目标天然冲突

Prefill（吞吐导向）

一次处理全部输入 token，构建 KV cache，产出首 token。计算密集、激活量大，适合层次化 dispatch/combine 与连续内存布局。

Decode（时延导向）

每轮只生成 1 个 token，用户可感知。时延比 Prefill 低数个数量级。数据量小，更适合直达通信与 masked 布局，避免 packing 拷贝。

以 MiniMax-M2.7、EP4 为例：8 个活跃 expert 的 decode grouped GEMM 仅 17.7–34.7 μs；16K token 的对应 prefill GEMM 却要 1.8–2.9 ms，约 84–101×。每一层都会再触发一次 MoE，阻塞会在层间累积成端到端 TPOT 恶化。

图 3　MiniMax-M2.7、EP4 上 grouped GEMM 的时长差。这是 APK 必须做 tile 级抢占，而不是等整个 prefill kernel 结束的直接原因。

2.3 Attention 与 MoE 的最佳并行也不一样

  • MoE：权重大，必须 EP；dispatch/combine 通常是 all-to-all。可用 TBO（跨 microbatch 重叠）或 SBO（同 microbatch 内与 shared expert 重叠）隐藏通信。
  • Attention：权重小。DP 利于吞吐和 KV 容量；TP 利于单请求时延，但增加通信，还可能因复制 KV 降低有效缓存。

所以“整实例一套并行配置”往往同时委屈 Attention 和 MoE。

图 4　Attention 与 MoE 的最佳并行本来就不同。强行“整实例一套配置”，两边都会被委屈。

3. 现有路线的结构性缺陷

3.1 实例级 Prefill-Decode Disaggregation（PDD）

DistServe / Splitwise / Mooncake 一类系统把两阶段放到不同 GPU 实例，隔离干扰，并为两阶段特化通信与 kernel。这对稠密模型很有效，但 MoE 会把部署粒度“放大”：

  • 每个阶段实例都必须持有完整模型副本，Expert 权重直接决定最小 GPU 数。
  • 重复权重挤占 KV cache。
  • 要匹配不对称的 P:D 资源比，最小部署单元变成“两阶段实例的笛卡尔积”。论文引用：DeepSeek-V3 一个单元 32 prefill + 320 decode GPU；另一负载用 176 GPU 作为一个单元；Kimi-K2 部署在 128 张 H200 上。
  • 小集群配不出目标比例 → 一阶段过载、另一阶段空转。
  • 大集群每次扩缩都以百卡为单位，跟不上中等流量波动。
  • 层次化通信把大量 rank 绑成一组，单 rank 故障可卡住整个单元，故障爆炸半径大。
PDD 用隔离换来了内存效率、弹性和故障隔离的三重损失。随着 Expert 变大，这个代价不再是边角料，而是主矛盾。

图 5　PDD 的隔离是“整模复制 × 阶段数”。MoE 越大，能独立扩缩的最小砖块就越笨重。

3.2 Prefill-Decode Colocation（共置）

共置避免复制整模。两条主流路：

  1. Chunked Prefill：把长输入切块，与 decode 交错。但要反复读前缀 KV 和模型权重，通信也重复。
  2. Green Context / 空间划分（PDMux、Nexus、semi-PD 等）：给两阶段预留不同 SM，既去重又隔离计算。

Green Context 路线在 MoE 上会在三个时间尺度上失效：

变化维度发生位置固定划分的后果
EP 负载随层变化rank × layer某卡 expert 突然变多/变少，SM 配比跟不上
同层 Attention vs MoE 需求不同模块级一阶段算 Attention、另一阶段算 MoE 时资源错配
MoE 内部 dispatch / compute / combine 交替算子级通信阶段占着 SM 却算不了，计算阶段又缺 SM

重配资源需要 CPU 介入，且要等 kernel 结束，所以现有系统最多在 prefill 层边界 调整。结果只有两种失败模式：

  • 队头阻塞（HOL）：decode 就绪时 prefill kernel 还占着 SM，后者可能跑几十到几百毫秒，前者只要几百微秒。
  • 资源气泡：decode 没活，预留给它的 SM 也不能借给 prefill。

此外，共置还留下三个通信问题：

  • 两阶段的 dispatch/combine 抢同一套 NIC/链路，大 prefill 突发会压死 decode。
  • 传统双边通信需要收发双方同时推进；不同 MoE rank 可能分别卡在不同阶段，形成跨阶段死锁。
  • 每张卡都被切开后，单阶段本地算力变少，为达 SLO 必须加大并行度 → 通信更多 → 干扰更重。

图 6　Green Context 的两种典型失败，以及它跟不上的三层动态性。现有系统最多在 prefill 层边界重配，仍然太粗。

4. 核心洞察与系统架构

4.1 混合“分离 + 共置”边界

论文的关键 insight 可以拆成三句：

  1. 共享 Expert：消灭 95%+ 的跨阶段权重重复，并让两阶段的稀疏计算互相填气泡。
  2. 分离 Attention：Attention 只占 <5% 参数，可以按阶段独立分配，且以整卡为单位，而不是 intra-GPU 切片。
  3. 边界与 MoE 权重解耦：扩缩、配比、故障域都以“几张 Attention 卡 + 共享 MoE 池”为单位，而不是“再复制一整份 MoE”。

每张 MoE GPU 常驻一个 Adaptive Persistent Kernel，tile 级调度、抢占、重分配，兼容 CUDA Graph。

独立 KV、独立网络路径。Decode 尽量直连 MoE；Prefill 尽量走 Attention 之间的层次化路径。

共享 Expert 之后，现有 GPU 共享原语都不够用：

同时，共享 MoE 把两阶段耦合到同一通信平面：双边协议在跨阶段调度下可能死锁；预留轮询 SM 又浪费算力。因此需要 Attention 发起、MoE 侧无进度依赖的单边通信。

5. 技术一：自适应持久化内核 APK

5.1 设计目标

有效的两阶段共享必须同时满足五点：Graph 兼容、空间复用、时间复用、有界抢占、有界重分配。Launch 级机制（拦截、优先级 stream）做不到 kernel 内切换；硬件划分（MPS / Green Context / MIG）做不到 tile 级时间复用。

5.2 为什么调度单元是 tile，而不是 kernel / layer / warp

  • Tile 是高性能 GEMM 的最小可独立完成单元，尺寸由 register、shared memory、TMA、Tensor Core shape 决定。
  • 输入变长只增加 tile 数量，不拉长单个调度间隔。论文 SM90 DeepGEMM 配置：CTA tile 至多 128×192 输出块 + 128-wide reduction。
  • 各 MoE 侧操作的 tile 边界落在 2.2–25.3 μs，与总操作长度无关。
  • 只在 tile commit 后切换：accumulator、TMA、shared memory、通信状态都已落地，无需 checkpoint / restore / 重算。
更细的抢占要保存流水线状态；更粗的（kernel/层）会留下毫秒级阻塞。Tile 是“现代 MoE kernel 特征（TMA multicast、CTA cluster、warp specialization）还能保住”的最细安全边界。

图 8　Tile 是“够短、且不必 checkpoint”的调度单元。蓝色块表示 decode 插入，橙色块是未完成的 prefill tiles。

5.3 运行时结构

  1. 启动前为每个 MoE 操作构建 template（buffer + TMA descriptor）。
  2. Attention server 发出就绪信号。
  3. CTA 0 把 template 实例化进 decode / prefill 队列，更新 layer、token 数、SM budget。
  4. 调度粒度为 CTA-cluster：被 TMA multicast 连在一起的 CTA 必须执行同一 tile。
  5. 不同 cluster 可同时跑不同阶段（空间复用）；同一 cluster 在 tile 边界换阶段（时间复用 + 快重分配）。

全程 GPU 侧完成，无 CPU 介入、无 kernel relaunch，因此兼容 CUDA Graph replay。

图 9　APK 不 relaunch kernel：CTA 0 管队列，cluster 内必须同 tile（TMA multicast），cluster 之间可以一个跑 P、一个跑 D。

5.4 有界协作式抢占

不能让各 warp / CTA 独立在 tile 边界检查——warp-specialized 流水线里，TMA warp 可能在装 tile k+1，math warp 还在算 tile k；cluster 内独立切换会卡在 TMA multicast / cluster barrier。每 tile 排空整个 cluster 又会毁掉微秒级流水线。

APK 沿存储层次传播一次协作决策：

  1. Attention 通过 system-scope 字 P 发出紧急 decode。
  2. CTA 0 在当前操作的 tile 边界读 P，给每个 cluster 写 device-scope 字 pi。
  3. Cluster leader 只读自己的 pi，经 DSMEM 广播，保证 multicast 同伴同操作。
  4. CTA 内第一个 pipeline warp 读决策，warp 内广播，再用 mbarrier 通知后续 warp，避免它们再领取旧阶段 tile。

最慢的 CTA 最多再跑完当前 tile，cluster 就会收敛到新阶段。抢占上界 = 一个 tile 时间 + 一次本地 cluster 检查周期，与被打断操作的总长度无关。

图 10　抢占信号从 system memory → device word → DSMEM → shared memory / warp，避免“半个 cluster 换阶段”造成的死锁。

5.5 在线 SM 重分配策略

离线优化器给出的 decode SM 预算 q 被解释为争用策略，而不是静态分区：

  • 只有一阶段就绪 → 占用全部 CTA cluster。
  • 两阶段争用 → 按当前 decode 的 tile 足迹 xmoe 相对离线期望 xmoe★ 缩放 q，向上取整到 cluster 倍数，并设 Qmax 保护 prefill 进度。
  • 优先保住 decode：已开始的输出比新请求的输入更时延敏感。
q′ = min( Qmax, ⌈ q · xmoe / xmoe★ ⌉c )

图 11　在线重分配优先保住 decode（已开始的输出更时延敏感），但绝不把 GPU 切成两堵墙。

6. 技术二：Attention 发起的单边 MoE 通信

6.1 双边协议在共享 MoE 上为什么会出事

传统 MoE all-to-all：发送端写入有界 ring buffer，接收端轮询、scatter 到最终 tensor、回信用额度。进度依赖双方。共享 MoE 后，部分 rank 可能在跑 prefill kernel、部分在跑 decode kernel——每个阶段都在等被另一阶段占用的 rank 上的 receiver kernel，ring buffer 排不空、credit 回不来，发送端退不下来，形成跨阶段死锁。

预留轮询 SM 能保活性，但 MoE 流量突发，这些 SM 大部分时间空转；借给计算又不安全，因为 receiver 进度会再次取决于“每个 rank 当时是否腾得出 SM”。网络侧，H800 上 DeepSeek-V3 报告节点内 NVLink 160 GB/s、跨节点 IB 仅 50 GB/s（3.2× 差距），prefill 突发很容易饿死 decode。

图 12　双边协议假设“每个 rank 上总有匹配的 receiver”。共享 MoE 后这个假设不成立。

6.2 单边 Push / Pull

APK 持久化要求操作 template、tensor 地址、通信描述符启动前固定，因此可以为最大 routed-token 量预分配最终 dispatch / combine buffer，并暴露给 Attention server，去掉中间 ring buffer。

  • Dispatch = Attention 侧 push：路由确定目的地和最终偏移后，经 NVLink peer store 或单边 RDMA write 直接写入；payload 可见后再发 ready。APK 不协调传输，只在 tile 边界看到信号后调度计算。
  • Combine = Attention 侧 pull：Expert 写完最终 combine buffer 并发布 done；Attention GPU 上极轻的单线程 WaitDone 观察到完成，再 NVLink load / RDMA read 拉回。WaitDone 只挡依赖它的 pull，计算流可继续 TBO/SBO。

MoE 侧不再需要匹配通信 kernel，也不再预留轮询 SM。于是可以出现跨阶段算通重叠：decode 等 combine 时跑 prefill tile；prefill 传输在飞时插入紧急 decode tile。两阶段依赖链独立，不受单阶段 TBO/SBO 约束。

图 13　Dispatch 是 Attention push，Combine 是 Attention pull。MoE 侧没有通信进度，两阶段依赖链因此可以交错。

6.3 层次化 Prefill 路径与流量隔离

单边消除了 MoE 侧协调，但 RDMA 仍可能被争用。策略是：

  • Decode：尽量 Attention ↔ MoE 直连（本地 NVLink 或远端 RDMA），保时延。
  • Prefill：尽量把 scale-out 流量放在 Prefill Attention 之间。源端把激活经 RDMA 发到目标节点同 local rank 的 prefill server，再经 NVLink 按 chunk multicast 给该节点上被激活的 experts。Combine 反向：NVLink gather + Prefill-only RDMA 返回。同一远程节点上多个 expert 只过一次昂贵的 scale-out 链路。
  • 目标节点没有 prefill server 时，才走直连 RDMA，但给 prefill 更低优先级的 IB virtual lane，保护 decode。

放置优化器会尽量把 prefill server 铺开到各节点，让层次化路径成为常态。

图 14　拓扑先隔离，QoS 做兜底。H800 上 NVLink 160 GB/s vs IB 50 GB/s，层次化是在省那条更窄的路。

7. 技术三：跨栈放置优化器

7.1 为什么必须联合搜索

改 prefill server 数量会同时改变并行度、KV 容量和通信路径。单独优化放置、重叠或 GPU 共享，都可能选出“局部高效、联合 SLO 不可行”的配置。优化器因此联合选择：Attention/MoE 并行、server 放置、P:D 配比、重叠策略（TBO/SBO）、APK 共享策略。

7.2 Goodput 目标

配置表示为布局 ℓ 与争用下的 decode SM 预算 q。Bp / Bd 是满足各自 SLO 的最大 batch，Tp / Td 为建模迭代时延，Õ 为平均输出长度：

G(ℓ, q) = min( Bp / Tp ,  Bd / (Td · Õ) )

取 min 是因为一条请求消耗 1 次 prefill 迭代、约 Õ 次 decode 迭代，goodput 由更窄的那一端决定。只在两阶段 SLO 都可行的候选中最大化 G，避免单独把某一阶段堆满。

图 15　单独把 Prefill 或 Decode 堆满没有意义。流水线平衡才是目标。

7.3 Tile-aware 时延模型

全集群穷举实测不可行。做法是：在少量代表 GPU 上 profile Attention / MoE（含 APK 开销）并插值；网络时延用 routed bytes × 测得带宽 × 层次化路径直接算，不必占 GPU。

对组件 c 拟合：

t̂c(x, s) = αc + βcx + γcx s + δcx s2

Attention：x 为本地 batch，s 为序列长度。MoE 的关键观察是：原始 routed-token 数不够，时延跟的是执行的 tile 数。Expert e 收到 me 行、tile 高 Mt 时：

xmoe = Σe | me > 0 ⌈ me / Mt ⌉

再用 x = xmoe, s = 1 代入拟合式。同 token 数、不同活跃 expert 数，时延可以差很多——每个活跃 expert 至少触发一个 tile 的 metadata、权重搬运和计算。这是 tiled MoE kernel 的一般性质，不是某一模型和 GPU 的特例。

图 16　用 token 数估 MoE 时延会漏掉 per-expert tile 税。优化器因此对 xₘₒₑ 插值，而不是对 raw routed tokens。

7.4 离线搜索

Algorithm 1：枚举布局 → 内存/KV 不可行则丢弃 → 枚举 q → 对两阶段二分最大可行 batch → 用关键路径（TBO 取两条路径 max，SBO 取 routed/shared/通信 max 再加 Attention）估迭代时延 → 两阶段都可行则计算 G，保留最大者。选出的配置同时钉死并行、放置、重叠和期望 decode SM 预算。

图 17　离线搜索只在少量 GPU 上 profile，网络时延用带宽公式算，避免对每个集群布局做全量实测。

8. 实验设置与主要结果

8.1 实现与测试床

  • 实现：改 DeepGEMM、DeepEP v1、SGLang。把两个 grouped GEMM、激活、MoE 前后处理、CTA-cluster scheduler 融进 MoE GPU 上的长寿命 persistent kernel；host 启动时把 tile size JIT 成常量以降寄存器压力。DeepEP 的 receiver-driven all-to-all 换成 Attention 发起的 M-to-N 路径；IBGDA 定制 nvshmemi_ibgda_get_nbi_warp 做细粒度 remote pull。
  • 模型：单节点 MiniMax-M2.7（FP8 约 230 GB，每 token 激活约 7.0B routed 参数，Full Attention）；多节点 GLM-5.1-FP8（FP8 约 756 GB，routed 专家总参 724.8B，每 token 约 22.6B，DSA）。两者均为每层 256 routed experts、每 token top-8。
  • 硬件：NVIDIA H800，节点内 8 卡 NVLink；多节点最多 3 机，每机 8×200 Gbps IB。不同节点数时吞吐统一报 每节点 requests/s。

结果解读：

  • Chunked Prefill 最差：反复读权重/KV、重复 MoE 通信；大 chunk 仍干扰 decode，小 chunk 伤 prefill 效率。长请求上甚至无法维持 SLO。
  • 朴素共置：为做大 batch 激进跑 prefill，长 kernel 拖垮 decode。
  • PDD：隔离干净，但复制 MoE、KV 变小、P:D 配比僵硬，prefill 侧即使 decode 不是瓶颈也用不满资源。更大的 GLM 在 24 卡上直接 OOM，反衬共享 Expert 的内存价值。
  • PDMux：Green Context 好于共置，但跟不上每 rank 实际活跃 expert 数；网络未隔离；并行度被迫加大。短请求上 TP Attention 给 PDMux 一点 TTFT 优势，故 GLM×ShareGPT 与 ExpertPlex 接近；长请求上网络干扰和利用率问题暴露，ExpertPlex 拉开到 1.66×。

8.4 机制消融与开销

APK vs 其他 GPU 共享

Pareto 前沿上，只有 APK 同时进入 decode 低时延区并保持 prefill 高性能。优先级 stream 无法隔离已启动 kernel（decode 慢 13.79×）；MPS / Green Context 接近独占 decode，但把 prefill 拖慢 3.33× / 4.07×。APK 对 decode 仅 +8%，prefill 仅 1.12×。

调度与通信开销

Prefill 连续布局：调度相对 DeepGEMM <12%。Decode masked 布局：调度 <20 μs，多活跃 expert 时相对开销 <10%。16 卡上单边通信正常模式与 DeepEP v1 差约 5%；低时延模式差约 45 μs 内。

抢占间隔：MiniMax 全部 MoE 操作 <25.3 μs，GEMM <10.7 μs。对比 LithOS / Bless / GPreempt / PipeSwitch / REEF 等（它们并非面向 MoE，也不支持 TMA multicast 等现代特征）：REEF 最好报道约 35 μs 且要重算被抢占 kernel。APK 在自然 tile 边界切换，间隔内仍做有效计算，无 checkpoint/restore/重算。

图 19　微基准：优先级 stream 牺牲 decode，固定划分牺牲 prefill。APK 是唯一同时靠近“独占 decode + 高 prefill”的点。

9. 贡献、局限与后续方向

9.1 论文自称的三点贡献

  1. 混合架构：去重 MoE 权重、复用动态稀疏计算、分离 Attention 以降低每阶段并行度与通信，同时保留细粒度隔离。
  2. APK 的 tile 级抢占/重分配 + Attention 发起的单边通信，减少网络干扰并实现跨阶段算通重叠。
  3. 跨栈联合优化，并在两个前沿 MoE 上验证 goodput。

9.2 我认为真正“新”的地方

  • 拆分边界选对了。Attention-Expert 分离（MegaScale-Infer、Janus、Step-3）已有，但它们多建在实例级 PDD 之上，会继承复制 Expert、放大部署单元、引入 pipeline bubble。ExpertPlex 把“阶段隔离”下沉到 Attention，把“权重共享”留在 MoE，这是针对 95%+ Expert 占比的结构解，而不只是调度技巧。
  • 调度单元与现代 GPU kernel 对齐。很多抢占系统在 kernel 边界或要 checkpoint。APK 承认 TMA multicast / CTA cluster / warp-specialized pipeline 的约束，把安全抢占点钉在 tile commit，这是工程上很“懂 kernel”的一刀。
  • 通信协议为共享 MoE 重写，而不是继续套 DeepEP 双边语义。死锁分析比“我们换了 RDMA write”更重要：共享计算平面必须同时改通信进度模型。
  • 时延模型用 tile 足迹而不是 token 数。这对所有 tiled grouped GEMM 都成立，可迁移到别的 MoE serving / 训练负载均衡工作。

9.3 局限与可质疑点

点说明
硬件与实现绑定深 H800 + NVLink + IB + DeepGEMM/DeepEP/SGLang/IBGDA。Hopper 的 TMA、DSMEM、CTA cluster 是 APK 的前提；到 Blackwell / 其他厂商需要重做 kernel 与同步层次。
预分配最终 buffer 按最大 routed-token 量预留，去掉 ring buffer 换来协议简化，但内存占用更“硬”。高并发、高 top-k、或 EP 很宽时，buffer 本身可能成为新的容量税。
Baseline 不完全同构 PDMux 只能 TP Attention；若干 baseline 无法表达 24 卡细粒度布局，GLM 实验用 16 卡再按节点归一。方向正确，但部分倍数含“布局表达力”而不只是调度质量。
GLM 上没有 PDD 数字 24 卡 PDD OOM 本身能说明共享 Expert 的内存收益，却也让“相对 PDD 2.01×”只建立在较小的 MiniMax 单节点 1P1D 上，外推到百卡 DeepSeek 式部署仍是论证而非实测。
故障与弹性多为定性 引言强调更小 blast radius 和更细扩缩粒度，评估几乎全是 goodput / SLO / 微基准，缺少注入 rank 故障、在线扩缩的实验。
优化器是离线 + 平均负载 在线只自适应 SM 预算。突发流量、输入长度分布漂移、expert 热点漂移，仍依赖 APK 的局部 multiplex，没有闭环重搜布局。
相关系统对比偏“机制级” 与 LithOS / REEF 等比的是抢占间隔，不是端到端 MoE serving。与 MegaScale-Infer / Janus 的端到端对比缺失，而这恰恰是最近最接近的架构邻居。

9.4 和相关工作的位置

  • PDD（DistServe, Splitwise, Mooncake）：隔离对，粒度错。
  • Chunked Prefill / POD-Attention：减轻干扰，引入重复访存。
  • GPU 划分共置（PDMux, Nexus, semi-PD, Bullet）：去重对，时间适应性和网络隔离不够。
  • Attention-Expert 分离（MegaScale-Infer, Janus, Step-3）：模块异构对，但若仍按阶段复制整条 Expert 流水线，PDD 的粗粒度会回来，并多一层 pipeline bubble。
  • Megakernel / 算通重叠（NanoFlow, FLUX, Comet, SonicMoE）：多服务单阶段或单层流水；ExpertPlex 可与之兼容，并额外做跨阶段重叠。
  • MoE 负载均衡 / Attention offload / 序列并行：正交，可叠加。

图 20　ExpertPlex 的位置：吸收 PDD 的阶段隔离、共置的权重去重、Attn-Expert 分离的模块异构，但拒绝“再复制一份 Expert 池”。

10. 对后续研究与工程的启发

1. 先找“参数质量比”

分离什么、共享什么，应看参数占比、计算密度、通信半径，而不是沿用稠密模型的实例边界。MoE 时代，默认共享 Expert、特化 Attention 是更自然的默认假设。

2. 调度粒度要对齐硬件原语

CTA cluster 和 TMA multicast 决定了“能安全抢占的最细点”。忽略这一点的抢占系统，要么破坏高性能 kernel，要么只能停在 kernel 边界。

3. 共享计算必须重写通信进度

计算平面一共享，双边 liveness 假设就破了。单边 + 最终 buffer + 发起方在 Attention，是一套可复用的协议模式。

4. 用 tile 而不是 token 建模 MoE

稀疏路由的代价有两项：token 体积，以及 per-expert 的 tile 启动税。负载均衡、批构造、SLO 估计都应显式用 xmoe。

5. Goodput 用短板而不是平均

G = min(prefill 吞吐, decode 吞吐 / Õ) 强迫系统做流水线平衡，避免“某一阶段很好看、请求却卡在另一端”。

6. 网络隔离可以靠拓扑而不只靠 QoS

Prefill 层次化走 Attention–Attention，Decode 直连 MoE，比单纯 IB 优先级更干净；QoS 只做兜底。

可做的后续工作

  1. 把同一套混合边界做到 DeepSeek-V3/V4 百卡单元，直接和官方 32P+320D 比弹性、故障恢复和 KV 容量。
  2. 与 MegaScale-Infer / Janus 做受控同模型对比，分离“Attention-Expert 分离”和“跨阶段共享 Expert”各自的贡献。
  3. 在线布局重配置：流量或长度分布漂移时，不只改 q，而是迁移 Attention/MoE server 角色。
  4. Buffer 的动态租约或分层：热 expert 预分配最终 buffer，冷 expert 回退 ring buffer，减轻内存税。
  5. 把 APK 的 tile 调度抽象成可复用 runtime，服务不止 MoE FFN，也包括 MLA / DSA 等同样 tile 化的 Attention kernel。
一句话收束：ExpertPlex 把 MoE serving 的主矛盾从“Prefill 和 Decode 要不要拆开”推进到了“在权重已经 95% 都是 Expert 的前提下，阶段隔离的最小充分边界在哪里”。答案是：Attention 按阶段拆，Expert 跨阶段共享；再用 tile 级内核和单边通信，把共享重新做成可隔离、可重叠、可优化的。
