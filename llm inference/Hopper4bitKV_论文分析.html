1. 一句话结论

4-bit KV 大约只读 FP8 一半的字节，但 Hopper 没有 FP4 硬件，解码必须在软件里做。论文用 NVBit 说明：vLLM 现成的 FlashInfer NVFP4 和 Triton UltraQuant，要么指令太多，要么加载、解码和矩阵乘串行，H200 上只能吃到 10–20% 的显存带宽，解码甚至比 FP8 慢。作者写了一个 Hopper 原生的 decode kernel（NVFP4 / MXFP4 / INT4），用 TMA 生产者 warp 与两组计算 warpgroup 重叠，在写入时把 cache 排成寄存器可直接喂给 tensor core 的布局，并交换矩阵操作数以免小 query group 填 padding。配上准确率配方后，做成 vLLM 0.33 的插件。

2. 问题：省了字节，Hopper 上却更慢

长上下文和大批次 serving 里，每一步 decode 都要读完整段 KV，注意力受显存带宽限制。以 Llama-3.1-8B（32 个 query 头、8 个 KV 头、head dim 128）为例：一行 BF16 的 K 或 V 是 256 字节，大约只喂 1,024 次浮点运算，约合每字节 4 次；H200 的标称密度是每字节约 206 次 BF16 tensor-core 运算（989 TFLOPS ÷ 4.8 TB/s）。步时因此接近「读了多少字节 ÷ 带宽」，少读字节本应更快，也能在一张卡上放下更多请求。

Blackwell 能在硬件里解码 NVFP4 这类 4-bit 格式。现存机器仍以 Hopper（H100 / H200 / H20）为主，只支持 BF16 和 FP8，4-bit 必须在注意力 kernel 里用软件拆开再乘 scale。论文在 H200、batch 32、16K 上下文上测到：FlashInfer 的 BF16 是 0.495 ms，FP8 是 0.395 ms（另一次任务里 XQA 是 0.255 ms），NVFP4 是 0.669 ms。也就是说，vLLM 用户在 Hopper 上打开 --kv-cache-dtype nvfp4，省了显存，解码却更慢。

QServe 已经在 A100 上指出：朴素 INT4 注意力可能比 INT8 更慢，因为 CUDA core 上的反量化会变成计算瓶颈。Hopper 把这个问题变得更紧：带宽涨得比指令发射更快，满带宽时每个字节能花的指令更少。

格式本身的字节数（含 scale，每行 128 维）见表：BF16 256、FP8 128、INT4 68、NVFP4 72、MXFP4 / UltraQuant 68。4-bit 相对 FP8 的字节比大约是 128/72 ≈ 1.78，这是 kernel 加速的理论上沿；只要软件解码吃掉的指令超出 Hopper 的发射预算，这个上沿就拿不到。

3. 现有 kernel 卡在哪

论文把 H200 满带宽时的发射预算估成大约每字节 7 条线程指令，再用 NVBit 数现有 4-bit decode kernel 的指令，并对照实际用到的带宽。结论是两类独立的原因：指令太多，以及加载、解码和矩阵乘互相等待；不同 kernel 卡在不同组合上。

4. 五个设计选择

作者自己也写了：单独拿出来，这些技巧都不新。流水结构跟 FlashAttention-3、LiquidGEMM；小 M 时交换 A/B 是常见 GEMM 做法（vLLM 的 SM90 FP8 GEMM 也这么做）；BitDecoding-FP4 在 Blackwell 的原生 FP4 tensor core 上对两次注意力矩阵乘都做了操作数交换；BitDecoding、Marlin、TensorBridge、FuTransformer、FServe 都从布局或寄存器里的反量化上做过类似的事。这篇加上去的，是把它们用在 Hopper、没有 FP4 硬件时的 E2M1（NVFP4、MXFP4）以及 INT4 decode 上，并且要快过所测的 FP8 decode kernel。

1. 重叠的流水

一个 TMA 生产者 warp 负责把 cache 搬进来，两个计算 warpgroup 做解码和 wgmma。加载、解码和矩阵乘不再串成一段。

2. 交换操作数

把小的 query group 放到 N 维，解码后的 K 和 V⊤ 作为 wgmma 的寄存器操作数。softmax 不必在 padding 行上做功。只有 P 走共享内存（每个 warpgroup 2 KB）。

3. 写入时排布局

cache 格式由自己控制，写 K 的每一行、以及每 256 token 的 V 块时就做置换，使每个线程的 fragment 落在连续的 16 字节块里：一次 128-bit 共享内存加载，无 bank conflict，无 shuffle。Scale 同样置换。置换发生在 cache-write kernel，不是离线预处理权重。

4. 便宜的重建

INT4 用 FP16 魔术数把码值嵌进浮点表示，每值大约 0.625 条指令。E2M1 则把指数、尾数和符号放到 FP16 的对应位，精确得到原值乘 2−14，包括次正规 0.5。

5. Scale 的处理。INT4 的 per-token scale 和 zero-point 折进乘法两边（论文写明用了 FOSCAR 的仿射折叠）。NVFP4 的每 16 个值一条 E4M3 scale、MXFP4 的每 32 个值一条 E8M0 scale，只能在寄存器里用成对的半精度乘法，因为 Hopper 没有 block-scaled tensor core。早期构建里，NVBit 数到 FP4 每值 3.8 条指令、INT4 2.6 条；其中大约 0.7 条来自 scale，其余多半来自 E2M1 重建。

测试还抓到两处数值坑。(1) INT4 魔术数里的 1024 若在乘法之后再减，累积几千 token 后相对误差会到 2×10−2，与 Hopper tensor core 累加不是 IEEE 就近舍入（会截断）相符；改到乘法之前减，误差降到 1.3–2.3×10−4。(2) 真实的 Llama-3.1-8B KV 里，强 sink 旁边成千上万的小注意力权重会掉进 FP16 次正规；把 P 乘上 210 即可，几乎没有代价。随机测试数据看不出第二类问题。

FP4 kernel 读 vLLM 风格的 paged cache（64-token 页、block table、每序列长度），与连续 cache 速度相当（0.99–1.035×，页被打乱）。INT4 kernel 只支持 dense。每条序列最前面 4 个 BF16 sink token 放在 4-bit cache 外面，在 split merge 时拼回去。Kernel 以 G=4 或 8 运行，其他 G≤8 用零把 q 补到这两个宽度。

5. 准确率配方

配方本身没有新组件，论文测的是每一步在同一套设定上各贡献多少。默认配方是：NVFP4，K 去均值，对 K 做 Hadamard 旋转，4 个 BF16 sink，第 0 层保持 BF16。

块 scale 把异常值关在自己的 16 维组里，Llama 和 Qwen3-8B-Base 的 KL 因此大幅下降。旋转在 Llama 上有用，但在 Qwen3-8B-Base 上会把很大的逐通道均值摊到每一组，KL 从 0.029 升到 0.281；去掉均值之后，旋转才重新变成 8–14% 的小收益。去均值是救 Qwen 家族的那一步：这些均值对 softmax 是公共偏置（q·μ 对所有 key 相同），量化前减掉不增加读时成本。它需要 sink：sink=0 时，去均值会让 Llama 变差。

Qwen2 家族的推理模型在 FP8 KV 下就会崩溃，不必等到 4-bit。论文复现了已有报告，并补了机制：第 0 层 K 的均值几乎就是 key 投影偏置经过 RoPE 之后的样子，用权重和 rope_theta 就能算，约占第 0 层均值能量的 99.7–100%。只把第 0 层留在 BF16，就可以恢复 FP8；4-bit 还要加上去均值。同一套 R1 蒸馏如果底座是 Llama（没有这个 key bias），就不会崩溃。只靠一个固定中心去偏、全部层仍用 FP8，在 R1-Distill-Qwen 上恢复得不完整，所以主配方仍然选择把第 0 层留在 BF16。

6. 怎么接到 vLLM

实现是 vLLM 0.33.0 的插件，替换 4-bit 后端的 cache 写入、decode 和 prefill 注意力。Prefill 注意力改走 FlashAttention-3 的 BF16（vLLM 的 4-bit 后端默认走 FlashAttention-2；PR #47531 也提过类似切换）。K 的均值是离线标定的静态逐头向量，页大小 64 token。

对照的 FP8 默认走 FlashInfer，并且要求日志里出现 decode_backend=xqa。论文特别提醒：FlashInfer 只有在访问 NVIDIA artifact 服务器的网络检查通过时才会用更快的 XQA；检查失败时（他们集群在代理后）会静默退回 FlashInfer 自己的 decode kernel，不报错。Serving 实验因此显式设置了 VLLM_HAS_FLASHINFER_CUBIN=1。

附录 A 还向 vLLM 报告了几件事：UltraQuant 格式里的一个 scale 常数、第 0 层 FP8 失败、一个前缀缓存正确性缺陷，以及哪些评测能抓住这类问题。跳过某些层时，FlashAttention-3 会在部分模型上崩溃（#65821，修复提案 #65891）。

7. 实验怎么做的

速度主平台是 H200 SXM（141 GB）；部分准确率和两处标明的速度用了更慢的 H200 NVL，没有把两种机器上的速度比混在一起。H100 SXM5 只用于 kernel 数字。带宽比例按读到的 K、V 字节除以标称峰值（H200 4.8 TB/s，H100 3.35 TB/s），不算 q、输出、block table、部分结果和 sink；一次大的 device copy 能到 H200 峰值的 86–90%。

Kernel 基准：CUDA 12.8、FlashInfer 0.7.3、FOSCAR commit 9089e1f、BitDecoding hopper 分支 584d0d3，随机 K/V/q，Llama-3.1-8B 的头形状。每个时间是 5 次预热后 50 次调用的中位数，每次前冲洗 L2。作者按 1–64 为每个 shape 选最好的 split，基线用各自的启发式，所以 kernel 表略偏向自己的 kernel。插件在 vLLM 里用的是固定规则 min(16, ⌊264/(B·Hkv)⌋)，不再按 shape 搜索；11 个主 shape 里有 9 个与搜索一致。

vLLM 侧用 0.33.0，gpu_memory_utilization=0.90。纯 decode 用 vllm bench forward（dummy 权重、CUDA Graph）。端到端用 vllm bench latency 和 throughput。Serving 是 Poisson 到达，SLO 采用 MLPerf Llama-3.1-8B server 的目标：TTFT ≤ 2 s，每输出 token 时延 ≤ 100 ms，至少 99% 请求满足才算可持续。准确率是 greedy；MATH-500 看规范化后的最后一个 boxed 表达式，多次运行做配对置换检验。

8. 结果怎么读

Kernel：能超过当时最快的 FP8 decode

在 H200 的 11 个 shape 上，作者的 NVFP4 相对 FlashInfer FA2 FP8 是 1.4–2.3×，相对更快的 XQA 是 1.2–2.1×（Table 4 全表是 1.24–2.05×）。把尚未合入、但评审认为可能成为 vLLM Hopper FP8 路径的 FlashAttention-4 原生 FP8 加进来之后，它在 11 个 shape 里的 8 个比 XQA 更快、最多快 1.5×，带宽在 batch≥8 时达到峰值的 85–89%。即便如此，作者的 kernel 仍然处处领先，幅度缩小为 1.12–1.49×（Table 5，CUDA Graph 重放，论文认为这是更保守的算法）。INT4 在相等字节下，15 个 shape 都快于 FOSCAR 的 INT4；H200 上是 1.08–1.61×。FOSCAR 的 H200 时间与其公布的 H100 数字接近，等于没吃到 H200 多出来的带宽。H100 上双方差距缩小：作者 INT4 为 1.02–1.31×，NVFP4 为 0.94–1.21×。

batch 32–128、16K 时，NVFP4 吃到 H200 峰值的 67–75%，INT4 为 74–83%。消融表明：去掉 E2M1 重建，B≥8 时只要全 kernel 时间的 0.87×，解码大约占 13%；其余空隙在流水、矩阵乘和 softmax。MXFP4 少读 6% 的字节，耗时却几乎一样，说明 H200 上 FP4 已经偏计算侧。H100 带宽/指令更低，两种格式都接近显存上限。

进 vLLM 之后，加速会明显变小

Llama-3.1-8B、完整配方，相对 FlashInfer FP8（XQA）：batch≥8 时每步 1.12–1.64×，batch=1 时每步 1.01–1.05×，端到端每输出 token 时延 0.96–1.03×。同一张表里，vLLM 自带 NVFP4 在 batch≥8 时是 FP8 的 0.43–0.72×，也就是慢 1.4–2.3×。Qwen3-32B 在 batch≥8 时只有 1.05–1.18×，Qwen3-30B-A3B（MoE）是 1.11–1.32×，Qwen2.5-72B（FP8 权重）是 1.04–1.18×。模型越大，一步里权重读取占比越高，注意力本身的加速就越不明显。

原因写得很清楚。Llama-3.1-8B 一步还要读 16 GB BF16 权重，按峰值带宽至少 3.3 ms；8×16K 时整步是 6.69 ms，注意力只是少数。一次剖析里，decode kernel 本身是 1.50 ms 对 2.88 ms（1.92×），加上 sink 合并、cache 写入、q 旋转和第 0 层 BF16 之后，与注意力相关的 kernel 合计 2.00 ms 对 3.02 ms；两边 GEMM 都大约 4.0 ms。Cache 能装 2,867,200 个 token，对 FP8 的 1,761,600，正好 1.63×。离线吞吐（8K/16K 输入、512 输出）只有 1.06–1.10×；偏 decode 的 16K 进、2,048 出是 1.17×，若对照默认 FlashAttention-3 FP8 路径则是 1.40×。

64×32K 是容量效应而不是逐步加速：FP8 的 cache 装不下全部 64 条（2.1M token 对 1.76M），每输出 token 38.7 ms 对 52.2 ms（1.35×），但整段请求（256 个输出 token）反而是 86.8 s 对 85.0 s，因为 2.1M prompt 的 prefill 慢了 7%（77.0 s 对 71.7 s）。Prefill 单独测 8 条 32K prompt，是 9.29 s 对 8.66 s。TTFT 端到端慢 1.5–6%。

Serving：思维链流量上赢在容量，prefill 重的流量上会输

思维链风格（约 1K 进、8K 出）在 1.25 req/s 及以下，两边都能让全部列出的请求满足 SLO，作者这边平均每输出 token 时延低 23–27%，cache 占用大约一半。超过这个速率，FP8 的 cache 先满并开始抢占。单卡最高可持续速率（至少 99% 满足 SLO）见表：

接近饱和时，vLLM 默认的单个 API server 进程会先限制作者这一侧（最多 19% 请求错过 SLO）；改成 4 个进程后，1.35 和 1.5 两个种子上作者一侧全部满足，FP8 则几乎不变，因为它的问题是 cache 满。论文还如实留下了两次没有复现的运行，没有从结果里删掉。

准确率：在所测任务上与 BF16 KV 无显著差，但统计只能排除大约 3.5 分以上的损失

vLLM 里完整配方在 7B 到 32B、以及一个 MoE 上，MATH-500 等任务相对 BF16 KV 的差值都落在运行噪声里。例如 Qwen2.5-7B-Instruct 五次平均 72.0 对 71.2（95% CI [−1.6, +3.3]），R1-Distill-Llama-8B 三次都是 67.7。困惑度上，配方相对 BF16 通常只有 +0.03–0.15%，而 FP8 KV 在 Llama-3.1-8B 是 +0.94%，在 Qwen2.5-72B 是 +0.95%。论文没有测 KV 量化是否会在困惑度几乎不变时拿掉安全拒答。Table 13 的区间大约 ±2.5–3 分，这些比较排除不了更小的损失。

作为对照，vLLM 自带 NVFP4 在 Qwen2.5-7B-Instruct 的 MATH-500 上三次都是 0.0%，困惑度 1542 对 6.27；FP8 也只有 1.6%。没有 key bias 的 R1-Distill-Llama-8B 和 Phi-4 上，自带 NVFP4 的任务分并不崩，只是慢。

9. 落地可行性

代码以 Apache-2.0 放在 thomaszhang2661/kv4-hopper，是 vLLM 插件，不是已经合进主线的后端。评测钉在 vLLM 0.33.0 和 H200/H100。对已经在 Hopper 上开了 NVFP4 或 UltraQuant、却发现 decode 变慢的人，这条路径是直接可试的；论文给 vLLM 用户的实用说明也很具体。

什么时候值得接：decode 占主导、KV 显存是限制（batch≥8、长输出、大模型单卡）。思维链风格、cache 先满的服务，收益会随模型变大而更接近容量比。什么时候不该指望它：batch=1 的低延迟、prefill 很重的流量、以及还没覆盖的 MLA、head dim 256/64。打开 FP8 时先确认日志里真的是 XQA，否则基线会被静默换掉。Qwen2 家族推理模型在 FP8 KV 下可能无报错地崩掉，需要跳过第 0 层；跳层本身在部分模型上会让 FlashAttention-3 崩溃。

和仓库里已有工作的关系：BitDecoding 解决的是低比特 KV 如何用上 tensor core；这篇默认读者已经接受 4-bit KV，焦点是 Hopper 上现成路径为什么慢、以及怎样在 vLLM 里跑赢 FP8。FOSCAR（接在 SGLang 上的 INT2/INT4 折叠）是 kernel 对照之一，作者的 INT4 在 H200 上更快，在 FOSCAR 针对的 H100 上优势变小。两者目前都还不是 vLLM / SGLang 默认路径。

10. 局限：这些倍数依赖什么假设

  • 形状覆盖。只支持 head dim 128、每个 KV 头 1–8 个 query 头。Kernel 按 G=4 或 8 跑，其余靠补零，浪费最多 1/8 的 tensor-core 工作。没有 MLA（DeepSeek-V3/R1），没有 head dim 256（Qwen3.x、MiniMax，也是 vLLM UltraQuant 的目标）或 64，基本没有滑窗模型。INT4 只有 dense、且 G=4。
  • Serving 场景。好吞吐扫描主要是一种 GPU、随机 prompt、思维链风格流量。没有对比共享前缀、真实 trace、分离式 prefill，也没有在更大模型上扫其他负载。张量并行只在 Qwen2.5-72B、TP=2 上做了正确性检查（前缀缓存、跨请求前缀命中、chunked prefill），没有测速度和准确率。
  • batch=1。64K 上下文时 kernel 大约只到 38% 带宽（16K 时 18%）。一次剖析里，decode kernel 是 382 µs 对 FlashInfer 的 702 µs，但 31 个 4-bit 层加上 sink 合并、写入和 q 旋转后是 848 µs 对 847 µs。下一步是把 sink 合并折进 split reduction、把 q 旋转折进 prologue。
  • 基线。比过 FlashInfer FA2 / XQA、vLLM 默认 FlashAttention-3 FP8，以及 FlashAttention-4 原生 FP8，没有直接比 TensorRT-LLM。在包含那两个未合入 PR 的开发构建里，配方相对 FlashAttention-4 FP8 在 batch≥8 时是 1.04–1.24×，batch=1 持平。一份尚未接入插件的原型把 K 改走类似 XQA 的 FP8 tensor-core 路径，在 batch≥8、每序列至少 16K 时比当前 kernel 再快 1.12–1.14×，离线 KL 升高 14–17%，论文其余数字都不用它。
  • 统计与安全。MATH-500 这类比较排除不了大约 3.5 分以下的准确率损失。没有评估量化是否削弱拒答。个别 serving 运行没有复现，论文留在了结果文件里，但随机种子和 API 进程数会明显影响饱和点附近的数字。
