1. 一句话结论

推理模型的成本往往不在 prompt，而在很长的思维链。这些轨迹里有大量循环、自我验证和纠错，token 不一定有用，但注意力分数仍然可以很高。RoCoKV 在 RocketKV 的稀疏注意力之上加了两件事：按模型此刻的把握动态调整保留多少 KV，以及用最近上下文的摘要把重复内容的分数压下去。更关键的是工程侧——三阶段融合的 CUDA 解码 kernel，以 platform_plugins 插件接到 vLLM，不改引擎内部，保留 paged KV 布局和 CUDA Graph，压缩省下来的带宽才变成端到端加速。

2. 问题：高注意力不等于有用

对普通 LLM，KV 压缩常常可以靠输入上下文判断哪些 token 重要。推理模型不一样：时延、显存和吞吐的大头往往是生成出来的长思维链，而不是 prompt。这些生成 token 里有很多来自过度思考、循环、自我验证和纠错，缓存里因此堆着不少低价值内容。

麻烦在于，它们在时间上或语义上靠近真正有用的步骤，注意力分数照样可以很高。按注意力裁剪，容易把「看起来重要、其实重复」的 token 留下，把后面还用得着的中间步骤挤掉。裁错了会打断思维链、诱发重复循环，或者把稍后才用得上的证据丢掉。

另一层缺口是系统。很多压缩工作只报告算法层面的 cache 缩小或精度，没有接到生产推理引擎里。压缩本身要打分、驱逐、管内存，这些开销会把省下来的 KV 吃回去。论文引用 Wei 等人（2025）的测量：H2O 在张量并行下，prefill / decode 吞吐只剩 FP16 基线的 0.58× 和 0.69×。R-KV 这类方法在他们后来的 vLLM 实现里，AIME25 时延也是 Full-KV 的 0.94×，是变慢而不是变快。

3. 两个观察

RoCoKV 建立在 RocketKV 之上。RocketKV 把 key 按 page 分组，只用一部分 query 维度做近似 top-k。作者在 DeepSeek-R1-Distill-Llama-8B、AIME25、KV budget 128、采样温度 0.6 上，用下一步分布的归一化熵衡量「这一步有多没把握」，再按十分位观察近似选择的后果。

观察 1：同样的近似误差，没把握时更伤

各十分位里，RocketKV 大约保住精确 top-k 注意力质量的 60%（58.87%–62.39%），key 重叠大约 19%（18.13%–20.38%），误差幅度本身差不多。真正分叉的是后果：模型很有把握时，分布集中，选错几个 key 往往改不了下一个 token；犹豫时几个候选概率接近，同样的误差就能把后续推理带偏。同一预算下，把 RocketKV 的近似选择换成精确 top-k，AIME25 精度从 0% 升到 16.67%。不确定度可以直接用上一步的输出分布估计，不必再做一次前向。

观察 2：生成越长，越容易答错

这和 R-KV、SkipKV 等近期工作一致：推理模型会写出大量冗余、不推进结论的 CoT token，压缩有空间。但识别这些 token 必须便宜，不能在每一步对整个 cache 做两两相似度。作者后面用「最近窗口的质心」近似冗余，就是冲着这一点。

政策很直接：没把握时多留上下文，有把握时剪得更狠；同时少把注意力预算分给重复内容。反向做会明显变差，第 8 节的消融里可以看到。

4. 现有方法差在哪

解码阶段的 KV 压缩大致分成两类。永久驱逐（H2O、SnapKV）能同时减存储和带宽，但删掉的 token 回不来，精度往往掉得明显。Query-aware 选择（Quest、SparQ）按当前 query 挑 token，对精度更友好，通常不减少总存储。RocketKV 走混合路线：prefill 之后做粗粒度永久驱逐，解码时再用混合稀疏注意力做动态选择，存储和带宽都能压，固定预算下精度也还过得去。

作者认为 RocketKV 还是把所有 token 一视同仁，只看近似注意力，没有对着长思维链的特点来分配预算。面向推理模型的后续工作各补一块：R-KV 用注意力重要性加上基于 key 的全局两两冗余来打分；RaaS 用 LRU 风格保住阶段性「里程碑」token，并保留全部 prefill token；SkipKV 在句子级驱逐语义重复，再加激活引导抑制重复生成。这些方法仍然有两个共同问题：冗余计算可能很贵，以及算法收益不一定能在 vLLM 里变成端到端加速。

5. 两个机制

5.1 不确定性引导的自适应剪枝

第 t 步用下一步采样分布 pt 的归一化熵当不确定度，再做时间平滑得到 ūt。两个阈值 τlow、τhigh 把它线性映射成松弛系数 αt∈[0,1]：有把握时 α 接近 0，没把握时接近 1。然后在硬剪枝和松剪枝两套参数之间插值：

kt = (1−αt−1) khard + αt−1 krelax，  ρt = (1−αt−1) ρhard + αt−1 ρrelax

其中 k 是这一步用于精确注意力的 top-k 预算，ρ 是 RocketKV 侧的压缩比。默认相对基准取 khard=0.9kbase、krelax=1.3kbase，ρhard=1.5ρbase、ρrelax=0.9ρbase，ρbase=1。kbase 在 {32, 64, 128, 256} 里取。用的是上一步的 α，不必为了估计把握再跑一遍模型。

5.2 冗余感知的 token 打分

R-KV 对整个 KV cache 做 token 两两余弦相似度，再和注意力重要性相加，cache 一长就贵。RoCoKV 只用最近 w 个已缓存、且已单位化的 key 做质心 μ̂t，每个历史 token 只算一次和这个质心的余弦相似度，得到冗余分 rt,i。最新的那个 token 强制 r=0，免得把正在用的局部上下文也惩罚掉。

近似注意力分数 s̄t,i（非负）再乘上 (1−λ rt,i)。因为两项都在 [0,1] 里，这一步只会降低或保持重复 token 的选择分数，不会把它抬上去。质心是最近窗口的紧凑摘要，不必维护全局相似矩阵。

6. 怎么接到 vLLM

集成走 vLLM 的标准插件机制 platform_plugins，注册自定义 attention backend，只接管 decode——长思维链里 KV 流量正是在这里占主导。调度器、分配器和 paged KV 布局都不动。作者明确写了：不修改任何 vLLM 内部实现。

t 个位置 Phase C 只对入选 token 做精确稀疏注意力 代价随 kt 而不是全长 一张 CUDA Graph kt 只在 device 上 上一步输出分布 → 不确定度 ū → 本步预算 kt、ρt（无额外前向、无 CPU 回读）

图 1｜三阶段 decode 流水线示意。根据论文第 2.4 节与附录 C 重画，不是原文插图。

三个阶段尽量在一次端到端流水线里走完，避免额外整遍扫描 KV，也避免 CPU 来回协调：

  • Phase A 流式扫 cache：算每个 token 对最近窗口质心的余弦相似度，以及用于近似选择的分数，再乘上冗余因子。作者还试了 NHD（vLLM 默认的 page-token-head-dim 布局）和 KT（把 key 转置以便按 hidden 维减流量）两种 kernel，长序列时 KT 更划算，因为 Phase A 要看的 token 远多于最终预算，减 KV 流量是主导因素。
  • Phase B 只读 Phase A 写出的 fp32 分数行做 top-k，不再碰 KV。动态 shape 下常规 top-k 容易破坏 CUDA Graph，他们用片上 bucket 近似 top-k，再在 block 内排序。选中的下标会按 token 位置重排，好让 Phase C 访问同一 page 时合并访存。
  • Phase C 只对入选的 kt 个位置做精确注意力，在线 softmax、分块累加，不物化完整注意力矩阵，代价随 kt 走。

每条请求的 kt、ρt 每步都在变。如果每步在 CPU 上解析这些值，CUDA Graph 就断了。做法是把 kt 做成 device tensor，kernel 自己读；解码期间 CPU 不回读任何 tensor。Phase A 还按请求长度做 split-KV：把一条请求的 cache 切成多段，用不同 thread block 算部分结果再归约，并按工作量给更长的请求分更多 CTA。切分方案在 CUDA Graph 之外、由 attention metadata builder 每步算一次（微秒级），grid 大小只跟 batch 有关，图可以按 batch size 捕获后反复重放。

7. 实验怎么做的

模型是 DeepSeek-R1-Distill-Llama-8B 和 DeepSeek-R1-Distill-Qwen-7B（文中简称 R1-Llama-8B、R1-Qwen-7B）。下游任务是 GSM8K、MATH500、AIME25 三个数学推理基准。最大新 token：GSM8K 为 2048，AIME25 和 MATH500 为 16384。精度按 pass@1，对 8 次正确与否取平均，设置与 TriAttention 等相关工作对齐。对照是 Full-KV，以及作者在同一仓库里复现的 RocketKV、RaaS、R-KV、SkipKV。

精度曲线扫了一系列 KV token 预算。对 RoCoKV，这个预算表示注意力模块里 top-k 的平均访存，不是「cache 里只存这么多 token」的另一种说法，读图时要对齐这个口径。效率实验在 NVIDIA A40 上跑 R1-Llama-8B，budget 512：AIME25 用 batch 16，合成负载用 batch 6。合成负载是给一个 prompt，然后一直采样到设定生成长度，用来看更长上下文下稀疏注意力和 vLLM 集成的吞吐，不是新的精度基准。

8. 结果怎么读

精度上，RoCoKV 在各预算下普遍是压缩方法里最高的一档，并在紧预算时拉开差距。GSM8K 上，最小预算时其他方法掉得更狠，它还能相对稳住。MATH500 需要更长推理，优势更明显：在 R1-Llama-8B 预算 74、R1-Qwen-7B 预算 83 时，论文写明相对 RocketKV 分别高出 46% 以上和 65% 以上（原文是 more than +46% / +65%，未给出该预算下双方的绝对精度，这里按原文保留，不自行换算成百分点）。更难的 AIME25 上，多数压缩方法在紧预算下掉得厉害；平均 token 预算 328 / 325 时，两模型精度分别是 20.83% 和 25.83%，仍高于其他压缩基线。最大评测预算下到 23.75% 和 35.00%，相对 Full-KV 的缺口收窄到 7.5 和 5.0 个百分点——更接近，但不是无损。

9. 落地可行性

和仓库里已有笔记的关系先说清楚：BitDecoding 问的是低比特 KV 能不能有效算；DQ 问的是 Prefill 和 Decode 要不要用不同量化；这篇问的是推理模型长解码轨迹里，按不确定度和局部冗余做稀疏注意力，能不能在 vLLM 里变成真实加速。它不替代前两篇，对象是 decode 阶段的 KV 选择与驱逐，不是权重量化。

相对好落地的点

走官方插件接口，不改 vLLM 内核，保留 paged KV 和 CUDA Graph。自适应预算放在 device 上，避免每步 CPU 同步。冗余只对最近窗口质心做一次余弦，比 R-KV 的全局两两相似度便宜。对照里 R-KV 在 vLLM 中时延回退，说明他们把「接到引擎里还能否加速」当成了必须回答的问题。

现在还缺什么

代码写明录用后才公开，v1 没有仓库、没有现成插件包。效率数字只在 A40 和 8B 蒸馏模型上给出，没有 H100 / B200、没有更大模型和更高并发的同口径表。接 SGLang 被明确留作未来工作。

上手时要注意

它站在 RocketKV 的混合稀疏注意力上，不是从 Full-KV 直接打一个补丁就能得到同样曲线。超参（阈值、λ、窗口、k/ρ 的硬松两档）会影响紧预算精度，反向策略会把结果打崩。压缩不是无损：AIME25 在最大评测预算下仍落后 Full-KV 5–7.5 个百分点。

若只是评估思路，现在就可以按第 5、6 节在自有 vLLM 插件里复现三阶段流水线；若要作为生产开关，需要等代码发布，并在目标卡、目标模型和真实并发下重测时延与精度，不能直接沿用 A40 + 8B 的 1.27×。

10. 局限：这些倍数依赖什么假设

  • 硬件和模型很窄。端到端加速来自 A40 上的 R1-Llama-8B。附录把 Hopper 的 Tensor Memory Accelerator、更激进的 kernel 与调度优化都列为后续工作，不能外推成「在 B200 集群上也是 1.27×」。
  • 任务是数学推理。GSM8K / MATH500 / AIME25 不能代表代码 agent、多轮工具调用或超长上下文服务。效率里的合成负载只用来拉长生成，不是新的正确率测试。
  • 精度有代价。即使是压缩方法里较好的一档，AIME25 在最大预算下仍比 Full-KV 低 7.5 和 5.0 个百分点。紧预算时绝对精度更低（budget 128 上两模型只有 14.58% 和 18.75%）。
  • 超参仍然在。作者自己在局限里写：依赖不确定度阈值和冗余系数；实验里还算稳定，但减少或取消这些依赖会更好部署。
  • 框架覆盖有限。目前是 vLLM 插件。接 SGLang 留作未来工作。
  • 代码未发布。脚注写「We release the source code upon the acceptance of the paper.」在仓库出现之前，第三方只能按论文和附录 C 的 kernel 描述重写。
