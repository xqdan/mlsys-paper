1. 一句话结论

Agent 和迭代检索不是“一次 Prefill + 一长串 Decode”。它们在同一次会话里反复插入增量 Prefill。现有 PD 拆分要么把所有 Prefill 扔回 P 实例（TTFT 和 KV 传输变差），要么按单轮的提示/输出长度去规划副本，都会配错。AMPD 用实时 TTFT/ITL 窗口决定增量 Prefill 在 Decode 实例就地做还是送回 Prefill 实例，再用窗口重排压 TTFT 尾部；离线用 ILP 配 P/D 的副本数和张量并行。相对 Dynamo，SLO 达成平均 +67%；相对 vLLM 平均 +340%。

这篇工作不发明新的 PD 互连，也不改模型。它站在 DistServe / Splitwise / Mooncake / Dynamo 已经把 P 和 D 拆开的前提上，专门补多轮交错：增量 Prefill 的落点、队列顺序、以及按交错负载而不是单轮长度来规划 GPU。

2. 问题：交错 PD 打穿现有拆分假设

LLM 推理仍是两段：Prefill 一次吃完整提示、算 KV，算力密集，决定 TTFT；Decode 逐步吐 token，带宽/显存密集，决定 ITL。同卡混部会互相抢资源。PD 拆分（DistServe、Splitwise、TetriInfer 等）把两段放到不同 GPU，已被 Dynamo 等生产框架采用。后续还有弹性扩缩、异构卡、多模态拆分。这些工作的负载模型几乎都是一轮：提示长度管 P，输出长度管 D。

多轮工作流打破这个模型。ReAct 式 Agent 在生成中插工具调用；迭代 RAG 在生成中再检索。环境返回的文本变成下一轮输入，于是同一次请求呈现 Prefill–Decode–增量 Prefill–Decode…。文中 TTFT 同时度量首次和增量 Prefill。

图 2 · 对应论文 Figure 1。单轮是一段 P 加一长串 D；多轮在生成中间反复插入增量 Prefill。规划如果还按提示/输出长度配卡，等于假装没有中间那些橙色块。

缺自适应调度

为避免 PD 干扰，增量 Prefill 本应回 P 实例。但 SLO 要求按实时负载决定：要不要在已绑定的 Decode 实例本地做；若否，送到哪个 P；P 队列怎么排。现有系统没有这套开关。

缺多轮感知的部署

P/D 各几副本、每副本切几卡，强烈依赖负载形状。只看提示和输出长度，等于假装没有中间那一串增量 Prefill，资源配比和并行度都会偏。

相关的多轮优化（InferCept 的 KV 丢/换/留、KVFlow 的多 Agent 前缀缓存、vLLM-Continuum 的工具等待 TTL、MARS/AugServe 的长度与显存预测）都在同卡混部上做。把 Decode 任务塞进 P 实例的混合拆分，在多轮里也不合适——这时 P 侧已经更重。

图 3 · 对应论文 Figure 6 的拆解逻辑。两端都被单一目标钉死；AMPD 用实时松弛在两点之间滑动，而不是固定落在某一端。

3. 系统：离线规划 + 在线协调

请求一到，Coordinator 先按显存把会话绑定到某个 Decode Worker：KV 主副本和所有 Decode 都在那里。之后每次需要 Prefill（首轮或工具返回后），走自适应路由：

图 4 · 对应论文 Figure 2。离线给出部署；在线只做两件事：增量 Prefill 去哪、队列里谁先跑。KV 主副本不随路由搬家。

  • 本地执行：在绑定的 Decode Worker 上做 Prefill。省去 KV 过网、减轻 P 负担，但要打断正在跑的 Decode batch。实现上沿用 vLLM：Prefill 优先于 Decode，以免堵住后续生成。
  • 远端执行：送到某个 Prefill Worker。Decode 可以继续稳态生成，但要搬 KV：执行前如有必要从 D 读历史 KV；执行后把增量 KV 写回 D。Decode 侧有本地前缀缓存，只传增量。

图 5 · 本地零传输、打断 Decode；远端保 ITL，但历史 KV 可能先过去、增量 KV 必须回来。论文 Figure 3 用「传输/计算」比说明永远远端并不免费。

工具调用由 Decode Worker 后台 CPU 处理；完成后组成增量 Prefill，再通知 Coordinator 回到路由。Profiler 离线建分段 α-β 性能模型，三类时间：

Tpre(ℓhist, ℓincr; θ)　·　Tdec(b; θ)　·　Tkv(ℓctx; θsrc, θdst)

首轮 Prefill 的历史长度为 0。θ 是该 Worker 的并行策略。队列与近 10 秒窗口 TTFT/ITL 放在分布式共享内存里，全局可读。

4. 自适应路由：本地还是远端

永远远端：ITL 好，但 KV 传输和 P 排队伤 TTFT。永远本地：TTFT 好，Decode 被 Prefill 打断，ITL 出现尖峰。AMPD 用窗口统计做 SLO 导向的三级决策（算法 1）：

图 6 · 算法 1。先找有松弛的 P，再看 D 是否扛得住打断，最后才动性能模型。α、β 略小于 1，是为了在真正撞 SLO 之前就开始挪负载。

  1. 随机打乱 P Worker。若某个窗口 TTFT ≤ α · TTFT 阈值，直接远端到它（P 还有松弛）。
  2. 若所有 P 都紧，再看本 Decode 的窗口 ITL。若 ≤ β · ITL 阈值，走本地（D 还有松弛）。
  3. 两边都紧，用性能模型估时延，选最小者。
tlocal = Tpre(ℓhist, ℓincr; θd) + Σ队列 Tpre(·; θd)
tremote,i = Tpre(·; θpᵢ) + Tkv(ℓhist; D→P) + Tkv(ℓincr; P→D) + 排队

图 7 · 式 (1)(2) 的构成。两边都紧时，比较的就是这两根堆叠条，而不是再猜「Prefill 该不该属于 P 池」。

元数据并发收集，估时很快，作者称开销可忽略。默认 α=0.9、β=0.85：略小于 1，让系统在真正撞 SLO 之前就开始挪负载。α 太小会过早放弃 P、P 吃不饱；β 太小会过早打断 Decode。

图 8 · 松弛带。路由先问「还有没有提前量」，估时是最后一档。阈值按 trace 手调，所以跨负载不能比绝对 TTFT/ITL。

5. Prefill 重排：窗口内最大化 SLO

路由解决“去哪”。队列里还有“谁先跑”。若某任务离 TTFT SLO 还远，可以往后排，把更危急的提前。对队列头 w 个任务枚举可行排列（w 实践上 <5，默认 3），预测完成时刻

图 9 · 算法 2。不在整队上做全局调度，只在队头窗口里最大化「还能赶上 TTFT」的个数。A 虽然先到，但松弛大，可以让路。

Cπ(k) = Σj=1…k tpre(π(j))
Sπ = |{ k : (Tnow − Tenq) + Cπ(k) ≤ TTFTthres }|

选使 S 最大的排列。每个任务最多被推迟 w 次，防止饥饿。排队时延估计（式 2）不算重排，但窗口相对整队很小，作者认为不影响路由。消融里重排单独再抬 13–15% SLO，主要砍 TTFT 尾部。

6. 离线 ILP：P/D 副本与张量并行

拆分部署要同时定：每类 Worker 的数据并行（副本数）和模型并行（每副本切几卡，通常 1/2/4/8）。决策变量 x(n)、y(n) 分别是 TP=n 的 Prefill / Decode 副本数。目标不是直接最大化 SLO（0/1，不好进线性规划），而是最小化所有已实例化 Worker 的最差 P95 时延 Z：

min Z
s.t.　Z ≥ τpre(n)　∀ n 且 x(n)≥1
　　　Z ≥ τdec(n)　∀ n 且 y(n)≥1
　　　Σ n(x(n)+y(n)) ≤ NGPU

τ 来自模拟器：先 profile 算子，再模拟连续 batch、复制、模型并行、PD 拆分和 α-β 的 KV 传输，并嵌入第 4 节的本地/远端决策。这是无界背包的多维版，用 SCIP 在 256 GPU 规模约 1 分钟。附录表 2 显示规划器排出的 Top-3 配置与实测最优一致。例如 Llama-3.1-70B + DuReader：P 侧 TP=4 DP=2，D 侧 TP=8 DP=1；GAIA 这种超长多轮则两侧都 TP=8 DP=2。

图 10 · 对应论文 Figure 4 与附录表 2。同一套 ILP，负载形状一变，P/D 的切分就换。GAIA 两侧都要大 TP，正是「多轮感知部署」相对单轮规划的差别。

用 P95 代理 SLO 是工程妥协。好处是能全局搜副本×切分；坏处是目标与在线真正优化的“达标率”不一致。作者用“规划结果碰巧等于实测最优”来辩护，没有给出代理间隙的理论界。

7. 实现与实验

实现叠在 NVIDIA Dynamo 上：Redis 共享队列与窗口统计，SCIP 解 ILP，NIXL 做 P↔D 的 RDMA。远端只先发元数据，真正轮到执行才懒读历史 KV，并与上一任务计算重叠。

图 11 · 实现细节。路由阶段不搬 KV；只有轮到执行才读历史。这降低了「远端」的可见开销，也让路由估时必须把 T_kv 算进去。

硬件：4 机 × 8×H20 96GB；机内 NVLink 900 GB/s，机间 IB 200 GB/s。模型：Qwen3-32B、Llama-3.1-70B、Mixtral-8x7B。基线：Dynamo（永远拆分）、vLLM、vLLM-Continuum。到达为泊松过程。基线的部署手工调到最好；AMPD 用自己的规划器。

主结果：AMPD 在全部配置上 SLO 最高。相对 Dynamo 最高 +968%、平均 +67%；相对 vLLM 最高 +3435%、平均 +340%。拆解符合故事：混部 TTFT 好、ITL 差；纯拆分 ITL 好、TTFT 被 P 资源和 KV 传输卡住。HotpotQA/DuReader/ToolBench 上拆分往往赢在 ITL；GAIA 超长增量 Prefill 让混部的 TTFT 更有竞争力，Dynamo 反而落后。AMPD 保住拆分的 ITL，再用本地执行+重排把 TTFT 拉回来。

图 13 · 对应论文 Figure 5。柱长按平均相对增益示意，不是把各 trace 的绝对达标率画出来。读论文主图时仍以原文曲线为准。

vLLM-Continuum 按会话优先、复用 KV，能缩短排队和 TTFT，ITL 不变；很多设置下 SLO 并不比 vLLM 好多少。消融（Llama-70B，2 req/s）：13.9–31.7% 的 Prefill 本地执行，自适应路由单独 +27–350% SLO；加上重排再 +13–15%。端到端时延与 Dynamo 接近，有时 Dynamo 略低，但 SLO 才是这篇的优化目标。

图 14 · 对应论文 Figure 7。本地比例不高，但足够把 P 从过载里拽出来。这解释了为什么永远远端和永远本地都不如自适应。

8. 局限和对近存 / 拆分部署的含义

  • SLO 阈值按 trace 手调（如图中 TTFT 130ms–5s、ITL 20–50ms），跨负载不可直接比绝对值。
  • HotpotQA/DuReader 用 Qwen3-32B 跑迭代检索录的 trace，再在 70B/MoE 上重放，长度分布与真实 70B Agent 可能不同。
  • 绑定 Decode Worker 之后 KV 不迁移；负载倾斜只能靠后续 Prefill 的本地/远端来补。
  • 规划是离线一次性，没有运行期改 TP/副本。和弹性 PD 扩缩（BlitzScale、TokenScale）是正交的，文中声称可组合，但没合在一起测。
  • 懒读 KV + 与前一任务重叠，依赖机间 200 GB/s IB；更慢的跨机链路会改变本地/远端分界。

图 15 · 多轮的关键流量是增量上下文。AMPD 的前缀缓存与近存「历史驻留、链路只走增量」是同一条原则，差别只在计算落点。

对同封装近存或机架级 PD：多轮的关键流量不是“整段历史 KV 每次都搬”，而是增量上下文。AMPD 只回传增量 KV、Decode 侧保留前缀，和“历史 KV 驻留近存、链路上只走激活/增量”是同一条原则。差别在落点：这篇把增量 Prefill 在 GPU P 实例和 GPU D 实例之间切换；近存架构则可能把译码注意力钉在近存模块，只有当本地矩阵阵列或链路打满时才把局部 Softmax 统计量送到中央。规划器按交错负载配 P/D 卡数，对应近存侧按头所有权/会话数配模块数，而不是按单轮提示长度。

可迁移的三条：用 TTFT/ITL 松弛而不是静态规则决定增量计算落点；队列按“谁快撞 SLO”而不是 FIFO；部署目标要对准瓶颈相位的尾部时延，而不是平均吞吐。不必照搬 ILP 的 P95 代理，也不必假定 Prefill 永远属于 P 池。
