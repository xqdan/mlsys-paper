1. 一句话结论

并行投机解码器用一次前向提出整块候选，但目标模型只接受第一处不一致之前的前缀，后面全部丢掉。早期一个错误比后期一个错误贵得多，而并行草稿在任何位置被选定之前就打完了所有分。CPA 在 DFlash 的并行骨干上加了一个选择器：每个位置的候选可以注意块内已经选定的更早 token。因为 shortlist 是固定的，任意一对候选之间的交互可以在选择开始前一次性算完，顺序遍历只做查表、累加和一次很轻的打分，不再逐步跑神经网络。训练时再给共享骨干加一条干净前缀上的自回归损失，推理时这条通路不存在。实现接在 vLLM-Ascend 上。

2. 问题：一次提出整块，校验却在第一处错误截断

投机解码用便宜的草稿模型提出若干 token，目标模型一次前向完成校验。EAGLE-3 这类自回归草稿器每提一个 token 都要跑一步，草稿一长就贵。并行草稿器把这块成本去掉：DFlash 在目标特征上条件化一个小的块模型，一次前向预测整块每个位置。CPA 沿用 DFlash 的骨干，改的是如何从提案里选出一条路径，以及骨干怎么训练。

校验规则与并行提案是冲突的。目标模型只接受它同意的最长前缀，在第一处分歧截断并丢弃后缀。速度因此取决于第一个错误出现在哪。并行草稿器给每个位置打分时，还没有任何位置被选定。论文举了一个结构依赖的例子：前面是 they 还是 she，后面动词该是 run 还是 runs，正确选择取决于两个位置之前的主语。逐位置 argmax 看不见实际选中的主语；只看前一个 token 的修正，在两条路径上可能看到同一个 often，仍然分不开。自回归草稿器能看到完整前缀，但每个 token 都要付一次骨干计算。

3. 和现有修正差在哪

最近的工作因此在并行通路之后再加修正。DFlash 2 对相邻候选对重新打分，相当于 CPA 的局部项；Domino 和 DSpark 用循环或马尔可夫头穿过整块；D-Loop 再跑一遍骨干，条件是已经选定的前缀。这条谱系的权衡很清楚：局部重打分便宜，但只看见一个 token；循环头和重复前向能看见更长前缀，却要在每个位置付出神经网络计算。

CPA 的观察是：并行通路之后，每个位置只留下固定的 top-K shortlist。位置 i 的某个候选和更早位置 j 的某个候选之间的交互，只取决于这两个 token，以及已经算好的块特征，不取决于最后走出哪条路。于是所有成对交互可以在选择开始前批量算完；对已选前缀做注意力，精确地变成边走边从表里取出并累加。顺序阶段里没有神经网络求值。论文把它放在局部重打分和循环修正之间：能像循环头那样看见所有更早的选择，但走的时候只查表。

4. 两个机制

编译后的前缀注意力选择器

已校验上下文以锚点 token a 结束。草稿器提出 m 个新 token，块长为 m+1（含锚点），默认 m=15。可训练骨干一次并行给出各位置状态，冻结的词表头得到一元 logits，每个位置保留 top-K=16 个候选，一元 argmax 放在第 1 槽。DFlash 在每个位置直接取 ci,1；CPA 则按块内已做的选择，为每个位置挑一个候选。

候选分数是三项之和：一元分数、与前一个已选 token 的局部项，以及对其更早选择的多头历史注意力。因为 shortlist 固定，局部项和历史项都可以先编成对表。选择时为每个未来位置、候选和头维护分子、分母；每确定一个位置，就把对应列累加到所有更靠后的位置上，然后做一次 K 路 argmax。论文证明，在精确算术下，编译后的选择与直接按公式计算一致。

造表代价是 O(m² K² H rh)，每块一次；顺序走 m 步，每步只做查表和轻量打分，总工作 O(m² K H)。在 m=15、K=16、H=4 时，打包后的有效历史表有 188,160 个数，FP32 不足 0.8 MB；实现里实际分配的是带掩码的稠密表。选择器本身很小：Qwen3-4B 上约 3.5M 参数，8B 上约 5.5M，都不到对应目标模型的 0.1%。尽管参数少，造表对 K 是平方的，更大的 shortlist 可能更慢，第 5 节的容量扫描验证了这一点。

只在训练时存在的干净前缀损失

总损失是 DFlash 原有的掩码块损失，加上调度起来的选择器损失，再加上 λAR=0.2 的自回归项。并行草稿器平时只在掩码块上学习，骨干从来没有练习过「从正确前缀预测下一个 token」——而这正是校验会奖赏的情形。CPA 用同一套骨干，在干净、因果掩码的前缀上再跑一次，用冻结词表头做全词表的 next-token 损失。这条通路只更新骨干、不更新选择器，推理时不运行。

选择器的监督是：在 shortlist 里对目标模型的贪心 token 做交叉熵；如果记录前缀已经离开贪心路径或 shortlist，后面的位置逐渐降权到 0.25。选择器损失前 2,000 步为 0，到第 4,000 步线性升到 0.5。还用回放检查拒绝那些会缩短「已经选对的前缀」的选择器更新。

校验方面，贪心模式提交与目标选择一致的最长前缀，并在第一处失配补上目标 token，或在全部匹配时给一个 bonus token，从而在精确算术下复现贪心目标解码。temperature=1 时，CPA 仍然输出一条确定路径（不带草稿概率），用 vLLM 标准拒绝采样把它当作点质量，以保持目标分布。近似的基于熵的校验和块校验被关掉。

解码在 vLLM-Ascend 上运行，CANN 9.1.0，BF16 权重。目标校验用 captured graph；草稿骨干 eager 执行，DSpark 和 CPA 的修正头用单独的 graph。论文给出的实现仓库是 MohammadMahdi1375/vLLM_NPU。主结果是单请求；并发数字在附录 Table 9。没有报告 GPU 上的 vLLM / SGLang 集成，也没有把选择器接到除昇腾之外的执行栈。

6. 实验怎么做的

目标是关闭 thinking 模式的 Qwen3-4B 和 Qwen3-8B。八个基准覆盖数学（GSM8K、MATH-500、AIME 2025）、代码（HumanEval、MBPP、LiveCodeBench）和对话（MT-Bench、Alpaca）。temperature 为 0 和 1，top-p=1，不截断 top-k，每条请求最多生成 2,048 个新 token。对照是目标模型自回归、并行草稿器 DFlash 与 DSpark，以及自回归草稿器 EAGLE-3。所有草稿器每轮提出 15 个 token（块大小 16）。DSpark 基于置信度的调度被关掉，各方法使用相同的固定提案预算。

所有草稿器（包括 EAGLE-3）都从零训练五个 epoch，数据是同一套 OpenPerfectBlend 提示加目标模型生成的回复。训练用八张昇腾 910B2：六张做数据并行，两张生成目标隐状态。Qwen3-4B 上一个 epoch：DFlash 17 小时，DSpark 23 小时，CPA 28 小时，EAGLE-3 34 小时。选择器消融是在同一份 CPA 检查点上，推理时关掉历史项或整个选择器；AR 损失消融则是另训一份 λAR=0、结构相同的草稿器，同样五个 epoch。

速度在一块 64 GB 的 910B2 上测。加速比 S 是输出吞吐除以固定的自回归参考：两个温度下都是 4B 为 47.83 tok/s、8B 为 39.63 tok/s。提交长度 τ 计入目标修正或 bonus token，不含锚点。工作负载平均不加权。阶段耗时在 vLLM-Ascend 路径里打点并在每个边界同步 NPU，按八个负载均值再取算术平均；「Other」是草稿、修正、校验之外的残差。吞吐和加速比在关闭这些打点后另测。

7. 结果怎么读

平均最快，但对话和数学不是同一个量级

Table 1 覆盖两种目标、两个温度。CPA 在四个设定里都有最高的平均加速和最长的平均提交长度：贪心下 4B 为 3.35× / τ=7.14，8B 为 3.37× / τ=7.19；采样下两个目标都是 2.86×，τ 分别为 6.29 和 6.32。相对 DSpark，τ 高 13–15%；相对 DFlash 高 25–26%。DSpark 贪心平均是 3.12× 和 3.19×，DFlash 是 3.00× 和 3.07×，EAGLE-3 只有 1.25× 和 1.38×。

拆开看，数学最强（4B 贪心 GSM8K 4.38×、MATH-500 4.68×），对话最弱（MT-Bench 1.98×、Alpaca 1.88×）。采样时差距同样在，而且 4B 的 MBPP 上 CPA 的加速 2.60× 略低于 DSpark 的 2.66×，虽然 τ 仍然更高（5.73 对 5.42）。接受得更多，不一定在每一个负载上都更快。

AR 损失把平均加速从 3.28× 提到 3.35×，τ 从 6.93 提到 7.14，推理路径完全相同。λAR 在 0.1 到 0.4 之间几乎平坦。这份无 AR 的草稿器是另一次训练，论文承认其他因素也可能进入这个差距，而且比较的是相同 epoch 数，不是相同训练算力。

更大的容量不一定更快；并发会把加速比压下去

K=32 时 τ 升到 7.19，加速却降到 3.26×；rank=512 时 τ 升到 7.31，加速同样是 3.26×。块大小 16 对三个并行草稿器都是最好的；扩到 32 时每家的 τ 和加速都不如 16，因为靠后的位置很少能活过校验，造表和草稿却更贵。CPA 相对 DSpark 的 τ 优势在块长 8 时最小（4.5%），在 16 和 32 时分别为 14.4% 和 10.3%，与「能看见的更早选择变少」一致。

并发上升时，目标模型自己的批处理变高效，投机加速比下降。Qwen3-4B 贪心、全部评测提示上的吞吐（tok/s）为：并发 1 时 CPA 160.23（3.35×），并发 8 时 631.22（2.54×），16 时 895.11（1.98×），32 时 986.39（1.52×）。同一行里 DSpark 是 1.42×，DFlash 是 1.36×。相对排序还在，但绝对加速已经接近「略快一点」。

8. 落地可行性

代码仓库指向 vLLM-Ascend 上的实现，不是通用 GPU 上的 vLLM / SGLang 插件。选择器参数量很小，推理时顺序阶段也被编成查表，这是它相对循环头或二次骨干前向更有吸引力的地方。但造表对 K 和块长是平方的，容量一加就可能把接受长度的收益吃掉；论文的扫描把这条边界画得很清楚。

如果已经在昇腾上用 DFlash / DSpark 一类并行草稿，CPA 是值得试的下一步：同样的 15 token 预算，平均能多提交约一到两个 token，单请求加速从大约 3.1× 到 3.3× 量级。若目标是 GPU 上的 vLLM 或 SGLang，这篇还不能当现成方案——需要把造表和顺序走步重新实现，并单独测 kernel 启动开销。训练更贵：4B 上每个 epoch 比 DFlash 多 11 小时，比 DSpark 多 5 小时。对话类负载的加速明显弱于数学和代码，不能用平均 3.35× 代表线上聊天。

贪心模式下，精确算术下与目标解码等价；BF16 里求和顺序变化可能在接近平局时翻转决策，论文建议在自己的 kernel 上检查输出一致性。temperature=1 走的是 vLLM 拒绝采样，提案被当成点质量，标准意义上保持目标分布，但草稿概率并没有从 CPA 里传出去。

9. 局限：这些倍数依赖什么假设

  • 模型和硬件很窄。只评了 Qwen3-4B 和 8B 一个家族，消融只在 4B 上做。吞吐只在一块昇腾 910B2 上测。顺序走步的相对成本取决于 kernel 启动开销，换到 GPU 或其他 serving 栈时，加速比不应直接套用。
  • 统计偏弱。各方法都是单次训练，没有对重训或重复计时给出置信区间。像 3.35× 对 3.34× 这样的差别，不足以下结论。最终恢复预算、训练数据修订和被评测检查点的标识，在附带运行元数据里也找不到。
  • 方法边界。选择器只能在并行通路的 top-K 里挑；目标 token 一旦不在 shortlist 里，接受前缀就在这里结束。造表随 K 和块长平方增长，K=32 时成本已经超过接受收益。AR 消融不是同等算力对比。选择器在记录前缀上训练，与自身决策仍有暴露不匹配。
  • 评测口径。加速比相对的是固定的、按模型给出的自回归吞吐参考，不是每个负载单独测一份 AR 吞吐。阶段拆分是带同步的仪器化执行，吞吐是关掉仪器后另跑的。并发结果来自附录，主表是单请求。
