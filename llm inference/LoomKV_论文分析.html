1. 一句话结论

多轮和 agent 请求要靠外部 KV 层（DRAM / SSD）复用前缀，同时每个在跑的请求还得在 GPU pool 里占一块空间。有损量化或驱逐能省空间，但会改输出。LoomKV 用按头校准的两级 3-bit 码，只压缩 BF16 的高字节（符号和指数高 7 位），低字节原样保存，在九个模型上把 BF16 KV 存到原大小的 0.71，FP8 KV 到 0.85–0.87。它接到未改动的 vLLM 0.30 和 LMCache 0.5.6 上：tier 模式用 TileStream 把压缩记录写成精确长度对象，解压后直接写回引擎打散的页；pool 模式用 FragPack 把变长记录装进更小的共享预算页，由融合 decode-attention kernel 就地读取。AgentX 上，压缩后的外部层表现得像 1.4 倍大的原始层。

2. 问题：容量卡在两层

引擎把算过的 KV 留下来，是为了避免每次把长前缀再 prefill 一遍。这块 cache 很大：论文举的例子是 Qwen3-30B-A3B 每个 token 要 96 KB KV，一张卡若只留 32 GB 给 KV，只能放下五个 64K 的 agent 会话。vLLM、SGLang 一类引擎因此把 KV 溢写到主机 DRAM 和 SSD，通过 LMCache、Mooncake、SGLang HiCache、CachedAttention、Strata 这类外部层，在前缀再次出现时装回来。

容量会在两个地方分别把服务卡住：

外部层：能不能复用前缀

DRAM（L1）和 SSD（L2）决定多少算过的 KV 还能留着。被淘汰后只能重新 prefill。论文在两张 H800、vLLM + LMCache、BF16 KV 上跑 AgentX：64 个在线会话共享 400 GB DRAM，总容量从 1200 GB 降到 1040 GB 时，命中率从 0.84 掉到 0.55，goodput 从 9.4 降到 4.6 请求/分钟。

GPU pool：能不能同时跑长请求

即便前缀已经在 DRAM / SSD 里，请求还得在 GPU 上占页才能跑。把外部层做大，解决不了这块。论文把 SSD 固定在 2 TB，把同时准入的请求数从 8 调到 12、16，说明 GPU KV 预算本身就会让请求在引擎里排队。

Goodput 的口径要先记住：引擎 TTFT ≤ 2 s 且 token 间隔（ITL）≤ 40 ms 的请求数，单位是每分钟。后面的倍数都按这个门槛算，不是裸吞吐。

图 1　示意：容量同时受外部层和 GPU pool 限制。LoomKV 的两种模式分别作用在这两层，引擎本身不改。

作者的目标不是再做一个更狠的有损 KV 量化，而是问：省下来的字节能不能变成「容量等价」——一块大小为 B、存储比为 r 的压缩层，行为是否接近一块大小为 B/r 的原始层。要做到这一点，压缩比、分配出来的空间、解压速度、decode 速度，以及变长记录的长度回读，都必须同时过关。这五条要求贯穿后文的设计。

3. 高字节很偏，低字节几乎压不动

BF16 能无损压缩的空间并不大。论文在 Qwen3-30B-A3B 的全部 48 层、每层的 K 和 V（共 96 个张量）上，分别统计高字节和低字节的取值频率：每个张量里最常见的 7 个高字节，平均覆盖约 94% 的出现次数；低字节同样集中（约 92%），但熵已经接近 8 bit 里的 7.97 bit，几乎没有可压的空间。因此编码只打高字节，低字节原样保存。

这也是它不走通用 GPU 压缩库的原因。同一份 KV、同一块 GPU 上，nvCOMP 的 ANS 把数据存到原大小的 72.5%，解压约 182 GB/s；LoomKV 是 70.9%、1182 GB/s。LZ4 在交错的 BF16 里几乎找不到字节级匹配，存储比变成 1.0005，等于没压。

和仓库里已有工作的差别在这里就清楚了。Hopper 4-bit KV、DQ、RoCoKV 改的是 KV 的数值表示，换容量和带宽，但输出要重新验收。MoRI UMBP 改的是 KV 放在哪一层存储，并不压缩内容。LoomKV 保留每一个原始值，因而也可以叠在已经量化过的 FP8 KV 上面。

4. 编码：两级 3-bit 高字节码本

编码和 ZipServ 是同一路子，但为 GPU 并行解码做了固定宽度的选择。每个 BF16 标量的低字节原样存放；高字节换成一个定宽符号，指向一张静态码本。不用变长熵编码，是因为每个符号的比特偏移会依赖前面所有符号，warp 就无法独立解压一个 tile。

图 2　示意：低字节不编码；高字节先走 3-bit 一级码，逃逸后再走 3-bit 二级码，只有剩下的少数值写回原始字节。

选 3 bit 是因为：最常见的 7 个高字节已经覆盖大约 94%，再加宽到 4 bit 等于每个标量都多付 1 bit；而 8 个 1 字节表项正好塞进 GPU 一条字节重排指令 PRMT 的 8 字节寄存器输入。一级逃逸大约 6%。如果每次逃逸都直接写回 8-bit 原值，会多出 0.06 × 8 = 0.48 bit/标量；于是一级逃逸改为再发一个 3-bit 二级符号，指向码本第二行的 7 个次常见值。只有落在 14 个表项之外的高字节，才用二级符号 7 逃逸到原始 8 bit——在 Qwen3-30B-A3B 上这是 0.19%。Pool 模式把第二级加宽到 4 bit（15 个次级表项），好让融合解压不用打循环。

码本按「每一层、K 或 V、每一个 KV 头」各做一张。全模型共用一张会丢掉不同张量的指数范围；再细到 per-channel，熵收益可以忽略，却逼着同一条 lane 换表。码本在服务启动后保持静态：先有一张通用回退表，再用一次 1024 token 的前向离线校准出模型专用表，并把码本摘要写进记录头以防对不上。Qwen3-30B-A3B 上码本只要 8.4 KB。校准过的码本在散文、源码、中文聊天、数学、合成 needle 和随机 token 上，BF16 存储比都是 0.706–0.709，和按域单独校准相差不超过 0.001；在 240K 上下文的各个位置上也维持 0.709–0.710。

对 FP8（E4M3）KV，同样的两级码原样保存 3 bit 尾数，只编码高 5 位（符号和指数）。因为同一头内各通道幅度不同，压缩前要先减去静态的 per-channel 整数指数偏移，解压时再加回去。K 上的 RoPE 会旋转通道对，所以校准 K 的偏移前，要先把捕获的 K 在 256K 上下文上重新转回去；BF16 不需要这些偏移，也就不用再转一次 RoPE。

在 Qwen3-30B-A3B 上，单张量 128 KB 原始大小被压到约 90.7 KB：低字节和一级符号固定花费 8 + 3 bit，逃逸与分组索引再加 0.34 bit，合计 11.34 / 16 bit，存储比 0.709。九个 4B–72B 的稠密和 MoE 模型上，校准后的 TileStream 记录都落在 0.705–0.709，离 0 阶熵下界只差 0.033–0.036。通用回退表要差一些，Qwen3-30B-A3B 从 0.764 降到 0.709 是最明显的一档。FP8 被压到 0.853–0.873。FragPack 因为每 warp 的头比 tile 索引更小，BF16 比还能再紧一点（0.700–0.705）。

5. Tier 模式：TileStream

省下的字节如果还按原始大小去预留，容量就不会增加。外部层因此按「精确长度」分配对象：GPU 压缩得到真实字节数后，L1 按这个长度分配，并原样写到 L2；L2 写完后把压缩长度记进主机元数据，之后从 L2 预取时可以先准备好精确大小的 L1 缓冲。变长的 L1 分配器和按字节的 LRU 淘汰都不用改。压不动的 chunk 回退到原始存储，最坏不超过原始大小。

TileStream 把一个 chunk 写成一条记录。以 Qwen3-30B-A3B 为例，一条记录覆盖 128 个 token、48 层共 96 个 K/V 张量，前面是 4 KB 对齐的逐张量偏移头，后面再留 4 KB 填充，方便 O_DIRECT 的 SSD 传输。每个张量的字节按类型拆成四条连续流：低字节、一级符号、二级符号、原始逃逸字节。定宽的数据可以合并加载，变长逃逸被隔离在后两条流里。

每个张量再切成 256 个标量的 tile：一条 32-lane 的 warp 里，每条 lane 一次用 128-bit 向量指令读写 8 个 BF16（16 B；FP8 则是 64-bit），正好覆盖 32 × 8 = 256 个标量。二级流和原始流的偏移依赖前面所有逃逸，若逐 tile 扫描就无法并行。于是每个张量附带分组索引：每 8 个 tile 一组，记下组起点的两个 32-bit 前缀计数，再加上 tiles 1–7 的 16-bit 组内偏移，代价大约 0.14 bit/标量，而不是每 tile 两个 32-bit 计数的 0.25 bit/标量。

加载时，每个 warp 解压一个 tile，直接写进引擎打散的 KV 页，不经过临时缓冲。一条 lane 的四步是：标出一级逃逸并在本地计数；用 warp 前缀和加上 tile 索引，得到自己在二级流和原始流里的位置；用两次无分支的 PRMT 查表并合并；把解压出的高字节和原样低字节交错后，写到目标页。写地址只来自主机校验过的元数据，记录里读出的偏移会被夹紧在加载缓冲范围内。

存储路径上，三个连续 GPU kernel 从引擎的分页块直接压缩一批 chunk，中间没有主机同步：计数逃逸、由单个 CTA 计算流偏移并标记压不动的 chunk、再把对齐的头、流和索引写进存储缓冲。相比先把 chunk 收成连续缓冲，少了两遍扫原始 KV，也少了大约两次 kernel 启动。

6. Pool 模式：FragPack 与融合 decode

Pool 模式把压缩后的记录直接放进 GPU KV pool，用一个树外的 attention 后端来算 decode，引擎源码仍然不改。页表布局保持固定大小，但把物理页缩小到接近一个 block 记录的典型压缩长度，同一笔 GPU 预算就能放下更多 KV block。

一条 FragPack 记录是 128 × 128 个标量（原始 32 KB），对应一个 128 token 的 block、一层、一个 KV 头、以及 K 或 V 其中之一。融合 kernel 用 256 线程（8 个 warp）的 CTA，沿着同一个请求、同一个 KV 头的连续页前进。压缩时就把标量排成 MMA 时每条线程要提供的 64 标量 fragment 顺序，解压后可以直接从寄存器喂给 tensor core。

计算路径可以看成三步：TMA 把下一条记录提前搬进共享内存（共享槽的地址余数要对齐到源地址模 128，否则会有大约 30% 的带宽惩罚）；线程在寄存器里做 PRMT 一级查表、warp scan 逃逸和无需循环的 4-bit 二级/原始修补，得到 fragment 顺序的 K 和转置后的 V；再用 m16n8k16 MMA 和在线 softmax 做注意力。K 步和 V 步对 token 与输出维的切分不同，CTA 会经共享内存交换 P。双缓冲的 K/V 槽让 TMA 始终比计算提前一条记录，把拷贝藏到解压和 MMA 后面。

只有完整的 128 token block 会被压缩。每个正在跑的请求把尚未写满的 open block 以原始格式放在每请求的暂存缓冲里，attention 会同时读压缩页和这块缓冲。Prefill 以计算为主，不是读 KV 为主，pool 模式因此不融合 prefill：先解压到临时 BF16 工作区，再跑引擎自带的 attention，prefill 时间最多增加 3%。

共享预算页大约能放下 1.38 倍的原始 block（如果按最坏 2 KB/记录预留是 1.33 倍，理想零空隙是 1.42 倍）。暂存缓冲、溢出区和记录表要从同一笔 54 GB KV 预算里扣掉，净 token 容量在 54 GB/GPU 时是 1.34 倍（缓冲约占 2–3%），在 28 GB/GPU 时是 1.31 倍（约占 4–5%）。

7. 传输：把长度回读移出关键路径

往外部层写变长记录时，CPU 必须把 GPU 算出的长度读回来，才能分配空间、决定传输大小。这次同步如果堵在处理线程上，就会挡住其他 KV 加载。LoomKV 把存储拆成两条线程：处理线程领一块 GPU 存储缓冲，启动三个压缩 kernel，记下 CUDA event，把批次交给后台存储线程后立刻回去处理排队的加载。存储线程在自己的 CPU 线程和 CUDA 流上等事件，一次同步读回整批长度，再分配精确长度的 L1 对象、拷进 L1，并触发写穿到 L2。存储缓冲在突发下用满时，处理线程会反压，而不是丢弃存储。

加载不需要再读长度，因为主机元数据里已经有每个钉住的 L1 对象的精确长度。为了避免多进程争用 GPU 时间片时卡住并不等待计算片的 PCIe DMA，加载把 PCIe 拷贝和 GPU 解压放在两条 CUDA 流上，轮转一组 GPU 加载缓冲（部署里是四个）。每个解压只等自己这块缓冲的拷贝，每个回填只等这块缓冲上一次解压。论文给过一个对照：加载 110K token 的前缀、同时另一个进程用 BF16 矩阵乘把 GPU 占满时，单缓冲会让延迟涨到 288–294 ms（原始拷贝在同样争用下是 117–141 ms）；四个缓冲把它降到 90 ms，接近空闲 GPU 上单缓冲的 83 ms，也和 0.71 倍原始字节的 PCIe 传输时间相当，解压被藏到 PCIe 后面。

Pool 模式复用这两条异步流水，但对象格式改成「一个完整 128 token block 的各层 FragPack 记录 + 4 KB 对齐头」，存储路径用导出 kernel 替换压缩，加载路径用导入 kernel 替换解压。导入可能因损坏的头或溢出区满而失败，处理线程会在为该请求排队完所有导入后做一次状态回读，避免在流水中途停住；失败的批次由引擎重算。

8. 实验怎么做的

主测试平台是一台带 1 TB DRAM、15 TB SSD 和两张 H800（80 GB，700 W）的服务器。默认服务 Qwen3-30B-A3B-Instruct，TP 2，BF16 KV 每 token 96 KB；对照模型是稠密的 GLM-4-9B-Chat-1M（80 KB/token）。存储比另外在九个 4B–72B 的稠密和 MoE 模型上测。引擎是未改动的 vLLM 0.30，128 token 的 block，默认 attention 是 FlashAttention-3。缓存服务是 LMCache 0.5.6，128 token 的 chunk，带上界的 DRAM / SSD 层和 LRU 淘汰。有损基线是 vLLM 的未再压缩 FP8 KV，GPU pool 和外部层的 KV 大小都减半。

主负载是 AgentX：回放 cc-traces 里 393 个 Claude Code 会话，带 subtagent 和记录下来的思考时间，指标只统计预热后的剖析窗口。会话之间不共享前缀，prompt 最长 254K，中位数 89K。每张 GPU 给 KV 留 54 GB（原始 118 万 token）；pool 模式下暂存、溢出区和记录表从同一笔预算扣除。因为测试夹具对每个在线会话只保持一个在飞请求，vLLM 前面加了一个 FIFO 代理，最多同时准入 S 个请求，以免引擎排队把缓存效果掩掉。默认 S = 8，这时 raw GPU pool 内部不再排队。在线会话数 P 决定复用工作集 W：P = 32 时 306 GB 原始 KV，P = 64 时 641 GB。多数实验是 P = 64、400 GB DRAM，SSD 从 400 GB 扫到 2 TB，剖析窗口 1800 s。

第二条负载是内部 AI IDE 服务的开环回放：三小时、5098 个请求、0.47 请求/秒，prompt 均值 68K、p99 192K，输出均值 505 token。这里没有 FIFO 准入代理，TTFT 直接包含 vLLM 排队。受约束节点是 128 GB DRAM + 512 GB SSD；对照是 400 GB + 2 TB 的大 raw 配置。

9. 结果怎么读

Kernel 是否够快

Table II 在单卡上做了逐字节校验。存储路径上，LoomKV 从分页块直接压缩，比 SplitZip 快 1.6 倍，比 ExANS 和 nvCOMP 快 4.7–59 倍。加载路径上，从寄存器直写打散页，达到原始分页拷贝速度的 81%，比 PCIe 带宽高一个数量级，也避开了 SplitZip 那种几乎把吞吐砍半的额外 scatter；同时比 SplitZip 少存 8% 的字节。变长 ANS（ExANS、nvCOMP ANS）尽管 ExANS 的存储比还紧 1.6%，解压要慢 6.3 倍。离线体积上，ZipServ 是 0.722，ZipFusion 是 0.79，都不如 LoomKV 的 0.709。

Pool 模式的融合 BF16 decode kernel 在满时钟下，几乎每个 shape 都快过 vLLM 所用的 FA3 和 FlashInfer：TP 1 时是 FlashInfer 时间的 0.80–0.92 倍、FA3 的 0.56–0.85 倍；单个 TP 2 rank 上，12 个 shape 里有 11 个是 FlashInfer 的 0.79–0.97 倍，只有 1×32K 升到 1.23 倍（这里 FlashInfer 从 8K 起就几乎不再变）。同一套 kernel 跑未压缩的 FragPack 记录，仍是 FlashInfer 的 0.90–0.96 倍，说明加速不全来自少读 30% 的字节，kernel 本身也更快。两张 H800 在持续 AgentX 服务里，超过 99% 的忙碌样本顶在 700 W 功耗墙；连续满负荷时，BF16 仍然领先，只是 1×32K 会到 FlashInfer 的 1.35 倍。FP8 在功耗墙上失去优势：相对 FlashInfer 是 0.98–1.15 倍，超过 32K token 时相对 FA3 是 1.21–1.30 倍。

外部层不够时：tier 模式

压缩后的外部层表现得像 1.4 倍大的原始层，也就是 0.71 存储比的倒数。论文用 880 GB 的压缩层对上 1231 GB 的 raw 对照，goodput 相当；只放大 SSD（1072 GB）或只放大 DRAM（1200 GB），也落在同一条曲线上。写穿 LRU 的悬崖大约按 1.4 倍向左移：raw LMCache 在总容量低于 1200 GB 时掉下去，tier 模式到 640 GB 仍接近峰值。夹在两道悬崖之间，640 GB 时是 raw goodput 的 2.8–2.9 倍，480 GB 多次重复是 2.7–3.6 倍，平均引擎 TTFT 降到 1.9–3.1 分之一。

GPU pool 不够时：pool 模式

当外部层已经装下工作集（Table IV 里命中率全程 0.93–0.94，400 GB DRAM + 2 TB SSD），瓶颈就只剩 GPU pool。S = 8 时两个 pool 都不排队，goodput 接近。S = 12 时 raw pool 开始缺页，平均 TTFT 大约变成三倍，goodput 从峰值明显掉下去；pool 模式排队几乎不涨，给出 raw 的 1.5 倍 goodput，并和 raw 在 S = 8 时的最好结果相当，prompt 吞吐相对 raw 的 S = 8 是 1.16 倍。S = 16 时两边都排队，但 pool 模式同时跑 14.0 个请求，raw 是 11.1，goodput 是 2.5 倍。GLM-4-9B 把同样的平移往后推了一档：S = 16 的 pool 模式达到 raw 在 S = 12 时吞吐的 1.22 倍。

把每卡 KV 预算收到 28 GB 时，即便 S = 8，vLLM 内部也会排队。这时 pool 模式相对仍用 raw pool 的 tier 模式，等待大约减半，goodput 高 1.8 倍，并和「把 raw pool 放大到同样 token 数」的对照对齐，说明它在 token 数上是容量等价的。28 GB 的 raw LMCache 被略去，是因为少数已经装入但还没开始跑的长请求占住 72–82% 的 pool、又没有正在跑的请求可抢占，运行会卡住——论文把它写成 vLLM 小 pool 的调度现象，不是压缩本身的结果。Pool 模式还会把 FragPack 记录原样导出到 L1 / L2，所以外部层偏紧时也有帮助：640 GB SSD、S = 8 时，goodput 与 tier 模式相当（14.5 对 13.5），平均 TTFT 再低 15%。

两层都紧：AI IDE 痕迹

受约束节点（128 GB + 512 GB）上，raw 的总命中率相对大 raw 对照（400 GB + 2 TB 的 0.87）少 7 个百分点（0.80）。重算那些长前缀把 GPU 打满，平均排队超过 20 s，ITL 到 54 ms，goodput 9.4。Tier 模式把总命中率拉回到 0.86，平均 TTFT 降到约 5.6 分之一，goodput 到 11.6（1.24 倍），但 GPU pool 成为新瓶颈，请求仍在排队。Pool 模式同时松开两层，大部分命中直接落在 GPU pool（0.81 + 0.06），排队降到 0.65 s，goodput 到 15.0（1.59 倍），甚至超过那份更大的 raw 对照（12.7），尽管 DRAM 只有三分之一、SSD 只有四分之一。

代价和「精确」分别指什么

四项系统开销把代价框住：tier 模式每卡大约多占 2.5 GB 显存（其中 2.1 GB 是 32 个 chunk 的存储缓冲和轮转加载缓冲）；外部层已经够用时，仅 DRAM（P = 24）掉 1.3% 吞吐，2 TB SSD 掉 2.2%；320 条互不重复的 32K prompt、一次都打不中时，端到端时间在 tier 模式增加 0.3%，pool 模式增加 0.9%；按 AgentX 的 chunk 速率在离线 vLLM 任务旁边跑存储和加载，会让 vLLM 再慢 1.5%（原始拷贝是 0.5%），来自多进程分时。Pool 模式里，FragPack 压缩占 GPU 时间的 1.5%，attention 占 48%。

Tier 模式在 Qwen3-30B-A3B 和 GLM-4-9B 上，贪婪解码输出与 raw 层按 SHA-1 一致，包括原始回退和部分 tile。这对可复现评测、RL rollout，以及量化会伤对齐的安全敏感部署有用。Pool 模式存的仍是无损 KV，融合 kernel 在压缩记录和 raw FragPack 记录上的输出也按位相同，说明编码本身没有误差；但注意力累加顺序和 FA3 不同，最终 logits 只在舍入精度上有差别。相对 FP64 参考，平均绝对 decode 误差与 FA3 相同：BF16 都是 3.1×10−5；FP8 上是 3.0×10−5 对 FA3 的 5.1×10−4（FA3 这时也量化了 query）。GSM8K 和 32K–128K 的 RULER 多 key needle、五跳变量追踪上，端到端准确率在一个标准差内（配对 McNemar p ≥ 0.42）；vLLM 的有损 FP8 KV 会错过 FA3 能找回的 needle（p = 0.03，未校正）。

10. 落地可行性

工程接口是这篇最有吸引力的地方：vLLM 0.30 不改源码，LMCache 继续管分配、淘汰、写穿和预取；tier 模式做在 LMCache 的缓存服务进程里，pool 模式是树外 attention 后端。评测钉在两张 H800、PCIe、TP 1 / TP 2。论文没有给出代码仓库或构件链接，所以目前还不能按仓库即装即跑，只能按设计复现。

什么时候值得接：外部 DRAM / SSD 已经顶在复用悬崖上，或者 GPU pool 限制了长请求并发——尤其是不能再加本地 NVMe 或 GPU 显存的节点。什么时候先别指望它：raw 层和 raw pool 已经装得下工作集、引擎也不排队，这时压缩没有容量收益，还可能掉最多 2.2% 吞吐。FP8 的 pool 模式收益有限，页必须按最难压的层来定大小（存储比 0.906，均值是 0.838），融合 kernel 在功耗墙上也慢于 FA3。

论文给的运行时选择很清楚，观察的是线上指标而不是离线假设：

  1. 外部层是瓶颈（SSD 命中多，或命中率明显低于无界层）→ 用 tier 模式，保留 FA3 的精确输出，不必重新验收模型。
  2. GPU pool 是瓶颈（命中率已经高，但引擎里持续有等待队列）→ 用 pool 模式；融合 kernel 需要一次性数值验收，与 FA3 比到浮点舍入。
  3. 两层都紧 → 用 pool 模式，因为它把 FragPack 记录原样导出到 L1 / L2，同时放大两层。AI IDE 痕迹就是这种情况。
  4. 两层都不紧 → 关掉压缩。

容量规划可以分两步。先估计活跃复用工作集 W。在 LMCache 的写穿 LRU 下，raw 部署大约要到 DRAM+SSD ≈ 1.8W，或仅 DRAM ≈ 1.2–1.3W，才离开悬崖——倍数大于 1，是因为 W 只是在线会话的平均 KV，LRU 还会留下尚未老化的过期 chunk，写穿又会在两层各留一份热 chunk。再乘上存储比：BF16 用 0.71，FP8 用 0.85–0.87。替换策略只决定悬崖在哪，无损压缩按同样的因子把它左移：模拟器里用 1/0.709 放大容量，能在 80 GB 内对上测到的两道 LRU 悬崖；把写穿 LRU 换成单层 exclusive LRU，压缩仍然把悬崖精确缩到 0.71 倍字节。

和仓库里已有工作的关系：MoRI UMBP 讨论的是 agentic KV 要不要跳过 DRAM、直接走 NVMe，解决的是层次和带宽路径；TideCache 是缓存管理侧的另一条线。LoomKV 不替代它们，而是在已有 LMCache 层次上把同样多的物理字节变成更多逻辑 KV。它和有损 4-bit / FP8 KV 也可以叠加，但一旦走有损，就不再享有 tier 模式那种按位一致的输出。

11. 局限：这些倍数依赖什么假设

  • 没有可复现的代码。正文和注释里都没有 GitHub 或构件链接。设计写得很完整，但落地首先要自己按 TileStream / FragPack 和 LMCache 0.5.6、vLLM 0.30 的接口复现。
  • 服务形态。评测是单机、TP 1 和 TP 2、走 PCIe。每个 TP rank 压缩、存储、解压自己的 KV 头，没有跨卡通信，存储比不随 TP 度数变化。流水线并行、专家并行、多引擎共享缓存服务、MLA 和 FP4 KV 都还没有测。对 MLA，作者认为 TileStream 可以直接压潜向量，但 pool 模式现有的 GQA kernel 需要改。
  • 后端覆盖。Pool 模式当前后端支持 BF16 和 FP8 KV、128 维头、最多 8 的 GQA 组、128 token 的 block。混合了线性或状态空间层的结构里，它只压缩注意力 KV 层。服务主结果来自 Qwen3-30B-A3B 和 GLM-4-9B，另外七个模型只贡献了存储比，没有端到端 goodput。
  • 主负载的形状。AgentX 会话不共享前缀，prompt 很长（中位 89K，最长 254K），并且用 FIFO 代理把并发钉在 S 上。共享前缀很重、短请求为主、或已经做了 prefill–decode 分离的集群，倍数不能直接搬。
  • FP8 pool 和功耗墙。BF16 融合 kernel 在功耗墙上仍大多领先；FP8 在墙上会慢于 FA3。若生产环境已经把卡顶在功耗上限，并且 KV 已经是 FP8，不要用 kernel 微基准的满时钟数字去外推端到端收益。
  • 小 pool 的调度。28 GB raw LMCache 的失败被归因于 vLLM 在小 pool 下的抢占问题。比较 pool 模式与「放大后的 raw pool」是公平的，但和「同样 28 GB 的 raw LMCache」比，会混进引擎调度效应。
