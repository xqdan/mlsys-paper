1. 一句话结论

张量并行推理即使走 NVLink，AllReduce 仍能占端到端延迟的约 9%–23%，但 vLLM、SGLang、TensorRT-LLM 默认都没有开计算–通信重叠：低延迟 serving 每轮 token 少，把计算切细再重叠，往往比不切更慢。TokenWeave 抓住被忽略的 RMSNorm，做成只占 2–8 个 SM 的融合 AllReduce–RMSNorm 内核，并用对 GPU wave 敏感的两路 token 切分，把一路的通信和归一化叠到另一路的计算上。它接进 vLLM 0.8.5 的 V1 引擎，在 8×H100 上相对已经用上 Multimem / NVSHARP 的基线，延迟最多 1.28 倍、吞吐最多 1.19 倍；1K token 的小 batch 仍有约 1.2 倍。不少场景里，它甚至快过“把通信完全拿掉”的反事实基线，因为连 RMSNorm 的带宽开销也被叠掉了。

1.28× 和 1.19× 都是相对已经启用 Multimem / NVSHARP 的 vLLM，不是相对默认 NCCL AllReduce。依赖第四代及以后 NVSwitch 上的 NVSHARP（Hopper / Blackwell）。完整的切分+重叠目前不支持 CUDA Graph；B200 上小 decode batch 只报了融合内核（约 1.01–1.05 倍），不要把 H100 预填充的 1.28 倍直接写成 Blackwell 解码倍数。

2. 问题：低延迟 serving 叠不上通信

大模型推理常常必须张量并行。互连已经很快，但通信并没有消失。论文在 8×H100 DGX、vLLM 0.8.5 V1 上锁 TDP 频率测量：Llama-3.3-70B、Qwen2.5-72B、Mixtral-8x22B 的 AllReduce 仍占端到端延迟的 9%–23%，RMSNorm 另占 4%–9%（图 1）。摘要把它概括成“即便走 NVLink，仍可到 20%”。

文献里叠通信的办法很成熟：把计算切成更细的子任务，做完一块就发一块。可以按 tile 切（Flux、TileLink 等），也可以按 token 切（NanoFlow、DeepSeek 的 DualPipe 一类）。但这些技术没有成为 vLLM、SGLang、TensorRT-LLM 里张量并行 serving 的默认开关。

原因不是没人写过，而是 serving 的问题规模不对。切分会引入 wave quantization：H100 有 132 个 SM，300 个 CTA 本来 3 波就能做完；均分成两份 150 个 CTA，每份都要 2 波，合计 4 波，计算本身变慢。AllReduce 已经被优化到只剩约 9%–23%，切分带来的损失很容易把重叠收益吃掉。先前方案往往要到 8K+ token 才划算，那是训练常见、低延迟推理少见的规模。vLLM 0.8.5 默认 chunk size 是 2048。于是生产系统继续付这笔通信账。

论文脚注对比了专家并行：DeepSeek 一类 EP 的 all-to-all 开销可到 50% 以上，更容易被重叠掩盖。TokenWeave 针对的是已经很快、但还没快到能忽略的张量并行 AllReduce，难度更高，也更贴近当前多卡 serving 的默认路径。

3. 三个判断

RMSNorm 不是边角料

它占 4%–9%，而且和 AllReduce 紧挨着：规约之后每个 GPU 都拿到完整 embedding，再各自做一遍完全相同的归一化，计算是冗余的。

拆成 RS+AG 再归一化，数学对、系统亏

ReduceScatter 之后每个 GPU 只对自己的 1/N 分片做 RMSNorm，计算量降到 1/N。但把 AllReduce 拆开会多出 HBM 读写，表 1 里简单融合在 512–8K 上甚至比串行更慢。

通信不该抢走计算的 SM

NVSHARP / Multimem 让交换机做规约和组播，6%–8% 的 SM 就能打满通信带宽。先前重叠方案常预留 16–20+ 个 SM 给通信，等于先削弱计算再去叠它。

这三条合在一起，才解释得通为什么“再做一个更细的重叠”解决不了 serving：需要一个几乎不比单独 AllReduce 慢的融合内核，还得少占 SM；切分最多两路，而且要按 wave 来切；token 太少时干脆只开融合、不开重叠。

4. 思路：融合、重排、按波切分

融合 AllReduce–RMSNorm

内核利用 Multimem：ReduceScatter 时由 NVSHARP 在交换机上规约本卡负责的那 1/N 分片，规约结果留在 SM 寄存器里直接算方差和缩放，再写回 Multimem 地址，由交换机做 AllGather。残差加法也融合在内。标准 RMSNorm 要对整个张量做两次 HBM 读、一次写；这里只操作本地分片，还省掉“先写再读”的那一趟。

表 1（hidden 8192、bf16、8×H100，单位微秒）里，融合内核相对串行 AllReduce+RMSNorm 是 1.34–1.39 倍，覆盖 64 到 32K token，并且几乎追上单独 AllReduce 的时间。例如 1K token：AllReduce 74.85、RMSNorm 29.82、串行 104.67，融合 75.71（1.38 倍）。“简单融合”（RS+RMSNorm+AG 拼在一个 kernel 里但不减流量）在 512–8K 上相对串行只有 0.92–0.98 倍，是倒退。图 10 显示 8 个 SM 已经接近饱和，再加 SM 收益很小。于是通信加归一化可以压到 2–8 个 SM，把其余 SM 留给另一路计算。

RMSNorm 重排

AllReduce 之后各卡 token embedding 已经相同，再各自做 RMSNorm 是 N 倍重复。把它插到 ReduceScatter 和 AllGather 之间，只对自己的 token 分片归一化。前提是 ReduceScatter 必须按 token 边界切，保证每张卡拿到完整的 token 向量。只做重排而不做流量融合，会被拆集合的开销抵消，所以重排必须和上面的融合内核绑在一起。

Wave-aware 的两路切分

最多切成两路，用两条 CUDA stream：通信流跑融合内核，计算流跑 Attention / FFN，用 stream.wait(stream) 处理依赖。例如 300 个 CTA 在 132 SM 上，均分会变成 4 波；Smart-splitting 切成 132 + 168，总波数仍是 3。图 9 显示，token 较少时，这种切法能明显压掉均分的损失。图 17 的消融说明：关掉 smart-splitting 后，加速比会随序列长度抖动；打开之后曲线平稳。

token 数低于阈值时，系统只启用融合内核、不做切分（图 3）。规则对预填充、混合 batch、纯解码一视同仁。分离式 serving 里，小的纯解码 batch 吃融合收益，大的纯预填充 batch 再开完整重叠。

5. 怎么接到 vLLM

实现基于 vLLM 0.8.5 的 V1 引擎，PyTorch 2.6.0、CUDA 12.4、Triton 3.2.0。通信走 PyTorch SymmetricMemory（symm_mem.empty() / rendezvous()），用 Triton 和自定义 CUDA 扩展写集合，注意力后端是 FlashAttention-3。主文实验在 8×H100 DGX（NVSHARP、128 核 CPU、800 GB 主机内存）上锁 TDP 频率；附录 B 用同一台机器的 4 卡，附录 C 是 8×B200。关闭前缀缓存以保证对比公平；端到端不计 detokenization。

端到端吞吐实验默认打开 chunked prefill：稠密模型 chunk 2K（vLLM 0.8.5 默认），Mixtral 用 4K。TokenWeave 对达到阈值的混合 batch 开完整重叠（稠密 1K+，Mixtral 4K+），更小的纯解码 batch 只用融合内核。

6. 实验与结果

模型是 Llama-3.3-70B、Qwen2.5-72B 和 Mixtral-8x22B，都用 instruction-tuned 版本。工作负载包括 ShareGPT、arXiv，以及固定输入/输出长度的合成请求。基线 vLLM-Multimem 已经是优化过的 Multimem AllReduce，不是默认实现；vLLM-nocomm 是去掉通信、只留计算的反事实对照。

端到端吞吐与单轮延迟

图 11：8×H100 上，稠密模型在真实轨迹上大约 1.19 倍吞吐（ShareGPT 上限），arXiv 轨迹最多 1.15 倍。图 12 里把 Llama-3.3-70B 的 chunk 大小扫一遍，加速在 1.14–1.26 倍之间，说明收益不是绑在某一个 chunk 上。图 13：预填充单轮延迟，稠密模型从 1K token 起就是 1.16–1.28 倍；图 2 写明 1K 约 1.2 倍，4K 及以上可以超过 vLLM-nocomm。Mixtral 的通信占比本身更低（图 1），完整重叠在 1K 和 2K 上会亏——MoE 的 token 还要再分到 8 个专家，FFN 在小请求上已经偏带宽，两路切分的损失补不回来。这时只开融合内核仍有收益。4 卡上趋势相同，但通信占比更低，倍数也更小。Mixtral 在 4×H100 上因 KV 容量不足没有测。

对比 TileLink 与 NanoFlow

两者都没有接到 vLLM，所以比较方式不同。TileLink 用 Llama-3.3-70B 的单层、batch 1 扫序列长度（图 14）：TokenWeave 在 1K 已是 1.20 倍，TileLink 在短序列上是净亏损，要到 ≥4K 才开始赚，并且饱和在大约 1.2 倍，TokenWeave 单层可到 1.35 倍。端到端倍数低于单层，因为还有 embedding、采样和运行时开销。作者还加了只重叠 MLP 的 TileLink-OnlyMLP：小 batch 时注意力投影给不出足够的重叠窗口，硬叠反而更慢。

NanoFlow 有自己的 serving 栈，原实现只支持 A100。作者把它改到 H100 上，发现 vLLM-V1 0.8.5 的绝对吞吐已经高于 NanoFlow 的框架，于是改比“各自相对自己基线收回了多少通信”。图 15：NanoFlow 大约 1.04–1.09 倍，接近原论文报告的 1.07 倍通信改善；TokenWeave 在宽范围上大约 1.19 倍。

消融与 B200

图 16：只开融合内核（TokenWeave-fuseonly）在各模型上是 1.04–1.09 倍，来自去掉重复 RMSNorm 和中间 HBM 访问；完整 TokenWeave 再把重叠加上去。附录 C：8×B200 上融合内核相对“Multimem AllReduce + RMSNorm 相加”是 1.24–1.38 倍。vLLM 0.8.5 还不支持 B200，解码实验改用较新的 vLLM，并关掉 torch.compile（当时还不支持 symmetric memory）。小解码 batch 上两路切分的开销会吃掉重叠，所以图 26 只报 fuseonly：Llama-3.3-70B（2K/4K 上下文）和 Qwen3-235B-A22B（2K）为 1.01–1.05 倍，上下文越长，RMSNorm 占比越低，相对收益越小。完整方案在 B200 上因不支持 CUDA Graph，预填充在 eager 模式下测：fuseonly 对 Llama 为 1.05–1.07 倍，完整方案在 1K–64K 上最多 1.22 倍（图 27）。

7. 落地可能性

这是本批里最接近现有推理栈的一篇：真机覆盖 Hopper 和 Blackwell，代码公开，已经接进 vLLM-V1，对比的是生产里会用的 Multimem 路径，而不是一张容易打的默认基线。chunked prefill、混合 batch、分离式预填充/解码都考虑到了，并且用阈值决定“只融合”还是“融合+重叠”，避免在 MoE 小 batch 上帮倒忙。

要进生产，还有几道坎。第一，硬件门槛是 NVLink4 及以后的 NVSwitch（NVSHARP / Multimem）。没有交换机内规约，融合内核的 SM 占用和带宽故事都会变；论文预期未来 NVIDIA 乃至 AMD 会普及类似能力，但没有在 AMD 上测。第二，工程缺口写得很清楚：torch.compile 当时不能分配 symmetric memory；完整切分+重叠不支持 CUDA Graph。解码路径若强依赖 Graph，目前只能先上 fuseonly，收益会从“重叠”缩到“少做一次 RMSNorm、少跑几次 HBM”。第三，它优化的是域内张量并行 AllReduce，不解决专家并行的 all-to-all，也不取代仓库里已有的 Zero-SM NCCL（后者针对大宗数据搬运、不占 SM 的训练/通道路径）。两者叠的是不同的集合、不同的消息尺寸。

比较现实的接入顺序是：先在 Hopper / Blackwell 的 NVSwitch 机器上，把融合 AllReduce–RMSNorm 接到 vLLM / SGLang 的 TP 路径，用 fuseonly 覆盖小解码 batch；等 CUDA Graph 和 torch.compile 认 symmetric memory 之后，再对超过阈值的 chunk / 预填充打开两路重叠。不要指望它在短上下文、已经算满的大 batch，或没有 NVSHARP 的机器上复制 1.28 倍。

8. 局限

  • 绑定 NVSHARP / Multimem。 没有第四代及以后 NVSwitch，这篇的内核设计和 SM 预算都不成立。
  • 完整方案和编译/Graph 栈还有缝。 对称内存与 torch.compile 不兼容；切分+重叠不能走 CUDA Graph。B200 解码因此只展示了融合内核的 1.01–1.05 倍。
  • MoE 小 batch 不能盲目开重叠。 Mixtral 在 1K、2K 上完整实现有净开销，必须回退到只融合。
  • 和 TileLink、NanoFlow 的对比不是同一套 serving 栈上的端到端对打。 单层或“相对各自基线”的比法是诚实的，但不能直接读成“在 vLLM 里替换它们会得到图上的倍数”。
  • 主结果在锁 TDP 频率、关闭前缀缓存的条件下取得，便于复现，和数据中心动态频率、前缀命中率高的流量会有差距。
  • 没有 AMD、没有跨节点 TP。 域外通信、多机张量并行不在评测里。
